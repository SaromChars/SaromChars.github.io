Maildir 与邮箱存储的一致性

2021年11月21日
|

设想一个常见的邮箱故障现场：投递代理正在向本地存储写入一封新邮件，数据刚写完尚未完成元数据登记，服务器突然异常断电或进程被强行中止。重启之后，系统究竟能否保证“要么该邮件完整可见，要么彻底回滚且不留下任何状态破坏”？

以下沿经过核对的开源邮件存储后端 Dovecot 2.3.16 一次保存过程，区分文件发布与元数据提交。在接入互联网消息访问协议（Internet Message Access Protocol，IMAP）的多客户端并发、唯一标识符分配、标志位同步与磁盘配额控制后，底层单文件的目录移动并不能自动提供跨文件、跨目录的多实体事务保证。

单邮件写入与生命周期的源码追踪

在标准 Maildir 格式中，每个逻辑邮箱包含三个基础子目录：

Maildir/
├── tmp/               # 正在流式写入的临时文件，尚未发布到邮箱视图
├── new/               # 新交付完成的文件，尚未在常规会话中转入 cur
├── cur/               # 常规存储文件，可通过文件名后缀记录标志位
├── dovecot-uidlist    # 记录 UIDVALIDITY、NEXT_UID 及 UID 与文件名映射
└── dovecot.index*     # 加速检索的索引、缓存与状态记录

需要注意的是，new/ 与 cur/ 并不严格等同于“未读”与“已读”：进入 cur/ 且未附加已读标志（S）的邮件同样是未读状态；普通新投递通常进入 new/，而包含需编码的标志或关键字的邮件则直接进入 cur/，复制或追加恢复等操作还受到近期标志（Recent）的影响。

在 Dovecot 的 Maildir 实现中（参考 maildir-save.c 资料2），保存一封邮件经历明确的阶段流转：

1. 分配临时文件与流式写入（maildir_save_begin / finish）

投递开始时，maildir_create_tmp 在 tmp/ 目录下生成一个唯一的临时文件名，并使用 O_WRONLY | O_CREAT | O_TRUNC | O_EXCL 打开文件句柄。若因时间回拨等极端情况遇到同名文件，循环会捕获 EEXIST 错误并重新生成重试。此时该文件仅存在于 tmp/，尚未发布给正常的邮箱扫描与读取逻辑。

邮件内容通过输出流写入文件句柄。在 maildir_save_finish_real 中：

  • 存储层依据配置（如 mail_fsync = optimized 或 always，参考 10-mail.conf 资料1）调用底层的 fsync(ctx->fd) 请求操作系统将脏页刷盘。如果 fsync 失败，上下文标记 failed = TRUE。
  • 如果流写入或落盘失败（例如遭遇磁盘空间不足 ENOSPC 或配额耗尽 EDQUOT），引擎调用 i_unlink_if_exists 将 tmp/ 下的半成品物理删除，并清理上下文返回错误。

操作系统层面的 fsync 调用是软件向存储介质发起同步的请求，其最终持久化效果受底层文件系统与硬件写入缓存影响；源码层面所实现的是在声明写入成功前向系统发出持久化指令，失败则终止流程。

2. 预提交与选择性加锁（maildir_transaction_save_commit_pre）

Maildir 的核心写入环节并非对所有投递统一加互斥锁，而是依据事务意图进行选择性锁调度：

/* src/lib-storage/index/maildir/maildir-save.c: Lines 969-984（节选，注释为说明性改写） */
sync_flags = MAILDIR_UIDLIST_SYNC_PARTIAL | MAILDIR_UIDLIST_SYNC_NOREFRESH;

if ((_t->flags & MAILBOX_TRANSACTION_FLAG_ASSIGN_UIDS) != 0) {
    /* 事务要求显式分配 UID，必须锁定 uidlist */
} else if (ctx->have_keywords) {
    /* 自定义关键字更新依赖 uidlist 锁 */
} else if (ctx->have_preserved_filenames) {
    /* 使用既有文件名保存，需加锁避免竞态 */
} else {
    /* 普通追加投递：采用 TRYLOCK 尝试加锁 */
    sync_flags |= MAILDIR_UIDLIST_SYNC_TRYLOCK;
}
  • 如果事务包含自定义关键字（keyword，指客户端或业务定义的非系统标签）或显式分配唯一标识符（Unique Identifier，UID，指在特定邮箱及 UIDVALIDITY 作用域下单调递增的 32 位整型序列，参考 maildir-uidlist.c 资料4），引擎必须成功锁定 dovecot-uidlist。
  • 对于常规投递，存储层使用非阻塞的 TRYLOCK 尝试获取锁。若未取得锁，引擎并不挂起等待，而是调用 maildir_save_rollback_index_changes 撤销在索引（index）中的预写记录，放行底层文件移动。这些物理文件将在后续的邮箱同步流程中被扫描并纳入元数据（metadata）管理。

3. 文件发布与目录项刷盘（maildir_save_move_files_to_newcur）

当数据准备就绪，引擎执行目录间移动：

  • 普通新投递通常通过 rename 移动到 new/；若包含需编码的标志或关键字，则直接移动至 cur/ 并在文件名后编码对应标志位。
  • 单次 rename 调用在 POSIX 语义下保证目录项切换的原子可见性，但并不保证包含该目录项的父目录元数据已同步到磁盘介质。因此 Dovecot 在移动文件后调用 maildir_transaction_fsync_dirs，通过 fdatasync_path 对 new/ 与 cur/ 目录本身发起刷盘。

4. 元数据登记、释放锁与失败清理

  • 若本次事务持有 uidlist 锁且文件移动成功，引擎调用 maildir_save_sync_uidlist 将新文件的 UID 映射、GUID 等元数据写入 dovecot-uidlist，并提交索引修改。
  • 随后在 maildir_transaction_save_commit_post 中调用 maildir_uidlist_unlock 释放锁资源。
  • 若在此期间发生错误（如 rename 失败），流程转入 maildir_transaction_save_rollback：对于已移动的文件尝试调用 i_unlink 执行清理回滚，回滚索引与 uidlist 状态，并最终释放锁。如果在此过程中进程因崩溃直接中止，未完成清理的孤立文件将留在磁盘上，必须依赖重启后的恢复机制处理。

邮箱同步机制与锁序边界

在处理多会话并发读取与外部投递并存的场景时，邮箱同步必须遵循严格的加锁顺序。根据 Dovecot 的同步逻辑（参考 maildir-sync.c 资料3 第 815–858 行）：

  • 避免死锁的锁序：存储层在需要同时更新 uidlist 与 index 时，规定必须先锁定 uidlist，再锁定 index。如果锁序颠倒，并发会话间极易诱发死锁。
  • 外部并发修改的竞争边界：Maildir 标准本身并未强制外部进程遵守统一锁。如果外部进程在未持有锁的情况下直接对目录执行 rename 或写入，正在执行 readdir 的 Dovecot 进程可能在单次扫描中漏读文件，进而误判其已被删除并在下一次扫描中重新分配新 UID。因此，跨服务的 Maildir 并发访问必须通过受控的协调机制或统一委托给邮件守护进程。

恢复与状态重建的边界

在系统运维或灾难恢复中，切忌将“元数据索引坏了直接删除让其重建”视作万能手段。针对不同状态，其重建边界与恢复约束如下：

  • 邮件物理正文与 RFC822 头：存放于 cur/ 与 new/。属于底层源数据，丢失无法凭空重建；若正文内容文件损坏或丢失，无法从索引反向提取邮件完整内容。
  • 标准系统标志（Flags）：存放于文件名后缀（如 :2,S）与索引。在正常同步状态下可从文件名解析恢复。
  • 临时脏标志（Dirty Flags）：存放于 dovecot.index。当遇到存储空间不足等原因导致文件名 rename 失败时，标志变更可能先暂存在索引中并标记为 Dirty（参考 maildir-sync.c 资料3）。若盲目删除索引，这部分未刷回文件名的状态将永久丢失。
  • 私有标志（Private Flags）：仅在 dovecot.index 中维护（参考 maildir-sync-index.c 资料5 第 578 行）。文件名后缀不记录私有标志，丢失索引将无法恢复。
  • UID 与 UIDVALIDITY 映射：存放于 dovecot-uidlist。文件名本身不记录 IMAP UID。虽然重建时若存在有效索引头可复用既有 UIDVALIDITY，但仅凭散落的文件名重新扫描排序，无法确保恢复完全一致的旧 UID 映射，可能触发客户端全量重新拉取，必须依赖一致的备份与恢复。
  • 关键字映射（Keywords）：存放于 dovecot-keywords。文件名中仅保存关键字索引字母，其实际名称映射由 dovecot-keywords 维护（参考 maildir-keywords.c 资料6）。若映射表丢失，对应的标签语义无法反解。
  • 派生缓存（Cache）：存放于 dovecot.index.cache。邮件结构和可从头字段解析的信息部分可重新解析，但部分元数据属性（如无法修改物理 ctime 时记录在缓存中的保存时间 save_date）在重建时可能失真。

删除、清除与回收责任

在 IMAP 协议设计与底层存储之间，邮件删除遵循多阶段语义：

  1. 标志标记（\Deleted Flag）：客户端通过 STORE 命令将邮件标记为已删除。在底层这仅更新索引标志位，或通过重命名在文件名后添加 T 字符。邮件并未从磁盘移除，依然正常占用配额。
  2. 永久清除（expunge）操作：依据 RFC 3501 规范 资料7，已标记 \Deleted 的邮件在可写邮箱收到客户端 EXPUNGE 命令（第 6.4.3 节）或带有隐式清除语义的 CLOSE 命令（第 6.4.2 节）时被永久移除；服务端管理策略也可触发清除。在底层，清除表现为调用 unlink 物理删除文件（参考 maildir-sync-index.c 资料5）并更新邮箱索引，而 uidlist 不必立即去除旧记录（参考 maildir-sync.c 资料3）。需要注意，常规的 LOGOUT 或连接断开并不等同于 CLOSE，不会触发隐式清除。

Maildir 底层格式并不自带垃圾箱保留期、版本管理或物理防误删保证。在工程设计中，相关能力应作为明确的上层职责：

  • 业务回收站：将邮件移动至名为 Trash 的独立邮箱文件夹。在协议与存储语义上，这相当于在目标邮箱生成具有新 UID 的新实体，并在源邮箱中执行删除流程。
  • 删除保留与延迟回收（工程推导）：自研系统若需支持合规留存（Retention Policy）或防误删回滚，可在存储适配层将物理 unlink 转化为软删除标记或将文件转存至冷存队列，并在满足保留期策略后再调度异步物理清理。

自研邮箱存储的一致性设计契约（工程推导）

结合 Maildir 的源码特征与实践局限，自研邮件存储系统无论采用本地文件还是解耦的内容存储，应遵循以下核心一致性契约：

  1. 内容优先持久化：先写底层数据块并请求可靠持久化；若写入失败，尝试清理半成品，清理失败留待恢复处理。在内容落盘成功前，不建立元数据与 UID 引用。
  2. 元数据关联与孤儿安全：内容写完后登记邮箱关联与 UID。跨步崩溃可能产生未被元数据引用的孤立内容块（孤儿文件）。回收孤儿块时，宽限期仅是辅助条件，还必须核对活跃写入、租约或锁，并复核当前引用与备份保留政策，防止并发慢写入被误回收。
  3. 清除与物理销毁解耦：响应协议清除时，优先解除元数据层面的引用和用户视图可见性，将数据块交由异步回收器在核验没有共享引用、满足保留期要求后再行物理销毁。

对照：单文件 mbox 的锁协调代价

与 Maildir 每个邮件独立文件的模式不同，传统 mbox 将文件夹内的全部邮件连续存放在单一文本文件中。根据 Dovecot 配置说明（10-mail.conf 资料1），多个进程并发操作同一个 mbox 时必须协调复杂的锁组合（如 dotlock 与 fcntl），并遵循全局统一的加锁顺序以避免进程间互锁；若写入或追加中途发生故障，存储层通常需要调用 ftruncate 将文件尺寸截断回退到事务开始前的偏移量（参考 mbox-save.c 资料8 第 725–737 行）。Maildir 通过目录隔离写入与原子重命名，显著降低了长事务期间对整个邮箱单文件的独占争用。

崩溃恢复验证案例（未执行方案）

为检验存储层在异常中止时的恢复表现，可设计如下崩溃注入验证方案（本方案为工程推导与测试设计，未在真实硬件上注入执行；SIGKILL 仅验证进程异常退出后的恢复，不能模拟底层断电或硬件设备缓存丢失）：

验证步骤设计

  1. 准备隔离测试邮箱，注入标准化输入的测试邮件数据（固定规范化换行 CRLF 口径以排除换行转换干扰）。
  2. 在模拟并发写入过程中，分别在以下两个典型时点通过进程强行中止（SIGKILL）注入崩溃：
    • 时点 A：临时文件刚完成 fsync 刷盘，尚未执行 rename 移动前；
    • 时点 B：文件已成功 rename 至 new/，但在 dovecot-uidlist 锁释放与最终元数据登记前。
  3. 重新启动服务并触发常规读取与同步流程。

恢复判据

  • 数据完整性：在 cur/ 或 new/ 中对外可见的邮件，其内容必须完整无损，不能出现 0 字节文件或截断文件。
  • 孤儿状态安全自愈：在时点 A 残留在 tmp/ 的孤立文件，不能被错误纳入用户视图，在通过租约与宽限期安全核对后能被正常清理。
  • UID 与身份连续性：在正常未损坏的元数据恢复中，已确认的既有 UID 保持稳定；若发生无法恢复的元数据损坏，必须通过递增 UIDVALIDITY 显式通知客户端状态失效，绝对不得暗中复用旧 UID 身份；在时点 B 已移动落盘但未登记的文件，在重启后同步扫描时应被赋予新的合法 UID，该 UID 不可与历史既有 UID 重复冲突（IMAP UID 允许存在空洞，但不允许逆序或重复）。
  • 客户端重试容忍度：针对时点 A 或时点 B 投递结果未获明确确认的场景，投递代理发起重试时，在缺乏全局去重键的条件下可能产生重复邮件，但存储层必须确保重复消息具备独立的合法标识，且不导致邮箱结构损坏。
