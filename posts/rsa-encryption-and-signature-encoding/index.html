RSA 加密与签名的编码差异

2018年9月5日更新于: 2026年11月7日
|

在学习公钥密码学时，许多人接触到的第一套数学公式通常是“教科书式 RSA”（Textbook RSA）：公钥由 (n, e) 构成，私钥由 (n, d) 构成。在有效密钥参数满足条件下，加密时算 c = me mod n，解密时算 m = cd mod n。由于数学上 (md)e ≡ (me)d ≡ m (mod n) 成立，一种极其流传的说法应运而生：“公钥加密、私钥解密；私钥加密、公钥解密，私钥加密就是数字签名”。

这种说法在数学符号上看似对称，但在工程安全上却是极其危险的误导。在现实密码协议中，“模幂数学运算”仅仅是底层原语（Primitive），绝不等于可以直接调用的“密码方案”（Scheme）。更重要的是，RSA 用于加密和用于签名时，面临的攻击模型与安全性目标截然不同，必须搭配完全不同的编码与填充机制（如 OAEP 与 PSS）。[RFC 8017 §5] · [RFC 8017 §6]

裸 RSA 模幂的局限

纯粹的模幂运算 me mod n 具有强烈的代数结构，如果不加任何填充编码直接使用，会暴露出严重的缺陷：

  1. 确定性加密的隐患： 相同的明文 m 每次加密都会生成完全相同的密文 c。攻击者若怀疑密文是特定已知词汇，只需用公钥分别加密比对即可，无法提供现代加密所追求的语义安全性。
  2. 乘法同态与延展性（Malleability）： 若 c1 = m1e mod n，c2 = m2e mod n，则 (c1 × c2) mod n = (m1 × m2)e mod n。攻击者可以在未解密的情况下将密文相乘，诱导解密端得到乘积明文；在签名中，攻击者也能利用同态性在不知道私钥的情况下组合出合法的新签名。
  3. 输入范围限制： 模幂运算要求输入必须是介于 0 ≤ m < n 的整数，对长数据无法直接分块裸算。

因此，RFC 8017（PKCS #1 v2.2）将纯模幂运算严格降格为基础原语：RSAEP（加密原语）/ RSADP（解密原语），以及 RSASP1（签名原语）/ RSAVP1（验签原语）。[RFC 8017 §5.1] · [RFC 8017 §5.2] 真正的安全保障，依赖于在上层对消息进行格式化与随机化填充的编码方案。

RSA 加密与签名的安全目标和接口差异

在密码学定义中，“加密”与“签名”服务于两组完全相反的安全目标：

  • 加密（Encryption）： 目标是机密性（Confidentiality）。只有拥有私钥的指定接收方能解密，解密操作直接恢复原始明文消息。
  • 签名（Signature）： 目标是真实性（Authenticity）与不可否认性（Non-repudiation）。数字签名（digital signature）在公钥已被可信绑定到作者且私钥未泄露的前提下由作者背书，任何持有公钥的人都可以通过验签算法（signature verification）验证该签名确实对应于指定正文且未被篡改。

如果把“私钥运算”简单粗暴地等同于“签名”，极易导致架构设计缺陷：

  1. 输入与输出完全不同： 签名方案（如 RSASSA-PSS）是对消息的哈希摘要进行编码后再做私钥运算，其输出是独立的签名标签；而验签过程绝不是用公钥把消息原文“解密”出来，而是验证签名是否合法。
  2. 错误接口的泄露风险： 如果系统错误地暴露了“直接对外部提供的任意整数进行 RSASP1 裸私钥运算”的接口，攻击者便可把截获的加密密文直接喂给该接口，从而骗取解密结果。合规的 PSS 签名流程先做 EMSA-PSS 编码，不直接暴露裸私钥幂输出，但依然要防范多方案混用的潜在交互。
  3. 密钥应当用途隔离： RFC 8017 建议一对 RSA 密钥只用于一种方案；对于新应用，不推荐（NOT RECOMMENDED）将同一密钥对跨方案复用（例如同时用于加密与签名），以避免某一方案实现的漏洞危及另一方案，并保持可证明安全边界。[RFC 8017 §6]

加密编码：RSAES-OAEP 的随机化与格式校验

为了使 RSA 能够安全地用于加密，RFC 8017 规范了 RSAES-OAEP（最优非对称加密填充，Optimal Asymmetric Encryption Padding）。[RFC 8017 §7.1]

OAEP 将明文消息 M 与一个随机生成的种子 seed 结合，采用双向掩码生成函数（mask generation function，MGF，本文示例选用基于 SHA-256 的 MGF1）：

  1. 将可选标签哈希 lHash、零字节填充 PS、分隔符 0x01 与明文 M 拼接成数据块 DB。
  2. 生成与哈希长度相同的随机种子 seed（以 SHA-256 为例，种子长度为 32 字节）。
  3. 利用掩码生成函数计算 dbMask = MGF(seed, len(DB))，将数据块掩蔽为 maskedDB = DB ^ dbMask。
  4. 再以 maskedDB 为输入计算 seedMask = MGF(maskedDB, len(seed))，将种子掩蔽为 maskedSeed = seed ^ seedMask。
  5. 最终组合成形如 0x00 || maskedSeed || maskedDB 的编码消息 EM，再执行 RSAEP 模幂运算。

OAEP 的安全机制：

  • 随机化加密： 新鲜生成的随机 seed 使得加密相同明文通常得到完全不同的密文，攻击者无法再简单地通过一次公钥加密结果直接比对猜测明文。
  • 解码格式校验： 解密端还原出 EM 后，必须逐一校验前导零、lHash 以及分隔符 0x01。在 RSA 难逆假设、掩码生成函数视为随机预言机的理论模型下，RSAES-OAEP 提供了抗自适应选择密文攻击（IND-CCA2）的可证明安全性。[RFC 8017 §7.1]

签名编码：RSASSA-PSS 的生成与验证

签名面临的威胁是“攻击者能否在没有私钥的情况下伪造合法签名”。为此，RFC 8017 推荐使用 RSASSA-PSS（概率签名方案，Probabilistic Signature Scheme）。[RFC 8017 §8.1]

签名生成

  1. 计算消息摘要 mHash = Hash(M)。
  2. 生成一个随机盐 salt（以 SHA-256 为例，典型可选长度为与摘要相同的 32 字节）。
  3. 将固定前缀、mHash 与 salt 拼接，计算摘要 H = Hash(padding || mHash || salt)。
  4. 将盐编码入数据块，用 MGF 生成掩码异或，拼入 H 与固定结尾标记（0xbc），得到编码块 EM。
  5. 签名者对 EM 执行 RSASP1 私钥运算，输出签名 S。[RFC 8017 §8.1.1]

验证与解密的根本差异

读者需要特别注意验签与解密在数据流上的本质不同：

  • 解密： 输入仅为密文和私钥，成功时输出明文消息 M。
  • 验签： 输入必须同时包含待验证的原始消息 M、签名 S 以及公钥，输出仅为“合法”或“非法”的布尔判定，绝不从签名中解密还原消息。[RFC 8017 §8.1.2]
    • 验证端先用公钥执行 RSAVP1 运算 m = s^e mod n 还原出 EM；
    • 检查结尾标记 0xbc，用 MGF 揭露数据块并从中提取出签名时使用的 salt；
    • 验证端基于自己持有的原始消息 M 独立重新计算 H’ = Hash(padding || Hash(M) || salt)；
    • 比对 H’ 与 EM 中携带的 H 是否一致。只有一致才判定签名有效。

在满足相应安全假设下，RSASSA-PSS 提供了紧致的安全归约；而随机盐的引入使相同消息在不同时刻生成的签名通常不同，有效阻止了代数同态伪造。[RFC 8017 §8.1]

填充与错误处理：密文填充攻击警示

在工程实现中，错误处理绝不仅仅是“代码风格问题”，而是会影响协议安全。

早期的 PKCS#1 v1.5 填充在解密时，如果服务端对“填充格式错误”与“内容解密错误”返回了不同的报错信息，或者在处理不同错误时存在细微的时序差异，攻击者就可以将其作为密文解密 Oracle（如 Bleichenbacher 攻击），通过不断构造畸形密文并观察响应，最终无需私钥即可完全还原密文。

因此，RFC 8017 在规范 RSAES-OAEP 解密步骤时特别强调：无论是在校验前导字节、lHash 匹配还是分隔符格式时出错，系统对外必须统一返回单一且毫无差别的错误信息（如“decryption error”），且处理时间必须保持一致，杜绝任何利用报错细节刺探密钥的侧信道通道。[RFC 8017 §7.1.2]

参考资料与固定版本来源

  • RFC 8017 §5: Cryptographic Primitives
    K. Moriarty, B. Kaliski, J. Jonsson, A. Rusch. PKCS #1: RSA Cryptography Specifications Version 2.2, November 2016. 明确了密码原语（RSAEP/RSADP 与 RSASP1/RSAVP1）仅为数学运算，不能独立作为完整方案使用。
  • RFC 8017 §5.1: Encryption and Decryption Primitives
    定义了 RSAEP 与 RSADP 的模幂计算流程及参数边界。
  • RFC 8017 §5.2: Signature and Verification Primitives
    定义了签名私钥运算 RSASP1 与公钥验算 RSAVP1 的具体步骤。
  • RFC 8017 §6: Overview of Schemes
    阐述了方案（Scheme）的设计目标，建议单一 RSA 密钥只用于一种方案，新应用不推荐跨方案复用。
  • RFC 8017 §7.1: RSAES-OAEP
    详细说明了 Optimal Asymmetric Encryption Padding 的构造、掩码机制与在理论假设下针对 CCA2 攻击的可证明安全性。
  • RFC 8017 §7.1.2: Decryption Operation
    规定了 OAEP 解密流程与严格统一的“decryption error”报错策略，以防范侧信道攻击。
  • RFC 8017 §8.1: RSASSA-PSS
    阐明了 PSS 概率签名方案的盐值机制与紧致安全归约特性。
  • RFC 8017 §8.1.1: Signature Generation Operation
    规定了 RSASSA-PSS 签名的完整计算流程。
  • RFC 8017 §8.1.2: Signature Verification Operation
    规定了 RSASSA-PSS 签名验证流程，明确其输入包括公钥、消息和签名，输出仅为真假判定。
