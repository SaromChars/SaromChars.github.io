TLS 的起源与演进：从 Netscape SSL 到 TLS 1.3

更新于:2026年11月7日
|

上一篇记了数字签名、证书和中间人攻击。这篇接着看 SSL 和 TLS：证书怎样参与建立连接，两端又怎样得到保护数据的密钥。

TLS（Transport Layer Security，传输层安全协议）源于 Netscape 的 SSL。1999 年，IETF 发布 TLS 1.0；TLS 1.2 的规范发表于 2008 年。TLS 1.3 这里按 2018 年 3 月 20 日公开的 draft-28 介绍，仍将它作为草案材料。RFC 2246 · RFC 5246 · TLS 1.3 draft-28

TLS 为什么会出现：可靠送达不等于安全送达

设想浏览器通过网络提交一段登录信息。如果应用直接发送明文，即使底层传输可以可靠地把字节送到另一端，也没有自动解决三个问题：经过链路的人能否读到内容、内容会不会被修改、连接的另一端是不是你想访问的服务。

TLS 把这些目标组合起来：保密性保护内容，完整性帮助发现篡改，身份认证（authentication）帮助确认对端身份。实际 HTTPS 中通常由服务器出示数字证书（digital certificate），客户端验证证书和目标名称；是否认证客户端取决于应用需求。TLS 的保护范围也有边界：终端被控制、应用主动泄露数据、或用户向恶意网站提交信息，都不能只靠加密链路解决。TLS 的目标，RFC 5246 §1

在传统 HTTPS over TCP 连接中，HTTP 负责请求和响应的语义，TLS 先协商参数、认证对端并建立密钥，再保护这些 HTTP 数据。证书参与认证；443 是常用端口，端口号本身不能说明连接协商了哪个版本。RFC 2246 附录 E

从 SSL 到 TLS：关键时间线

下表记录协议及标准文档的关键节点。RFC 的归档时间、协议首次出现的时间和浏览器实际淘汰的时间不是一回事。

时间节点应该记住什么一手来源
1995 年Netscape SSL 2.0 文档TLS 出现之前的 SSL 路线；RFC 6176 引用的原始 SSL 2.0 文档日期为 1995-02-09RFC 6176 §6.2
1996 年SSL 3.0后来 TLS 1.0 的直接基础；RFC 6101 归档的是 1996-11-18 版本RFC 6101 摘要
1999 年 1 月TLS 1.0IETF 发布 RFC 2246，将 SSL 3.0 的基础推进为 TLS 标准RFC 2246
2006 年 4 月TLS 1.1改善 CBC 记录保护，包括使用显式初始化向量（initialization vector，IV）RFC 4346 §1.1
2008 年 8 月TLS 1.2增加 AEAD 密码套件支持，并调整哈希、签名等机制RFC 5246 §1.2
2011 年 3 月禁止 SSL 2.0旧协议正式退出可协商版本RFC 6176
2015 年 6 月弃用 SSL 3.0修补旧实现不能消除其协议层面的全部问题RFC 7568
2018 年 3 月 20 日TLS 1.3 draft-28已公开的草案设计：缩短握手、清理旧机制；本文以这一固定版本为依据draft-28

特别容易混淆的是 SSL 3.0 与 2011 年：RFC 6101 于 2011 年发布，是为了保存早期协议文档，不能据此说 SSL 3.0 发明于 2011 年。RFC 6101

部署时可以参考 2015 年的 RFC 7525：要求支持并优先协商 TLS 1.2；对 TLS 1.0 / 1.1 使用 SHOULD NOT，并保留无更高版本可用时的例外。建议、禁止协商和规范状态变化需要分别看。RFC 7525 §3.1.1

SSL 为什么改叫 TLS：既有继承，也有协议变化

SSL 是 Secure Sockets Layer；TLS 是 Transport Layer Security。两者确有直接继承关系，但把 TLS 1.0 解释成“SSL 3.0 换个名字”会漏掉标准中的实质差异。

RFC 2246 明确说明 TLS 1.0 基于 Netscape 的 SSL 3.0 规范，同时两者的差异足以使它们不能直接互操作。当时的实现可以支持多个版本并协商回退，这不等于两个协议本身完全相同。这里是在描述历史，不能据此为今天启用 SSL 回退。 RFC 2246 §3

今天仍常听到“SSL 证书”。在网站语境中，这往往是沿用下来的商品或习惯名称，并不能证明连接在运行 SSL。判断连接使用的协议，要看实际协商结果，而不是证书商品名。

TLS 1.1 与 1.2：让记录保护和算法选择继续演进

TLS 的变化不只发生在握手上，它还必须规定怎样把应用数据分成记录并加以保护。

TLS 1.1 对 CBC 模式的处理做了调整，例如显式 IV。TLS 1.2 则支持带关联数据的认证加密（authenticated encryption with associated data，AEAD），并改进了哈希与签名算法的选择方式。前者修正已有路径，后者给更现代的数据保护机制提供了协议空间。RFC 4346 §1.1 · RFC 5246 §1.2

这也解释了为什么“版本支持 TLS 1.2”只是判断条件之一：同一个协议版本还可能允许不同的密码套件。讨论安全性需要同时看版本、算法、实现和配置，而不能只在版本号上打勾。面向实际配置时，应结合具体平台文档与适用规范；本文侧重历史，不提供一份适用于所有服务的配置清单。2015 年的安全使用建议：RFC 7525

TLS 1.3 草案：把密钥交换提前

draft-28 中，TLS 1.3 把握手收紧：保留 AEAD 数据保护，移除静态 RSA 密钥交换等旧机制，并在 ServerHello 之后加密更多握手内容。这里的“移除 RSA 密钥交换”不等于“RSA 证书都不能用了”：密钥交换与身份签名是不同职责。draft-28 §1.3

在常见的、基于证书和临时密钥交换的连接中，客户端不必等服务器回应后才首次发送密钥交换参数。它把 key_share 提前放进 ClientHello，减少了等待。这是下面动画对比的重点。

从客户端开始发 ClientHello，到它能够发出常规应用数据，这个简化场景里 TLS 1.2 需要约 2 个网络往返（2-RTT），TLS 1.3 需要约 1 个网络往返（1-RTT）。这里没有计入 DNS、底层连接建立、证书验证耗时，也没有覆盖所有恢复路径。HelloRetryRequest 会增加往返，不能把这里的 1-RTT 直接等同于网页加载时间减半。TLS 1.2 握手：RFC 5246 §7.3 · TLS 1.3 草案握手：draft-28 §2

证书、公钥、会话密钥分别做什么

这部分可以接着阅读本站以前的数字签名、证书与中间人攻击笔记。旧笔记中的“用私钥加密摘要”是直观类比；理解现代协议时，应使用“签名算法与验签算法”的表述，不把所有签名都理解成公钥加密的逆过程。

按 draft-28 的证书认证握手，可以这样分工：

  • 证书与信任链：帮助客户端把服务名称与公钥建立可信关联，还需要正确完成名称、有效期和信任路径等验证。
  • CertificateVerify：服务器用对应私钥对握手上下文签名，证明持有私钥，并把身份认证绑定到本次握手。
  • 临时密钥协商：两端利用各自秘密和交换的公开参数通过临时密钥协商（key agreement）建立共享秘密，再按协议派生流量密钥。私密密钥材料不会原样传输。
  • 对称流量密钥：用于高效保护后续记录。证书里的公钥并不直接承担每个 HTTP 响应正文的加密工作。

这些职责在握手里相互配合：只交换密钥而不认证对端，仍可能遭遇中间人攻击；只持有证书而不证明私钥持有，也不能完成这里描述的认证。draft-28 §4.4 · draft-28 §7

0-RTT 为什么不是“免费加速”

draft-28 允许在特定的预共享密钥或恢复场景下发送早期数据（0-RTT）。它不是首次连接的通用能力，也没有与常规 1-RTT 数据完全相同的安全保证，尤其需要处理跨连接重放风险。draft-28 §2.3

以业务理解这个区别：如果一次请求会创建订单或扣款，被重复执行的后果远比重复读取内容严重。是否允许早期数据，必须由应用协议和服务端一起判断。仅仅因为“用了 TLS 1.3”就把所有操作放进 0-RTT，并不是正确结论。draft-28 §8

SSL 2.0 与 SSL 3.0 已分别有禁止或弃用文档。历史规范可以帮助理解旧系统，具体部署仍需核对当时的安全建议、实现版本与密码套件。RFC 6176 · RFC 7568 · RFC 7525
