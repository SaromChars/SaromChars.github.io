垃圾邮件判定与误杀成本

2021年9月5日
|

在开放的互联网邮件通信中，简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）的低准入门槛使得垃圾邮件（Spam）治理成为系统运维的长期课题。垃圾邮件通常表现为未经收件人请求而批量发送的推广、诈骗或滥用信息。治理垃圾邮件不能仅依赖单一规则，而是需要综合连接、行为、信誉、内容与用户反馈等多层信号。

在设计过滤策略时，动作的选择直接影响系统的容错能力。如果在会话期间直接拒绝，发信方能及时获知失败状态；如果在接受责任后再进行隔离或处置，排错链路就会变得复杂。实际规则可能误拦或漏放，因此评估误杀的代价与口径，并保持收发两端治理职责的分离，是构建平衡系统的核心。

治理维度：连接、行为、信誉、内容与反馈

邮件的过滤与评估贯穿整个交互周期。从客户端发起 TCP 连接，到最终决定是否投递进收件箱，系统可以结合不同维度的信号进行判断：

判定维度核心检测信号触发处理阶段典型机制与工程边界
连接与行为信号对端 IP 地址、连接频次、并发连接数、发信速率TCP 握手至 SMTP 交互全过程RFC 2505 第 2.5 节与 2.8 节提出的来源限制与速率控制（Rate Control）。用于缓解突发流量与拒绝服务攻击（Denial of Service，DoS），但偶发业务高峰不宜直接等同恶意外发。
协议与信封信号握手参数、信封发件人、收件人探测行为EHLO/HELO、MAIL FROM、RCPT TO 阶段校验发件人域名在域名系统（Domain Name System，DNS）中的有效记录（RFC 2505 第 2.9 节）；限制针对系统用户的探测命令（如 VRFY 与 EXPN，RFC 2505 第 2.11 节）。但信封发件人易被伪造，不可单凭地址字符串作信任依据。
外部网络信誉信号基于 DNS 的名单、IP 分组、域名分类会话建立阶段或 MAIL FROM 阶段基于 DNS 的名单（DNS-Based List，DNSBL，RFC 6471），涵盖发信 IP、域名右侧名单（Right Hand Side Blacklist，RHSBL）及白名单（DNS Whitelist，DNSWL）。依赖第三方维护，存在滞后与误收录风险。
邮件内容信号邮件头字段完整性、邮件正文特征、正文外链指向DATA 阶段及传输结束后的邮件内容检查头字段结构校验（RFC 2505 第 2.2 节关于 Received: 追踪信息的维护）、统一资源标志符黑名单（Uniform Resource Identifier Blacklist，URIBL，RFC 6471 第 1.1 节）、文本统计特征。处理开销取决于正文大小与解析深度。
交互与反馈信号用户举报垃圾、从垃圾箱移出、申诉反馈投递入库后及日常运营阶段用户的主动标注与申诉为本地策略调优提供样本，但在没有人工复核的情况下，反馈样本本身通常存在抽样偏差。

1. 中继授权与发件人伪造风险

未受保护的开放中继（Open Relay）曾被广泛用于滥发垃圾邮件。攻击者利用第三方邮件服务器的中转能力发送邮件，不仅隐藏了真实发信源，还会消耗中继主机的网络与计算资源。

最佳当前实践 RFC 2505 第 2.1 节要求，邮件传输代理（Message Transfer Agent，MTA）必须具备限制未授权邮件中继的能力（MUST be able to restrict unauthorized use as Mail Relay）。RFC 2505 将 SMTP 会话中的四个要素列出：

  • HELO 主机名（极易伪造）；
  • MAIL FROM 地址（极易伪造）；
  • RCPT TO 地址（收件目标）；
  • 发起连接的对端 IP 地址（SMTP_Caller，较为真实，对应的主机名取决于反向 DNS 解析是否可信）。

由于前两项极易伪造，MTA 绝不能单独依赖 HELO 主机名或 MAIL FROM 地址来授予中继权限。RFC 2505 建议的判定分支为：若 RCPT TO 属于本域或本系统承诺代转的域，则接受转交；或者，若发起连接的对端 IP（或经确认的完全限定域名 Fully Qualified Domain Name，FQDN）属于已授权的内部来源，则允许中继；若两者均不满足，则应拒绝中继请求。

2. 基于 DNS 的名单机制（DNSBL）

为便于分发发信源的声誉信息，业界发展出了利用 DNS 分发信誉名单的技术。互联网研究任务组（Internet Research Task Force，IRTF）的反垃圾研究组在 RFC 6471（Informational 备忘录）中总结了 DNSBL 的运维与使用实践。

RFC 6471 明确指出，DNSBL 是基于 DNS 分发的各类名单的统称，既包括针对不良 IP 的黑名单，也包括善意发信白名单（DNSWL）、域名名单（RHSBL）以及针对正文链接的 URIBL。RFC 6471 第 1.2 节强调，DNSBL 本身不具备强制阻断能力，是否采用该名单、如何解释其返回值完全由本地系统管理员决定；因此，DNSBL 使用者必须自行承担过滤决策所产生的后果（The DNSBL user MUST assume responsibility for dealing with the consequences）。如果管理员将用于单机对端 IP 评估的名单误用在邮件头中解析出来的历史中转 IP 上，往往会导致严重的误拦截。

协议底线：不能仅凭特定地址值直接拒收

在制定过滤规则时，运维人员有时会设置过于严苛的条件。RFC 2505 明确指出了若干项不能仅凭地址字符串就粗暴拒收的场景，以保障邮件系统的正常运转：

1. 不能仅因空反向路径而拒绝

根据 RFC 2505 第 2.6.1 节，MTA 绝不能仅因为反向路径为空就拒收会话（MUST NOT refuse “MAIL From: <>”）：

MAIL From: <>

空反向路径（Null Reverse-Path）是邮件系统传输投递状态通知（Delivery Status Notification，DSN）与错误退信的标准信封标识。如果接收端直接拒收这类邮件，发信方用户在邮件投递失败时将永远无法收到退信通知，排错链路就会彻底断裂。

部分发信者确实会利用空反向路径向多个收件人投递垃圾邮件。但在邮件列表中，多个列表所有者可能位于同一远程站点，向其并发发送系统通告属于正常现象。RFC 2505 规定，系统即便在检测到多个收件人时，也不能仅因此拒收；但作为防御措施，MTA 可以对这种连接降低数据读取频率进行节流（MAY throttle down the TCP connection）。同时，根据 RFC 2505 第 2.7 节末段，如果对端 IP 本身属于被明确列入拒收策略的恶意来源，该连接仍可被整体阻断，并非因为发件人写了 <> 就享有全面放行特权。

2. 不能仅因发件人包含本地域名而拒绝

根据 RFC 2505 第 2.6.2 节，当外部主机发起连接并声明发件人属于本地域名时（例如 MAIL From: <user@sub.example.com>），MTA 同样不能仅凭该域名字符串就直接拒收（MUST NOT refuse）。

直接根据本地域名拦截外部来信，会破坏两类合法业务流：

  1. 别名与自动转发（Aliases）：本域用户发送邮件给外部合作伙伴，该伙伴通过 .forward 文件或邮件别名将邮件重新转发回本域；
  2. 外部邮件列表（Mailing Lists）：按照 RFC 1123 的要求，邮件列表外发时的信封发件人应当反映列表所有者的地址。如果列表所有者属于本域，而列表服务器位于外部主机，外部服务向列表成员投递邮件时，就会出现外部对端使用本域发件地址的情况。

对于冒用本域地址的外部伪造风险，应当结合经验证的身份和来源信息进行综合鉴别，而不能在 SMTP 握手阶段简单地按域名黑名单一刀切。

动作选择：RCPT 响应、DATA 终结与接受后处置

当判定引擎认为会话或邮件存在嫌疑时，应当在哪个阶段采取何种动作，直接决定了系统的责任划分与发件人的排错感知。

发信方客户端                                      接收方 MTA
     |                                                |
     |---- MAIL FROM:<sender@example.net> ----------->|
     |<--- 250 OK ------------------------------------|
     |                                                |
     |---- RCPT TO:<user@sub.example.com> ----------->|
     |     [收件人校验与基础信誉检查]                 |
     |                                                |
     |-- 分支 1: 临时拒绝当前收件人 ----------------->|
     |<--- 451 4.7.1 Try again later -----------------|
     |     (客户端保留该收件人事务，通常按策略退避重试)
     |                                                |

     |<--- 550 5.7.1 Recipient rejected --------------|
     |     (客户端通常停止原样重试；后续按责任及反向路径处理)
     |                                                |

     |                                                |

     |<--- 354 Start mail input ----------------------|
     |---- 邮件内容传输及 <CRLF>.<CRLF> ------------->|
     |     [内容扫描、病毒过滤、综合评分]             |
     |                                                |
     |<--- 250 2.0.0 Message accepted for delivery ---|
     |     (接收端正式接管整封邮件的后续投递或安全责任)

1. RCPT 阶段的状态码权衡

在 RCPT TO 阶段，接收端针对单个收件人给出响应：

  • 5xx（永久性失败）：通常表示当前收件人请求被明确拒绝，客户端不再原样自动重试受影响的收件人事务。若发件方持有原始邮件且信封反向路径非空，由发件方系统向用户生成未送达退信。5xx 适用于已确认的恶意 IP 或不存在的账户，但若属于配置失误，可能直接中断正常通信。
  • 4xx（临时性失败）：告知客户端当前无法完成该收件人事务，发信客户端通常会将该事务留在队列中等待退避重试。RFC 2505 第 1.6 节建议将 4xx 作为多数反垃圾规则的首选响应。这为管理员在日志中发现配置错误留出了缓冲时间；如果是真实垃圾发信源，持续的重试队列会消耗其本地资源；若是借用合法中继，队列积压也更容易引起中继方的注意。

不过，4xx 响应在多 MX 场景下存在副作用。如果接收域配置了多台 MX 主机，当优先选用的低 preference 值主机返回 451 时，发信客户端可能转而尝试列表中下一台优先级较低的备用 MX 主机。如果该备用主机未同步配置相同的过滤名单，邮件就可能在备用机上被收下，从而打乱预期的拦截效果。此外，在校验发件人域名 DNS 时，若遇到临时性网络故障（TempFail），MTA 必须返回 4xx 响应；若遇到权威的域名不存在（NXDOMAIN），RFC 2505 第 2.9 节建议在多数情况下仍首选 4xx 以防主从 DNS 同步延迟，但也允许管理员配置为 5xx 永久拒绝。

2. DATA 阶段后的责任移交与处置边界

必须注意，在 RCPT TO 之后收到的 250 OK 仅代表当前收件人地址被语法接受，并不意味着邮件内容已被接收。只有在客户端传输完完整邮件内容（包括头字段与正文）并发出结束符后，服务端返回的 250 OK 才标志着接收端正式接管了该邮件的后续投递责任。

根据 RFC 2505 第 1.6 节，接收端若在返回 250 OK 承诺接收后盲目将邮件静默丢弃（例如直接丢入 /dev/null），公然违背了邮件传输协议的可靠性原则。因为此时发信方认为邮件已成功送达，不再发出告警；而收件人实际上从未收到邮件，导致双方沟通陷入静默中断。

但这并不意味着接受后绝对不能做任何特殊处置：

  • 对于普通可疑邮件，合理的做法是将其隔离入待查队列、打上垃圾标记后投递至用户的垃圾邮件文件夹（Spam Folder），保留用户核对与取回的途径；
  • 在极其特殊的高置信度恶意场景下（例如确凿的病毒扩散、严重欺诈或协议滥用攻击），邮件系统在有明确安全边界与严格策略授权的前提下，可以执行丢弃处理，以阻断恶意的进一步扩散；
  • 若接收端在接管责任后因本地后续投递失败而生成退信，必须检查原信封反向路径；如果原反向路径为空（<>），则绝不能再针对该退信生成新的退信，以防引发反向散射（Backscatter，回散）与死循环。

误杀成本、评估口径与收发治理

在垃圾邮件对抗中，误杀合法邮件（False Positive）与漏放垃圾邮件（False Negative）的控制取决于判定阈值的权衡。误杀可能导致业务合同、账单或系统通知丢失，增加跨组织的人工排错与沟通成本；而漏放则会增加用户的干扰与安全风险。

1. 评估口径与反馈偏差

为了科学评估规则效果，需要明确两类指标的定义与分母。以垃圾邮件为正类，系统判定输出为垃圾（拦截/隔离）或正常（放行投递）：

真实类别 \ 系统判定判定为垃圾（拦截/隔离）判定为正常（放行投递）真实总数
真实正常邮件误杀（False Positive，FP）准确放行（True Negative，TN）真实正常邮件总数（N_legit）
真实垃圾邮件准确拦截（True Positive，TP）漏杀（False Negative，FN）真实垃圾邮件总数（N_spam）
  • 误杀率（False Positive Rate，FPR）：FP / N_legit，分母是所有真实的合法邮件总数，而非所有被拦截的邮件数；
  • 漏杀率（False Negative Rate，FNR）：FN / N_spam，分母是所有真实的垃圾邮件总数。

以明确标为教学示范的简单计数为例：若系统接收 10,000 封真实正常邮件，其中 5 封被规则错误拦截，则误杀率 FPR 为 5 / 10,000 = 0.05%；若系统遭遇 100,000 封真实垃圾邮件，其中 2,000 封未能识别而漏入收件箱，则漏杀率 FNR 为 2,000 / 100,000 = 2.0%。

在实际工程中，真实标签的获取非常困难。被同步拒收的邮件通常无法直接统计其合法性，除非收到发信方的离线申诉；被投递至垃圾箱的邮件，依赖用户主动将其移回或标记为“非垃圾”；而漏放的邮件则依赖收件人点击“举报”。这些运营反馈只能提供局部抽样，且带有明显的主观倾向与未反馈偏差。因此，评估名单或模型效果不能只看单一拒收计数，而需要配合小流量试用、定期抽样人工复核和持续的本地基线监控。

2. 名单系统的运营风险与维护约定

外部信誉名单（DNSBL）能有效降低本地计算开销，但引入了外部依赖风险。RFC 6471 总结了运维 DNSBL 时应当遵循的最佳实践：

  1. 名单的有序下线（Graceful Shutdown）：历史上曾有 DNSBL 服务商在终止运营时，为了促使管理员尽快移除失效配置，直接将全网所有 IP 均解析为命中黑名单，导致使用该名单的邮件系统发生全网大面积拒收。RFC 6471 第 3.4 节明确要求，DNSBL 停运时绝不能收录整个互联网（MUST NOT list the entire Internet）。运营方必须提前发布下线预警（原文建议持续一个月或更长时间），并可采用文档建议的方案示例：将 DNSBL 的名称服务器指向保留的测试网络（TEST-NET，如 192.0.2.1）以制造超时延迟，提示管理员主动清理无效配置。
  2. 测试条目与异常信号识别：根据 RFC 6471 第 3.3 节与第 3.5 节，多数 IP 类 DNSBL 遵循使用 127.0.0.2 作为服务存活测试的行业惯例（域名类名单则没有统一事实标准，RFC 6471 建议使用保留顶级域 test）。同时，正常运行的 DNSBL 绝不能收录 127.0.0.1。如果在检测时发现针对 127.0.0.1 返回了正向命中记录，通常说明该名单已发生异常或处于恶意全网收录状态，本地系统应立即停用该名单以避免大面积误杀。
  3. 移除通道与时限：RFC 6471 第 2.2.3 节规定，名单运营方应对申诉与移除请求保持响应，应该在 2 天内响应，最迟必须在 7 天内给出响应（SHOULD respond within 2 days and MUST respond within 7 days）；若运营方认定不符合移除条件并已通知申请人，则属例外。当符合移除条件时，应同样迅速执行移除。此外，RFC 6471 第 2.2.5 节明确禁止负面信誉名单以“加速审核”或“解封费用”名义收取金钱或索要捐款。

3. 收件治理与发件治理的分离

邮件治理不能只关注入站拦截，收发两端在防御目标与控制手段上承担着截然不同的责任：

  • 收件端治理（保护收件人与系统资源）：核心目标是在有限的带宽与存储资源下，过滤有害垃圾并尽可能避免误伤正常来信。作为一种常见的可选方案，系统可在入口处结合连接频次、DNSBL、发件人有效性与内容特征进行多因子加权评分；将高风险邮件予以会话拒绝，中风险邮件打标放入隔离区或垃圾文件夹，并依据用户的白名单或取回行为动态调整信任边界。
  • 发件端治理（保护外发信誉与本地账号安全）：核心目标是防止内部被盗账号或恶意租户滥用系统外发垃圾，避免本域外发 IP 被公网名单列入黑名单。在此过程中需清晰区分标准规范与条件性运营方案：
    1. 协议层建议能力：RFC 2505 第 2.8 节建议系统具备限制发送速率的工具能力（Rate Control），第 2.10 节建议允许对外发用户名（local-part）进行真实性核验，以拦截用户拼写错误或恶意伪造的本地发件人；
    2. 条件性运营与排查：作为工程方案，服务运维方可结合队列堆积、异常发信速率以及在具备可用反馈渠道时（如用户投诉与外部退信）收集的信号展开排查；当有可靠证据表明账号遭受滥用时，再按本地安全策略采取针对性限速、隔离或人工复核，避免仅凭偶发的网络延迟或局部退信就武断封锁正常用户。

将收件的防护策略与发件的合规约束分离，配合基于本地样本的持续观察与调整，有助于在有效压制垃圾邮件的同时，将误杀对业务与系统声誉的负面影响维持在可控范围内。
