AES 为什么还需要工作模式？——从 CBC、CTR 到 GCM

更新于:2026年11月7日
|

在梳理 密码算法分类笔记 时，我们把 AES 归在“对称加密”的分类下。很多刚接触安全开发的工程师在查看系统配置或接口文档时，看到系统注明“采用了 AES-128”或“采用了 AES-256”，便往往认为数据已经得到了充分的加密保护。

然而，仅知道系统“用了 AES”，在工程上根本无法判断通信或存储到底是否安全。甚至可以说，“用 AES 加密一段数据”这句话在密码学实现层面是不完整的。

因为 AES 本质上并不是一个可以直接吃进任意长度数据并吐出密文的完整加密方案，它只是一个固定尺寸的分组密码（Block Cipher）。要把这个针对固定长度积木块的数学变换，扩展到现实世界中不同长度的数据或持续传输的数据流上，必须引入工作模式（Mode of Operation）。选择不同的工作模式，不仅决定了数据如何对齐与迭代，更决定了密钥流是否会暴露、密文能否被攻击者篡改，以及整个方案是否真正具备抗攻击能力。

分组密码与工作模式：算法与模式不可混为一谈

要搞清楚工作模式的意义，首先要把两个常被混淆的概念拆开：分组密码的块大小与密钥长度。

根据 AES 的标准定义FIPS 197 §1, §3，AES 的分组大小（Block Size）恒定为 128 位（16 字节）。而常说的 AES-128、AES-192 与 AES-256，指的完全是密钥长度（Key Size），它们分别对应 10 轮、12 轮与 14 轮的轮函数变换。无论密钥是 128 位还是 256 位，每一次算法执行所吞吐的明文块与密文块永远是 128 位。

这意味着：AES 算法本身只回答了一个问题——在给定密钥 K 下，如何把某一个特定的 16 字节明文块 P，一一对应地置换为一个 16 字节密文块 C。

现实业务中的 HTTP 报文、数据库记录或文件，几乎不可能刚好只有 16 个字节。当面对由多个 16 字节组成的长消息时，怎样把它们切分、如何把前后的运算关联起来，以及遇到不足 16 字节的尾部数据该怎么办？这就是工作模式要解决的事情。工作模式并不是算法的附属小开关，它与底层分组密码是两层独立的构造。选错了模式，即便底层的 AES 算法自身在数学上符合规范，整个加密体系依然可能出现严重缺陷。

最朴素的尝试：ECB 模式

面对多个明文块，最直观的想法是切块并分别独立加密：

明文块: P1   P2   P3   ...   Pn
        ↓    ↓    ↓          ↓
      AES  AES  AES        AES (同一密钥 K)
        ↓    ↓    ↓          ↓
密文块: C1   C2   C3   ...   Cn

这就是电子密码本模式（Electronic Codebook, ECB）SP 800-38A §6.1。

ECB 的核心缺陷在于它的独立性：在同一个密钥下，相同的明文块永远输出完全相同的密文块。

这并不意味着攻击者仅凭密文就能直接还原出所有原始明文，但当业务数据中出现重复且恰好对齐到 16 字节块的内容时（例如大面积相同填充或重复的结构化字段），密文块之间会原样呈现出重复关系，直接暴露出明文的统计特征与重复位置。此外，攻击者还可以通过交换、删除或替换密文块来干扰解密结果。

引入状态与链式依赖：CBC 模式

为了打破相同明文块产生相同密文块的静态对应关系，必须让每一个块的加密过程都与上下文产生关联。密文分组链接模式（Cipher Block Chaining, CBC）通过链式结构引入了动态依赖SP 800-38A §6.2。

加密与解密公式

在 CBC 模式中，每一个明文块在进入底层分组加密前，必须先与前一个密文块进行异或；而第一个明文块由于没有前序密文块，必须引入一个初始化向量（initialization vector，IV）：

CBC 加密：
C1 = CIPH_K(P1 ⊕ IV)
Cj = CIPH_K(Pj ⊕ Cj-1)   (j = 2, ..., n)

CBC 解密：
P1 = CIPH^-1_K(C1) ⊕ IV
Pj = CIPH^-1_K(Cj) ⊕ Cj-1 (j = 2, ..., n)

文本流程示意如下：

[加密过程]
P1 ──⊕──> [ AES Encrypt (K) ] ──> C1 ──┬──> 传输/存储
     ↑                                 │
    IV                                 │
P2 ──⊕ <───────────────────────────────┘
     ↓
   [ AES Encrypt (K) ] ─────────> C2 ──┬──> 传输/存储
                                       │
                                      ...

[解密过程]
C1 ──┬──> [ AES Decrypt (K) ] ──⊕──> P1
     │                          ↑
     │                         IV
     └──> (作为下一块的异或输入)
          ↓
C2 ─────> [ AES Decrypt (K) ] ──⊕──> P2
                                ↑
                               C1

在 CBC 加密中，由于第 j 块的输入依赖第 j-1 块的密文输出，加密过程无法并行化，必须串行推进。而在解密时，各个块直接取用已知的密文进行 AES 逆向解密并异或前一块密文，解密计算是可以并行的。

IV 的核心要求：公开但不可预测，需保护完整性

IV 不需要保密，它可以明文附在密文前一同发送或存储。但根据标准规范SP 800-38A §6.2, Appendix C，CBC 模式的 IV 必须是不可预测的（Unpredictable）。

常见的工程错误是将简单自增的序号或固定时间戳直接当作 IV。SP 800-38A 推荐生成 IV 的方式包括使用随机数发生器生成独立随机块，或在同一密钥下使用底层分组密码加密单次唯一的计数器（Nonce）来产生不可预测的 IV。

此外，CBC 解密首块明文公式为 P1 = CIPH^-1_K(C1) ⊕ IV。根据 SP 800-38A Appendix D，如果 IV 的完整性没有受到保护，攻击者若修改 IV 中特定比特，解密后 P1 对应位置的比特也会精确地发生翻转。

填充机制：以 CMS / PKCS#7 举例

CBC 是严格基于块的运算，每一块都必须是完整的 16 字节。因此，当原始数据长度不是 16 字节的整数倍时，必须在末尾补齐。

常见的填充标准有 RFC 5652 / PKCS#7 填充RFC 5652 §6.3。其规则为：缺少几个字节，就填充几个数值为该长度的字节。

  • 若数据差 1 个字节对齐，填充 0x01；
  • 若差 5 个字节对齐，填充 0x05 0x05 0x05 0x05 0x05；
  • 如果明文本来就是 16 字节对齐的，必须在末尾追加一个由 16 个 0x10 组成的完整填充块。

必须追加整块的原因在于消除歧义：解密端在处理完毕后直接读取最后一个字节的数值 k 并校验剥除。若对齐时不追加整块，接收端无法区分末尾究竟是业务数据还是填充。

需要说明的是：CMS / PKCS#7 是常见的具体填充方案，并非所有 CBC 模式在数学上只能使用这一种填充（例如 SP 800-38A Appendix A 还说明了其他填充方式）。

CBC 不自带认证：篡改与完整性风险

CBC 属于保密性模式，其本身不提供数据真实性或完整性检验。

根据 SP 800-38A Appendix D，对密文块 Cj 引入的比特错误不仅会导致解密后的 Pj 出现大面积随机错误，还会直接导致下一块 Pj+1 的相同比特位置产生特定翻转。如果缺乏独立的完整性保护机制，系统无法检测密文或 IV 在传输中是否遭到故意篡改或损坏。

把分组密码变为流模式：CTR 模式

既然分组密码存在块对齐需求且 CBC 加密无法并行，计数器模式（Counter Mode, CTR）提供了另一种方式：不再直接把明文送入 AES 置换，而是让 AES 加密一组递增的计数器块，生成伪随机密钥流块，再将密钥流与明文进行逐位异或SP 800-38A §6.5。

运作机制与特点

CTR 模式的加解密公式如下：

CTR 加密：
Oj = CIPH_K(Tj)   (j = 1, ..., n)
Cj = Pj ⊕ Oj      (对于前 n-1 个完整块)
Cn* = Pn* ⊕ MSB_u(On) (对于最后不足 128 位的 u 位部分块)

CTR 解密：
Oj = CIPH_K(Tj)   (j = 1, ..., n)
Pj = Cj ⊕ Oj      (对于前 n-1 个完整块)
Pn* = Cn* ⊕ MSB_u(On) (对于最后不足 128 位的 u 位部分块)

该模式具备以下特点：

  1. 加解密均只调用 AES 的正向加密函数（CIPH_K）。解密时不需要逆向解密函数，直接重新计算密钥流并与密文异或即可恢复明文。
  2. 完全不需要块填充。若最后一个明文块不足 16 字节，仅截取第 n 个密钥流块 On 的前 u 位（即最高有效位 MSB）与明文异或，剩余多余的密钥流丢弃，密文长度与明文完全一致。
  3. 加解密均支持并行计算与随机访问。任意数据块只要确定其计数器块 Tj，便可独立加解密。

核心约束：完整计数器块全局唯一、不可回绕

CTR 采用流式异或，其安全性依赖底层 AES 生成的伪随机流不重复。

核心要求是：在同一密钥下，所有消息所使用的全部计数器块 Tj 必须全局互不相同，严禁重复或回绕SP 800-38A §6.5, Appendix B。

SP 800-38A Appendix B.2 给出了两种保证跨消息唯一的有效构造：一种是顺序累加的全局计数器；另一种是为每条消息分配一个唯一的高位消息 Nonce（例如 64 位），低位保留给块索引并逐块递增。只要保证消息 Nonce 唯一且每条消息的块数不超过低位计数器的容量上限，便是符合规范的构造。若使用随机生成 Nonce，则必须关注其碰撞风险并限制消息总数。

密钥流复用的后果与位翻转

如果攻击者截获了两段在相同密钥下使用了相同计数器序列加密的密文 C1 与 C2：

  • C1 = P1 ⊕ O
  • C2 = P2 ⊕ O

将两段密文进行异或： C1 ⊕ C2 = (P1 ⊕ O) ⊕ (P2 ⊕ O) = P1 ⊕ P2

密钥流 O 被完全抵消，攻击者可直接得到两份明文的逐位异或值。如果已知其中一段明文，便可直接计算恢复出另一段明文。

此外，CTR 模式本身不提供完整性认证，且具有可控的位翻转特性（见 SP 800-38A Appendix D）。攻击者若翻转密文中的某个比特，解密后明文对应的比特也会精确翻转，而 CTR 解密过程本身完全无法察觉这种修改。

认证加密模式：GCM 模式

为了同时解决保密性与完整性问题，避免手工拼接加密与消息认证码（message authentication code，MAC）带来的失误，带关联数据的认证加密（authenticated encryption with associated data，AEAD）把这两项功能结合在同一构造中。伽罗瓦/计数器模式（Galois/Counter Mode, GCM）是其中的代表标准NIST SP 800-38D 与 RFC 5116。

结构：计数器保密 + GHASH 认证

GCM 结合了 CTR 模式的变体（GCTR）与基于有限域多项式的哈希函数 GHASHSP 800-38D §5.3, §6.4。

其认证范围覆盖加密后的密文 C，以及附加认证数据（Additional Authenticated Data, AAD）。AAD 是指那些需要保证完整性但不需要保密的数据（例如报文头部、通道编号或协议状态），它们可以明文传输，也可以由通信双方依据上下文直接重建。

最终的认证标签（Authentication Tag, T）由 GHASH 计算结果结合预计数器块的加密生成SP 800-38D §7.1：

  1. 派生哈希子密钥 H = CIPH_K(0^128)。
  2. 由初始化向量 IV 生成预计数器块 J0。
  3. 从 inc_32(J0) 开始，调用 GCTR 对明文进行流式加密生成密文 C。
  4. 将 AAD 和密文 C 分别以零比特补齐到 128 位整数倍，再连同各自的 64 位长度字段组合输入 GHASH，得到 S。
  5. 使用 AES 生成的掩码保护 GHASH 输出，得到最终的 Tag：T = MSB_t(GCTR_K(J0, S))。

Nonce 长度与 Tag 长度说明

关于 GCM 参数：

  1. Nonce 长度：GCM 标准支持多种字节对齐的 IV 长度（SP 800-38D §5.2.1.1 要求长度为 8 的倍数，且实现可限制所支持的长度）。标准推荐使用 96 位（12 字节）IV，此时系统可直接追加 0^31 || 1 生成 J0，免去了对 IV 进行 GHASH 计算的开销。而在 RFC 5116 §5.1 中定义的 AEAD_AES_128_GCM 具体算法套件中，Nonce 长度则被明确固定为 12 字节。
  2. Tag 长度：根据 SP 800-38D §5.2.1.2，标准仅允许选择 128、120、112、104、96 位（特定受限应用下允许 64 或 32 位），且每个密钥必须固定一个所支持的 Tag 长度。短 Tag（如 32 或 64 位）在使用时受到严格的最大消息长度与密钥寿命限制（见 SP 800-38D Appendix C）。在 AEAD_AES_128_GCM 具体套件中，Tag 长度固定为 16 字节（128 位）。

工程使用约束

在实现与配置 GCM 时，需要注意以下事项：

第一，认证成功前不得向业务交付明文；Tag 校验失败须返回 FAIL。实现可以选择内部计算顺序，但不得释放未经认证的明文SP 800-38D §5.2.2, §7.2。

第二，同一密钥下 Nonce 严禁重复使用。

  • 根据 RFC 5116 §5.1.1 与 SP 800-38D Appendix A，一旦 Nonce 复用，不仅会暴露两份明文的异或值，还会削弱 GHASH 认证保障，可能使攻击者恢复出哈希子密钥 H，进而在已观察到的合法 IV 和 Tag 条件下修改或伪造消息。
  • 随机生成 Nonce 存在碰撞概率，因此 SP 800-38D §8.3 对包含随机字段的构造规定了同一密钥下全实例总调用上限（不超过 2 的 32 次方次）。若采用计数器确定性构造（如固定设备字段加上单调递增字段），则需要管理并发与系统重启时的状态持久化（见 RFC 5116 §3.1）。

第三，AAD 不提供保密性，且 GCM 自身不提供防重放保护。

  • 不应将需要保密的敏感信息放入公开传输的 AAD 中。
  • Tag 校验成功说明数据由持有该密钥的一方生成，且密文与 AAD 的完整性得到验证；不自动证明现实实体身份，也不防止合法报文被原样重放（见 SP 800-38D Appendix D 与 RFC 5116 §1.2）。防重放还需上层协议维护接收状态，并校验认证过的序号、窗口或时间信息。

四种模式对比

工作模式核心设计输入与填充IV / Nonce 核心约束是否自带认证并行能力
ECB独立分组置换输入须为整块；不齐时需补齐（如采用 CMS/PKCS#7 则每条均填充）无 IV否加密、解密均可并行
CBC密文反馈链接输入须为整块；不齐时需补齐（如采用 CMS/PKCS#7 则每条均填充）必须不可预测；需保护完整性否（保密性模式）加密串行；解密可并行
CTR计数器生成密钥流无须填充（按位截断）同一密钥下完整计数器块全局唯一、不可回绕否（具有位翻转延展性）加密、解密均可并行
GCMGCTR 保密 + GHASH 认证无须填充（按位截断）同一密钥下 Nonce 严禁复用（标准建议 96 位）是（AEAD 模式），同时认证密文与 AAD加密、解密、认证均可并行

对称加密的实际安全性并不由“AES”这个算法名称单独决定。分组密码只是定义了固定数据块的置换规则；在具体应用中，必须结合工作模式的特性、IV 与 Nonce 的生成约束，以及完整性认证机制，才能构成完整的安全实现。
