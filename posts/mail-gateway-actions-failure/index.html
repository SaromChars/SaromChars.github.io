网关动作、故障策略与投递责任

2022年1月5日更新于: 2026年11月12日
|

当反垃圾网关后面的扫描引擎发生异常时，开发者面临的首要问题是：这封邮件现在究竟归谁保管。如果处理不当，可能导致正常业务信件在故障期间被静默遗失，或是在事后生成大量退信并投向伪造发件人。简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）作为一个基于存储转发的传输协议，对消息确认、重试责任以及最终落盘有着明确的状态转换界限。理解这些界限与本地队列机制，是设计网关动作与故障容灾策略的前提。

扫描故障时的 SMTP 责任移交边界

在标准 SMTP 会话中，客户端与服务端依次执行信封与内容协商。根据 RFC 5321 第 4.2.5 节与第 6.1 节，传输责任的移交点有清晰的界定：

  1. MAIL FROM 与 RCPT TO 阶段：服务端返回 250 OK 仅表示接受当前命令中的参数并允许会话继续，并不代表服务端接管了整封邮件的保管责任，也不等同于对最终路由有效性的绝对保证。在 RCPT TO 阶段，服务端可以逐个收件人进行差别化校验并独立返回拒绝（如对不存在的邮箱返回 550 No such user），而继续保留其他已被接受的收件人。
  2. DATA 握手阶段：客户端发送 DATA 后，服务端返回中间状态码 354 Start mail input; end with <CRLF>.<CRLF>，这只是授权客户端开始发送内容流的信号，此时邮件传输随时可能中断，保管责任仍在发送方。
  3. 消息结束（End of Message，EOM）阶段：客户端发送独立的单个句点行（<CRLF>.<CRLF>）表示邮件内容结束。只有当服务端在收到该终结符并成功将邮件持久化存储到本地安全介质后，向客户端发出最终的 250 OK 响应那一瞬间，整封邮件的传输责任才正式从客户端移交到服务端。

如果网关在收到终结符之后、返回最终响应之前发生了扫描故障，向客户端返回 4xx 临时失败状态码（Temporary Failure，如 451），责任依然保留在客户端，正常的邮件传输代理（Mail Transfer Agent，MTA）通常会将邮件保留在本地出站队列中，并根据本地调度策略后续安排重试投递。如果网关返回 5xx 永久失败状态码（Permanent Failure，如 554），发送方将终止针对该事务的重试；对于最终返回的 4xx 或 5xx，接收端在当前事务中均不得再尝试向本地或下游投递。

需要注意的是，普通 SMTP 事务在收到正文终结符后的回复是针对整个事务全部有效收件人的统一响应。在标准 SMTP 下，无法在正文内容判定完成后，为同一会话中已接受的多个收件人返回不同的最终状态码。

在诸如 Postfix 等成熟 MTA 的内部实现中，为了支持流式接收大尺寸邮件而不耗尽物理内存，当客户端开始发送正文内容时，清理服务通常就已经在磁盘的进件队列中创建了临时队列文件，并分配了内部队列标识符（queue_id）。但队列文件在本地文件系统中的预分配，绝不代表该邮件已经被确认接收。若接收端在发出最终 250 前明确失败，上游仍需负责重试；若客户端只是没有收到最终响应，则不能据此证明接收端没有接管保管责任，必须结合接收端的持久化记录核对。

反之，一旦向客户端发出了最终的 250 OK，邮件的投递责任便转移到了本地系统，此时必须由本地持久化队列保证其不丢失。网关不能在断开连接后追溯性地向发件人补发 SMTP 拒绝，更不能向信封发件人盲目回退反弹邮件。在垃圾邮件场景中，恶意信件的信封发件人（MAIL FROM）可能伪造无辜第三方地址；若网关在发送最终 250 OK 后因内部处理失败而由本地队列生成投递状态通知（Delivery Status Notification，DSN）并向伪造发件人回发，会造成回散（Backscatter，退信轰炸）。

根据 RFC 5321 第 6.2 节，规范虽然允许在确信邮件属于恶意滥用且无法拒绝时有条件地静默丢弃，但这属于高置信恶意流量的例外处置，绝不能将静默丢弃当做常规扫描故障时的容错机制。此外，若最终 250 OK 网络报文在传输中丢失或客户端因超时先断开，发送方会认为该次投递未完成并重新发起重试，网关需要具备处理重复信封与幂等接收的能力。

网关动作映射：以 Rspamd 与 Postfix 为例

在现代邮件系统中，反垃圾网关通常通过 Milter（邮件过滤接口）接入 MTA。以 Rspamd 2.7 与 Postfix 3.6.2 为例，可以追踪正文扫描完成后的动作映射机制。

Rspamd 2.7 的 Milter 动作映射

在 Rspamd 2.7 源码 src/libserver/milter.c 中，当 Milter 连接读取到客户端正文结束标记 RSPAMD_MILTER_CMD_BODYEOB 后，会保留会话并触发 priv->fin_cb 异步完成回调。扫描引擎分析完毕后，调用 rspamd_milter_send_task_results 将判定结果转换为 Milter 协议动作指令：

  • 拒绝（Reject）：在 action->action_type 为 METRIC_ACTION_REJECT 分支下，若未开启特殊开关，默认使用定义在 milter_internal.h 的常量：响应码 554、增强状态码 5.7.1、文本 "Spam message rejected"，通过 rspamd_milter_set_reply 向 MTA 注入拒绝响应。
  • 软拒绝（Soft Reject）：在 METRIC_ACTION_SOFT_REJECT 分支下，设置响应码 451、增强状态码 4.7.1、文本 "Try again later"，常用于要求客户端延后重试。
  • 添加邮件头（Add Header）：在 METRIC_ACTION_ADD_HEADER 分支中，先调用 rspamd_milter_remove_header_safe 尝试删除既有的同名头，再注入新的判定头（默认为 X-Spam: Yes），最后向 MTA 发送 RSPAMD_MILTER_ACCEPT 接受指令。
  • 隔离（Quarantine）：在 METRIC_ACTION_QUARANTINE 分支中，向 MTA 发送 RSPAMD_MILTER_QUARANTINE 并在其后紧跟一条 RSPAMD_MILTER_ACCEPT 指令。若配置了 quarantine_on_reject = true，原定的拒绝动作也会转化为“先发隔离、再发接受”。

需要指出，这里的添加邮件头动作只负责在传输流中插入或修改 RFC 5322 文本头，并不等同于将邮件放入垃圾箱或隔离区。邮件最终是被投递到用户的收件箱还是垃圾邮件箱，完全依赖下游邮件存储系统（如 Dovecot 配合 Sieve 脚本）或用户代理的规则解释。下游系统必须配置显式的信任策略，剥除公网发件人自行构造的外来同名头，由本地生成的信任头决定归宿。

Postfix 对 Milter 指令的解释与隔离机制

Postfix 在接入 Milter 时有独立的内部映射通道。在 Postfix 3.6.2 的 src/milter/milter8.c 中，当读取到 Milter 返回的 SMFIR_QUARANTINE 指令时，Postfix 调用 milter8_def_reply(milter, "H")，将内部应答映射为单字符指示符 "H"。

在后续的清理模块 src/cleanup/cleanup_milter.c 中，函数 cleanup_milter_apply 检查该应答：当 resp[0] == 'H' 时，设置内部标志位 state->flags |= CLEANUP_FLAG_HOLD，记录日志 milter triggers HOLD action。

这意味着在 Postfix 的实现中，Milter 请求的隔离本质上是将邮件推入本地的滞留队列（Hold Queue）。Postfix 本身并不提供面向终端用户的 Webmail 隔离区、申诉流或到期自动清理产品。邮件被挂起在磁盘队列上并停止调度出站，等待系统管理员通过命令行或自研管理后台进行人工审查。

此处追踪的 Rspamd 正文扫描结果动作协商均发生在客户端发送 EOM 之后、MTA 返回最终 SMTP 250 OK 之前。对于隔离动作，MTA 在将队列文件置为 HOLD 后，对客户端返回最终的 250 OK。此时外部发件人认为邮件已成功接收，而信件实际已被本地截留。这与直接丢弃（Discard，在 Postfix 中映射为单字符指示符 "D"，内部置 CLEANUP_FLAG_DISCARD，不保留在队列中）在存储生命周期上有本质区别。

故障分层：避免粗暴的单一容灾策略

网关系统在面临组件故障时，不能把所有异常都归纳为简单的放行或拒收。故障发生的层级不同，协议应答的责任和行为截然不同。

扫描器代理与后端失效的独立判定

如果网关在 Postfix 中配置了 milter_default_action = accept，当扫描组件发生异常时，邮件并不一定会全部自动放行。

查看 Rspamd 2.7 的代理模块 src/rspamd_proxy.c：当 Rspamd Proxy 进程健康，但其后端工作扫描进程无响应或连接超时（proxy_backend_master_error_handler）且重试耗尽时，会触发 proxy_client_write_error。由于此时 Proxy 与 MTA 之间的 Milter 管道连接 session->client_milter_conn 依然处于活跃状态，函数直接执行：

rspamd_milter_send_action (session->client_milter_conn,
        RSPAMD_MILTER_TEMPFAIL);

此时，Rspamd Proxy 向 MTA 返回的是一个显式的 Milter 临时失败（TEMPFAIL）协议响应。对于 Postfix 而言，这属于过滤器主动要求暂缓处理，因此 MTA 会如实向客户端返回 451 4.7.1 Service unavailable - try again later。在这种情况下，Postfix 配置的 milter_default_action 根本不会生效，因为与 Milter 的套接字通信本身并未发生通道层面的错误。

通信错误与配置错误的降级分支

只有当 MTA 与 Milter 之间的底层套接字连接拒绝、读写超时或协议格式损坏时，Postfix 的容灾策略才会被触发。在 Postfix 源码 src/milter/milter8.c 中，错误被严格区分处理：

  • 通信错误（milter8_comm_error）：
    • 若 milter_default_action = accept：忽略该 Milter，继续后续检查；
    • 若为 reject：返回 550 5.5.0 Service unavailable；
    • 若为 tempfail：返回 451 4.7.1 Service unavailable - try again later；
    • 若为 quarantine：将应答设为 "H"，放入滞留队列。
  • 配置与格式错误（milter8_conf_error）：
    • 若 milter_default_action 为 accept，则放行；
    • 若为 quarantine，则挂起；
    • 否则统一返回 451 4.3.5 Server configuration problem - try again later。

注意其实现差异：当发生配置或未预期的语法错误时，即便将 milter_default_action 设为 reject，Postfix 依然会降级为 451 4.3.5 临时错误，而不是返回 550。这是 MTA 源码中内建的防灾设计，避免因配置手误导致邮件被永久反弹。

响应返回的时点取决于故障发生时的 Milter 事件阶段。如果连接握手阶段套接字就不通，MTA 可以在连接初始化或下一条支持回复的命令处直接拒绝；如果是正文扫描超时，则必须等到 EOM 之后才能向客户端返回状态码。

辅助依赖故障：DNS 与 Redis 边界

在反垃圾网关内部，核心引擎通常依赖域名系统（Domain Name System，DNS）服务（用于反向解析、DNS 黑名单（DNS-based Blacklist，DNSBL）与发件人策略框架（Sender Policy Framework，SPF）记录查询）和 Redis（用于灰名单、频控及贝叶斯统计）。这些依赖发生故障时，不应等同于整机扫描失败。

在 Rspamd 2.7 的 SPF 插件 src/plugins/lua/spf.lua 中，当底层异步 DNS 解析器遭遇网络临时错误时，会置位 flags.temp_fail 标志位。在函数 flag_to_symbol 中，该标志被转换为 local_config.symbols.dnsfail（即产出 R_SPF_DNSFAIL 符号）。该符号仅表明当前网络环境下 SPF 验证暂时未知，并不等同于认证失败（fail），更不能直接推导出内容具有恶意。工程团队需要按自身定位显式编排策略：若系统属于严格防钓鱼的特权入口，可配置在遇到关键认证 DNSFAIL 时于 EOM 统一返回 451 要求延后重投；若面向公网一般收件，DNS 暂时解析失败可仅导致对应打分项缺失，引擎依然可以根据其他符号完成综合评分。这需要显式配置，引擎版本不会自动做出主观假设。

对于 Redis 依赖，在 Rspamd 2.7 官方灰名单插件 src/plugins/lua/greylist.lua 的查询回调 redis_get_cb 中，当 Redis 读取发生错误时，此读取回调只记录日志并返回，不直接设置预判定动作（pre-result）。但后续动作还受后过滤（postfilter）阶段及其他策略影响，不能据此保证整机最终必定放行（250）。

而在写入阶段，查看 src/plugins/lua/greylist.lua 中的 greylist_set：当满足灰名单处理条件时，代码先调用 greylist_message，通过 task:set_pre_result 设置了 soft reject（对应 451）。随后异步向 Redis 发起 SETEX 命令记录初见时间戳。如果此时 Redis 发生连接失败或写入错误，redis_set_cb 仅打印错误日志，而之前设置的 soft reject 判定并不会被撤销。其结果是：MTA 确实向发送方返回了 451 要求重试，但由于 Redis 未能成功记录初见时间，当远端合法邮件服务器后续发起重试时，网关读取到的依然是空记录，重复暂缓可能持续发生。

因此，不能笼统认为 Redis 故障必然导致全放行或全拒绝，必须根据具体功能插件的异常捕获与状态清理逻辑分别评估。

网关决策顺序与输入契约设计

在自研邮件过滤网关或编排控制层时，动作选择应当遵循清晰的工程决策顺序，而不是将所有异常粗暴归为全局开关：

  1. 第一步：明确当前责任阶段与可回复事件。先确定当前可回复的 SMTP 事件，再按前述 Milter 故障策略决定继续、暂缓或拒绝；本篇追踪的 Rspamd 正文扫描结果通常在 EOM 收到终结符后应用。若缺失关键依赖，应等到对应事件触发时统一返回状态码。
  2. 第二步：标明必需依赖状态与缺失信号。根据会话上下文中标记的外部网络与存储状态，区分“认证条件暂时未知”与“明确判定为垃圾”。若缺失关键依赖，标记缺失信号集（如 R_SPF_DNSFAIL），交由策略层裁决。
  3. 第三步：显式权衡并选择执行动作。在系统投递延迟、误杀漏杀成本、本地滞留队列（Hold）容量与报警预算之间进行权衡。所谓的“故障放行（fail-open）”通常指在缺失非核心检查时继续处理并入队；而“故障关闭（fail-closed）”通常指返回 451 暂缓投递或受控导入隔离区，绝不等同于对所有错误一律回复 550 永久拒绝。

对于自建系统，运维与架构团队需要对网关配置、超时预算、本地队列容量及灾后恢复负责；对于自研策略引擎，判定模块之间需要传递版本化的输入契约，且不应将易被伪造或缺失的 Message-ID 作为唯一主键。推荐的契约字段示意如下：

{
  "policy_version": "2022-01-05.v1",
  "correlation_id": "c1f7b9e0-8b3d-4c7b-a1e2-9d8f6e7b4a11",
  "stage": "EOM",
  "queue_id": "4M9JqB0yHzz9KBp",
  "client_ip": "198.51.100.24",
  "envelope_from": "sender@example.net",
  "envelope_rcpt": ["recipient@example.com"],
  "dependency_status": {
    "dns_spf": "temporary_error",
    "redis_greylist": "timeout"
  },
  "verdict": {
    "score": 6.8,
    "missing_signals": ["R_SPF_DNSFAIL"],
    "action": "soft_reject",
    "smtp_reply": "451 4.7.1 Temporary system error, please retry later"
  }
}

其中 queue_id 仅在本地已预分配队列文件时记录（未分配时可置空或省略），action 为自研策略层定义的处理枚举，为审计日志与下游流转提供统一追踪依据。关于隔离区消息引用存储、人工释放流与申诉机制，属于受控保管后的独立管理面，留待后续专门展开。

队列后扫描与重注入防环责任

在大吞吐量邮件服务中，为了防止正文扫描拖垮公网 SMTP 连接池，架构常采用队列后（Post-Queue）扫描方案：MTA 先以 250 OK 将邮件完整接收进本地队列，随后由内部调度器将邮件提取并送交扫描引擎。

队列后扫描的状态责任

采用队列后架构时必须明确：服务端已经向前序客户端发送了 250 OK，此时整封邮件的投递责任已完全归属本地系统。

如果后置扫描器返回判定：

  • 若判定为临时失败（4xx）：本地调度系统必须将邮件保留在本地队列中，并在后续按退避策略重新送交扫描；
  • 若判定为永久失败（5xx）：由于已不可能在原会话中拒绝发送方，若直接向信封发件人发送退信，在垃圾邮件场景下存在严重的回散风险。对于常规合法邮件，系统仍应按标准生成投递状态通知（若反向路径为空则不生成）；而对于高置信垃圾邮件，仅在符合 RFC 5321 第 6.2 节的严重滥用条件下，才由系统进行静默丢弃。对于因扫描故障或未完成扫描的信件，绝不能作为恶意邮件静默丢弃，必须安全保留在受控队列或隔离库中等待恢复。

重注入防环机制设计

后置扫描完成后，合规邮件通常需要被重注入（Re-injection）回 MTA 继续执行投递。为了防止邮件在 MTA 与扫描器之间产生无限循环，需要设计明确的防环边界：

  1. 专用的受信重注入入口：在 MTA 上配置独立的监听端口或 Unix 域套接字，限制仅允许本地扫描器访问，并显式跳过已经执行过的那一段过滤链。
  2. 信任边界与内部标记：重注入通道可以依赖内部特权标记或特定监听实例，但公网入口必须强制剥除任何外部传入的同名特权头字段，绝不能直接信任公网邮件自带的跳过标记。
  3. 投递完成的边界确认：重注入到本地 MTA 并获得 250 OK，仅代表信件重新进入了本地传输队列，不等于最终邮箱存储投递已经完成。下游 LMTP 投递或本地写入仍可能遭遇磁盘配额或用户权限故障，这些属于投递后期的独立状态。

未运行的故障验证方案

为了在工程落地前验证网关在面对底层依赖失效时的协议表现，可以设计一套隔离测试方案。本方案为教学与架构推导设计，未在真实环境中运行邮件服务。

1. 测试前提与基准拓扑

  • MTA（如 Postfix）配置 milter_default_action = accept，关闭 soft_bounce，确保 5xx 状态码不被强制转为 4xx；设置有界的 Milter 通信超时预算；
  • 使用独立的 Rspamd Proxy 与独立的后端扫描工作进程（避免单进程 self_scan 模式），且后端全部尝试、重试与处理开销的总预算应小于 MTA 的 EOM 等待预算并留余量；本方案需确认先收到有效 TEMPFAIL，否则可能转为通道超时分支；
  • 每次测试使用一封合成纯文本数据流，信封设定为 MAIL FROM:<probe@invalid.test>，收件人为 RCPT TO:<user@invalid.test>，注入内部跟踪字段 case_id: "TEST-20220105-FAULT-001"；故障可在连接或扫描阶段注入，并记录 EOM 最终响应，测试时所有前置传输检查均通过。

2. 四组计划测试子步骤与预期断言

子步骤 A：计划阻断 Milter 底层套接字（通道级通信错误）

  • 操作方式：停止 Milter 监听进程，或阻断套接字（TCP 配置本地防火墙拦截，Unix 域套接字撤销访问权限）。
  • 预期行为：Postfix 触发 milter8_comm_error。由于配置了 milter_default_action = accept，Postfix 记录通信错误警告日志，跳过该 Milter 继续后续检查。在其他检查均通过的前提下，MTA 在 EOM 响应 250 2.0.0 Ok。
  • 断言：邮件被 MTA 本地进件队列接收，投递责任转移至本地。

子步骤 B：计划阻断独立扫描后端（代理层 TEMPFAIL 穿透）

  • 操作方式：保持 Rspamd Proxy 正常监听，但停止所有后端扫描进程并禁止重连。
  • 预期行为：MTA 正常与 Rspamd Proxy 建立 Milter 通信。在正文传输完毕后，Proxy 向后端转发扫描请求，后端超时耗尽后触发 proxy_client_write_error。由于 Milter 连接正常，Proxy 向 MTA 发送 RSPAMD_MILTER_TEMPFAIL。Postfix 接收到显式 Milter 指令，向客户端返回 451 4.7.1 Service unavailable - try again later。
  • 断言：Postfix 的 milter_default_action = accept 无法覆盖该错误，因为 Milter 连接本身未出错。投递责任留在发送方队列中。

子步骤 C：计划阻断 Redis 灰名单写入（状态悬挂风险）

  • 操作方式：在测试桩中强制设置当前邮件为灰名单候选，构造 Redis 读取返回无记录，同时阻断对 Redis 的写入请求（模拟写入超时或失败）。
  • 预期行为：Rspamd 灰名单模块在 greylist_set 中先调用 greylist_message 注入 soft reject，随后发起的 SETEX 失败并在回调中记录错误。由于代码未撤销预判定，MTA 收到软拒绝并返回 451；同时由于初见时间未落盘，后续客户端重试时仍读取不到记录，重复暂缓可能持续发生。
  • 断言：系统需通过业务监控观察该写入失败，并按预设策略评估容灾处置（如超时降级放行或报警恢复），验证期间不应假设系统会自动撤销该 soft reject。

子步骤 D：计划模拟外部 DNS 临时失败（认证未知对照）

  • 操作方式：保持网络连通，但配置本地 DNS 测试桩对 SPF 查询返回 SERVFAIL 或网络超时。
  • 预期行为：Rspamd 的 SPF 模块捕获底层 flags.temp_fail 标志，产出 R_SPF_DNSFAIL 符号。若系统显式配置了“关键认证暂时失败则 EOM 拦截”的自定义策略，MTA 返回 451；若未配置该策略，网关将根据其余规则进行综合评分。
  • 断言：待核验 DNSFAIL 原生仅作为暂时未知信号，是否触发暂缓取决于显式策略编排。

恢复相关依赖后，重新测试应确认通信恢复正常、邮件正常入队，且未产生投递环路。
