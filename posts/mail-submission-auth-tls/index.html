邮件提交、SMTP AUTH 与 TLS

2021年8月15日
|

在互联网邮件体系中，用户将邮件交给自己的提交服务器，与服务器在广域网中向下一站中继邮件，使用的是极为相似的扩展简单邮件传输协议（Extended Simple Mail Transfer Protocol，ESMTP）命令，但两者承担着截然不同的协议责任。

早期的简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）并未在传输通道上严格区分这两类行为，公网服务器普遍开放中转，会话默认不要求身份认证（authentication）。随着垃圾邮件泛滥与网络边界防护需求提升，RFC 6409 规范了邮件提交（message submission）与邮件中继（message relay）的职责划分；配合 RFC 4954 定义的 SMTP 认证扩展（SMTP Service Extension for Authentication，SMTP AUTH）与 RFC 8314 规定的传输层安全（Transport Layer Security，TLS）机制，现代邮件系统在首跳注入连接上建立了明确的身份核验、授权（authorization）与链路加密要求。

邮件提交（Submission）与邮件中继（Relay）的区别

虽然邮件提交与邮件中继均采用基于 RFC 5321 的命令交互，但在网络拓扑、主体信任假设与责任边界上具有清晰的分工：

  • 邮件提交（Message Submission）：发生在邮件用户代理（Message User Agent，MUA）与其归属的邮件提交代理（Message Submission Agent，MSA）之间。这是邮件注入传输管网的第一跳。此时客户端与服务端属于同一管理域或具备预置凭据，服务端负责确认发信者的身份合法性，并按规范检查或补齐邮件头部。
  • 邮件中继（Message Relay）：发生在邮件传输代理（Message Transfer Agent，MTA）之间。中继节点负责跨网络路由与转交已有报文，服务器之间无法预置全局用户凭据，因而公共中继通常不进行基于单一用户账号的身份认证；除按规定追加 Received 等追踪字段外，中继节点不应擅自改动正文与已有报文头。

为了便于网络边界实施访问控制，RFC 6409 第 3.1 节将 TCP 端口 587 保留为邮件提交协议的专用端口，而 TCP 端口 25 继续用于 MTA 之间的通用邮件中继。需要说明的是，协议并非以物理端口作为区分角色的绝对标准，站点在特定策略下仍可配置指定主机在端口 25 上监听并提供提交服务；但对于公共互联网接入，端口分离有助于网络服务商阻断失陷终端对公网端口 25 的直接滥用。

邮件提交代理（MSA）的职责与报文修整

依据 RFC 6409 第 4 节至第 8 节，MSA 在接收客户端提交时承担着合规检查与报文修整的职责。

1. 提交检查与拒绝条件

  • 身份认证要求：RFC 6409 第 4.3 节规定，若会话尚未通过 SMTP AUTH 认证，MSA 默认必须对 MAIL 命令返回错误代码 530（表示需要认证），除非服务端已通过独立的途径建立了认证或授权（例如位于受保护的专用子网中，或通过其他底层凭据确立了权限）。
  • 完全限定域名（Fully Qualified Domain Name，FQDN）：RFC 6409 第 4.2 节要求 MSA 必须确保 SMTP 信封中的所有域名均为可在域名系统（Domain Name System，DNS）中全局解析的 FQDN。此外，若 MSA 检查或修改了正文内容（除添加追踪头外），也必须确保地址头字段中的域名同样为完全限定形式。若报文使用了单层本地名（如 sales），本地约定可按策略展开（如补全为 sales.example.net），但不完整的层级名称（如 squeaky.sales）则建议直接拒绝。
  • 反向路径与空路径处理：依据 RFC 6409 第 3.2 节，如果 MSA 无法通过有效 MAIL FROM、有效源 IP 地址或已认证身份确定发信者的有效返回路径，通常应当（SHOULD）立即以 550 拒绝 MAIL 命令。但必须注意，用于递送状态通知等用途的空反向路径（即 MAIL FROM:<>）是合法规范格式，服务单凭反向路径为空本身绝对不得（MUST NOT）直接拒绝该邮件。
  • 通用拒绝代码：若无更具体的错误代码，包含语法缺陷或违规参数的 MAIL、RCPT 或 DATA 命令统一使用错误代码 554 拒绝（第 4.1 节）。

2. 报文修改与补全（Message Modifications）

与中间 MTA 严禁修改邮件内容的规则不同，RFC 6409 第 8 节允许并在特定缺陷下推荐 MSA 对首跳提交的报文进行修整：

  • 补全或修正 Date：若提交的报文缺失 Date 字段或语法非法，MSA 可以为其添加合规的当前日期时间（第 8.2 节）。
  • 补全 Message-ID：针对未由客户端生成唯一标识的报文，MSA 应当（SHOULD）为其生成并添加符合规范的 Message-ID 头字段（第 8.3 节）。
  • 核验或添加 Sender：当认证提交者的身份明确，但邮件头中的 From 字段与其不符且未声明实际代理者时，MSA 可以依据策略添加合规的 Sender 字段（第 8.1 节）。

注意：RFC 6409 第 8 节明确指出，提交阶段对报文头或正文的任何修整，均可能导致客户端先前附带的数字签名（digital signature，如采用 Pretty Good Privacy，PGP 或 Secure/Multipurpose Internet Mail Extensions，S/MIME 方案）校验失败。因此 MSA 的修整行为应当严格限于具备明确解决方案的已知缺陷。

SMTP AUTH 扩展与 SASL 机制

为在应用层验证用户发信凭据，RFC 4954 定义了 SMTP 的认证服务扩展。该扩展引入了简单认证与安全层（Simple Authentication and Security Layer，SASL）框架。

1. EHLO 广播与能力发现

支持认证的服务端在响应客户端的 EHLO 命令时，会广播 AUTH 关键字及当前可用 SASL 机制列表（RFC 4954 第 3 节）。依据 RFC 4954 第 6 节安全原则，服务端在尚未建立充分强度的加密层时，通常不应广播未受保护的明文机制。在成功执行 STARTTLS 升级连接后，服务端广播的可用机制列表可以动态更新。

下面是一段简化的协议交互示意（C 代表客户端，S 代表服务端）：

S: 220 smtp.example.com ESMTP
C: EHLO client.example.com
S: 250-smtp.example.com Hello client.example.com
S: 250-AUTH DIGEST-MD5
S: 250 STARTTLS
C: STARTTLS
S: 220 Ready to start TLS
... 双方完成 TLS 握手，后续会话处于加密通道内 ...
C: EHLO client.example.com
S: 250-smtp.example.com Hello client.example.com
S: 250 AUTH PLAIN DIGEST-MD5

2. 认证交互时序与规则

客户端通过发送 AUTH 命令启动认证交互流程。RFC 4954 第 4 节规定了核心语法与状态机规则：

  1. 机制选择与初始响应：客户端在 AUTH 后面指定机制名称，并可在同一行附带可选的 Base64 编码初始响应（initial response），以节省一次网络往返： 
    C: AUTH PLAIN dGVzdAB0ZXN0ADEyMzQ=
    若客户端需要传递长度为 0 的初始响应，协议规定必须发送单个等号字符（=），用于明确表示“初始响应存在但内容为空”。
  2. 多轮质询与应答：若所选机制需要多步握手，服务端返回包含 Base64 编码质询数据的 334 中间状态行；若质询无需携带数据，服务端发送后面带有一个空格的 334 响应行。客户端随后回复其 Base64 编码数据。
  3. 取消交换：在认证交互阶段，客户端若想主动放弃，可发送仅包含单个星号的行（*），服务端接收到后必须以 501 响应终止认证。
  4. 状态机约束：在同一连接会话中，一旦某个 AUTH 命令成功通过，服务端必须拒绝任何后续的 AUTH 调用（返回 503 代码）。在已经开始的邮件事务（如已发出 MAIL FROM）过程中，同样不允许穿插调用 AUTH。

3. SASL 机制的特性

对照 RFC 4954 与 RFC 8314 的标准条款，不同 SASL 机制在协议要求上的核心特征如下：

SASL 机制名称凭据传输形态协议规范要求与安全边界
PLAIN明文（Base64 仅为字符编码格式，不具备加密功能）RFC 4954 第 4 节要求服务端必须实现一种禁止无保护明文密码的配置，且建议站点不使用允许明文裸传的配置。RFC 4954 第 4 节与第 14 节强制要求客户端与服务端必须实现运行于 TLS 之上的 PLAIN。
CRAM-MD5质询-应答散列（Challenge-Response）机制本身不提供服务端身份认证能力，RFC 4954 第 4 节指出新实现可为兼容既有软件而提供，但需注意其缺乏服务端认证的缺陷。
EXTERNAL应用层不交换口令，由下层安全信道提供主体身份在隐式 TLS 提交服务中，服务端若接受客户端 TLS 证书作为充分授权依据，RFC 8314 第 4.2 节要求其必须启用 SASL EXTERNAL 机制。

4. MAIL FROM 中的 AUTH 参数

RFC 4954 第 5 节为 MAIL FROM 命令引入了可选的 AUTH 参数，用于在受信任的中继协作节点之间，传递最初向系统提交该邮件的发信人邮箱（authorized mailbox）：

C: MAIL FROM:<alice@example.com> AUTH=alice@example.com
S: 250 OK

若服务端无法充分信任客户端身份，或客户端未经过认证，服务端在本地必须按视同收到 AUTH=<> 的规则处理（表明原始提交者未知）；当该服务端需要将该邮件转发给另一个本服务器已使用 AUTH 认证的下游服务器时，必须在转发的 MAIL FROM 中显式携带 AUTH=<>。

传输层保护：隐式 TLS 与 STARTTLS

由于 SMTP AUTH 的口令机制（如 PLAIN）在应用层直接传输凭据，若无底层加密，网络窃听与中间人攻击（Man-in-the-Middle，MITM）将导致凭据泄露。因此，传输层安全至关重要。

需要明确的是，此处讨论的 TLS 加密仅对客户端到当前提交服务器之间的首跳传输连接提供机密性与完整性保护。邮件在提交后依然会在互联网 MTA 之间逐跳流转，首跳 TLS 并不自动延伸至全路径中继，也不能替代对邮件内容自身的端到端数字加密。

在演进过程中，邮件生态主要存在两种 TLS 连接协商模式：显式升级（STARTTLS）与隐式加密（Implicit TLS）。RFC 8314 对邮件接入层的 TLS 实践作出了关键规范。

1. STARTTLS 模式与明文协商阶段的风险

在端口 587 上，客户端通常首先与服务端建立明文 TCP 连接，并在接收到带有 STARTTLS 的能力广播后，显式发送 STARTTLS 命令升级到加密信道。

这种机制在安全性上的主要脆弱点发生在 TLS 建立之前的明文阶段：

  • 握手升级前的 EHLO 命令与能力广播均以明文传输。
  • 处于通信链路上的主动中间人攻击者可以剥离服务端的 STARTTLS 响应（例如抹去该行广播，或篡改应答）。如果客户端未配置“必须使用 TLS”的强制策略，可能会被诱导退回明文连接，进而导致后续 AUTH 凭据以明文暴露。
  • 不过，RFC 8314 第 3.3 节同时指出：只要实现正确，且客户端与服务端均强制要求在提交前必须成功协商 TLS，那么端口 587 上的 STARTTLS 与端口 465 上的隐式 TLS 在安全属性上并没有显著区别。因为在严格策略下，一旦中间人剥离了 STARTTLS 广播，客户端将直接中止连接，绝不会继续发送身份凭据。

2. 隐式 TLS（Implicit TLS）的机制与端口 465

为了从根本上消除连接启动阶段的明文探测与剥离机会，RFC 8314 第 3 节推荐优先采用隐式 TLS：

  • 客户端在建立 TCP 连接后，不发送任何明文 SMTP 握手命令，而是立即启动 TLS 握手（发送 ClientHello）。
  • 双方仅在 TLS 握手顺利完成、服务端证书有效性与目标主机身份校验通过后，才开始在加密通道内交换 SMTP 应用层报文（包括首个 220 欢迎语）。
  • 在端口分配上，RFC 8314 第 3.3 节与第 7.3 节正式将 TCP 端口 465 重新确立为标准隐式 TLS 提交端口，服务名注册为 submissions。同时，为兼顾既有存量客户端，规范建议在过渡期内服务端应同时支持端口 465 隐式 TLS 与端口 587 STARTTLS。
隐式 TLS（端口 465）握手时序示意：
客户端                                服务端
  |                                     |
  |------------ TCP SYN --------------->|
  |<----------- TCP SYN+ACK ------------|
  |------------ TCP ACK --------------->|
  |                                     |
  |-- TLS ClientHello (开始TLS握手) --->|
  |<- TLS ServerHello + 证书等 ---------|
  |-- 密钥协商与 Finished ------------->|
  |<- Finished (握手完成) --------------|
  |                                     |
  |<~~ 220 smtp.example.com (加密应用数据) ~|
  |~~~ EHLO client.example.com (加密) ~~>|
  |<~~ 250 AUTH PLAIN (加密) ~~~~~~~~~~~|
  |                                     |

显式升级（STARTTLS）587（submission）先明文交互，后发送命令升级依赖客户端配置强制 TLS 策略以防剥离过渡期内建议继续支持兼容（§3.3）
明文提交（无 TLS）25 / 587（用于提交场景）全程明文传输凭据与正文极易遭受网络监听与篡改建议尽快废弃用于提交服务的明文支持（§4.1）

3. RFC 8314 核心安全实践

  • 协议版本底线：邮件提交服务端与客户端必须（MUST）支持 TLS 1.2 或更高版本；服务提供商应尽快停止对历史 SSL 2.0、SSL 3.0 以及 TLS 1.0 的支持（第 4 节与第 4.1 节）。
  • 证书校验与交互提示：RFC 8314 第 5.3 节要求客户端必须完整校验服务端证书的有效性及主机名身份。依据第 5.2 节，对于配置了最低机密性要求的账号，当证书校验不通过时，客户端软件通常不应向用户提供容易被习惯性忽略的“一键点击跳过”警告界面，以防用户无意中暴露凭据。
  • Received 追踪头记录加密套件：RFC 8314 第 4.3 节定义了新的可选追踪字段。提交服务器在接收到经 TLS 保护的邮件后生成 Received 头字段时，建议（SHOULD）记录协商的密码套件名称（如 tls TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256），为各受信节点的运维排错与日志溯源提供参考（该字段本身并不对全链路不可篡改性提供密码学保证）。

典型状态码与授权故障边界

在实际配置与调试邮件提交服务时，遵循规范的状态码有助于准确定位认证与会话状态错误：

1. 常见状态代码解析

  • 530 5.7.0 Authentication required：客户端未认证即发起 MAIL FROM，被 MSA 的默认安全规则拒绝（RFC 6409 第 4.3 节）。
  • 503 Bad sequence of commands：客户端在已成功完成认证的会话中再次尝试执行 AUTH，或在正在进行的邮件事务内部调用 AUTH，违反了 RFC 4954 第 4 节的命令时序约束。
  • 535 5.7.8 Authentication credentials invalid：客户端提供的身份凭据无效，或提供的凭据不足以通过服务端的身份核验（RFC 4954 第 6 节）。若客户端请求了服务端不支持或受策略限制未启用的机制，服务端则会以 504（如 5.5.4）代码拒绝。
  • 500 5.5.6 Authentication Exchange line is too long：客户端发送的 Base64 编码数据超出了服务端分配的认证行读取缓冲区。RFC 4954 第 4 节指出，实现必须有能力处理其所支持机制可能产生的最大编码长度，文档成文时通常认为 12288 字节的缓冲限额足以应对当时已部署的机制。

2. 认证身份与发信授权检查

身份认证（Authentication）确认的是连接者的账号主体身份；而授权（Authorization）则判定该账号是否拥有使用特定地址发信的权限。 依据 RFC 6409 第 6.1 节，MSA 在收到 MAIL FROM 时，有权（MAY）检查该地址是否与当前会话认证身份相匹配。如果某个已认证账号（例如 bob@example.com）未获授权使用特定的发信地址（例如试图声明 MAIL FROM:<ceo@example.com>），MSA 可按本站策略返回 550 5.7.1 拒绝该事务。这样可以拒绝本事务中未经授权使用该信封发件地址的请求；至于可见 From 等头部字段是否合规，还需由 MSA 的报文数据检查逻辑另行校验（RFC 6409 §6.3）。
