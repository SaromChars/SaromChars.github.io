IMAP UID与多端增量同步

2021年11月28日
|

在多设备访问同一邮箱的场景中，常见故障包括：用户在手机上已读一封邮件，桌面客户端重连后仍显示未读；或者某端删除了中间某封邮件并清空垃圾箱，另一端断线重连后却残留无法打开的“幽灵邮件”。若邮箱客户端仅按“拉取大于本地最大 ID 的新邮件”这一常规接口思维开发，便无法感知远端历史邮件的标志改变与物理删除。

互联网消息访问协议第 4 版修订版 1（Internet Message Access Protocol - Version 4rev1，IMAP4rev1，RFC 3501）设计了“消息序号（message sequence number）”与“唯一标识符（unique identifier，UID）”双重定位方式。后续的条件存储扩展（Conditional Store，CONDSTORE，RFC 7162）与快速重同步扩展（Quick Resynchronization，QRESYNC，RFC 7162）进一步补足了基于变更序列号（modification sequence，MODSEQ）的增量拉取机制。本文基于 RFC 规范与开源服务端 Dovecot 2.3.16 源码（Dovecot 2.3.16 源码与公告），梳理邮箱状态同步的协议规则、服务端内部链路及工程自研契约边界。

一、消息标识模型：序号、UID 与 UIDVALIDITY

IMAP 协议在邮箱（mailbox）内部区分了瞬时序号与持久标识符两套标尺。

1. 动态变化的消息序号

消息序号是当前邮箱中从 1 递增至当前消息总数（EXISTS）的连续整数。依据 RFC 3501 第 2.3.1.2 节与第 7.4.1 节，消息序号由服务端动态维护，不具备长期稳定身份。一旦邮箱内某封邮件被永久物理移除（EXPUNGE），排在其后的所有邮件序号都会立刻向前递减 1。因此，序号仅适合单次连接中对当前活跃消息集做临时寻址，不可跨连接持久化至客户端本地数据库。

2. 递增非连续的 UID

依据 RFC 3501 第 2.3.1.1 节，UID 是一个 32 位无符号整数（取值范围为 1 至 4,294,967,295）。其分配规则具备以下约束：

  • 单调严格递增：新分配给追加邮件的 UID 必须严格大于该邮箱历史已分配的最大 UID；
  • 允许非连续：因邮件投递失败、跨文件夹移动或底层存储策略，UID 序列允许存在空洞，协议不要求连续；
  • 邮件身份稳定：在同一个有效邮箱生命周期内，邮件一旦分配 UID，其 UID 保持不变；邮件删除后，其 UID 永远作废，不会重新分配给新邮件。

3. 邮箱代际标识：UIDVALIDITY

若仅依赖 UID，一旦服务端发生邮箱重建、存储格式迁移或数据从冷备恢复，重新生成的 UID 序列极易与客户端旧本地缓存产生严重重叠。

为此，RFC 3501 引入了 32 位无符号整数形式的邮箱代际有效性标识符（unique identifier validity，UIDVALIDITY）。客户端所缓存的邮件身份空间由三元组界定：账户/授权邮箱 + UIDVALIDITY + UID。

  • UIDVALIDITY 不变：表明服务端的 UID 身份空间依然有效，旧 UID 的对应身份可沿用，但并不代表邮箱内的邮件成员集合与标志属性未发生改变；
  • UIDVALIDITY 改变：表明服务端的 UID 序列已发生代际重置，客户端必须废弃本地记录的所有 UID 映射与同步水位标记。但如果本地已完整缓存了邮件正文，可保留独立的正文缓存文件待与新代际下的新 UID 重新核对，不承诺任何自动绑定，也不必直接盲目删除全部正文副本。

另外，服务端在 SELECT 响应中通报的 UIDNEXT 仅为服务端下一次分配新 UID 的预测值，不是当前邮件数量，也不能充当标志变更扫描的增量游标。

二、多端并发与重连状态转移教学示意

为说明对象身份、成员集合与可变标志在并发时的分离，设定如下教学示意状态转移场景。

初始时邮箱有 3 封邮件，服务端分配状态如下表所示：

消息序号UID 与初始状态
1UID 101, 标志 ()
2UID 104, 标志 (\Seen)
3UID 109, 标志 ()

假定发生如下时序演进：

  1. 客户端 A（移动端）修改标志：发出 UID STORE 101 +FLAGS (\Seen)，服务端将 UID 101 标记为已读并更新属性。
  2. 客户端 B（桌面端）并发删除：发出 UID STORE 104 +FLAGS (\Deleted) 并发起 EXPUNGE。服务端物理移除 UID 104。
  3. 服务端序号动态重排：原 UID 101 保留为 Seq 1；原 Seq 3（UID 109）前移变为 Seq 2；消息总数降为 2。
  4. 新邮件到达：服务端新投递一封邮件，分配 UID 为 112，成为 Seq 3。
  5. 客户端 A 断线重连：客户端 A 在断线后重新建立连接，此时本地记录的最大已知 UID 为 109。

在此场景下，客户端若处理不严谨将产生如下缺陷：

  • 单纯 UID 增量漏删：若客户端仅发出 UID FETCH 110:* (UID FLAGS)，虽然能抓取到新邮件 UID 112，但无法得知 UID 104 已在远端被移除，本地仍保留 UID 104，成为幽灵邮件；
  • 反向范围语义：若此时远端恰好无任何新邮件到达（最大 UID 仍为 109），客户端发出 UID FETCH 110:* (UID FLAGS) 时，根据 RFC 3501 第 6.4.8 节，星号 * 解析为邮箱当前最大 UID（109），该范围变为逆序范围 110:109，服务端仍会返回 UID 109 的信息。客户端必须对返回的 UID 做实际过滤判断，避免把旧数据当成新邮件；
  • 序号与 UID 混淆：若客户端使用非 UID 指令更新 Seq 2，将直接误操作到 UID 109 上。即便执行 UID FETCH，RFC 3501 规定的返回格式外层依然是当前序号（例如 * 2 FETCH (UID 109 ...)），客户端解析器必须提取内层的 UID 键值，绝不能将外层前导数字直接赋值给本地 UID。

三、Dovecot 2.3.16 增量同步链路分析

开源 IMAP 服务端 Dovecot 2.3.16 将协议处理、索引缓存与文件存储清晰解耦。其增量同步核心实现集中于 src/imap 与 src/lib-storage/index 模块。

1. 邮箱状态装载与重同步入口：select_open

在 cmd-select.c：select_open 中，函数 select_open 负责装载邮箱视图：

  • 首先调用 mailbox_open 打开目标邮箱，并通过 mailbox_sync(..., MAILBOX_SYNC_FLAG_FULL_READ) 获取最新索引视图；
  • 调用 mailbox_get_open_status 获取当前邮箱的统计信息，向客户端推送 EXISTS、RECENT、UIDVALIDITY 和 UIDNEXT；
  • 在已启用相应变更跟踪且支持持久 MODSEQ 时，输出 HIGHESTMODSEQ；nonpermanent_modseqs 为真时通报 * OK [NOMODSEQ]；
  • 当客户端发送带有 QRESYNC 参数的请求时，代码检查客户端传入的代际值：若客户端提供的代际与当前一致、非零且服务端支持持久 MODSEQ，则调用 select_qresync 执行快速重同步；否则退出该快速分支（ret = 1），交由后续常规流程响应，由客户端主动发起常规对账。

2. 索引层变更产出顺序：index_mailbox_sync_next

在 index-sync.c：index_mailbox_sync_next 中，函数 index_mailbox_sync_next 定义了变更记录的产出顺序：

  1. 优先输出标志变更：优先遍历 ctx->flag_updates，产出 MAILBOX_SYNC_TYPE_FLAGS 变更记录；
  2. 输出隐藏版本变更：对于启用了 CONDSTORE 的邮箱，输出隐藏标志更新的 MAILBOX_SYNC_TYPE_MODSEQ；
  3. 最后输出删除事件：调用 index_mailbox_sync_next_expunge 产出 MAILBOX_SYNC_TYPE_EXPUNGE。

在遍历删除记录时，函数倒序访问 ctx->expunges 数组（从大序号向小序号迭代输出）。这种从高到低的倒序发射策略，保证在向未启用 QRESYNC 的客户端发送单条序号删除时，较小序号不会因前置删除发生偏移，确保序号消减过程自洽。

3. 同步排空循环、背压与清理：imap_sync_more

在 imap-sync.c：imap_sync_more 中，函数 imap_sync_more 循环消费索引记录并向客户端发送无标签响应：

  • 遇到标志变更调用 imap_sync_send_flags；
  • 遇到删除事件调用 imap_sync_send_expunges 并相应递减内部 ctx->messages_count；
  • 当输出缓冲区达到写上限时，函数返回 0（buffer full），保留当前 ctx->seq 序号位置以便下次调度重入；
  • 循环结束后，若客户端启用了 QRESYNC，调用 imap_sync_vanished 将序号范围转为 UID 范围，直接向客户端发射实时的 * VANISHED <UID-Set> 响应（区别于 SELECT 重同步时的历史 EARLIER 形式）；
  • 最终调用 imap_sync_finish，释放内部事务和读取邮件对象，调用底层 mailbox_sync_deinit 解构同步上下文。代码中明确规定：即使用户网络连接已中断，服务端仍必须执行内部同步收尾，并在检测到底层视图不一致或 UIDVALIDITY 冲突时主动断开连接。服务端完成内部同步仅表明服务端内部索引视图推进完成，并不保证网络数据已被客户端接收。

4. 条件更新防护与部分失败：cmd_store

在 cmd-store.c：cmd_store 中，支持 CONDSTORE 扩展的命令处理逻辑如下：

  • 当客户端指定 UNCHANGEDSINCE <modseq> 条件时，服务端遍历待更新消息，比较 mail_get_modseq(mail) 与传入的 ctx.max_modseq；
  • 若某封邮件的当前 MODSEQ 大于客户端指定阈值（说明期间被其他端修改过），Dovecot 跳过该邮件的标志更新，并将其收集入 modified_set；
  • 当存在冲突时，命令最终返回携带失败集合的响应：OK [MODIFIED <set>] Conditional store failed。注意：此处的返回状态仍为 OK，表示命令本身执行完毕但携带了部分条件失败的消息集合（对于 UID STORE，集合为 UID；对于普通 STORE，集合为序号）。客户端不可将全量请求盲目重新覆盖，而应仅对受冲突影响的邮件重新评估状态。

四、增量同步扩展：CONDSTORE 与 QRESYNC

为了规避全量轮询，IETF 在 RFC 7162 中规范了 CONDSTORE 与 QRESYNC 扩展。

1. CONDSTORE 的 MODSEQ 机制

CONDSTORE 为邮箱引入了 64 位单调递增版本号：

  • 服务端为每个邮箱单独维护一个 HIGHESTMODSEQ（单邮箱作用域，不代表全局跨邮箱时钟）；
  • 被该机制跟踪的标志或关键字（如 \Seen、\Flagged 或自定义关键字）发生改变，该邮件的 MODSEQ 便更新为递增的新版本号；
  • 客户端在启用后，只需在 FETCH 时追加 (CHANGEDSINCE <last_modseq>) 调节子，服务端便仅返回在此版本之后变动过的邮件，大幅降低了常规标志轮询的开销。

2. QRESYNC 快速重连与回退

QRESYNC 在 CONDSTORE 基础上进一步解决了离线删除同步的问题。使用流程如下：

  1. 握手与能力协商：客户端每次建立新连接并认证后，先查询 CAPABILITY；只要服务端支持 QRESYNC，客户端发出 ENABLE QRESYNC 并在收到服务端的 * ENABLED QRESYNC 响应后即可（QRESYNC 规范已蕴含 CONDSTORE 能力，无需重复协商）；
  2. 快速重同步：客户端发送 SELECT INBOX (QRESYNC (<uidvalidity> <last_modseq> [<known-uids>]))；
  3. 历史删除通报：服务端如果支持且代际匹配，会先输出形如 * VANISHED (EARLIER) <UID-Set> 的响应，告知客户端在离线期间已物理删除的 UID 集合。客户端收到 EARLIER 后仅需从本地缓存中剔除对应的 UID，绝不对当前已选定打开的新视图执行历史删除引起的序号递减；随后服务端推送发生标志变化的邮件；
  4. 回退与全量对账：QRESYNC 不提供跨请求的全局快照原子性承诺。若服务端返回 * OK [NOMODSEQ]（表明底层存储不支持持久 MODSEQ），快速重同步路径将不生效。此时客户端必须回退到全量对账：先通过 UID SEARCH ALL 获取服务端全部 UID，在本地做集合差运算以定位删除邮件；对保留下来的全部 UID，仍必须通过 UID FETCH 1:* (FLAGS) 重新拉取最新的标志状态，仅凭 UID 集合无法获知标志变动。若服务端返回的 UIDVALIDITY 发生改变，则必须彻底废弃本地全部旧 UID 映射与同步水位，不可继续用旧 UID 集合与新服务端对账。

五、自研邮箱系统同步契约设计（工程推导）

在自研邮件存储系统、邮件网关或同步中间件时，可参考上述机制建立简洁严密的数据契约。

1. 存储层基础数据契约

在数据存储引擎中，邮件元数据与同步标记建议抽象为如下数据契约规则：

  • 完整复合主键：每条邮件索引记录必须以四元组 (account_id, mailbox_id, uid_validity, uid) 作为唯一主键，彻底消除多租户、多文件夹及代际重建时的主键碰撞；
  • 单邮箱版本号（modseq）：modseq 仅在单个 (account_id, mailbox_id) 以及同一 uid_validity 代际内单调递增，不承担跨文件夹或全局时钟职责，也不暗示跨代际延续；底层不支持时可设为可选字段；
  • 可变属性与删除墓碑：flags 记录已读、星标等可变位掩码；is_expunged 作为墓碑标记保留物理删除历史以支持增量删除同步；
  • 独立的新邮件发现机制：新邮件的发现仍必须依赖单调递增的 uid 扫描路径，不能假设 modseq 是覆盖所有写入事件的通用事件流；
  • 时间与排序边界：邮箱内 UID 的分配仅代表其入库登记顺序，绝不等于邮件头部的 Date，也不必然等同于接收时间 INTERNALDATE。在自研系统开发中，不能将 UID 递增误当成发信时间的绝对递增。

2. 客户端同步状态机与重试一致性

客户端维持增量同步的状态机时，应遵循以下规则：

  1. 代际校验优先：发起同步前先核对服务端的 UIDVALIDITY。若代际改变，清空本地 UID 映射与同步版本游标（保留可独立重新校验的正文缓存文件）；
  2. 完整批次事务推进：客户端拉取增量响应后，对本地数据库的更新（新增邮件、修改标志、清除已删除 UID）必须与更新本地检查点游标（checkpoint_modseq）置于同一本地存储事务中；
  3. 断线不推进游标：若拉取中断或响应不完整，绝不能提前推进 checkpoint_modseq。重连后以旧游标重试拉取；
  4. 同代际幂等应用：在相同代际内，客户端应用增量应满足幂等性：新增邮件按 UID 幂等写入，标志更新按高 MODSEQ 覆盖旧 MODSEQ，删除操作对不存在的 UID 静默忽略。

3. Webmail 业务 API 与分页边界

Webmail 与移动端现代应用常使用基于 HTTP 的 JSON 接口访问后端，需明确同步令牌（Sync Token）与分页游标（Paging Cursor）的职责划分：

  • 同步令牌（Sync Token）：绑定特定用户、特定邮箱、代际值与服务端单邮箱变更版本（如 (account_id, mailbox_id, uid_validity, modseq)）。仅用于前台轮询或长轮询探测增量变动，其生命周期覆盖整个文件夹。每次请求前必须校验用户对该邮箱的当前访问授权；一旦令牌因服务端维护或代际更新失效，必须要求客户端重新对账；
  • 分页游标（Paging Cursor）：用于列表渲染展示，游标必须严格绑定查询条件、排序规则、过滤项与当前代际。若按 UID 倒序展示，初次加载应固定当前最大 UID 作为上界锚点（例如 before_uid=10500&limit=50），或与前端约定明确的实时视图语义，避免依赖易受增删影响产生空洞或跳页的 offset；
  • 时间排序与过滤：若按接收时间排序，应以 (internal_date, uid) 联合锚定游标；若按邮件头部的发信时间排序，应以解析后的 (date, uid) 联合锚定，以 UID 作为确定性的 tie-breaker。对于条件过滤视图，服务端需与前端明确约定是基于固定查询快照分页，还是实时动态视图，避免滚动加载时邮件位移重叠。

六、验证方案与待执行步骤说明

待执行验证说明

以下为工程团队验证增量同步与重连逻辑的标准化测试步骤设计，未在当前环境作实测。

验证场景：并发标志修改、物理删除与重连对账

  1. 环境准备与基线获取：使用测试保留账号建立新连接并完成认证，发送 CAPABILITY 确认包含 QRESYNC；发送 ENABLE QRESYNC 确认收到 * ENABLED QRESYNC；发送 SELECT INBOX，记录服务端返回的 UIDVALIDITY 与 HIGHESTMODSEQ（设为 M1）。
  2. 模拟多端并发修改：
    • 客户端 1：发送 UID STORE <uid_a> +FLAGS (\Seen)；
    • 客户端 2：发送 UID STORE <uid_b> +FLAGS (\Deleted) 并执行 EXPUNGE，删除 <uid_b>。
  3. 正常重连与增量重同步验证：
    • 客户端 1 断开并建立全新连接，完成认证并重新发送 ENABLE QRESYNC 且确认收到 * ENABLED QRESYNC；
    • 发送 SELECT INBOX (QRESYNC (<uid_validity> M1))；
    • 预期判定：服务端应首先返回 * VANISHED (EARLIER) <uid_b>；随后返回 <uid_a> 的最新标志变更信息；服务端通报的当前 HIGHESTMODSEQ 大于 M1。客户端根据 EARLIER 仅剔除本地 <uid_b>，不对新打开视图递减序号。
  4. NOMODSEQ 降级分支验证：
    • 在不支持持久 MODSEQ 的文件夹或显式返回 * OK [NOMODSEQ] 的服务端上执行相同步骤；
    • 预期判定：服务端不输出 VANISHED 与增量 FETCH，客户端检测到状态后，应自动执行 UID SEARCH ALL，将全量 UID 列表与本地记录对比计算出已删除的 <uid_b> 并在本地剔除；同时执行 UID FETCH 1:* (FLAGS) 重新拉取存活邮件的最新标志，确保 <uid_a> 的 \Seen 状态成功更新。
  5. UIDVALIDITY 变更分支验证：
    • 模拟服务端重建邮箱（或由管理端调整代际标识）；
    • 客户端重新连接后发现服务端返回的 UIDVALIDITY 与本地不一致；
    • 预期判定：客户端彻底废弃本地全部旧 UID 索引与 MODSEQ 水位标记，触发全量重新拉取，确保不会发生历史数据错位碰撞。
