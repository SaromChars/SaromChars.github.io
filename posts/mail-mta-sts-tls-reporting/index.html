MTA-STS 与邮件传输报告

2021年10月10日
|

在跨域邮件传输中，邮件传输代理（Message Transfer Agent，MTA）之间通过简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）升级传输层安全（Transport Layer Security，TLS）通常依赖 STARTTLS 命令。当发送方连接到目标主机的端口 25 并收到服务端的问候后，会发送 EHLO 命令探测服务能力。如果攻击者在传输链路上直接剥除服务端返回的 250 STARTTLS 响应，发送方往往无法判断对端是否本来就缺少 TLS 能力，便会按机会性安全设计回退至未加密的明文通道继续发送。

此外，若域名系统（Domain Name System，DNS）未配置防篡改机制，攻击者还可以伪造邮件交换（Mail eXchanger，MX）记录将流量引流至恶意服务器。

为了给邮件中继引入确定的加密策略与传输状态反馈，互联网工程任务组（Internet Engineering Task Force，IETF）发布了 RFC 8461（SMTP MTA 严格传输安全，SMTP MTA Strict Transport Security，MTA-STS）与伴随规范 RFC 8460（SMTP TLS 报告，SMTP TLS Reporting，TLS-RPT）。收件域可以通过 DNS 与由 TLS 保护的 HTTP（HTTPS）端点声明策略，要求发送方对 MX 主机实施证书身份校验，并通过聚合报告通道收集握手与策略执行结果。

机会性 STARTTLS 的降级风险与策略机制

在协议演进中，基于 DNS 的命名实体认证（DNS-Based Authentication of Named Entities，DANE）通过域名系统安全扩展（Domain Name System Security Extensions，DNSSEC）分发认证记录，提供了抗降级的 TLS 发现与验证机制。但当收件域尚不具备部署 DNSSEC 的条件时，DANE 便无法直接生效。

MTA-STS 采用了另一套工程折中：它不依赖 DNSSEC，而是利用 DNS TXT 记录提供策略版本标识，并将具体的策略文件存放在基于 X.509 公钥基础设施（Public Key Infrastructure X.509，PKIX）证书保护的 HTTPS 站点上。发送方在本地缓存该策略后，可在后续投递中抵御偶发的降级尝试。需要明确的是，若发送方同时支持 DANE 与 MTA-STS，依据 RFC 8461 第 2 节，发送方绝不能允许 MTA-STS 的校验通过来覆盖失败的 DANE 验证。

MTA-STS 策略发现与获取

收件域发布 MTA-STS 策略包含 DNS 版本指示与 HTTPS 策略正文获取两个环节。以下 DNS 记录与策略正文均为使用保留域名的教学示意，并非现网实测配置。

收件方管理域在其子域名 _mta-sts 下发布 TXT 记录。以 example.com 为例：

_mta-sts.example.com.  IN TXT "v=STSv1; id=20211010080000Z;"

记录以 v=STSv1 开头，其 id 字段限定为 1 到 32 个 ASCII 字母或数字字符。发送方通过比对该标识与本地缓存，即可在不发起 HTTP 请求的前提下判断策略是否发生变化。如果 DNS 解析返回多条记录，发送方需丢弃不符合版本的条目；若最终结果不恰好为一条有效记录，则判定收件域未提供可用的 MTA-STS 策略。

当发送方本地未缓存该策略或发现 id 更新时，会通过 HTTPS GET 请求访问固定知名路径：

https://mta-sts.example.com/.well-known/mta-sts.txt

在获取策略时，策略主机（mta-sts.example.com）出示的证书必须有效且未过期，必须能链式追溯至受信根证书认证机构（Certification Authority，CA），且仅依据证书中的 DNS 名称标识符（DNS-ID）匹配策略主机名。HTTP 响应状态码必须为 200，发送方绝不能跟随 3xx 重定向，也不得使用 HTTP 缓存。策略文本由纯文本键值对构成，示例字段如下：

version: STSv1
mode: enforce
mx: mail.example.com
mx: *.example.net
max_age: 604800

其中 mode 指定策略执行模式，mx 声明被允许处理该域邮件的 MX 模式（支持完整域名或最左侧单标签通配符），max_age 则是发送方应当维持该策略本地缓存的最长秒数。

策略验证与执行模式

发送方获取策略后，依据模式对解析出的 MX 列表与连接实施校验。

验证包含两个独立条件：首先，解析出的候选 MX 主机名必须匹配策略中的某条 mx 规则；其次，该 MX 主机必须支持 STARTTLS，并在握手时出示未过期、证书链通往发送方信任根 CA、且使用者可选名称（Subject Alternative Name，SAN）中的 DNS-ID 按规定匹配该 MX 主机名的有效证书。

需要区分两处验证对象：策略端点验证的是 mta-sts 策略主机身份，而投递阶段验证的是实际连接的 MX 主机身份。

模式策略校验未通过时的投递行为报告行为
testing发送方可按未发生 MTA-STS 失败继续常规投递流程（但仍受常规网络与 SMTP 协商结果影响）若双方均支持 TLS-RPT 且收件域声明了聚合地址，记录并发送报告
enforce发送方不得向未通过校验的主机投递邮件；若所有 MX 均失败，应当视为临时错误并稍后重试记录失败会话，在具备 TLS-RPT 条件时发送聚合报告
none视为收件域未实施 MTA-STS 策略，发送方不执行强制约束策略校验不计为失败；若收件域仍配置了独立的 TLS-RPT 记录，发送方仍可就常规 TLS 结果进行报告

在 enforce 模式下，若首选 MX 校验失败，发送方应依序尝试后续候选 MX。若全部候选均不可达或未通过验证，发送方应当将邮件保留在队列中安排稍后重试，而绝不能在未通过 DNS 重新检查 _mta-sts TXT 记录前直接产生永久投递失败。这一强制检查机制允许发送方及时发现并应用收件域发布的最新策略修正。

缓存生命周期、发现异常与运维更新

MTA-STS 的防护能力建立在缓存机制之上，由此产生了特定的安全边界与运维约束。

在处理策略拉取时，RFC 8461 第 3.3 节规定了明确的分支逻辑：如果发送方查到了合法的 DNS TXT 记录，但因网络超时或证书错误无法获取 HTTPS 策略，且本地没有任何未过期的缓存策略，发送方必须像收件域未实施 MTA-STS 那样继续后续投递；此时若网络遭到干扰，传输存在被降级的可能。

反之，若实时网络中无法解析 TXT 记录或无法获取 HTTPS 内容，但本地持有尚未过期的合法缓存策略，发送方则必须严格应用该缓存策略，按其 mode 执行，仅在 enforce 模式下因校验失败而禁止投递。

这意味着在初始发现阶段，能够阻断 DNS 响应的主动攻击者依然可以阻碍策略的首次建立。为了缩短风险窗口，规范推荐将 max_age 设置为数周或更长，并建议发送方在后台主动定期刷新缓存策略。当后台刷新持续失败时系统应向管理员告警，但在本地缓存模式为 none 时例外，以避免干扰正常的停用流程。

在基础设施调整时，运维操作需注意时序：收件域应当先更新 HTTPS 策略正文，再更新 DNS TXT 记录的 id，防止发送方提前缓存旧正文。

当需要更换或调整 MX 时，收件域必须在策略与 DNS 记录中做好平滑过渡。需要注意的是，MTA-STS 策略中的 mx 字段是合法主机白名单而非路由解析缓存，发送方仍需遵循 DNS 的 MX 记录进行选路；在 enforce 模式下，若新 MX 已在 DNS 中生效但未包含在发送方的旧策略缓存中，该候选将被直接拒绝。收件方在下线旧 MX 时需结合 DNS 缓存生存时间与邮件队列重试周期进行评估。

若要彻底停用 MTA-STS，应先将策略调整为较短 max_age 的 none 模式，待旧策略在全网缓存耗尽后，再移除相关记录。

同时应厘清技术边界：对应用有效 enforce 策略的发送方而言，MTA-STS 约束其对下一跳 MX 采用经过身份验证的 TLS 传输，但它无法抵御网络物理中断或阻断，策略验证失败反而会导致邮件延期；它既不能验证发件人的真实身份，也不承担反钓鱼或端到端内容加密的职责。

TLS-RPT 聚合传输报告与问题定位

收件域在 DNS 中发布 _smtp._tls TXT 记录声明报告接收端点，例如：

_smtp._tls.example.com.  IN TXT "v=TLSRPTv1; rua=mailto:reports@example.com,https://reporting.example.com/v1/tlsrpt"

该记录包含版本 v=TLSRPTv1 与接收地址 rua。发送方通常按 UTC 全天（00:00–24:00 UTC）汇总数据，在引入随机延迟后提交 JSON 报告。必须指出的是，TLS-RPT 纯粹用于反馈传输统计，其本身既不强制加密也不直接改变投递行为；发送方是否因握手或验证失败而停止投递，取决于另行采用的传输策略，例如 MTA-STS、DANE 或本地配置。

报告正文采用标准化字段进行结构化呈现，主要由三个层级组成：

首先是策略信息（policy），记录发送方在处理投递时所匹配到的具体策略类型及目标域配置，包含 policy-type: "sts"、policy-domain 与 mx-host 等字段。

其次是会话汇总（summary），包含 total-successful-session-count 与 total-failure-session-count。其中成功计数统计的是完全符合应用策略的 TLS 会话总量，充当连接通道正常的健康信号；失败计数则汇总结算期内的异常。

最后是失败明细（failure-details），针对特定错误类型记录发起方 IP（sending-mta-ip）、目标主机名（receiving-mx-hostname）以及该错误出现的具体会话频次（failed-session-count）。

当传输出现异常时，报告会提供标准化的错误分类代码。常见的结果类型及排查方向包括：

结果代码（result-type）故障性质典型排查方向（教学示意）
starttls-not-supported协商失败目标 MX 服务未正确响应 STARTTLS，或明文应答被中间网络设备阻断剥除。
certificate-host-mismatch身份不符MX 服务器呈现的证书中，SAN 内没有能按规定匹配该 MX 主机名的 DNS-ID。
certificate-expired证书失效接收端 MX 的 TLS 证书已过有效期，需检查证书自动更新机制。
sts-policy-fetch-error策略拉取受阻发送方无法通过 HTTPS 获取策略文件，需排查策略主机的 Web 服务状态或网络阻断。

在分析报告时需要注意，聚合报告并非实时告警通道，其成功计数仅表明传输会话建立了符合策略的 TLS 连接，不能直接等同于邮件最终送达用户收件箱。同时，偶发的网络抖动与边缘节点维护也可能造成失败，其中部分暂态错误规范并不要求报告，其实际覆盖取决于发送方的实现策略，排查时应结合 IP 分布与错误代码综合研判，不能单凭数字波动推断存在主动攻击。
