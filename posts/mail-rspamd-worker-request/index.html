Rspamd 工作进程与扫描请求生命周期

2021年12月12日
|

在开发邮件网关与反垃圾代理时，一个直接的工程疑问是：Rspamd 收到同一封邮件时，为什么既可以直接在代理进程就地处理，也可以转发给后端工作进程；在这个过程中，究竟是谁创建并持有了检测任务上下文，扫描结果与连接资源又如何在异步回调中回收？如果不理清进程职责与任务状态机的推进边界，当遇到网络抖动、依赖超时或对端异常断开时，系统就容易陷入排查无据的困境。

本文基于固定公开版本 Rspamd 2.7 源码（commit 4c56c1210dac78be727fc07d1c29c140034e4b19），聚焦扫描请求在服务进程内的流转主线，解析工作进程的分工拓扑、任务对象的数据结构、异步调度阶段以及超时与异常时的清理机制。

工作进程分工与请求流转入口

Rspamd 内部通过结构体 worker_t 划分不同职责的进程实例。在涉及邮件扫描的主路径上，存在三类核心工作进程（worker）配置名：normal、rspamd_proxy 与 controller。

normal 工作进程是核心的扫描计算节点。在 src/worker.c 中，normal_worker 标记了 RSPAMD_WORKER_SCANNER 与 RSPAMD_WORKER_SOCKET_TCP。它通常监听特定 TCP 端口，通过 HTTP 协议接收扫描请求，装载消息体并驱动后续检测。

rspamd_proxy 工作进程承担网关与代理集成职责。在 src/rspamd_proxy.c 中，rspamd_proxy_worker 同样具备 RSPAMD_WORKER_SCANNER 标志。它既可作为 Milter（MTA与过滤器之间的邮件过滤接口）服务端对接外部邮件传输代理（Mail Transfer Agent，MTA），也可接收 HTTP 扫描请求。重要的是，rspamd_proxy 并不一定会将请求跨进程转发出去：如果后端配置匹配到了 backend->self_scan，代理进程便直接调用 rspamd_proxy_self_scan 在当前进程内部创建任务并就地执行扫描；只有在未启用就地扫描时，才经由网络连接转发给远端的 normal 节点。

controller 工作进程则属于管理与控制单元。在 src/controller.c 中，controller_worker 带有 RSPAMD_WORKER_CONTROLLER 与 RSPAMD_WORKER_SCANNER。其 HTTP 路由除统计与配置操作外，还挂载了 /scan、/check、/checkv2 等检测端点。这些端点在处理前先经过 rspamd_controller_check_password 访问检查，再进入扫描处理。因此它主要服务于管理工具、调试以及贝叶斯学习等交互，不作为常规 MTA 自动化批量处理邮件的高频必经路径。

当系统通过 Milter 协议与 MTA 对接时，请求流转的主线十分明确。当邮件数据传输完成，触发 proxy_milter_finish_handler。该函数调用 rspamd_milter_to_http 将 Milter 会话与数据缓冲区转译为内部 HTTP 请求结构，随后执行 proxy_send_master_message。在此处，程序根据配置决定是进入 rspamd_proxy_self_scan 执行就地扫描，还是建立网络连接转发至 normal 后端。

扫描任务对象结构与上下文边界

扫描请求在进程内被承载于 struct rspamd_task（定义于 src/libserver/task.h）。该结构体并非 MTA 中具备磁盘持久化与重试队列语义的持久队列条目，而是过滤引擎在内存中执行单次评估的瞬时上下文对象。

在 struct rspamd_task 中，关键字段维护着网络身份、邮件元数据与运行时环境：

  • sock 为连接套接字描述符；client_addr 记录当前网络连接对端的 IP 地址（如发起请求的本地代理或 MTA 连接套接字地址）；from_addr 则记录请求中显式声明的邮件发送源 IP。网关开发中需明确二者边界，避免将内网转发节点的套接字地址与发信源地址混淆。
  • from_envelope 与 rcpt_envelope 分别记录简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）握手中的信封发件人与信封收件人；而多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）报文解析得到的 From:、To: 等头字段保存在 message 中。二者分别存储，后续安全规则根据不同策略选用对应的身份。
  • processed_stages 为记录处理进度的位掩码；s 是异步会话指针 struct rspamd_async_session，负责追踪并发未决事件计数；re_rt 为正则表达式运行时缓存；msg 为原始报文存储；result 指向综合指标结果 struct rspamd_scan_result；err 保存执行错误 GError。
  • task_pool 为该任务运行所使用的内存池（rspamd_mempool_t）。

任务初始化由 rspamd_task_new 实现（src/libserver/task.c）。当调用者传入的 pool 为 NULL 时，函数内部创建新内存池并标记 RSPAMD_TASK_FLAG_OWN_POOL；若调用者传入了已有池，则该任务复用现有内存池。在 normal_worker 接收连接时（src/worker.c 的 rspamd_worker_body_handler），连接关联的 session 结构体所有权会直接移交给 task，并在其内存池中注册析构器，在池销毁时代为调用 g_free 释放 session 并减少工作进程连接计数 worker->nconns。

在具体调用链路中，请求并不是在建立 TCP 连接时就立刻装载完毕，而是经历如下逐步解析与启动链：

rspamd_worker_body_handler
  -> rspamd_task_new -> rspamd_session_create
  -> rspamd_protocol_handle_request -> rspamd_task_load_message
  -> ev_timer_init/ev_io_init (timeout/guard) -> rspamd_task_process

其中 rspamd_protocol_handle_request 解析请求命令；rspamd_task_load_message 内部先调用 rspamd_protocol_handle_headers 处理请求头参数，再装载邮件数据。输入可以来自请求体，也可以走文件或共享内存映射路径。随后激活全局超时定时器与套接字看门狗，最后才驱动 rspamd_task_process。在 rspamd_proxy 的 self_scan 路径下，同样使用这组协议处理、消息装载与任务处理函数组合。

异步状态机调度与阶段运转

Rspamd 扫描的核心驱动力是 rspamd_task_process 状态机。在任务生存期内，状态机按预设顺序依次调度不同阶段。

在前半程中，状态机依次处理连接与正文解析：先执行连接过滤器（CONNFILTERS），随后调用 rspamd_message_parse 执行报文与 MIME 解析（READ_MESSAGE），并调用 rspamd_message_process 提取正文文本与特征（PROCESS_MESSAGE）。

在主体过滤与分类计算中，依次执行预过滤器（PRE_FILTERS）与主体过滤器（FILTERS），后者承载并行的异步检测。接着依次经过三段分类器阶段（CLASSIFIERS_PRE、CLASSIFIERS、CLASSIFIERS_POST），并进入复合符号计算阶段（COMPOSITES）。

在收尾与后处理阶段，状态机依次经过后置过滤器（POST_FILTERS）、三段学习阶段（LEARN_PRE、LEARN、LEARN_POST）以及后置复合符号计算（COMPOSITES_POST）。学习阶段按 LEARN_SPAM 或 LEARN_HAM 标志决定是否执行学习；自动学习是设置学习条件的另一条入口。当进入幂等过滤回调（IDEMPOTENT）时，状态机首先主动停止任务超时定时器 timeout_ev，随后执行符号缓存中注册的该阶段回调，最后推进至完成阶段（DONE）。

状态机推进的核心控制逻辑体现为事件挂起与收敛推进：

/* 基于 Rspamd 2.7 源码 (src/libserver/task.c, Apache-2.0) 整理的简化逻辑 */
if (rspamd_session_events_pending (task->s) != 0) {
    /* 存在未决的异步事件，等待事件循环回调触发 */
    return ret;
}
else {
    if (all_done) {
        /* 当前阶段完成，置位当前阶段标志，推进下一阶段 */
        task->processed_stages |= st;
    }
    return rspamd_task_process (task, stages);
}

当某阶段派发了异步请求时，异步会话 task->s 内的挂起计数增加，rspamd_task_process 立即退出以让出事件循环。当所有挂起事件归零后，异步会话唤醒注册的恢复函数（如 rspamd_task_fin、rspamd_proxy_task_fin 或 rspamd_controller_check_fin_task），驱动状态机继续往下流转。

结果输出与职责边界

当状态机推进完毕或发生中断时，完成回调调用应答逻辑：

  • 在 normal 进程中，调用 rspamd_protocol_write_reply 向套接字输出；
  • 在 rspamd_proxy 就地扫描路径下（rspamd_proxy_scan_self_reply），对 Milter 客户端通过 rspamd_milter_send_task_results 回写修改动作，对 HTTP 客户端通过 rspamd_http_connection_write_message 输出响应；
  • 在 controller 进程中，通过 rspamd_controller_scan_reply 输出响应。

根据协议序列化逻辑（src/libserver/protocol.c），现代 CHECK_V2 命令通常输出包含以下字段的 JSON 结构：

  • score：累积计算的评估得分；
  • required_score：响应中报告的分数门槛，取自可用且非 HAM、非无阈值动作的限制；不能用它单独代替 action 判断所有处置；
  • action：引擎建议的处置动作（如 no action、greylist、add header、rewrite subject、soft reject 或 reject）；
  • symbols：命中的特征符号集合及详情。

需要强调的是，HTTP 传输层返回 200 状态码并带有 JSON 内容，仅代表 HTTP 通信与协议应答本身成功，不能直接证明扫描分析一定无误或已完整执行。响应中仍需检查 is_skipped、错误信息或超时中断痕迹。同时，过滤引擎给出的建议动作与 MTA 最终是否接收邮件属于完全不同的职责层次：MTA 需结合本地配置、Milter 状态码与实际投递约束，决定是否向发件方回复最终的 SMTP 接收响应。

失败处理、超时控制与生命周期清理

在网关运行过程中，异常处理与资源回收机制决定了系统的健壮性。

1. 全局超时与 Soft Reject 条件

任务超时由 rspamd_task_timeout 定时器函数处理（src/libserver/task.c）。若超时触发时任务仍未完成 FILTERS 阶段，系统检查配置 soft_reject_on_timeout：如果该选项开启且当前动作不是 reject（action->action_type != METRIC_ACTION_REJECT），系统将通过 rspamd_add_passthrough_result 注入 METRIC_ACTION_SOFT_REJECT 动作，附带原因 "timeout processing message"。接着执行 rspamd_session_cleanup(task->s) 清理挂起事件，强行将 processed_stages 置上 FILTERS 完成位，并再次调用 rspamd_task_process 继续执行后续阶段。

可见，超时并不必然产生软拒收（若配置未开启或已被判定为 reject），也不会立刻中断全部生命周期，而是跳过尚未完成的主体过滤器并尝试让后续阶段收敛。若超时发生在后处理阶段，同样检查该选项并确认当前动作不是 reject 后注入软拒收，再置位 RSPAMD_TASK_STAGE_DONE 推进结束。

2. 套接字看门狗防护

在任务完整装载完毕后，系统通过 guard_ev 监听连接套接字（rspamd_worker_guard_handler），用于检测客户端是否在发送完毕后过早关闭连接。当套接字产生可读事件：

  • 若读取到数据，提示多余数据告警；
  • 若读取到对端关闭（r == 0），代码判定为对端异常关闭。此时只有在命令非 CMD_CHECK_V2 且配置启用了 enable_shutdown_workaround 时，才执行读关断兼容；对于正常的 CMD_CHECK_V2 命令，即便开启该兼容选项，依然会视作异常关闭并调用 rspamd_session_destroy(task->s) 销毁会话。

3. 释放清理与所有权约束

任务对象的回收通常在异步会话收敛后由终结器（finalizer）触发 rspamd_task_free 执行，不能将其内存释放与物理网络写入完成的绝对时间顺序画等号。在 rspamd_task_free 中：

  • 逐一释放信封地址、正则运行时、HTTP 连接引用、网络地址对象以及错误对象；
  • 注销 timeout_ev 与 guard_ev 事件，关闭连接套接字 sock；
  • 解除 Lua 缓存引用并释放配置引用计数；
  • 只有当 task->flags & RSPAMD_TASK_FLAG_OWN_POOL 成立时，才会调用 rspamd_mempool_delete 销毁内存池。

这意味着当 rspamd_proxy 或 controller 借用外部已有 session 内存池创建 task 时，task 销毁并不会释放借来的内存池。工程推导表明：任何生命周期需要超出 task 异步执行范围的数据，都必须自行深拷贝或建立独立所有者，不可依赖 task 内存池的隐式存续。

最小验证方案（未运行教学设计）

本方案用于在隔离环境中观察请求调用流转与超时清理边界，本方案为未运行的教学设计方案，不作为已测试保证。

  1. 测试准备：构造一封脱敏测试邮件样本（设定固定发件人、收件人），并在隔离测试网络中配置本地测试 MTA 与 Rspamd 实例。确保两路对比使用一致的规则、设置与受控依赖。记录请求关联的队列 ID（Queue-ID）、连接对端 IP（client_addr）及声明来源 IP（from_addr）。注意：队列 ID 由协议参数指定，并非直接来自 EML 头部。
  2. 两路转发与网络身份传递：分别配置代理开启 self_scan = true 以及将请求转发至独立的 normal 节点。通过隔离 MTA 发送相同样本。在 proxy 转发至 normal 时，连接对端 IP 自然发生改变（由客户端地址变为 proxy 地址），但声明来源 IP 应被正确保持并传递至后端。由于本地 DNS 缓存与外部规则集环境可能不同，验证时着重比对连接与信封头字段是否正确传递，不应强求两次检测输出的特征符号完全相同。
  3. 依赖超时与连接断开观察：配置外部测试依赖产生确定性延迟并使总耗时超出 task_timeout，在开启 soft_reject_on_timeout 后，分别验证当前命中为非 reject（注入软拒收）与已被判定为 reject（保留 reject）时的输出差异，观察超时处理中挂起事件的清理与后续阶段推进；同时模拟客户端在发起 HTTP 检测后主动重置套接字，验证看门狗捕获异常关闭后销毁异步会话与释放资源的过程。在此过程中，MTA 最终对发件方返回的 SMTP 状态码需在隔离 MTA 端进行观察。
