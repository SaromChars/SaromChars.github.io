域、账号、别名与多租户隔离

2021年8月29日
|

在构建支撑多个组织或海量用户的邮件系统时，开发者往往容易将邮件地址（email address）、登录账号（account）与底层物理存储（storage）简单等同。例如，同一个对外接收地址可能映射到共享邮箱，允许多个不同凭据的账号并发访问；或者单个用户为了归类业务而拥有多个别名地址，但内部均汇入同一个存储实体。

RFC 5598 是一份提供互联网邮件架构说明的信息型备忘录（Informational RFC），它通过角色与实体分层澄清了现实邮件体系的协作模型，而非规定具体实现的协议强制标准；而 RFC 4314 则是标准跟踪文档（Standards Track RFC），规范了互联网消息访问协议（Internet Message Access Protocol，IMAP）的访问控制列表（Access Control List，ACL）扩展。混淆公网路由标识与系统内部访问主体，容易在多租户（multi-tenancy）环境下引发越权访问、循环投递或退信权责错位。本文结合这两份文献，厘清域、账号、邮箱与别名的职责边界，并梳理存储共享与访问控制层面的隔离机制。

邮件域、邮箱与账号：三层职责划分

根据 RFC 5598 第 2 节的架构模型，互联网邮件体系由三大类参与者角色（Actors）构成：用户角色（User Actors）、报文处理服务角色（Message Handling Service Actors，MHS Actors）以及管理角色（Administrative Actors）。在此模型下，域、邮箱与账号承担着不同维度的系统职责：

1. 域名与管理域边界

邮件地址的右半部分是一个可在域名系统（Domain Name System，DNS）中解析的完全限定域名（Fully Qualified Domain Name，FQDN）。在 RFC 5598 第 2.3 节与第 3.3 节的描述中，域名通常作为全局资源引用，可对应一个组织、一组主机或单台机器，并在管理上关联到一个管理域（ADministrative Management Domain，ADMD）。

需要说明的是，管理域是独立运营管理与策略权限的抽象边界，负责定义可靠性、访问控制与报文过滤策略。管理域与 DNS 邮件域名并非必须是一对一的强绑定关系：一个企业内部的不同部门、总公司 IT 与外包服务提供商可能构成不同的管理域；而在多租户托管场景下，单个邮件服务提供商（Mail Service Provider，MSP）也可以作为独立管理域，同时托管成百上千个属于不同租户的外部邮件域名。

2. 邮箱（Mailbox）是逻辑接收实体

依据 RFC 5598 第 3.1 节引用 RFC 5322 的定义：“邮箱（mailbox）负责接收邮件，它是一个概念实体（conceptual entity），并不必然对应于文件系统中的物理存储。”邮件地址（addr-spec）由本地部分（local-part）与域名（domain）通过 @ 符号连接而成。

在该模型的分工中，RFC 5598 第 3.1 节指出：除目标域所属的管理实体外，公网传输网络中的其他中间参与者将 local-part 视作全局不透明的字面字符串（globally opaque literal string），并在传输过程中保留其所有细节。只有负责该域终点处理的系统，才有权依据本地规则解析 local-part 的内部语义（如映射到具体目录、展开别名或分发脚本）。

3. 账号与认证主体（Identity）

账号属于系统内部凭据体系中的实体，是身份认证（authentication）与访问控制的主体。一个账号可以对应一个独立邮箱，但也可以被授权代管多个邮箱；反之，一个公共邮箱也可通过授权策略允许多个账号并发访问。

别名、重发者与邮件列表：中介机制的边界

在邮件投递过程中，常常需要根据业务规则对收发地址进行转换。运维系统中常将各类“地址重写”笼统称为转发，但在 RFC 5598 第 5 节的模型中，这类处理被归入中介者（Mediators）的范畴。

中介者既具备邮件用户代理（Message User Agent，MUA）重新生成或修整报文的灵活性，又参与传输流转。RFC 5598 细分了别名（Alias）、重发者（ReSender）以及邮件列表（Mailing Lists）等不同形态，各自对传输信封（Envelope）与报文内容（Content）头部有着不同的处理方式。

1. 别名（Alias）机制与退信权责

依据 RFC 5598 第 5.1 节的模型描述，别名是一种简单的重寻址设施（re-addressing facility）。当报文投递代理（Mail Delivery Agent，MDA）判定收件地址为别名时，它并不将邮件写入本地单个内部存储，而是提供一个或多个新的邮件地址，使邮件继续通过传输系统投递。

别名的典型特征在于：它改变传输信封中的收件人地址（RFC5321.RcptTo），而信封发件人反向路径（RFC5321.MailFrom）以及报文头部（RFC5322.From、To、CC 等）均保持原样。

保留原始 MailFrom 会对后续失败通知的去向产生直接影响：

  • 故障排查困境：当别名展开为多个外部地址，且下游中继在接受投递责任后发生不可达等异步投递失败时，生成的递送状态通知（Delivery Status Notification，DSN，即退信通知）如果反向路径非空，将按照信封中未修改的 RFC5321.MailFrom 发送给该地址。需要注意，该反向路径地址是原始事务指定的处理地址，并不一定等同于报文头部可见的 RFC5322.From 作者；而且原始提交方通常并不知晓下游别名的存在，往往难以理解退信原因，真正维护别名配置的收件人反而收不到异常报告。
  • 空反向路径例外：若原始邮件的反向路径本身为空（即 MAIL FROM:<>，如系统通知或已生成的退信），依据基础传输规则，下游发生投递失败时不得再生成新的退信通知，以防止出现反弹风暴与死循环。

2. 重发者（ReSender / ReDirector）

依据 RFC 5598 第 5.2 节，重发者不同于简单的别名展开。重发者通过“拼接”原邮件与新邮件的寻址信息，将原始作者与新收件人连接起来，使新收件人能够直接使用 MUA 的回复功能与原作者交流。

在该模型中：

  • 报文内容保留原始作者的 RFC5322.From 与 Reply-To 字段；
  • 重新提交该报文的中介参与者负责引入一组 Resent-* 头字段（如表明执行重定向参与者的 RFC5322.Resent-From，以及指示新收件人的 RFC5322.Resent-To 等）；
  • 负责重新提交的参与者同时负责为该事务指定新的信封反向路径 RFC5321.MailFrom。

3. 邮件列表（Mailing Lists）

依据 RFC 5598 第 5.3 节，邮件列表接收发送给特定群组地址的邮件，并将其重新分发给所有订阅成员。在架构模型中，邮件列表扮演了完整用户的角色：

  • 信封反向路径与退信接管：邮件列表在转发时可能会修改正文（如移除附件、添加列表标识说明），因此列表是新报文的责任主体。列表通常会将其信封 RFC5321.MailFrom 指定为列表自身的退信处理地址，以便下游投递失败的通知由列表系统集中处置，避免将分发故障发送给原始发件人。不过 RFC 5598 第 5.3 节也指出，虽然复用原始发件人的返回地址容易引发问题，但在实现中并非绝对不存在这种做法。
  • 头部控制与回复权衡：列表保留原始 RFC5322.From，并添加 List-Id 与 List-* 等群组头字段。对于是否在报文中设置 Reply-To，RFC 5598 指出，列表将自身地址填入 Reply-To 虽较常见，但可能会干扰发信人仅希望私下回复给原作者的意图；是否修改 Reply-To 本质上属于该列表群体的协作文化选择。

多租户隔离：虚拟域与租户作用域设计

在共享端点托管（Shared Multi-tenant Hosting）场景下，同一套服务器与存储集群往往需要同时承载多个客户域（如 customer-a.example 与 customer-b.example）。本节讨论在工程实践中实现多租户隔离的常见设计模式，这些属于特定托管环境下的条件性推导与架构建议，而非 RFC 5598 或 RFC 4314 的底层协议强制要求。

1. 认证上下文与内部存储解耦

在多租户系统中，系统避免将操作系统的单一本地用户（如本地系统账户 alice）直接作为全局唯一的主键：

  • 可信租户作用域（Tenant Context）：在用户认证时，服务端需要根据接入端点、专用主机名或登录标识，解析并确立该连接归属的可信租户上下文。需要注意，外部用户输入的域名字符串不能在未校验凭据所有权前直接盲信为租户标识，所有后续的数据查询、路由与权限判定都必须在已验证的可信租户作用域内执行。
  • 稳定内部标识解耦：在底层存储与索引设计中，采用不随外部域名变动而改变的内部稳定键（例如通用唯一标识符 Universally Unique Identifier，UUID）来定位租户与邮箱实体。邮件地址字符串仅作为外部路由映射表的键，当企业发生域名变更或用户调整别名时，底层存储结构无需经历物理迁移。

2. 避免租户间信息侧信道探测

在多租户环境下，信息隔离需要防范未授权的探测行为：

  • SMTP VRFY 与 EXPN 限制：早期的 SMTP 允许客户端通过 VRFY 验证收件人，或通过 EXPN 展开邮件列表。在面向公网的多租户服务器中，未受限的探测可能导致外部攻击者遍历并推断特定租户内部的员工邮箱或群组结构。因此，面向非受信网络的端点通常建议关闭这些命令，或在策略上限制对其的使用。
  • 目录服务逻辑隔离：当系统提供轻量目录访问协议（Lightweight Directory Access Protocol，LDAP）等通讯录查询服务时，系统应当施加严格的访问控制与逻辑作用域过滤，确保各租户账号仅能查询本组织内部的用户与群组，杜绝跨租户检索。

共享存储与细粒度权限：RFC 4314 IMAP ACL

在企业协作场景下，同一租户内部的多名成员往往需要共享特定邮箱（例如公共客服邮箱或日程归档箱）。为了在 IMAP 协议层面精细化管理访问控制，作为标准跟踪协议的 RFC 4314 规范了 IMAP4 访问控制列表（ACL）扩展。

RFC 4314 修正了 RFC 2086 中较为模糊的权限定义，将控制细化为独立的单个字符。

1. 标准权限项与其控制动作

依据 RFC 4314 第 2.1 节，定义的标准权限（Standard Rights）全部采用小写字母表示：

权限字符权限名称对应受控操作与协议行为（RFC 4314 §2.1、§4）

rread允许执行 SELECT 或 EXAMINE 检视邮箱，允许执行 STATUS 查询邮箱状态。

废弃字符 c 与 d 的兼容映射

RFC 4314 第 2.1.1 节指出，早期 RFC 2086 中定义了 c（create）与 d（delete）。由于早期各服务端实现存在理解差异，RFC 4314 归纳了两种兼容实现模型：

  • 模型一：定义 create 为 k 与 x 的并集，delete 为 e 与 t 的并集。
  • 模型二：定义 create 等同于 k，delete 为 e、t 与 x 的并集。

服务端实现根据所选取的兼容模型进行映射。当客户端在 SETACL 中包含 d 时，服务端按选定模型展开；而在返回 MYRIGHTS 或 ACL 响应时，若授予的权限包含所选集合中的成员，服务端必须（MUST）同时附带虚拟的 c 或 d。符合 RFC 4314 的客户端必须（MUST）忽略响应中的虚拟 c 与 d 字符。

2. ACL 管理交互流程

在管理会话中，具备管理员权限（a 权限）的用户可以通过标准命令操作指定邮箱的 ACL。以下示例展示具备管理权限的用户为账号 bob 增加写入与标记删除权限，随后展示服务端依据“模型二（c=k，d=etx）”向其返回的 ACL 响应：

C: A001 GETACL "Shared/Support"
S: * ACL "Shared/Support" admin lrswipkxteacd bob lrsi
S: A001 OK Getacl complete
C: A002 SETACL "Shared/Support" bob +wt
S: A002 OK Setacl complete
C: A003 GETACL "Shared/Support"
S: * ACL "Shared/Support" admin lrswipkxteacd bob lrsiwtd
S: A003 OK Getacl complete

在上述响应中，因为账号 bob 被授予了 t 权限（属于虚拟 d 的成员），依据规范服务端在 ACL 响应中自动附带了虚拟字符 d，而未被授予的 a 权限绝对不会被凭空添加。

  • 标识符规范化：依据 RFC 4314 第 2 节与第 3 节，访问标识符采用 UTF-8 编码。服务端在处理包含标识符参数的命令（如 SETACL、DELETEACL、LISTRIGHTS）时，应当（SHOULD）首先使用 SASLprep 规范对身份标识符字符串进行规范化处理；若规范化失败或结果为空，服务端必须（MUST）返回 BAD 响应拒绝该命令。标识符 "anyone" 保留为通用匿名及所有已认证用户的全称标识；以 - 开头的标识符保留为负权限（Negative Rights，用于显式剔除某用户的特定权限，但服务端并非必须实现负权限支持）。
  • 只读与读写状态推导：RFC 4314 第 5.2 节规定，当客户端执行 SELECT 打开邮箱时，若当前用户未被授予 i（写入）、e（永久移除）以及该邮箱定义的任何“共享标志修改权限”（即能够影响其他用户的标志权限，如共享的 w、s 或 t），服务端在成功响应中必须（MUST）返回 [READ-ONLY] 响应代码；只要具备上述任一权限，服务端应当（SHOULD）返回 [READ-WRITE]。

3. 安全防范与信息隐匿

依据 RFC 4314 第 6 节的安全考量，在共享与多租户环境下，服务端实现必须防范通过访问控制命令泄露信息：

  • 防范 ACL 命令枚举存在性：如果用户对某个邮箱不具备 l（lookup）查看权限，当该用户针对该邮箱执行 GETACL 等访问控制查询命令时，服务端必须（MUST）返回与该邮箱根本不存在时完全相同的错误响应，从而避免通过权限拒绝信息反向确认敏感邮箱的存在。
  • 区分查看与选择权限：在 IMAP 中，SELECT 命令要求的是 r（read）权限，而非 l 权限；在特定策略下，用户可能在未被授予目录枚举 l 权限的情况下，通过精准输入已知邮箱名并凭借 r 权限成功打开邮箱。
  • 警惕 "anyone" 权限扩散：客户端在允许用户配置 ACL 时，应当（SHOULD）对将完整权限或 a（管理）权限赋予保留标识符 "anyone" 的行为发出明确警告，防止配置者无意中将私有邮箱开放给全系统用户。

边界故障与排查清单

在日常运维排错中，多租户与别名配置常引发一系列典型异常：

  1. 别名级联导致的投递循环（Mail Loop）：当别名配置形成环路（例如域 A 的别名转发至域 B，而域 B 内部的规则又重新转回域 A）时，报文会在传输节点间反复流转。一种工程上的循环防护是邮件传输代理（Message Transfer Agent，MTA）检查报文头中累积的 Received 等追踪字段数，并按配置中断可疑投递（此处不指定统一的绝对阈值或响应码）；在维护本地别名映射表时，运维系统可在写入配置阶段执行局部有向无环图检查，但对于跨组织或未知的外部转发链路，仍需依赖报文头追踪进行动态拦截。
  2. 多租户下的代发权限控制：在共享端点托管环境中，已认证账号 user@customer-a.example 若尝试在信封发件人中声明 MAIL FROM:<admin@customer-b.example>，邮件提交服务可依据本地管理策略检查认证身份与信封发件人的授权关系。若该会话未获跨租户代发授权，服务可直接拒绝该事务，防止租户间的仿冒行为。
  3. IMAP 标志修改失败与部分成功：用户在共享文件夹中修改邮件旗标却未生效时，需排查其 ACL 权限。依据 RFC 4314 第 4 节，修改 \Seen 需具备 s 权限，修改 \Deleted 需具备 t 权限，修改其他标志需具备 w 权限。若用户发起的 STORE 命令同时包含多项标志修改请求，只要用户对其中至少一项具备修改权限，服务端不应（SHOULD NOT）使整个 STORE 命令报错失败；但若用户对请求中的所有标志均无修改权限，则该操作无法持久化更新对应标志。
