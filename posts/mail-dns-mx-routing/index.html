邮件地址、DNS 与 MX 路由

2021年8月4日
|

在互联网邮件传输体系中，按目标域进行域名系统（Domain Name System，DNS）直投的邮件传输代理（Message Transfer Agent，MTA）从本地队列取出待发邮件时，核心任务是将收件人地址中的目标域名解析为网络上可达的具体传输目标。

这一解析过程由 RFC 5321（简单邮件传输协议，Simple Mail Transfer Protocol，SMTP）第 5 节规范，并与 RFC 1035 定义的邮件交换资源记录（Mail eXchanger Resource Record，MX RR）相衔接。理解这一路由机制，需要掌握 MX 记录的优先级排序与负载分散规则，以及规范名称记录（Canonical Name Record，CNAME）别名、无 MX 记录时的隐式回退机制（Implicit MX）、空 MX 规范（Null MX，RFC 7505）与候选地址重试边界。

邮件地址的结构与解析边界

在 SMTP 协议对话中，客户端通过 RCPT TO 命令指定信封收件人邮箱（Mailbox），并据此确定投递的目标域。根据 RFC 5321 第 4.1.2 节的语法规范，标准邮箱地址定义为：

Mailbox = Local-part "@" ( Domain / address-literal )

@ 符号将地址划分为本地部分与域名（或地址字面量），两部分在解释与路由中的职责不同：

1. 本地部分（Local-part）

  • 语法组成：由点分隔字符串（Dot-string）或带双引号的引用字符串（Quoted-string）构成。
  • 解释边界：协议规范规定，Local-part 的解释权限完全归属于接收端邮件系统。发送端 MTA 与任何中间传输中继在进行外部路由计算时，不得对 Local-part 进行语义假设、拆解或大小写规整。传输系统仅将其视为交付给接收主机的透明标识。虽然 RFC 5321 建议接收端实现避免对本地部分区分大小写，但协议允许其区分。

2. 域名（Domain）与地址字面量（address-literal）

  • 域名：路由决策的默认依据。RFC 5321 第 4.1.2 节要求，客户端与服务端的域名标签必须由字母、数字和连字符构成（即 sub-domain = Let-dig [Ldh-str]），禁止在域名标签中使用下划线（_）。
  • 完全限定域名（FQDN）约束：域名通常应为完全限定域名（Fully-Qualified Domain Name，FQDN）。RFC 5321 第 5.1 节规定，中间（中继）SMTP 服务器绝不能（MUST NOT）从不完整名称或本地别名推导 FQDN；初始提交服务器原则上也不应（SHOULD NOT）进行此类推导，但专门的邮件提交服务器（RFC 4409）具有相对更灵活的本地策略空间。
  • 地址字面量（address-literal）：当目标主机未接入 DNS 或需要绕过 DNS 故障时，协议允许使用方括号包裹的 IP 地址作为直接目标（RFC 5321 第 4.1.3 节），例如 IPv4 的 [192.0.2.1] 或 IPv6 的 [IPv6:2001:db8::1]。在此情况下，发送端 MTA 绕过 DNS 解析，直接向该 IP 地址发起 TCP 端口 25 的连接。

DNS 解析顺序与 MX 记录语义

根据 RFC 1035 第 3.3.9 节，MX 记录的 RDATA 字段由两部分组成：

+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
|                  PREFERENCE                   |  (16 bit 无符号整数)
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+
/                   EXCHANGE                    /  (<domain-name> 目标主机域名)
+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+--+

其中 PREFERENCE 决定优先级（数值越小优先级越高），EXCHANGE 必须是一个指向目标主机的合法域名。

解析与排序流程

当 MTA 针对目标域名 example.com 寻找交付目标时，RFC 5321 第 5.1 节规定了以下处理步骤：

  1. 查询 MX 记录：客户端向 DNS 解析器发起 example.com 的 MX 查询。
  2. 处理 CNAME 别名：如果在查询过程中遇到 CNAME 记录，客户端必须将解析目标重定向至 CNAME 所指向的规范域名，并重新针对该规范域名执行 MX 查询。
  3. MX 目标的主机名约束：MX 记录中 EXCHANGE 字段返回的域名，在被查询时必须直接返回至少一条地址记录（A 或 AAAA 记录）。RFC 5321 第 5.1 节明确禁止 EXCHANGE 指向另一个 CNAME 别名。
  4. 优先级排序与负载分散：
    • 客户端必须将获取到的多条 MX 记录按 PREFERENCE 升序排列。
    • 若存在多条优先级数值相同的 MX 记录，且客户端没有明确理由偏好其中某个目标（例如识别出某个更易到达的本地地址）时，发送端 MTA 必须对这些同优先级的记录进行随机打乱（Randomize），以在组织的多台接入网关之间分散入站负载。

下表梳理了常见 DNS 响应与 MTA 动作的映射关系：

DNS 查询响应状态协议含义说明MTA 的标准处理行为（RFC 5321）投递状态判定
存在有效 MX 记录目标域明确指定了一组邮件交换主机按 PREFERENCE 升序排序；无偏好理由时同数值记录随机打乱后逐个尝试连接正常投递尝试
NXDOMAIN（域名不存在）所查询的域名不存在（RFC 1035 第 4.1.1 节）作为永久失败报告；在当前 SMTP 会话中可直接同步拒绝，若已接受且反向路径非空则产生退信通知永久失败（Permanent Failure）
DNS 临时错误（SERVFAIL / 超时）权威 DNS 抖动、网络中断或递归超时保留邮件在本地队列中，按照退避算法等待后续重试临时失败（Transient Failure）
NOERROR 但 MX 列表为空域名存在，但未配置专用 MX 记录触发“隐式 MX（Implicit MX）”回退机制，查询该域名的 A/AAAA 记录协议向后兼容回退
单一 MX 记录为 0 .目标域声明不接受任何电子邮件（RFC 7505）立即按永久失败结束投递，不发起 SMTP 投递连接，不进行 A/AAAA 回退永久失败（Null MX）

隐式 MX 回退机制（Implicit MX）与失败边界

在早期互联网阶段，很多主机直接挂载在公网，未专门配置独立的邮件交换网关。为了保障向后兼容性，RFC 5321 第 5.1 节规定了隐式 MX 回退规则。该规则转述如下：

如果针对目标域名的 DNS MX 查询返回了空列表（即域名存在但无 MX 记录），客户端必须将该域名视同具有一条优先级为 0 的隐式 MX 记录，且其 EXCHANGE 目标即为该域名本身。

随后，MTA 会尝试获取该域名自身的地址记录（IPv4 的 A 记录或 IPv6 的 AAAA 记录）。如果找到对应 IP，客户端将直接连接该主机尝试交付。

关键失败边界：有 MX 不可用与无 MX 的区别

必须严格区分“没有 MX 记录”与“存在 MX 但连接失败”：

  • 只有在完全未查询到 MX 记录时，隐式 MX 回退规则才生效。
  • 如果目标域发布了一条或多条 MX 记录，但所有 MX 目标均无法解析出有效 IP，或者所有 MX 主机均无法连通，MTA 绝对不能回退去查询目标域名本身的 A/AAAA 记录（RFC 5321 第 5.1 节两次明确强调）。绕过已发布的 MX 记录去直连收件域 A/AAAA 属于违反协议行为，此时必须直接作为投递失败报告。
  • 此外，如果隐式 MX 自身也未查询到可用地址或连接均失败，同样必须报告投递错误，并根据具体的 DNS 响应或连接错误类型判定为临时或永久失败。

隐式 MX 的运维影响

隐式 MX 规则在保障老旧服务连通的同时，也可能造成无效连接与重试：

  1. Web 与 Mail 服务混淆：许多机构为根域（例如 example.com）配置了指向 Web 服务器或 CDN 节点的 A 记录，但其实际邮件业务由第三方托管（或根本不提供邮件服务）。如果未显式配置 MX 记录，发往该域名的误输入邮件将被投递给 Web 服务器。
  2. 占用队列资源与投递延迟：Web 服务器通常不监听 TCP 25 端口，防火墙也可能丢弃连接请求。发送端 MTA 遭遇超时或拒绝后会判定为临时网络故障，从而转入重试队列。按照 RFC 5321 第 4.5.4.1 节的一般建议，放弃重试的等待时间通常应至少为 4 至 5 天（具体策略可配置，RFC 7505 则提及实践中通常可达一周），这会导致发件人迟迟得不到退信通知，并占用发信方的队列资源。

不接收邮件的明确宣告：Null MX（RFC 7505）

为了让不提供邮件服务的域名明确声明拒绝接收邮件，避免无效排队与连接，IETF 于 2015 年发布了标准跟踪文档 RFC 7505，正式确立了“空 MX（Null MX）”机制。

1. 记录格式

Null MX 规定，如果一个域名不希望接收任何电子邮件，它必须在 DNS 中发布唯一一条满足以下条件的 MX 记录：

  • PREFERENCE 为 0；
  • EXCHANGE 为单根点字符 .（在 DNS 主区域文件中写为 .，表示长度为零的根标签）。

DNS 区域表示例：

example.net.  IN  MX  0 .

RFC 7505 第 3 节明确要求：发布 Null MX 的域名，绝不能同时发布任何其他 MX 记录。

2. 客户端处理契约

支持 RFC 7505 的 MTA 在解析到 0 . 记录时：

  • 必须立刻认定该目标域不接受任何邮件；
  • 绝对禁止向该域名发起 SMTP 投递连接，并且绝对禁止回退查询该域名的 A/AAAA 记录；
  • 必须立即按永久失败结束对该域的投递。

在错误处理与通知方面：

  • 若在当前的 SMTP 会话中处理（如提交服务器或中继在收到 RCPT TO 时检测到目标域配置了 Null MX），服务器可直接同步拒绝，推荐返回响应码 556（RFC 7504 定义，代表请求未执行：域名不接受邮件）与增强状态码 5.1.10。
  • 若接收端 SMTP 服务器因发件人地址（MAIL FROM）所在域名发布了 Null MX 而拒绝接收入站邮件，推荐返回响应码 550 与增强状态码 5.7.27。
  • 只有在邮件已被前置系统接受、随后在异步投递中遇到 Null MX 时，才根据 RFC 5321 第 6.1 节构造投递状态通知（Delivery Status Notification，DSN）退信；且当信封反向路径为空（MAIL FROM:<>）时，绝对不能发送通知，防止形成垃圾邮件反弹风暴。

自环检测与候选 MX 过滤

邮件跨域中继时，MTA 还需要处理自环规避与多地址连接策略：

1. 排除自身及更低优先级目标（自环规避）

根据 RFC 5321 第 5.1 节，当一台 MTA 作为指定邮件交换主机接收到邮件，并决定在不改写收件人地址的情况下继续中继转发时，必须执行以下防自环过滤：

  • MTA 对目标域的 MX 记录按优先级升序排序；
  • MTA 检查列表中是否存在本服务器的知名主机名或本机的 IP 地址；
  • 一旦在列表中匹配到自身，MTA 必须将该优先级记录以及所有数值更大（即优先级更低）的 MX 记录从候选列表中全部丢弃；
  • 仅保留比自身优先级数值更小（更高优先级）的主机作为候选投递目标；
  • 如果过滤后没有任何候选记录剩余，表明存在路由配置错误，邮件已无更高级别的中继路径，系统必须判定为错误并按不可投递退信，严禁将邮件转发给自己。

2. 多宿主（Multihomed）与多候选地址重试策略

当目标主机为多宿主主机（即单个主机名对应多个 A 或 AAAA 记录），或者存在多个同优先级的备选服务器时：

  • 若 DNS 解析器已对 IP 列表按偏好排序，发送端 MTA 必须按照解析器给出的顺序依次尝试连接。
  • RFC 5321 第 5.1 节建议客户端在遇到多个候选地址时，应至少尝试两个不同地址；同时系统也可配置替代地址的尝试数量上限，特定安装也可以根据网络环境限制或禁用对替代地址的使用。这在网络瞬时故障与避免无谓资源消耗之间提供了可配置的平衡。
