SPF 发件主机授权与边界限制

2021年9月8日
|

在简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）的传统通信过程中，客户端在连接握手与信封指令中声明的身份信息（HELO / EHLO 主机名与 MAIL FROM 反向路径）缺乏来源合法性校验。任何连接到接收端邮件传输代理（Message Transfer Agent，MTA）的主机，均可在信封中声称代表任意域名发信。

发件人策略框架（Sender Policy Framework，SPF，RFC 7208）允许域的所有者在域名系统（Domain Name System，DNS）中显式发布规则，声明哪些网络主机（IP 地址）获权使用该域名的身份发送邮件。

本文基于标准跟踪规范 RFC 7208，阐述 SPF 授权验证的执行模型，重点分析信封身份提取、SPF 记录选择与语法预检、机制评估与全局 DNS 预算上限，以及邮件转发与中介处理时的验证边界。

身份认证与授权的概念边界

身份认证（Authentication）与授权（Authorization）在邮件安全中解决不同层面的问题：

  • SPF 本质上是主机授权机制，即由域所有者在 DNS 中发布策略，判定当前的发信主机（TCP 客户端 IP 地址）是否获权使用给定的域名身份。
  • SPF 本身不对邮件正文提供防篡改签名，也不验证具体个人发件人的登录凭证；同时，它检验的是 SMTP 会话中的信封身份，并不直接验证邮件内容头部的 From: 字段（RFC 7208 第 11.2 节）。

1. 验证的身份标识：HELO 与 MAIL FROM

在 SMTP 事务中，SPF 检验两类身份标识：

  • HELO / EHLO 身份：SMTP 客户端在握手阶段通过 HELO 或 EHLO 命令声明的标识。RFC 7208 第 2.3 节建议（RECOMMENDED）接收端优先对 HELO 身份进行验证。由于单个发信主机的主机名策略通常直接对应明确的主机授权，若 HELO 检验已产生决定性策略结果，可避免后续对更复杂的 MAIL FROM 策略进行额外处理。需要注意的是，只有当 HELO 字符串为有效的多标签域名时才能执行该项检验；如果客户端提供的是 IP 地址字面量或格式畸形的字符串，验证器无法直接进行域名 SPF 查询。
  • MAIL FROM 身份：SMTP 会话在传输信封时通过 MAIL FROM 指令声明的反向路径（Reverse-path）。若未执行 HELO 检验或 HELO 检验未达成最终决定性结果，RFC 7208 第 2.4 节要求（MUST）校验 MAIL FROM 身份。
  • 空反向路径（Null Reverse-path）的处理：在处理系统退信等场景时，信封 MAIL FROM:<> 的反向路径为空。此时协议规定，必须将本地部分固定为 postmaster，并将 HELO 声明的域名作为发送方域名（即合成 postmaster@<helo-domain>）送入 SPF 评估（RFC 7208 第 2.4 与 4.3 节）。

2. 检查发生的时机与投递处理

RFC 7208 第 2.5 节建议（SHOULD），SPF 授权检查应当在接收邮件的 SMTP 事务进行过程中实时完成（通常在接收到 MAIL FROM 或 RCPT TO 之后）。在会话阶段完成检查具备两项关键优势：

  1. 准确获取客户端 IP：连接方的 TCP 客户端套接字 IP 地址直接明确，避免邮件存入本地后再试图从可能被篡改伪造的信件跟踪头部中提取发信 IP。
  2. 支持同步拒绝与抑制回散射（Backscatter）：若评估判定为未授权，接收端可在当前 SMTP 对话中直接返回永久错误拒绝信件。若在接收信件之后再异步生成未送达退信发送给伪造的 MAIL FROM，容易演变为针对无辜第三方的垃圾退信反弹（回散射，Backscatter，RFC 7208 第 2.5 节）。

SPF 记录发布格式与语法结构

SPF 记录必须以 DNS TXT 资源记录（Resource Record，RR）形式发布在域名的所属节点（RFC 7208 第 3.1 节）。历史实验阶段曾定义的专用 SPF RR（类型代码 99）已被正式废弃，协议要求仅使用 TXT 记录。

一个合法的 SPF 记录由版本声明、机制（Mechanism）与修饰符（Modifier）按顺序组成：

v=spf1 ip4:192.0.2.0/24 include:_spf.example.com -all

1. 机制（Mechanisms）与限定词（Qualifiers）

接收端从左向右依次评估各个机制。当某个机制匹配当前客户端 IP 时，立即终止后续评估，并返回机制前缀所指定的限定词结果；若不匹配，则继续评估下一个机制。

限定词包括以下 4 种（若省略限定词，默认为 +）：

限定词对应评估结果语义说明（RFC 7208 第 2.6 与 4.6.2 节）
+Pass明确授权该客户端 IP 代表该域名发信。
-Fail明确声明该客户端 IP 未获该域名授权。
~Softfail弱声明未授权（介于 Fail 与 Neutral 之间）。发布者认为可能未获授权，但未发布硬性拒绝策略。
?Neutral中立声明。发布者明确声明不对该 IP 是否获权作断言。

核心机制定义如下：

  • ip4 / ip6：指定精确的 IPv4/IPv6 地址或无类别域间路由（Classless Inter-Domain Routing，CIDR）网段（例如 ip4:192.0.2.1、ip4:192.0.2.0/24、ip6:2001:db8::/32）。该机制评估时无需进行 DNS 查询。
  • a：查询目标主机名（若未提供参数则为当前查询域名）的 A 或 AAAA 记录，若客户端 IP 在返回的地址列表中则匹配。
  • mx：查询目标域名的邮件交换（Mail Exchanger，MX）记录，随后对解析出的所有邮件交换主机查询 A 或 AAAA 地址，若匹配则成立。
  • include:<domain>：触发对目标域名的递归 SPF 评估。
  • exists:<domain>：对宏展开后的域名执行 DNS A 记录查询，只要返回任意 A 记录即视为匹配（RFC 7208 第 5.7 节）。
  • ptr：逆向查询客户端 IP 的指针记录（Pointer Record，PTR）并正向交叉校验。由于对 DNS 服务器性能消耗过大且不可靠，RFC 7208 第 5.5 节明确建议发布者不应使用（SHOULD NOT use）；但由于其仍属协议组成部分，合规的 SPF 验证器在评估时仍必须支持已有 ptr 策略的解析。
  • all：无条件匹配当前处理流。通常作为最后一条规则（如 -all 或 ~all）。若省略 all 且无修饰符重定向，记录末尾存在隐式 ?all，默认结果为 neutral。

2. 修饰符（Modifiers）与重定向

修饰符以键值对（name=value）形式存在，通常置于记录末尾：

  • redirect=<domain>：当且仅当所有机制均未匹配时生效，使评估转向新域名的 SPF 记录。若重定向目标不存在有效 SPF 记录，返回 permerror。
  • exp=<domain>：用于当产生 fail 结果时，通过查询该域名的 TXT 记录获取向发信方展示的自定义解释文字。

记录选择、预检与 check_host() 评估模型

RFC 7208 第 4 节定义了标准化模型函数 check_host(ip, domain, sender)。验证器在对机制进行从左向右评估前，必须严格完成记录选择与语法校验：

  1. 记录选择（RFC 7208 第 4.5 节）：
    • 验证器查询目标域名的 TXT 记录，筛选出版本字段恰为 v=spf1 的记录。根据协议规范，版本段后必须紧跟空格（SP）或到达记录结尾；若形如 v=spf10 则不属于匹配记录，必须直接丢弃。
    • 若筛选出的匹配版本记录数为 0，评估结果直接为 none。
    • 若同一个域名下发布了多于一条匹配版本的记录，验证器必须直接返回 permerror，而不得随意挑选其中一条执行。
  2. 整条记录的先验语法校验（RFC 7208 第 4.6 节）：
    • 验证器在开始逐条计算机制前，必须首先校验所选 SPF 记录的整体语法。
    • 如果记录的任意位置存在语法错误（例如未知修饰符格式错误、重复出现非法修饰符等），验证器必须立即以 permerror 终止退出，绝不能因为前面的机制能够匹配就忽略后面的语法错误。

include 的递归逻辑与判定映射

机制名称 include 容易引起字面误解。它并非在语法层面将被引用域名的规则文字展开合并进来，而是对被引用域名执行独立的子 check_host() 评估（RFC 7208 第 5.2 节）：

递归子 check_host() 返回结果对当前父 include 机制的影响
Pass匹配（Match）。当前机制根据其限定词决定结果（如 +include 产生总体 pass）。
Fail未匹配（Not Match）。父级 SPF 忽略此结果，继续向后评估下一条机制。
Softfail未匹配（Not Match）。父级继续向后评估。
Neutral未匹配（Not Match）。父级继续向后评估。
Temperror异常终止，向上级返回 temperror。
Permerror异常终止，向上级返回 permerror。
None异常终止，向上级返回 permerror（被引用域未发布有效 SPF 记录属于策略配置错误）。

例如，域名 example.com 发布了记录：

v=spf1 include:_spf.example.net -all

若发信客户端 IP 在 _spf.example.net 的子评估中返回了 fail、softfail 或 neutral，这仅表示该 include 机制未发生匹配。父策略不会因此中断，而是继续向下执行，最终由 example.com 末尾的 -all 裁定总体结果为 fail。

7 种评估结果与本地策略处置

根据 RFC 7208 第 2.6 节与第 8 节，check_host() 的输出严格划分为 7 种状态。协议本身不规定强制的全局邮件拦截动作，最终如何处置交由接收端的本地策略决定：

评估状态状态触发原因协议建议的本地处理行为（RFC 7208 第 8 节）
None域名未发布 SPF TXT 记录，或未提取到有效域名。视同无策略，继续执行其他反垃圾与安全过滤。
Neutral匹配到 ? 限定词机制，或策略未匹配且默认隐式 ?all。必须（MUST）按与 none 完全一致的基线处置，不得仅因 neutral 比 none 采用更严厉的惩罚；其余独立过滤照常执行。
Pass客户端 IP 成功匹配带有 + 的授权机制。验证通过，发信域对此会话承担信誉责任。
Fail客户端 IP 匹配带有 - 的机制（显式未授权）。由本地策略决定接受或拒绝：若选择在 SMTP 会话期间拒绝，建议（SHOULD）使用 550 状态码并在支持时附带 5.7.1 增强状态码；若选择接受，建议在邮件头部记录结果供后续处理。
Softfail客户端 IP 匹配带有 ~ 的机制（弱未授权）。属于弱未授权声明。接收端软件不应（SHOULD NOT）仅凭此结果直接拒绝邮件，可辅以更严格的内容过滤或灰名单机制观察。
Temperror评估遭遇 DNS 暂时性故障（如查询超时、SERVFAIL）。属于临时性错误。若选择在 SMTP 会话中拒绝，建议使用 451 4.4.3 临时错误以便发信方后续重试；也可选择放行并在头部标明状态。
Permerror策略存在永久性错误（如存在多条 SPF 记录、语法非法、超出 DNS 评估预算等）。属于需要发信域管理员介入修正的配置错误。若选择拒绝，建议使用 550 5.5.2 状态码。

当邮件被接收后，接收端通常在邮件头部记录验证状态（RFC 7208 第 9 节）。常见的标准跟踪字段为 Received-SPF，记录详尽的评估入参与推导依据；也可采用包含更多综合认证结果的 Authentication-Results 头部，供下游组件或收件人邮件用户代理（Message User Agent，MUA）展示安全状态。

DNS 评估预算与防护限制

SPF 验证依赖 DNS 解析，为了防止恶意方构造极端 SPF 记录发起拒绝服务攻击或利用验证器放大 DNS 查询流量，RFC 7208 设定了严密的操作预算限制：

1. 触发 DNS 查询的项（term）评估上限（10 次预算）

根据 RFC 7208 第 4.6.4 节规定：

  • 凡在评估过程中会触发 DNS 查询的特定项（term，指机制或修饰符，包括 include、a、mx、ptr、exists 以及 redirect），在整个 check_host() 评估流程中累计触发的项数量总计绝不能超过 10 个（MUST NOT exceed 10）。
  • 该计数器在所有的递归嵌套（例如多层嵌套的 include 或链式 redirect）中全局共享累加。
  • 一旦该计数器超过 10，验证器必须立即终止评估并返回 permerror。
  • 不需要执行 DNS 解析的项（如 all、ip4、ip6）以及在会话阶段不执行即时查询的 exp 修饰符，不计入这 10 次项评估预算。
  • 此外，验证器可以使用本地 DNS 缓存；此项限制是针对评估逻辑中触发 DNS 查询的项总数设立的硬性上限，而非仅针对底层网络报文计数。

2. MX 与 PTR 记录评估引发的附加地址查询限制

在上述全局 10 次项预算之外，RFC 7208 第 4.6.4 节对单个 MX 与 PTR 机制展开时的地址解析施加了单独限制：

  • 在评估 mx 机制时，除了该机制本身计入全局 10 次预算外，评估每个 MX 记录所引发的 A 或 AAAA 地址记录查询不得超过 10 次。若超出此限制，该 mx 机制必须产生 permerror。
  • 在评估 ptr 机制（以及展开 %{p} 宏）时，除了逆向 PTR 查询计入全局 10 次预算外，评估每个 PTR 记录所引发的正向 A 或 AAAA 地址记录查询同样不得超过 10 次；若超出此限制，验证器必须直接忽略第 10 条之后的所有记录。

3. 空查询（Void Lookups）限制

RFC 7208 第 4.6.4 与 11.1 节指出，针对指向不存在域名的探测攻击，验证器应对返回空答案（RCODE 0 但无记录）或域名不存在（RCODE 3，NXDOMAIN）的查询（即“空查询”，Void Lookup）施加限制：

  • 协议建议（SHOULD），验证器应限制空查询次数，默认推荐上限为 2 次（实现上可提供可配置参数）。
  • 若单次评估中空查询次数超出该限制，验证器应以 permerror 异常退出。

邮件转发与中介处理的验证边界

SPF 的根本特性在于：它将发件人域名授权绑定在直接建立 TCP 连接的客户端 IP 地址上。这一模型在端到端直投时工作良好，但在涉及中介转发的场景下存在明确的验证边界（RFC 7208 第 10.3 节与附录 D）。

1. 传统自动转发场景下的验证表现

考虑以下具体拓扑示例：

原始发件域 (example.org, SPF 记录为 "v=spf1 ip4:198.51.100.1 -all")
       │
       ▼ (1) 发送信件 (客户端 IP: 198.51.100.1, MAIL FROM: alice@example.org)
中继转发服务器 (example.net, IP: 203.0.113.50)
       │
       ▼ (2) 转发信件 (保持 MAIL FROM: alice@example.org)
最终收件网关 (example.com)

在上述设定下：

  1. 发件人 alice@example.org 通过授权的服务器（IP: 198.51.100.1）将信件投递至 example.net。此时 example.net 执行 SPF 校验，客户端 IP 匹配 example.org 的授权规则，判定为 pass。
  2. 用户在 example.net 配置了转发规则，服务器将信件重新投递给外部的 example.com。在本例中，转发服务器保持原始信封不变（仍为 MAIL FROM: <alice@example.org>）。
  3. 收件网关 example.com 接收到 TCP 连接，此时直接相连的客户端 IP 为中继主机的 203.0.113.50。
  4. example.com 针对 example.org 的策略进行评估。在假定 DNS 正常响应且策略未包含中继 IP 的情况下，由于 203.0.113.50 未列入 example.org 的允许列表中，评估会触发末尾的 -all 而判定为 fail。
  5. 若 example.com 的本地策略配置了在 fail 时直接拒收邮件，该封原本合法的转发邮件就会被拦截。

2. 中介服务（Mediators）的处理机制

RFC 7208 第 10.3 节与附录 D.2 指明，邮件列表与转发服务属于中介服务角色：

  • 重写反向路径：中介服务可以将信封中的 MAIL FROM 改写为中介服务自身管辖的域名（例如列表管理地址），并在该域名的 DNS 中发布允许自身服务器发信的 SPF 记录。此时，收件端 MTA 校验的是中介域名的发信授权，在策略匹配且正常解析时能够产生 pass 结果。采用此方案时，退信会返回给中介服务处理，中介需具备将退信重新关联或通知原发件人的映射能力。
  • 接收端的可信中介策略：收件端若明确信任特定中介服务，可在本地策略中对已知的中介来源 IP 跳过 SPF 校验，或者利用其他会话信息调整判断逻辑（附录 D.3）。
