Postfix 的 cleanup 处理与消息入队边界

2021年11月3日
|

在基于简单邮件传输协议（Simple Mail Transfer Protocol，SMTP，RFC 5321 #）的普通邮件接收交互中，邮件传输代理（mail transfer agent，MTA）在接收端完成 DATA 内容传输（CRLF.CRLF）后，需要明确界定接收责任的转移点。在普通入队投递流程中，服务端只有在完成持久化入队或按策略完成终结动作后，才向发送方返回 250 OK 确认应答。

在 Postfix 架构中，该队列前处理防线由独立的 cleanup(8) 守护进程承担。无论是来自 smtpd(8) 的网络接入，还是来自本地提交组件，消息数据与控制指令都会通过进程间通信（inter-process communication，IPC）流经 cleanup 进行信封解析、头部检查、规范化改写、资源限制评估，并最终在 incoming 队列中完成提交。本文基于 Postfix 3.6.2 源码 #，梳理其记录流结构、状态机切换、改写限制以及落盘确认边界。

记录流架构与队列文件布局

Postfix 队列文件并非松散的纯文本文件，而是由类型与长度界定的二进制/文本混合记录流（record stream，见 src/global/rec_type.h #）。

整个队列文件在物理布局上按阶段写入，依次由三个逻辑区段组成：

  1. 信封区段（Envelope Segment）：以占位记录 REC_TYPE_SIZE（C）开头，随后记录到达时间（REC_TYPE_TIME）、发件人（REC_TYPE_FROM）、收件人列表（REC_TYPE_RCPT）及各种属性。
  2. 消息内容区段（Message Content Segment）：以 REC_TYPE_MESG（M）记录标记起始，存储邮件头部和正文。每行内容以普通记录（REC_TYPE_NORM）写入；若单行超出 var_line_limit 配置，则切片为连续的长数据记录（REC_TYPE_CONT）。
  3. 提取信息区段（Extracted Segment）：以 REC_TYPE_XTRA（X）记录起始，记录从头部解析提取的元数据或由 cleanup 计算补充的内部属性，最终以严格的结束记录 REC_TYPE_END（E）作为文件完整的封顶边界。

在 src/cleanup/cleanup_out.c # 中，cleanup_out() 函数实现记录输出与超长行切片：当文本行长度超过行长限制时，循环将其切成固定长度的 REC_TYPE_CONT 块，最后以剩余长度写入原始类型。下游读取消息内容的程序可按 CONT/NORM 重建逻辑行，切片操作在逻辑语义上等价于原文本行，不是物理截断。若底层写文件返回 EFBIG 错误，cleanup 置位 CLEANUP_STAT_SIZE；其余写入失败则置位 CLEANUP_STAT_WRITE。

分层大小配额限制

邮件大小的管控在系统内是分层生效的。在网络接入层，smtpd 通过流式读取的字节计数（见 smtpd/smtpd.c #）进行早期拦截；而在 cleanup 进程中，cleanup_post_jail()（见 src/cleanup/cleanup_init.c #）在启用大小限制时调用底层的 set_file_limit(var_message_limit)，其中 message_size_limit 对应源码变量 var_message_limit。该资源限制直接约束整个队列文件的磁盘占用，因而不仅包含邮件正文，还涵盖了信封记录、路由属性以及提取区开销。此外，附件编码后的消息大小与原始附件额度也不同，业务设计中的原始附件额度不能等同于底层队列文件的大小预算，必须为信封与记录元数据保留合理安全裕量。

会话流程与状态机流转

在 src/cleanup/cleanup.c 的核心驱动函数 cleanup_service() # 中，cleanup 为每封消息维护 CLEANUP_STATE，其内部通过处理函数指针 state->action 实现阶段状态机的递进流转：

客户端连接 -> cleanup_open() (创建 incoming 文件，分配 queue_id)
        -> 向前端回传 queue_id 与协议版本
        -> 读取前端控制标记 (flags 与 err_mask 初始化)
        -> state->action: cleanup_envelope (解析信封 REC_TYPE_FROM / RCPT 等)
        -> 遇到 REC_TYPE_MESG -> state->action 切换为 cleanup_message (处理头部与正文)
        -> 遇到 REC_TYPE_XTRA -> state->action 切换为 cleanup_extracted (提取元数据与收尾)
        -> 遇到 REC_TYPE_END -> 循环接收结束
        -> cleanup_flush() (首部更新、落盘、权限变更与完成确认)
        -> 向前端回传 MAIL_ATTR_STATUS 与原因说明

在建立会话之初，cleanup_open() 内部通过 mail_stream_file() 在 incoming 队列目录下创建文件并生成 queue_id。紧接着，cleanup 立即通过 IPC 将该 queue_id 回传给前端 smtpd。

前端日志中此时记录的 queue_id 仅代表本次会话在磁盘上分配的队列文件标识，绝对不代表该邮件已经成功入队。此时甚至尚未接收到具体的正文数据。

在随后的记录读取循环中，cleanup 持续累积错误位 state->errs。若在传输过程中遭遇错误（如大小超限或格式非法导致 CLEANUP_OUT_OK(state) 变为假），cleanup 不会立即强行关闭套接字，而是在仍有输入的情况下继续读取丢弃数据，尽量排空到 REC_TYPE_END（或直到读取出错）。这种处理能尽量让先写后读的前端进入接收状态报告的阶段。

规范化改写、多用途互联网邮件扩展检查与安全边界

cleanup 承担了由 Postfix 配置决定的规范化处理，但其职责范围与独立的安全网关存在明确的工程分界：

  1. 信封地址规范化： 在 src/cleanup/cleanup_addr.c # 中，信封发件人与收件人分别通过 cleanup_addr_sender() 与 cleanup_addr_recipient() 处理。地址首先经由 cleanup_rewrite_internal() 补充本地上下文，随后根据配置的 flags 决定是否应用规范化映射（canonical_maps）与域名伪装（masquerade_domains）。如果映射查询发生临时错误，cleanup 会将状态标记为临时错误（置位 CLEANUP_STAT_WRITE）。 信封地址与正文头部的地址改写规则及配置上下文并不相同，邮件头部的 From: 绝不会直接覆盖或自动成为信封的发件人（MAIL FROM）。
  2. 头部检查与条件补全： 在 src/cleanup/cleanup_message.c # 中，cleanup 通过多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）状态机解析邮件头部与结构。 解析头部由 cleanup_header_callback() 处理，可根据头选项 HDR_OPT_DROP 剔除 Bcc:，并可另外通过 header_checks 匹配丢弃或拒绝等动作。 而缺失头部的补全则位于 cleanup_header_done_callback()：只有在满足重写上下文（hdr_rewrite_context）或者显式配置了总是补充缺失头（always_add_missing_headers，由源码变量 var_always_add_hdrs 控制）时，才会条件性地补全 Message-Id:、Date:、From: 等头部，而非无条件全量补充。
  3. 安全扫描边界： 虽然 cleanup 支持配置 header_checks、body_checks 以及接入邮件过滤接口（Milter），但其核心定位是协议清洗、结构规范化与状态流转。它不会对压缩包或多层嵌套附件执行深度解构、恶意宏分析或行为沙箱检测。开发邮件系统时，不能将入队阶段的结构规范化等同于建立了完整的反病毒与反垃圾邮件安全防护。

提交与最终应答

当全部记录接收完毕后，流程进入 cleanup_flush()（位于 src/cleanup/cleanup_api.c #）执行最终提交与状态收尾。

索引更新与 cleanup_final

在最终持久化之前，cleanup_final()（位于 src/cleanup/cleanup_final.c #）被触发。它首先调用 vstream_fflush() 冲刷应用层写缓冲区，随后通过 vstream_fseek() 将文件指针定位至起始位置，将根据提取区与内容区偏移之差计算的内容段大小、消息内容起始偏移（data_offset，包含邮件头部）、有效收件人计数（rcpt_count）以及消息内容长度等字段重新格式化写入文件头部的 REC_TYPE_SIZE 记录，使下游投递调度进程能够直接索引文件结构。

落盘提交机制：mail_stream_finish_file

与常见的“写入临时目录后通过原子重命名移动到工作队列”不同，Postfix 采用直接就地初始化的机制：

  1. 原地创建与权限限制：文件自创建开始就位于 incoming 队列目录下，但初始权限为严格限制（通常未赋予执行位 +x），下游队列管理器在扫描时会自动忽略未就绪的文件。
  2. 同步与权限赋予： 在 src/global/mail_stream.c 的 mail_stream_finish_file() # 中：
    • 显式刷新应用层缓冲 vstream_fflush()。
    • 调用 fchmod(fd, 0700 | info->mode) 为文件增加执行权限位。
    • 在编译并开启 HAS_FSYNC 条件的系统上，显式调用 fsync(fd) 请求操作系统内核将脏数据同步至底层存储介质。这一系统调用的成功返回依赖于宿主操作系统与底层存储硬件对于持久性刷盘语义的实现。
    • 需要注意，权限位设置早于 fsync() 执行完成，单一的执行位并不能证明邮件已完整提交；文件必须具有包含 REC_TYPE_END 的完整记录结构才会被队列识别。
  3. 关闭校验： 接着调用 info->close(info->stream) 关闭文件。即使前面的写入和 fsync() 没有报错，close() 调用依然可能因网络文件系统冲刷或元数据提交失败而返回错误。若 close() 返回失败，状态仍会被标记为写入错误。
  4. 下游通知：唯有持久化和文件关闭全过程无误返回 CLEANUP_STAT_OK 时，若配置了对应的投递服务，系统才会调用 mail_trigger() 发送通知唤醒下游队列调度。下游被唤醒并不意味着邮件已经投递到收件人，仅代表正式进入投递调度管辖。
  5. 责任转移与清理钩子解除：一旦确认持久化完成且状态正常，cleanup 会立即将全局清理路径变量置空（cleanup_path = 0），以此解除运行时的异常清理钩子。源码注释特别强调：“宁可发生重复投递，也绝不能在已承诺接收后丢失邮件”。

终结动作的特殊状态语义

在 cleanup_flush() 中，部分终结状态具有偏离常规队列流转的特殊语义：

  • 策略丢弃（DISCARD）：若访问规则命中丢弃指令，cleanup 会将错误码归零（state->errs = 0），向 SMTP 前端报告成功（返回 250 应答），但在物理层面会主动调用 REMOVE(cleanup_path) 删除该队列文件。这种“向客户端伪装成功但在底层静默销毁”的行为是反垃圾防护中的有意设计。
  • 本地来源退信（BOUNCE）：对于本地特定来源（如通过本地命令行提交或特定转发）产生的错误，cleanup 可能会就地生成退信通知，在通知发送成功后重置错误码并请求删除当前队列文件，其应答状态并不代表邮件保留在 incoming 队列中。
  • 挂起保留（HOLD）：若命中保留策略，cleanup 会在关闭文件前通过 mail_stream_ctl() 提前将队列目标切换为 hold 队列并调整文件路径，避免其直接流入常规调度队列。

内部状态码与 SMTP 状态映射

cleanup 完成后将处理状态传回前端服务。src/global/cleanup_strerror.c # 定义了内部状态位与对外应答状态之间的转换关系：

CLEANUP_STAT_OK：

250 2.0.0

处理成功。在普通入队投递流程中代表邮件已可靠提交至队列目录并移交调度管辖。

CLEANUP_STAT_SIZE：

552 5.3.4

邮件或队列文件大小超出配置限制，属于永久性拒绝。

CLEANUP_STAT_WRITE：

451 4.3.0

队列文件写入、表查询或落盘关闭失败，属于临时拒绝。

CLEANUP_STAT_BAD：

451 4.3.0

内部协议异常或数据记录结构损坏，属于临时拒绝。

CLEANUP_STAT_DEFER：

451 4.7.1

服务临时不可用，要求客户端稍后重试，属于临时拒绝。

CLEANUP_STAT_RCPT：

550 5.1.0

未能指定任何有效收件人，属于永久性拒绝。

在 smtpd 的实现中（见 smtpd/smtpd.c 3620–3740 行 #），接收端必须完整等待从 cleanup 获得的最终处理状态。只有在状态为 CLEANUP_STAT_OK 时，才向客户端发出 250 2.0.0 Ok: queued as <queue_id>。

应用层集成设计考量

基于上述底层机制，在设计自研 Webmail、API 发送中台或邮件网关时，需要遵循以下工程推导出的设计原则：

  1. 已发送副本与双写补偿： MTA 入队只负责邮件在传输队列中的流转，不会为用户自动保存已发送邮件（Sent 文件夹）。业务系统中的“发送并保存”属于跨系统的双写操作。若 MTA 返回 250 确认后，本地存储写入已发送副本失败，应用层的重试补偿机制只能针对已发送存储的副本写入进行重试，切勿盲目向 MTA 重新发起 SMTP 发送请求，否则将导致收件方收到重复邮件。
  2. 应用层去重设计： Postfix 依赖自身分配的 queue_id 管理队列，不会以 Message-ID 头字段自动保证跨 SMTP 事务去重。若业务客户端在网络超时等场景下可能重发邮件，应用层必须在网关前端基于业务全局唯一标识（如自研提交 ID）设计幂等防重机制。
  3. 原始邮件审计存证： 如果业务有严格的合规审计或取证需求，要求保留发件人提交的不可变原始报文，应当在邮件提交至 cleanup 之前由接入网关留存原始数据。因为 cleanup 在处理过程中可能补全缺失头部、折叠清洗格式或改写地址，不可直接以队列内部文件的内容替代原始提交凭证。

未运行的故障注入验证设计

为了在离线测试环境中检验入队失败路径的契约行为，可以通过故障注入验证推导出的状态映射。以下为推导的测试场景设计（注：本方案属于工程推导设计，未执行这些测试）：

场景一：文件大小超限

  • 模拟注入方式：在单元隔离测试中对记录输入设置桩（stub），使 cleanup 写入触发并返回 EFBIG。
  • 内部路径与状态：cleanup_out() 捕获 EFBIG，置位 CLEANUP_STAT_SIZE，在有后续输入时排空 IPC 到 REC_TYPE_END，最后删除未完成的队列文件。
  • 对外预期响应：
552 5.3.4 message file too big

属于永久性拒绝，发送方不应直接原样重试。

场景二：持久化提交中断

  • 模拟注入方式：在 fsync() 或 close() 阶段注入 EIO 或 ENOSPC 故障。
  • 内部路径与状态：mail_stream_finish_file() 捕获返回错误，置位 CLEANUP_STAT_WRITE，取消下游唤醒并删除残余队列文件。
  • 对外预期响应：
451 4.3.0 queue file write error

属于临时拒绝，发送方可稍后重新发起投递。

场景三：响应断链不确定窗口

  • 模拟注入方式：确保服务端 cleanup 已完全完成持久化提交并生成 250 应答，但在网络发送前拦截丢弃 TCP 响应。
  • 内部路径与状态：队列文件已在 incoming 目录中完成持久化，后续调度投递正常推进；客户端因等待应答超时判定传输失败而发起重试。
  • 对外预期响应：客户端无响应。此场景下服务端已产生投递责任，需依赖应用层幂等机制应对后续重复重试。

综上所述，Postfix 的 cleanup 服务通过记录流抽象、阶段状态机流转与严格的刷盘关闭校验，为邮件入队提供了明确的接收责任划分与状态边界。
