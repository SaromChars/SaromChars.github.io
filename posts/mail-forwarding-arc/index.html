邮件转发、邮件列表与 ARC

2021年9月19日
|

在互联网邮件传输体系中，发件人策略框架（Sender Policy Framework，SPF）基于连接发起方的源 IP 地址评估发信权限，域名密钥识别邮件（DomainKeys Identified Mail，DKIM）则通过发信域的数字签名（digital signature）保护邮件指定头部与正文的完整性。基于域名的消息认证、报告与一致性规范（Domain-based Message Authentication, Reporting, and Conformance，DMARC）进一步将这两项机制与邮件头部的作者地址（RFC 5322 From）进行标识符对齐（Identifier Alignment），允许域所有者在域名系统（Domain Name System，DNS）中声明针对未对齐邮件的处置偏好（如隔离 quarantine 或拒收 reject）。

当邮件直接从发信域的出站服务器送达目的域时，这套验证机制运行通畅。然而，当邮件流经第三方节点——例如个人邮箱设置的自动转发（Forwarding / Aliasing）、邮件列表（Mailing Lists）、或者跨域内容安全网关时，传输路径与报文内容可能发生变化。IETF 信息性备忘录 RFC 7960 专门整理了 DMARC 与此类“间接邮件流（Indirect Email Flows）”之间的互操作问题。为了在经历中介转交后仍能向后续节点传递前序处理中的认证记录，IETF 制定了实验性协议认证接收链（Authenticated Received Chain，ARC，RFC 8617）。

间接邮件流中的认证变化

在邮件中继与转交过程中，中介节点对信封地址、传输连接以及报文内容的改动，会对 SPF 与 DKIM 的评估条件带来不同程度的影响（RFC 7960 第 3 节）。

1. 自动转发与 SPF 评估

自动转发通常由接收端配置的别名（Alias）或重定向规则触发。中介服务器在转交邮件时，通常会建立新的简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）会话将邮件递交给下一跳邮件传输代理（Message Transfer Agent，MTA）。

在此会话中，下游接收方观察到的 TCP 连接来源是中间转发节点的 IP 地址：

  • 若转发节点保留原始信封发件人（RFC 5321 MAIL FROM，例如 user@example.com），下游接收方在查询 example.com 的 SPF 记录时，假设 DNS 查询正常且无更早机制匹配，若该转发节点的 IP 未包含在原始域授权列表且策略以 -all 终结，SPF 判定将返回 fail；
  • 若转发节点将信封 MAIL FROM 重写为中介自身的独立域名（例如采用可变信封投递地址技术以便接收退信），虽然该中介域名的 SPF 可以通过，但该域名若与邮件头部声明的原作者组织域（如 From: user@example.com）不属于同一组织域，则依然无法满足 DMARC 的 SPF 标识符对齐要求。

2. 邮件列表与 DKIM 签名影响

邮件列表管理器（Mailing List Manager，MLM）接收订阅者的投稿后，会向全体列表成员分发邮件。在此分发过程中，邮件列表软件通常会执行一些既定的操作（RFC 7960 第 3.2.3 节）：

  • 修改邮件头（Header Fields）：在 Subject 头部追加列表标签（如 [dev-core]），新增 List-Id、List-Unsubscribe 等列表管理头，或者对已有头部进行格式调整；
  • 修改邮件正文（Body）：在正文末尾追加列表说明、退订链接或免责声明，甚至修改部分 MIME 结构的编码格式。

DKIM 验证数字签名（验签，signature verification）的机制依赖于发信端对选定邮件头与正文摘要（digest）计算的密码学签名。中继转发若保持原报文与签名头字段完全未变，原有 DKIM 签名依然可能正常通过验签；但如果中继修改了已被纳入签名范围（h= 标签所列）的头部，或者改变了正文内容并使得规范化后的正文哈希（通过哈希函数（hash function）计算的 bh=）发生变动，下游接收端计算出的摘要将与签名记录不符，导致该 DKIM 签名判定为 fail。

3. DMARC 与缓解方案

若一封邮件在流转中同时失去了有效的 SPF 对齐，且既有的 DKIM 签名因内容被修改而全部失效，下游接收端在执行 DMARC 评估时将判定为不合规。如果作者域在 DNS 中发布了 p=reject 策略，且接收端未配置任何本地偏离策略，该邮件便可能在 SMTP 阶段被拒绝接收，影响正常通信。

在 RFC 7960 第 4 节中，讨论了当时已被采用的若干可选缓解策略，但它们在不同场景下各有条件限制与工程代价：

缓解方式常见做法潜在影响与限制条件
From 头部重写将 From: 改写为列表管理者域的地址，将原发件人挪至 Reply-To:改变发信人名义；部分邮件用户代理（Message User Agent，MUA）在执行“回复全部”或归档整理时可能偏离用户习惯
消息封装（MIME encapsulation）将原始邮件作为附件打包进 message/rfc822，外层以列表地址发出外层签名独立合规；但部分移动端或特定 MUA 对多层附件解析与展示支持有限
接收端本地策略覆写接收端维护已知转发节点的特征或列表，在评估时执行本地偏离（Local Policy Override）需接收端主动维护规则；小规模或长尾中继不易覆盖，若规则过于宽松可能带来误判风险
保持原始报文未修改邮件列表放弃修改主题前缀与页脚，以透明转发保留 DKIM 签名能够最大程度保护原有 DKIM 签名；但列表失去了添加控制信息与附注文本的灵活性

为了在允许中间节点正常处理邮件的同时，向后续接收端提供结构化的历史认证依据，IETF 提出了实验性的 ARC 协议。

ARC 核心概念与三元组头部结构

认证接收链（ARC，RFC 8617）是一项实验性协议。它的设计目标并非阻止中间节点修改邮件，而是在报文流经各个处理机构（管理域，Administrative Management Domain，ADMD）时，通过一组带有数字签名的头部构建监管链（Chain of Custody）。

当支持 ARC 的中继节点接收到邮件时，首先记录该节点入站时所测得的认证评估，并在转发出站前，将这一认证结果连同对当前报文及历史链条的数字签名以特定头部附加至邮件中。

这一组数据单元被称为 ARC 集（ARC Set）。在每一个处理跳步上，添加的 ARC 集中必须严格包含且仅包含一个以下三类头部字段（RFC 8617 第 4.1 节）：

Note

下列字段仅展示 ARC 头部的语法结构与标签排布。为便于阅读，b= 与 bh= 中的实际签名字节与摘要数据已作省略示意，并非可验签的真实抓包报文：

ARC-Seal: i=1; a=rsa-sha256; cv=none; d=lists.example.org; s=dk-lists; t=1632010000; b=...
ARC-Message-Signature: i=1; a=rsa-sha256; c=relaxed/relaxed; d=lists.example.org;
        h=message-id:date:from:to:subject; s=dk-lists; t=1632010000; bh=...; b=...
ARC-Authentication-Results: i=1; lists.example.org;
        spf=pass smtp.mfrom=alice@example.com;
        dkim=pass (1024-bit key) header.i=@example.com;
        dmarc=pass

1. ARC-Authentication-Results（AAR）

AAR 头部记录了当前参与 ADMD 在刚刚接收到该邮件时，针对上游连接执行各项认证所得到的评估陈述（RFC 8617 第 4.1.1 节）。

  • 其语法参考了常规 Authentication-Results（RFC 8601）规范，记录入站时 SPF、DKIM、DMARC 等机制的检测结果；
  • 增加了实例序列标签 i=（Instance Tag），指示该记录属于第几个 ARC Set；
  • 每个 ARC Set 仅允许存在一个 AAR 头部。如果当前 ADMD 内部生成了多个常规的入站认证头，必须将其综合为单个 AAR 头部载荷。

2. ARC-Message-Signature（AMS）

AMS 头部负责由当前节点对其转发时的邮件内容承担签名责任（RFC 8617 第 4.1.2 节）。

  • 语法与 DKIM-Signature（RFC 6376）类似，对指定的邮件头字段（h=）以及通过哈希函数计算的正文摘要（bh=）用本地私钥生成数字签名 b=；
  • AMS 不使用 DKIM 的 v= 版本标签（若遇到必须忽略），也不使用 DKIM 的 i=（Agent or User Identifier，AUID）标签，统一由实例标签 i= 标识所属序号；
  • 签名防污染要求：AMS 签名的头部列表（h= 标签）绝对不能包含（MUST NOT）常规的 Authentication-Results 头，也绝对不能包含（MUST NOT）任何 ARC 相关头部（AAR、AMS、AS）；但应当（SHOULD）包含邮件中已存在的常规 DKIM-Signature 头，以保留前序签名的完整性状态。

3. ARC-Seal（AS）

AS 负责将前序各跳记录的认证陈述与消息签名串接成一条不可随意篡改的有序链条（RFC 8617 第 4.1.3 与 5.1.1 节）：

  • 不签正文：AS 签名的计算对象完全不涵盖邮件正文（Body），因此没有 bh= 标签，也不对正文执行规范化；
  • 标签限制：头部规范化仅支持松弛模式（relaxed）；仅支持 i、a、b、d、s、t 以及 ARC 特有的 cv（Chain Validation）标签。严禁出现（MUST NOT）h= 标签，若在 AS 中检测到 h= 标签，验证器必须判定链状态为 cv=fail；
  • 签名覆盖范围：AS 的签名对象为从实例 1 开始直到当前实例 N 的所有 ARC Set 头部。在每个实例集合内，严格按以下顺序送入哈希函数：
    1. ARC-Authentication-Results
    2. ARC-Message-Signature
    3. ARC-Seal（当前实例自身的 AS 在计算摘要时，b= 标签值按规范置为空）。
+---------------------------------------------------------------+
| ARC 监管链结构与 AS 保护范围（两跳中继示意）                  |
|                                                               |
|  [ARC Set 1]  (i=1，首个支持 ARC 的中继节点添加)               |
|    - AAR: i=1 (记录该节点入站时检测到的认证状态)              |
|    - AMS: i=1 (覆盖该节点转发时选定的 Header 与 Body)         |
|    - AS:  i=1, cv=none                                        |
|      ▲                                                        |
|      │ 密封保护 (Hash 覆盖 Set 1 全部 ARC 头)                 |
|                                                               |
|  [ARC Set 2]  (i=2，第二个支持 ARC 的中继节点添加)              |
|    - AAR: i=2 (记录从上一跳接收时的入站认证结果)              |
|    - AMS: i=2 (覆盖本节点再次修改后的 Header 与 Body)         |
|    - AS:  i=2, cv=pass                                        |
|      ▲                                                        |
|      └──────── 密封保护 (Hash 严格按序覆盖 Set 1 与 Set 2 ARC 头) |
+---------------------------------------------------------------+

协议动作：密封与验证算法流程

在流转链路中，支持 ARC 的节点分别承担密封者（Sealer）或验证者（Validator）的角色。

1. 密封者（Sealer）动作

中间节点在向外转交邮件时，按下列顺序执行操作（RFC 8617 第 5.1 节）：

  1. 完成所有报文修改：对邮件正文追加文本、修改头部或添加常规 DKIM 签名等操作，必须在密封前全部完成（MUST）；
  2. 入站状态检查：若邮件入站时接收到的链条最高序号 AS 已经声明为 cv=fail，说明上游链条此前已判定损坏，密封者无需继续构造后续合法链条（算法在此停止）；
  3. 计算实例编号：若邮件尚无 ARC 链，实例号设为 i=1；若已有链条，则取最高实例号加 1（取值范围为 1 至 50 的整数）；
  4. 附加 ARC Set：
    • 生成 AAR（填入本节点入站认证结果）；
    • 生成 AMS（对修改后的正文与选定头部签名）；
    • 生成 AS：根据入站验证结果设置 cv 标签（此前无链为 none，前序链有效为 pass，本节点新检测到前序链异常则为 fail），按规范顺序对全部 ARC 头部计算签名。
Note

失效链密封范围（RFC 8617 第 5.1.2 节）： 若本节点在入站验证时新发现上游链条损坏，而本地策略仍决定标记 cv=fail 密封转发，为避免在畸形或断裂的历史头部上产生不确定的哈希行为，该 AS 签名的覆盖范围必须仅包含本节点自身生成的这组最新 ARC Set 头部，视同只有这一组头部存在。

2. 验证者（Validator）校验流程

接收端或下游支持 ARC 的 MTA，按以下步骤校验链条结构与签名有效性（RFC 8617 第 5.2 节）：

开始验证
  │
  ├─ 1. 收集所有 ARC Set (统计最大序号 N)
  │      ├─ 无任何 ARC Set? ─────────► [链状态 cv=none，验证终止]
  │      └─ N > 50? ─────────────────► [链状态 cv=fail，验证终止]
  │
  ├─ 2. 检查最高编号 Set N 的 AS 头部
  │      └─ 其 cv 标签声明为 "fail"? ─► [链状态 cv=fail，验证终止]
  │
  ├─ 3. 结构完整性校验
  │      ├─ 每个 Set 是否严格仅含 AAR、AMS、AS 各一个?
  │      ├─ 实例序列 i 是否严格呈现 1..N 连续单调递增无间断与重复?
  │      └─ cv 标签是否合规: i=1 必须为 none，i>1 必须为 pass?
  │      (任一不符直接终止) ─────────► [链状态 cv=fail，验证终止]
  │
  ├─ 4. 验证最新 AMS (i=N)
  │      └─ 验签失败? ───────────────► [链状态 cv=fail，验证终止]
  │
  ├─ 5. [可选] 回溯检查历史 AMS (从 i=N-1 递减至 1)
  │      (定位 oldest-pass，可帮助确认仍能对当前报文验签通过的历史签名范围；
  │       旧 AMS 验签失败不影响整链有效性，也不能作为内容由特定跳步修改的确定性取证)
  │
  ├─ 6. 验证全量 AS (从 i=N 递减验签至 i=1)
  │      └─ 任一 AS 验签失败? ────────► [链状态 cv=fail，验证终止]
  │
  └─ 7. 全部通过 ─────────────────────► [链状态 cv=pass]

3. 验证失败的性质与基线处理规则

在理解验证失败时，需要区分链状态、处理基线与 SMTP 处置动作：

  • 链失败判定具有永久性（RFC 8617 第 5.2.1 节）：ARC 链条的验证是一次性的完整性计算。验证过程中的任何异常——包括查询签名公钥时遭遇的 DNS 超时或临时网络故障——在协议定义下均使该条链的状态直接判定为 cv=fail，不可在后续重试中对该链进行部分修复或拼接；
  • 必须等同于无 ARC 邮件（第 5.2 节）：cv=fail 仅代表该条 ARC 链条本身失效，不能提供有效的历史认证补救证据。根据规范要求，链验证失败的邮件必须按完全没有 ARC 链的普通邮件同等对待（MUST be treated the same as a message with no Authenticated Received Chain）。它并不直接等同于邮件必须被永久丢弃，接收端应依据常规 SPF、DKIM 及本地安全策略继续评估；
  • SMTP 响应码选择（第 5.2.2 节）：若接收端在综合评估后决定在 SMTP 事务期间拒绝接收该邮件，可以（MAY）使用增强状态码 5.7.29（ARC validation failure），也可以选用更通用的综合认证失败码 5.7.26（Multiple authentication checks failed），并配合相应的 SMTP 基本响应码（如 550）。

认证陈述与本地采信策略

当验证器得出 arc=pass 判定后，下游节点需要合理使用链条中包含的信息（RFC 8617 第 7 节）。

1. 签名能够证明的事实范围

根据 RFC 8617 第 9 节的安全考量，一封通过校验的 ARC 邮件（最新实例为 N）在密码学层面提供了如下证据：

  1. 消息来源归属：最新密封域（即 AS[N] 中声明的 d= 域）确实发出了与当前报文正文哈希及选定头部匹配的消息；
  2. 陈述未被篡改：AAR[N] 中所记录的认证结果在传输中未遭非授权改动，确为该密封域在入站时声称的评估记录；
  3. 前序链条完整：前序的 ARC 链条（从实例 1 到 N-1）在该密封域处理时客观存在，且其各级封印状态与记录吻合。

需要强调的是，密码学签名能够证明这些陈述属于对应的密封域，但并不能保证该域记录的陈述一定准确无误，也不证明该域本身可信。

2. 本地采信策略与 DMARC 偏离

当一封邮件由于中介转发导致当前 SPF 与 DKIM 均未通过 DMARC 对齐时，DMARC 处理流程可以作为本地策略（MAY as a matter of local policy）参考 ARC 链条中的历史陈述（RFC 8617 第 7.2.1 节）：

  • 检查链条中首个支持 ARC 的参与节点所记录的 AAR[1]（注意：AAR[1] 是首个添加 ARC 的中继节点视角，并不必然等同于全网绝对的第一跳连接）；
  • 若接收端通过本地配置确认相关密封域具备良好信誉或属于受信任的合作节点；
  • 且整条 ARC 链验证状态为 cv=pass，历史 AAR 记录显示原始域认证此前曾达到合规对齐；
  • 接收端可在本地策略中选择覆盖原有的未对齐判定，避免直接拒收邮件。这一覆盖是接收端自身的本地业务决策，ARC 验证通过本身并不产生必须投递入箱的协议保证。

3. DMARC 聚合报告中的覆盖反馈

当接收端因参考 ARC 信息而对 DMARC 判定执行本地偏离时，可以（MAY）在生成的 DMARC 聚合报告 XML 中通过 policy_evaluated 记录该情况（RFC 8617 第 7.2.2 节）：

<policy_evaluated>
  <disposition>none</disposition>
  <dkim>fail</dkim>
  <spf>fail</spf>
  <reason>
    <type>local_policy</type>
    <comment>arc=pass as[2].d=d2.example as[2].s=s2 as[1].d=d1.example as[1].s=s1 remote-ip[1]=192.0.2.10</comment>
  </reason>
</policy_evaluated>

此项记录向域所有者提供了接收端应用本地策略的反馈线索，但该报告并非完整物理路由的追踪记录，也不代表邮件最终被用户阅读的确认。

ARC 的采信条件与安全考虑

在部署与实现 ARC 时，核心原则在于理清密码学签名与业务信任之间的界限。RFC 8617 附录 A.2 与第 9 节对此给出了明确约束。

1. 签名不等于信任保证

  • ARC 不是信任框架（ARC is not a trust framework）：ARC 仅提供了一套验证传输历史记录完整性的密码学手段，它不包含任何对参与节点声誉或善意的评估机制；
  • 恶意发件人同样可以搭建符合标准的邮件服务器、配置合规的公私钥与 DNS 记录，为其发出的垃圾或仿冒邮件生成语法合规、验签通过的 ARC 头部（甚至在其控制的节点生成的 AAR 中填报伪造的认证通过结果）；
  • 如果接收系统将任意 arc=pass 结果无条件视为合法并放行，ARC 就可能被滥用为绕过源身份校验的途径。

2. 接收端的本地采信条件

接收端若要将 ARC 评估作为本地策略决策的输入，必须建立独立的采信机制：

  • 评估密封域的信誉：接收方需要自行判断链条中相关密封者（d= 域）的可信程度，例如参考长期通信声誉、行业认证或明确的业务合作关系；
  • 采信策略的选择：接收方可以选择相对保守的策略，要求整条链条上的每个中间节点均在受信任名单内；也可以选择只关注其直接对接的上一跳或特定知名中继节点的签署陈述。这些均属于接收方本地策略的选择范畴，而非协议强制的统一算法；
  • 防范重放风险（Replay Attacks）：ARC 沿用了基于域名的密码学签名机制，因此同样面临 RFC 6376 第 8.6 节讨论的重放风险（RFC 8617 第 9.5 节）。攻击者若截获带有合法 ARC 签名的报文，可能在签名与公钥有效期内将其重复投递给其他收件人。工程上接收方可按场景结合发送速率监测、报文查重或内容安全扫描等综合措施进行协同防范。

3. 资源开销与网络边界

部署 ARC 还会对系统的运行开销带来额外影响（RFC 8617 第 9.1 与 9.2 节）：

  • 报文头膨胀：每个中继跳步增加三个较长的文本头部，多跳转发会使邮件头部显著增大，可能触及部分老旧系统对头部总长度的解析上限；
  • DNS 查询负载：验证一条包含 N 个 ARC Set 的链条时，在不计 DNS 重定向（如 CNAME）的情况下理论上可能引入最多 2 * N 次 DNS 记录查询。不过在实际运行中，本地 DNS 缓存、遇到验证失败即终止算法的短路机制，以及攻击者伪造他人合法签名的难度，会在一定程度上限制无效查询的放大。
