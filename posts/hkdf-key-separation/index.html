KDF 怎样从共享秘密导出不同用途的密钥

更新于:2026年11月7日
|

在前文探讨 DH/ECDH 协商机制时，我们看到了通信双方如何安全地计算出一个相同的共享秘密（如有限域的 ZZ 或按协议编码的椭圆曲线共享点坐标）。

但是在讨论的 DH/ECDH 握手协议中，这个计算出的共享秘密不应直接当对称加密密钥使用。一方面，它在代数上并非严格的均匀随机分布；另一方面，一个现实的安全通信协议（如 TLS 1.3）在一次会话中往往需要多把不同职责的密钥：客户端向服务端发数据的加密密钥、服务端向客户端发数据的加密密钥、双方的初始化向量（initialization vector，IV），以及用于校验握手完整的 MAC 密钥。

如果直接复用同一把原始秘密处理所有任务，会超出既定安全分析的用途边界并带来交互风险。为了解决这一矛盾，现代协议广泛采用密钥派生函数（key derivation function，KDF），尤其是基于 HMAC 的密钥派生函数——HKDF（HMAC-based Key Derivation Function）。[RFC 5869 §1]

核心设计范式：Extract-then-Expand

RFC 5869 规范的 HKDF 将密钥派生过程严谨地解耦为两阶段：提取（Extract） 与 展开（Expand）。[RFC 5869 §1] · [RFC 5869 §2]

1. 提取阶段（HKDF-Extract）：熵的浓缩

  • 输入： 可选的盐（salt，若不提供则默认为 HashLen 长度的零字节串）和原始输入密钥材料（IKM，Input Keying Material）。[RFC 5869 §2.2]
  • 背景： 许多协议协商出来的原始秘密（例如 Diffie-Hellman 的输出）虽然对攻击者保密，但在统计分布上可能不完全均匀。在输入具有足够不可预测性（最小熵）的前提下，提取阶段的目标是将这些分散的熵平滑浓缩，生成一个在密码学上表现良好的伪随机密钥（PRK，Pseudorandom Key）。
  • 计算公式： 
    PRK = HMAC-Hash(salt, IKM)
    输出 PRK 的长度正好等于底层哈希函数的输出长度（HashLen，例如 SHA-256 为 32 字节）。

2. 展开阶段（HKDF-Expand）：按需派生与隔离

  • 输入： 提取出的 PRK、上下文信息标签（info）、以及期望输出的密钥字节长度 L。
  • 背景： 将 PRK 扩展为所需长度的密钥流（受限于最大长度约束），同时根据 info 参数确保不同用途的派生子密钥在密码学伪随机函数假设下相互隔离。
  • 计算公式： 通过循环迭代追加计数器块： 
    T(0) = ""

T(1) = HMAC-Hash(PRK, T(0) || info || 0x01) T(2) = HMAC-Hash(PRK, T(1) || info || 0x02) … OKM = first L octets of (T(1) || T(2) || …) 由于计数器仅为一个单字节，HKDF-Expand 限制输出长度为 L ≤ 255 × HashLen（例如对于 SHA-256，上限约为 8160 字节）。[RFC 5869 §2.3]

Salt 与 Info 的职责界定

许多人在使用 HKDF 时，容易混淆 salt 与 info 的角色：[RFC 5869 §3.1] · [RFC 5869 §3.2]

  1. Salt（盐）属于提取阶段：
    • 作用： 作为提取函数的独立随机因子，增强提取器的分析强度与源独立性。盐可以省略（此时采用全零串），也可以在多个提取实例中安全复用，并不强求每会话必须提供新鲜随机盐。
    • 保密性与独立性： salt 不需要保密。在某些协议（例如 IKEv2）中，若协议能保证交换的 Nonce 具备防篡改认证且满足独立性要求，可由 Nonce 形成 salt；但这是一种协议通用例子，并不是所有协议（例如 TLS 1.3）的固定取值方式。[RFC 5869 §3.1]
  2. Info（上下文标签）属于展开阶段：
    • 作用： 强制实施上下文绑定（Context Binding）与用途隔离（Key Separation）。
    • 内容： info 通常包含明确的协议标识、算法名称、密钥角色（如“client write key”、“server write key”）或特定的握手上下文摘要。
    • 隔离效果： 在 PRK 具备足够强度且底层 HMAC 满足伪随机函数假定的条件下，清晰不同的 info 能有效隔离不同用途：已知某一用途的子密钥通常无法推导其余用途的子密钥。但必须警惕：若底层 PRK 或初始 IKM 本身因熵不足被攻击者猜中，则所有基于此派生的子密钥都将一并沦陷。[RFC 5869 §3.2] · [RFC 5869 §3.4]

关键边界：HKDF 不是口令拉伸（PBKDF）的替代品

在工程选型中，必须清醒区分两种不同类型的 KDF：

  • 输入熵决定边界：
    • HKDF 是专门为“高熵”输入设计的（例如数百比特不可预测的 DH 共享秘密）。HKDF 执行的是极速的单次或少次 HMAC 计算，绝不凭空增加输入熵，也没有刻意拖慢计算的机制。[RFC 5869 §4] 如果输入是一个只有几位的人类口令（低熵），使用 HKDF 派生密钥极易遭受高速离线暴力枚举字典攻击。[RFC 8446 §2.2]
    • PBKDF（如 PBKDF2、scrypt）是专门为“低熵口令”设计的。正如在前文探讨口令存储中所述，口令派生必须刻意消耗计算循环或占用可调内存，通过人为抬高攻击者离线猜测的经济成本来防范穷举。

因此，绝不能用 HKDF 直接替代 PBKDF2 或 scrypt 去保护人类设置的登录口令。

典型应用：TLS 1.3 的分层密钥调度树

在 RFC 8446 规定的 TLS 1.3 中，HKDF 被用作协议状态机的核心密钥调度器：[RFC 8446 §7.1]

TLS 1.3 依序推进三级调度状态（在无 PSK 的常规证书握手中，初始 PSK 位置输入为全零串）：

  1. Early Secret： 
    Early Secret = HKDF-Extract(Salt=0, IKM=PSK或0)
  2. Handshake Secret： 将上一阶段派生的状态通过 Derive-Secret(Early Secret, “derived”, "") 作为新的 Salt，而将新鲜协商出的 (EC)DHE 临时共享秘密作为 IKM 传入提取器： 
    Handshake Secret = HKDF-Extract(Salt=Derive-Secret(Early Secret, "derived", ""), IKM=(EC)DHE)
    由此分别展开出绑定各自握手记录范围的流量秘密（Traffic Secrets）：
    • client_handshake_traffic_secret
    • server_handshake_traffic_secret 这两个秘密再各自通过 HKDF-Expand-Label 派生出记录层真正用于加解密握手报文的 key 与 iv。[RFC 8446 §7.3]
  3. Master Secret： 将 Handshake 阶段派生出的状态作为 Salt，全零串作为 IKM，再次执行提取： 
    Master Secret = HKDF-Extract(Salt=Derive-Secret(Handshake Secret, "derived", ""), IKM=0)
    最终由此展开为保护后续业务应用数据的 client_application_traffic_secret_0 与 server_application_traffic_secret_0，并进一步导出应用层 key 与 iv。

通过这种精细的分层提取与带标签展开，握手流量与业务流量被严格隔离。同时需要明确：连接的前向保密性来自于每会话新鲜生成的临时 (EC)DHE 密钥及其使用后的及时销毁，HKDF 调度本身负责实现严格的用途隔离与状态推进。[RFC 8446 §7.1]

参考资料与固定版本来源

  • RFC 5869 §1: Introduction
    H. Krawczyk, P. Eronen. HMAC-based Extract-and-Expand Key Derivation Function (HKDF), May 2010. 阐述了密钥派生函数的目标与 Extract-then-Expand 的两阶段设计范式。
  • RFC 5869 §2: HMAC-based Key Derivation Function (HKDF)
    给出了 HKDF-Extract 与 HKDF-Expand 的形式化定义与计算流程。
  • RFC 5869 §2.2: Step 1: Extract
    定义了提取阶段的参数、默认全零盐及 PRK 计算。
  • RFC 5869 §2.3: Step 2: Expand
    说明了展开阶段的计数器循环机制及 L ≤ 255 * HashLen 的最大长度限制。
  • RFC 5869 §3.1: To Salt or not to Salt
    剖析了 Salt 在提取阶段提供源独立抽取与提高分析强度的作用，指明其无需保密及可选复用。
  • RFC 5869 §3.2: The 'info' Input to HKDF
    阐明了 Info 标签在展开阶段绑定协议上下文、防止不同用途间密钥碰撞的机制。
  • RFC 5869 §3.4: The Role of Independence
    说明输入密钥材料与 salt 的独立性及条件熵要求。
  • RFC 5869 §4: Applications of HKDF
    讨论了 HKDF 的适用场景，指出其不提供口令拉伸等慢哈希特性。
  • RFC 8446 §2.2: Resumption and Pre-Shared Key (PSK)
    E. Rescorla. The Transport Layer Security (TLS) Protocol Version 1.3, August 2018. 警示低熵预共享密钥容易遭受离线字典穷举攻击。
  • RFC 8446 §7.1: Key Schedule
    详细定义了 TLS 1.3 密钥调度树中各个 Extract 阶段的真实 Salt 与 IKM 输入流。
  • RFC 8446 §7.3: Traffic Key Calculation
    说明了从 Traffic Secret 经 HKDF-Expand-Label 进一步导出记录层具体 key 和 iv 的过程。
