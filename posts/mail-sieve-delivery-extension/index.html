Sieve过滤与投递扩展

2021年12月5日
|

在邮件系统的投递流程中，邮件过滤规则匹配成功并不直接等同于最终动作已成功提交。一封邮件在判定应归档到特定文件夹或重定向至其他地址后，仍可能在实际写入存储或调用外发接口时因资源限制、网络中断而受阻，进而面临部分动作完成、降级回退或触发系统重试的复杂状态。

这源于投递阶段的过滤引擎具备分阶段的生命周期。Sieve 是一种专门用于邮件在投递阶段进行过滤与裁决的规则语言（RFC 5228）[1]。它在本地投递代理（Local Delivery Agent，简称 LDA）或本地邮件传输协议（Local Mail Transfer Protocol，简称 LMTP）服务中并不按常规脚本语言即时产生不可逆的副作用，而是经历规则解释、动作准备与最终按策略提交的分阶段过程。

本文以 2021 年 8 月 6 日发布的 Pigeonhole 0.5.16 及其配套的 Dovecot 2.3.16 源码实现为例，分析这一投递扩展的执行机制与系统边界[7]。Pigeonhole 作为独立归档分发，默认遵循 LGPL-2.1 许可（以源码个别文件标注为准）[3]，在投递挂钩中提供了与 Dovecot 核心存储与传输交互的参考实现。

投递挂钩与执行上下文

在投递流水线中，Pigeonhole 通过动态挂钩接管投递控制权。在 src/plugins/lda-sieve/lda-sieve-plugin.c 中[4]，初始化函数 sieve_plugin_init 调用 mail_deliver_hook_set(lda_sieve_deliver_mail) 将过滤入口嵌入流程。

当邮件进入投递阶段，lda_sieve_deliver_mail 与 lda_sieve_execute 负责准备运行上下文：

  1. 装配消息数据（sieve_message_data）：装载消息内容、认证用户名（auth_user）以及 SMTP 传输层的信封参数（envelope.mail_from、envelope.rcpt_to 等）。
  2. 构建脚本环境（sieve_script_env）：绑定默认收件箱（default_mailbox，通常为 INBOX）、自动创建与订阅选项，以及本地外发传输接口回调（smtp_start、smtp_send、smtp_finish 等）。
  3. 多脚本执行序列（sieve_multiscript）：调用 lda_sieve_execute_scripts，按配置顺序遍历前置管理员脚本、个人规则脚本与后置脚本。

在此阶段，解释器运行编译后的字节码并收集动作。在多脚本序列推进时，系统可能调用 sieve_result_execute(commit=FALSE) 预先准备存储事务（如分配并打开目标邮箱），但正如版本说明中所强调，具有确定性后果的提交动作（Definitive Actions）被推迟至成功会话末尾统一处理，并不能等同于执行期完全无底层资源交互。

规则解释与动作收集

Sieve 语言在解释阶段进行条件评估与动作登记。在 src/lib-sieve/tst-header.c 中，标头测试操作 tst_header_operation_execute 读取指定的邮件头字段（Header Field）与模式匹配，随后调用 sieve_interpreter_set_test_result 记录分支真假以驱动条件跳转。

需要明确区分：邮件头字段绝不等于传输信封（Envelope）。邮件头字段属于邮件内容中的头部，不等于正文，也不等于传输信封；头字段里的地址可以与实际收件人不同，密送收件人也可能不出现在 To/Cc 中。传输信封字段记录的是 SMTP 会话协商确定的实际投递上下文，但同样由传输层传入，并非据此就能保证其身份绝对可信。Sieve 提供了专门的 envelope 测试扩展来提取信封字段，若在脚本中混淆两者将导致在别名或群发转发时出现判断失误。

条件求值成功后，具体指令开始向结果集（sieve_result）登记：

  • fileinto（归档至指定文件夹）：由 RFC 5228 定义。src/lib-sieve/ext-fileinto.c 中的 ext_fileinto_operation_execute 验证文件夹名称合法性后，调用 sieve_act_store_add_to_result 登记存储动作。
  • redirect（重定向转发）：由 RFC 5228 定义。src/lib-sieve/cmd-redirect.c 中的 cmd_redirect_operation_execute 解析目的地址合法性，并在追加至结果集时结合实例配置施加跳转上限（max_redirects）限制。
  • 隐式保留（Implicit Keep）：RFC 5228 规定，若脚本执行期间未生效任何取消保留的动作，邮件必须默认保留在收件箱中。在 Pigeonhole 中，隐式保留状态是在动作进入执行阶段（execute）时被明确变更的，例如存储或重定向动作执行成功时将隐式保留标记置为假，而非在命令刚刚解析压入结果集时立即注销。
  • :copy 修饰符：由 RFC 3894 扩展规范定义[2]。它作为 redirect 或 fileinto 的参数，在执行时不取消当时的隐式保留状态，也不会恢复之前已被其他动作取消的隐式保留。
  • stop 指令：用于终止当前脚本后续规则；在多脚本配置中，是否继续其他脚本还取决于序列配置和保留状态，并不代表已在物理介质上完成提交。

分阶段提交与原子性边界

在过滤处理的最终收束阶段，所有收集到的动作由 src/lib-sieve/sieve-result.c 集中调度执行[5]。Pigeonhole 并不具备跨物理存储与外部网络传输的分布式事务协调能力，提交过程是分步串行推进的。

在 sieve_result_transaction_commit_or_rollback 函数中，系统首先遍历所有动作链表，提取带有 SIEVE_ACTFLAG_MAIL_STORAGE 标志的普通存储动作统一执行提交（act_store_commit）；在处理完普通存储动作后，系统再根据累计状态提交或回滚非存储动作（如 redirect 的网络外发）。

对于简单动作集，若脚本中同时包含 fileinto "Builds"; redirect "archive@example.net"; 且均执行成功，底层是先对 Builds 文件夹执行落盘提交，再调用外发网络接口发送邮件。绝不能依据 Sieve 脚本代码书写的先后顺序假设网络外发会先于存储动作发生。

在本地存储提交时（src/lib-sieve/sieve-actions.c）[6]，act_store_commit 调用 Dovecot 的 mailbox_transaction_commit。若此时命中配额上限（MAIL_ERROR_NOQUOTA）或存储错误，存储事务执行回滚清理（act_store_cleanup）。

在重定向转发提交时（cmd-redirect.c），act_redirect_commit 调用本地 SMTP 发送流程。smtp_finish 函数的返回值仅表明本地外发传输接口对该邮件的处理结果（正值表示外发传输接受，0 表示本地或协议永久错误，负值表示临时故障）。外发接口接受并不等同于远端目的收件箱已最终成功落盘；后续的邮件路由、外发队列重试与退信均由外部邮件传输代理（Mail Transfer Agent，MTA）或传输系统独立负责。

系统无法提供跨存储介质与网络投递的全局原子性。若存储成功提交但随后的网络转发遇到故障，该实现没有跨动作撤销已经完成提交的机制。

失败处理与恢复路径

面对执行异常，Pigeonhole 与投递框架提供了分级处理与降级兜底路径：

  1. 普通失败与隐式保留恢复（SIEVE_EXEC_FAILURE）： 在 sieve_result_execute 中，系统在完成常规动作提交或回滚之后，会独立检查并执行隐式保留（sieve_result_implicit_keep_finalize）。若常规动作由于逻辑或配置原因失效，但兜底的隐式保留成功将邮件写入默认邮箱，lda-sieve-plugin.c 中的 lda_sieve_handle_exec_status 会捕获该状态，在日志中记录隐式保留成功，投递钩子返回 1，向调用方表示该插件已成功处理。
  2. 临时故障（SIEVE_EXEC_TEMP_FAILURE）： 若过滤及恢复路径最终仍返回 SIEVE_EXEC_TEMP_FAILURE，插件向上层报告临时失败；LMTP/LDA 各自映射结果，上游按该收件人状态决定重试。显式 fileinto 已经提交而 redirect 随后失败时，已完成动作不能整体回滚；最终状态还会受 committed 与隐式 keep 恢复结果影响，不应未经判定重试整个动作集，否则可能导致已落盘的邮件被重复存储。
  3. 保留动作亦告失败（SIEVE_EXEC_KEEP_FAILED）： 当脚本常规动作失败且系统试图以隐式保留挽回邮件，但默认邮箱本身也无法写入导致保留提交失败时，引擎返回 KEEP_FAILED，必须向上层报错中止。
  4. 配额超限的处理边界： 过滤规则无法绕过系统存储配额。无论是用户显式 fileinto 还是兜底的隐式保留，若目标存储返回 MAIL_ERROR_NOQUOTA，该次存储事务均会失败。若默认投递目标仍允许写入，隐式 keep 可能恢复成功；若同样受到账号共享配额限制，切换文件夹也不会增加可用配额。具体判断由存储返回决定，若所有目标均拒绝写入，系统将严格向上层返回失败。

教学示例与场景推演

以下提供一段纯教学推演脚本（注：本脚本仅用于规则语法与执行机制教学推演，完全未在任何实际运行环境或脚本引擎中执行测试）：

require ["fileinto", "copy"];

# 规则 1：持续集成系统通知归档
if header :contains "Subject" "[Build]" {
    fileinto "Builds";
    stop;
}

# 规则 2：重要业务通知抄送归档邮箱
if header :contains "Subject" "[Order]" {
    redirect :copy "archive@example.net";
    stop;
}

假设系统环境中 Builds 文件夹已存在或配置允许自动创建：

  • 场景 A：收到主题包含 [Build] 的邮件
    • 过程：规则 1 匹配成功，fileinto "Builds" 压入结果集；stop 终止后续规则计算。在执行阶段，隐式保留被取消。
    • 全成功预期：第一阶段存储提交将邮件成功存入 Builds 文件夹，默认收件箱不保留副本，无外发网络动作。
  • 场景 B：收到主题包含 [Order] 的邮件
    • 过程：规则 1 不匹配，规则 2 匹配。因使用 :copy 参数，redirect 动作进入结果集时不会取消隐式保留。
    • 全成功预期：在常规提交与隐式保留结算完成后，本地默认收件箱（INBOX）成功保存一份邮件原件，同时本地外发传输接口成功接受了发往 archive@example.net 的外发投递任务。
  • 场景 C：收到普通主题邮件
    • 过程：规则 1 与规则 2 均未命中，无显式动作产生，隐式保留保持有效。
    • 全成功预期：系统执行隐式保留机制，邮件平稳存入默认收件箱（INBOX）。
  • 场景 D：场景 A 中目标文件夹存储配额耗尽
    • 失败推演：
      1. 规则 1 匹配并尝试向 Builds 写入，但在保存或事务提交环节捕获底层返回的 MAIL_ERROR_NOQUOTA。
      2. Builds 事务回滚，显式归档动作宣告失败。
      3. 引擎尝试进入故障恢复分支评估是否可执行隐式保留。若默认收件箱未超配额且默认 keep 成功，则由该恢复分支报告已处理，邮件留存收件箱；若默认收件箱同样受制于账号配额无法写入，隐式保留判定失败（KEEP_FAILED）。
      4. 仅在恢复仍失败时，插件将错误向上层传递，由外层投递接口返回相应失败；恢复成功则按步骤 3 的已处理结果收束。

工程接入与控制面设计考量

自建时要另装兼容的 Pigeonhole，在 LDA/LMTP 投递服务启用 sieve 插件，核对服务用户权限、脚本位置与激活方式、邮箱创建策略和外发接口。下面为自研控制面的工程设计建议，不代表 Pigeonhole 的强制部署形态：

  1. 版本化编译与原子激活： Pigeonhole 依赖将文本源码编译为二进制结构。控制面应在规则保存阶段进行语法解析，并结合运行时预算配置防止超限，生成带有版本标记的编译目标文件。在存储节点生效时，应采用原子重命名或软链切换，避免运行时因读取到未写完的半成品而触发解析错误。
  2. 多租户身份校验与命名空间约束： fileinto 接收的目标文件夹参数必须在接入层进行合规性校验。控制面应结合不同用户的存储格式与命名空间配置规范化文件夹名称，过滤非法编码与跨目录字符，防止越权访问底层隔离路径。
  3. 转发限额、防环流与外发审计： 针对 redirect 动作产生的对外通信流量，单机底层的循环检测标头（如 X-Sieve-Redirected-From）仅能防范简单闭环。平台需要在控制面上配置每个租户的转发频率与配额阈值，将重定向邮件路由至受控的外发队列进行审计，防止被异常脚本滥用为反射攻击跳板。
  4. 逐收件人状态与链路监控： 在群发或多收件人场景下，投递流程必须保持收件人之间的独立处理。控制面日志应精确采集每个收件人在 Sieve 过滤层最终生成的动作列表与执行退出状态，区分业务规则主动丢弃、文件夹归档或网络中继，为邮件全链路排查提供明确依据。
