邮件网关中的灰名单、速率限制与入口过载

2022年1月12日
|

在公网邮件入口处，常见的问题是连接尚未接收邮件正文，后端邮件传输代理（Mail Transfer Agent，MTA）的工作进程或连接槽就已被占满。简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）是一种面向连接的文本协议。当大量恶意主机或僵尸网络发起慢速挂起连接、并发扫描或高频垃圾邮件试探时，若直接为每个入站连接分配重量级的解析和过滤资源，系统会面临资源耗尽与投递排队。

为了在协议早期拦截无效连接并保护核心系统，网关常组合使用连接前置筛查、灰名单（greylisting）以及基于漏桶算法的速率限制（rate limiting）。以下基于 Postfix 3.6.2 与 Rspamd 2.7 的源码实现与随版本提供的配置样例，分析它们在协议各阶段的状态流转、数据结构及失效降级路径。

连接前置控制：Postfix postscreen 的机制与边界

在 Postfix 架构中，postscreen 作为单进程事件驱动的独立接入层，运行在网络连接进入实际 smtpd 进程之前，用于早期过滤协议异常的非标客户端（源码见 Postfix postscreen 源码）。

1. 连接状态检查与响应码划分

客户端完成 TCP 握手并进入 postscreen 端点回调函数（psc_endpt_lookup_done）后，系统会在早期执行连接与队列检查，而非等待连接移交时才临时判断：

  • 单 IP 并发连接数限制：postscreen 在内存哈希表（psc_client_concurrency）中为每个来源 IP 维护一个 client_info 结构。当某个 IP 当前的活跃连接数超过配置参数 postscreen_client_connection_count_limit 时，连接会被立即切断，并返回： 421 4.7.0 Error: too many connections 这是单个 postscreen 进程在本地内存记录的局部计数，不是跨主机的全局计数。
  • 连接交接队列上限：端点回调早期还会检查等待移交的连接计数 psc_post_queue_length。如果该计数达到配置的 postscreen_post_queue_limit，表明连接交接队列已达到上限，系统会直接返回： 421 4.3.2 All server ports are busy 这里表示的是交接队列已满，并不等同于后端系统总体吞吐容量的绝对枯竭。
  • 前置筛查连接差值上限：正在由 postscreen 进行筛查测试的连接差值为 psc_check_queue_length - psc_post_queue_length。如果该差值达到 postscreen_pre_queue_limit，说明前置筛查队列已满，新连接会被拒绝： 421 4.3.2 All screening ports are busy

上述 pre_queue 与 post_queue 均为 postscreen 内存中维护的活跃网络套接字连接队列，并非磁盘上的邮件排队队列（如 incoming 或 deferred 磁盘队列）。

2. 本地缓存与过期淘汰

通过连接数检查后，postscreen 会按客户端来源 IP 查找本地缓存（默认使用 Berkeley DB，即 btree:$data_directory/postscreen_cache）。这与灰名单使用发件人、收件人和 IP 网段构造信封键存在明显区别。

在缓存判定逻辑中，postscreen 解析该客户端各项测试的时间戳（源码见 postscreen 状态与测试逻辑 中的 psc_parse_tests）。只有当所有启用的测试结果仍处于有效时限内且客户端并发数为 1 时，才会直接标记为通过（PASS OLD）并允许进入移交逻辑。通过筛查只说明满足已启用的测试，不证明客户端身份或邮件安全。

常见配置中的 7 天保留时间（postscreen_cache_retention_time = 7d）是整条记录在所有测试过期后继续保留以防日志震荡的物理清理周期，并非各项具体行为测试的统一有效窗口。默认的本地 btree 缓存为各前置节点独立持有，并不跨网关节点自动共享。

3. stress 压力模式的行为特征

当入站并发增大时，postscreen 根据当前连接总数触发压力控制。源码中将 psc_check_queue_length（包含前置与待移交连接）与从 postscreen_pre_queue_limit 派生出的高低水位阈值进行比较：

当连接数达到高水位（约 90%）时进入 stress 模式；当连接数降至低水位（源码为 <=, 约 70%）时退出。进入 stress 模式后，系统仅将支持 stress 的部分超时参数（主要是问候等待时间 greet_wait 和命令超时 command_time_limit）切换至对应较短的预设值，从而缩短等待占用，并按命令超时终止超时会话。stress 机制不执行动态进程扩容，也不会额外拉起新的 worker。

Rspamd 灰名单：双键模型与状态流转

灰名单机制的基本原理在于利用合规邮件服务器会按规范延后重试的特点，暂缓首次投递（参见 RFC 6647 适用性声明）。在 Rspamd 2.7 插件实现中（参见 Rspamd 灰名单插件源码），系统通过 Redis 维护状态，采用正文与元数据的双键模型。RFC 6647 第 6 节建议重试范围应可配置、鼓励边界 MTA 共享数据库与策略，并建议排除已认证的提交连接；而在具体实现中，Rspamd 选择将等待超时默认设为 300 秒、生存时间设为 1 天，并使用独特的双键派生方案。

1. 键构造方式

Rspamd 灰名单不维护原始的明文三元组，而是构造两个专用的 Redis 键：

  • 正文哈希键（data_key）：截取邮件原始正文（task:get_rawbody()）的前 10240 字节计算哈希，截取其 base32 编码的前 20 位，拼装前缀形成 rgb<hash>。此处使用的是原始正文切片，不包含邮件头部字段。
  • 元数据哈希键（envelope_key）：提取 SMTP 信封中的发件人地址（MAIL FROM，空反弹记为 <>）、排序后的全部收件人地址（RCPT TO），以及经过掩码计算的客户端 IP（IPv4 默认使用 /19，IPv6 默认使用 /64）。对上述字段拼接哈希后生成 rgm<hash>。

元数据键将一封邮件的所有收件人排序后统一计算哈希，因而它是整封邮件信封级别的记录，而非针对每个收件人独立拆分。默认情况下，本地网络来源（check_local = false）与已通过认证的登录用户（check_authed = false）会直接跳过灰名单处理。

2. 检查阶段与匹配优先级

在检查阶段（greylist_check），插件通过 Redis 的 MGET 命令同时读取正文键与元数据键记录的创建时间戳 t。判断函数计算当前时间与记录时间的差值 now - t 是否达到等待期（默认 timeout = 300 秒）：未达到则标记为过早重试，达到则标记为记录成熟。

键匹配存在严格的先后判定顺序：

  1. 首先检查正文键：如果正文键存在且已经成熟（now - t >= 300），系统直接记录正文白名单放行，此时不再继续检查元数据键。
  2. 若正文键不存在，但元数据键存在且成熟，系统记录元数据白名单放行。
  3. 若正文键存在但尚未成熟，即使元数据键存在且已成熟，后续判断分支依然会判定为正文尚未成熟，进而注入暂缓响应（soft reject）。
  4. 只有当正文键与元数据键在 Redis 中均无记录时，系统才标记该邮件为全新记录。

这里存在明确的分支边界：如果邮件正文发生变动，且新正文对应的键此前已被其他投递记录占用且尚未成熟，即使旧信封键已经成熟，依然会被拦截暂缓；但若新正文键在 Redis 中完全不存在，而旧信封键成熟，则可以顺利走元数据成熟分支放行。

3. 设置阶段与生效条件

在后续的设置阶段（greylist_set）：

  • 如果在检查阶段或其他前置插件中已经生成了任何预设结果（has_pre_result()），或者当前动作属于拒绝（reject）、或者综合评分未达到灰名单阈值，设置阶段会直接跳过。这意味着过早重试的请求由于在检查阶段已经设定了 soft reject，并不会在设置阶段再次执行 Redis 写入。
  • 只有当该请求需要新建灰名单记录，且经过动作与阈值判断符合灰名单触发条件时，插件才注入 soft reject（默认提示 Try again later），并使用 SETEX 命令将当前时间戳写入正文键与元数据键，生存时间（time to live，TTL）默认设为 86400 秒（1 天）。
  • 当邮件成熟并放行时，插件会通过 EXPIRE 命令将两键的 TTL 重新刷新为 86400 秒。

需要指出，灰名单并不是身份认证机制。合规邮件客户端会按规范退避重试，具备重试逻辑的攻击脚本同样可以完成重试，因此通过灰名单不能保证邮件没有垃圾或威胁属性。此外，写入两个键的 SETEX 命令是分步发出的，不是跨键的原子事务。

Rspamd 速率限制：漏桶状态机与并发边界

Rspamd 的速率限制插件（参见 Rspamd 速率限制插件源码）用于防止单位时间内特定主体的高频投递。在默认配置样例中，限制规则（rates）处于注释状态，网关必须根据业务拓扑显式定义规则，系统开箱并不对所有流量自动限流。

1. 限流键与身份来源

限流键通过 gen_rate_key 组合生成。其关键词包括 IP、信封发件人（from，取自 task:get_from(0) 并转为小写，非邮件头中的 From:）、认证用户（user）以及收件人（to）。

在入站网关中，未经身份核验的公网来源 IP 与信封发件人不能等同于可信身份。对于 user 维度，其取值来自上游可信 MTA 传递的会话元数据（如简单认证与安全层 Simple Authentication and Security Layer，SASL 产生的用户标识，上游也可能采用其他认证方式）。如果当前请求中缺失上游提供的认证元数据，插件在生成带 user 的限流键时会返回空，从而跳过对应规则的检查，而不是整个插件规则无法装载。

2. Redis 漏桶脚本的状态转移

限流状态存储在 Redis 的 Hash 结构中，由 Lua 脚本（bucket_check_script）维护四个字段：上次更新的毫秒时间戳 l、当前累积的水位 b、动态漏出速率乘数 dr 以及动态突发容量乘数 db。

在执行检查时，调用检查脚本前，将配置的每秒速率除以 1000 换算为每毫秒速率；脚本再结合动态乘数计算上次检查到当前时刻漏出的消息量。扣除漏出量后，如果剩余累积水位加上当前请求的增量超过了配置的突发容量乘以动态容量因子，脚本返回超额标记。

默认情况下，每次检查传入的水位增量为当前会话中的收件人总数，仅在配置了 skip_recipients 时才按固定值 1 计算。键在 Redis 中的默认生存时间为 172800 秒（2 天）。新桶创建时设置过期时间，后续更新阶段通过 EXPIRE 刷新；不是每次检查都刷新。记录过期后整个桶将重新开始计数，这并非固定的 48 小时滚动统计窗口。

3. 检查与更新阶段的并发特征

Rspamd 将限流拆分为两个异步阶段：

  1. 检查阶段（ratelimit_cb）：执行 bucket_check_script。若超出阈值，依据配置设置软拒收或仅插入警告符号（settings.symbol）。
  2. 更新阶段（ratelimit_update_cb）：在内容过滤结束时执行 bucket_update_script，真正累加消耗的水位并根据邮件信誉调整乘数。如果前序逻辑已设定了任何处理结果（has_pre_result()），更新阶段直接退出。

由于检查与更新不在同一个原子事务中，并发请求在检查阶段读取到的可能均为未包含自身增量的历史水位。因此该设计属于行为管控工具，高并发突发下可能观察到放行总量超出突发阈值，不能作为强一致性的硬配额系统使用。

典型场景与工程权衡

场景一：重试时序、拓扑漂移与跨节点孤岛

当一封合法邮件在时刻 t0 首次到达时，若命中灰名单规则，网关记录时间戳并返回暂缓响应（如 451）。

  • 重试时序：若发送方在 t0 + 2分钟 发起重试，由于时间差 120秒 < 300秒，请求命中过早重试分支并维持暂缓。过早重试不会更新 Redis 中记录的初始时间戳 t0。若在 t0 + 6分钟 重试，由于 360秒 >= 300秒，记录已满足等待期，邮件放行并刷新 TTL。依据 RFC 5321 §4.5.4.1 的要求，发送方在遇到临时错误时需延后重试，但标准并未规定统一的重试间隔算法，无法确保对端恰好在第 5 分钟发起尝试。
  • 拓扑漂移：发信方常使用多出口与集群分发。若重试时客户端公网 IP 从 198.51.100.1 变更为 203.0.113.1，其超出 /19 掩码范围会导致元数据键改变；正文微调（如添加动态追踪标识）则会改变正文键。只有当两者同时改变时，双键才会同时失配。
  • 跨节点同步：若多台前置网关各自维护独立的本地 postscreen 缓存，重试命中不同节点将导致 postscreen 重复执行前置测试；若 Rspamd 节点未接入相同的逻辑 Redis 实例或分片不一致，也会导致对端面临二次灰名单等待。

场景二：共享出口与多租户隔离

网络地址转换（Network Address Translation，NAT）网关与第三方发信平台通常由多用户共享公网出口：

  • 掩码聚合的影响：Rspamd 默认采用 IPv4 /19 掩码。由于元数据键同时包含发件人与排序后的收件人，单台主机的泛洪不会直接导致整个 /19 网段的所有邮件被灰名单封禁；但较宽的掩码使同信封组合跨主机共享等待状态，虽能减少重试抖动，却削弱了对不同客户端的区分度。
  • 维度分离：对于共享出口，基于 IP 的限流可能误伤同出口的其他合法发送者；而基于认证身份的限流应针对上游验证后的 user 维度独立配置。白名单配置应当审慎，将公共 IP 列入白名单仅会跳过特定的限流或灰名单检查，无法替代对邮件内容的综合安全审查。

场景三：状态异常与暂缓响应的责任边界

当底层持久化服务发生异常时，防御机制可能引发连锁反应：

  • 故障降级差异：若 Redis 读取发生错误，灰名单插件仅记录错误日志并退出，最终动作交由后续规则决定，不等于全系统自动放行；而在首次判定需要灰名单后，若 SETEX 写入失败，对端后续重试将因为缺少历史时间戳而反复触发冷启动。限流插件在遇到 Redis 错误时同样仅记日志，系统最终动作取决于 MTA 的全局错误处理策略。
  • 责任边界与队列堆积：根据 RFC 5321 §4.2，4xx 响应属于临时失败。在接收方返回最终的 250 OK 之前，邮件的暂存与投递责任完全留在发送方队列中。当网关大量返回 4xx 时，上游发送方会将邮件保留在本地队列并持续重试，导致网关面临重试流量与新流量叠加的冲击。
  • 容量估算与资源预算：在架构规划时需预留缓存预算。假设系统持续接入新发信组合的平均速率为每秒 50 次，双键保留 86400 秒，单条键值及底层开销假设约 250 字节（此数值为教学示意，生产中必须结合键前缀长度、编码及 Redis 内部分配机制实际测量）： 50 * 2 * 86400 * 250 字节 ≈ 2.16 GB 在实际场景中，正文键的复用可能降低总键数，而成熟后的 EXPIRE 刷新则可能延长键的实际占用时间，因此理论估算不能当作硬性上限。更重要的是，在入口处收紧连接并发并不等于内容过滤层具备了充足的资源，网关架构仍需为正常邮件与管理通路预留专门的计算预算，并严格约束扫描并发、排队等待长度与超时阈值。

隔离验证与工程设计推导

1. 状态流转推导方案（未实际运行的验证计划）

在不发起真实网络请求的前提下，可通过设定确定性的输入参数推导状态机行为。验证过程中需重点记录各键名称、记录时间、键 TTL、组件判定动作、MTA 实际返回响应、扫描队列深度以及正常邮件的端到端时延：

  • 固定键与时钟推导：注入固定的元数据键与正文键，设定基准时间 t=0。预期首次投递触发写入并返回暂缓响应；在 t=120秒 注入相同键，预期命中过早重试分支并维持暂缓；在 t=360秒 注入，预期状态标记放行并刷新键的 TTL。
  • 出口与节点漂移推导：保持正文键不变，修改来源 IP 使其超出 /19 掩码范围。预期元数据键生成新键，但检查逻辑首先读取到原正文键已成熟，整体依然判定通过；若同时修改正文前 10KB 内容，预期两键均失配并触发重新记录。
  • 存储异常降级推导：模拟 Redis 连接中断或清空状态。预期读取阶段记录错误日志并回退；写入阶段若无法保存时间戳，后续请求将无法完成成熟判定，预期导致多次暂缓。
  • 并发限流推导：以高于突发上限的并发频率同时注入请求。预期由于检查与更新分步执行，并发请求在检查阶段均读取到较低的历史水位，可能观察到超出配置上限的放行数量，体现其非严格配额的行为特征。

2. 严格配额方案的教学设计推导

如果业务场景要求绝对不能超出发信配额，则不能直接依赖 Rspamd 的两阶段限流脚本。在工程设计上可推导如下机制：

  • 原子预留：客户端请求到达时，服务端生成该消息事务的唯一请求标识符（request_id），通过单个 Lua 脚本在 Redis 中原子性校验水位并预扣减配额，同时写入带有较短超时的租约（Lease）。
  • 两阶段确认：若确认处理失败且未移交后端接收，则释放；已接收或结果未知则保持消耗或未决状态并进入对账流程。
  • 未决状态处理：当系统异常崩溃或对端断线导致处理结果未知时，不能简单将租约超时等同于未发信而直接回退额度，必须进入对账流程，结合上游事务日志确认最终投递状态。
