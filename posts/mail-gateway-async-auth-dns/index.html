Rspamd的DNS与身份认证异步检查

2021年12月26日
|

SPF 查询超时，而 DKIM 验证通过且与 From 域对齐时，DMARC 仍可通过。这里需要区分认证失败和暂时无法完成检查。Rspamd 2.7 的实现展示了 DNS 请求与任务会话的绑定、查询结果到符号的映射，以及超时后的清理职责。1

异步查询与任务生命周期管理

在事件驱动的邮件处理流水线中，一条邮件检查任务（struct rspamd_task）需要触发多项并行的网络探测，包括拉取发件域的 SPF TXT 记录、提取 DKIM 签名的公钥 TXT 记录，以及查询发信 IP 在域名系统黑名单（Domain Name System-based Blackhole List，DNSBL）中的映射状态。这些网络请求均由底层的域名系统（Domain Name System，DNS）解析器异步调度。

会话计数与符号缓存回调

Rspamd 的底层通过 rspamd_async_session（异步会话）与符号缓存 symcache 协同管理并发查询的生命周期。整个生命周期的调用顺序为：注册入口发起请求并增加挂起计数，解析器进入异步等待，底层应答触发回调并在安全的栈中执行业务逻辑，最后递减挂起计数完成收尾。

在 Lua 层的解析器接口中，C 模块 src/lua/lua_dns_resolver.c 在向底层发起任务关联的 DNS 请求前，会检查当前执行环境关联的符号项，并调用 rspamd_symcache_item_async_inc 显式增加挂起事件计数。2 若底层解析器请求创建失败（如任务处于阻断状态、未初始化解析器或域名非法），代码会转入错误处理分支，立即通过 rspamd_symcache_item_async_dec_check 递减计数并返回请求创建失败，避免符号项在缓存中永久挂起；3 自研网关的业务调用方在此类失败路径中应显式记录请求未能创建的具体原因。

当底层通信完成或触发事件后，回调函数 lua_dns_resolver_callback 负责在准备好的协程环境内执行 Lua 脚本回调，并在退出前调用 rspamd_symcache_item_async_dec_check 递减挂起计数。4 只有当注册在该符号上的所有异步操作全部返回后，该符号才会被标记为就绪状态。异步回调的职责边界在于：请求创建失败时立即就地完成自身分支；请求创建成功后则由任务会话持有该未决请求，无论网络正常返回还是会话清理均触发终结器释放资源，业务调用方不得在此计数归零前过早释放任务。

会话清理与超时伪造应答

网络环境的不确定性意味着个别 DNS 查询可能因丢包而长期处于无应答状态。在 src/libserver/dns.c 中，Rspamd 为每个挂载在异步会话上的 DNS 请求包装了完成回调 rspamd_dns_fin_cb。

当收到正常响应时，底层传入解析结果指针；但若在未收到实际响应（结果指针为空）的情况下会话超时被清理，Rspamd 构造一个状态码设为 RDNS_RC_TIMEOUT 的虚构应答对象回传给上层回调，并在释放请求后递减当前符号的异步计数。5 通过这一层伪造应答，上层协议状态机无需感知底层的断连细节，统一按超时错误收尾。

任务超时推进与软拒绝条件

当邮件处理耗时达到配置时限时，libev 定时器会触发 rspamd_task_timeout。在 src/libserver/task.c 中，系统会强制推进阶段流转：6

  1. 检查配置项 task->cfg->soft_reject_on_timeout 是否开启；若未开启，则不注入软拒绝。
  2. 若开启了该选项，系统检查当前已累计评分所决定的动作；若已达到硬拒绝（METRIC_ACTION_REJECT），系统将保留硬拒绝动作；若尚未达到硬拒绝，则注入临时软拒绝结果。
  3. 随后，处理逻辑调用 ev_timer_again 重新激活定时器，将阶段标记置位（task->processed_stages |= RSPAMD_TASK_STAGE_FILTERS），接着调用 rspamd_session_cleanup 注销当前会话中的未决事件，随后调用 rspamd_task_process 推进后续流水线，最后调用 rspamd_session_pending 检查状态。

身份认证协议中的 DNS 状态区分

反垃圾邮件处理涉及多个维度的状态空间，在工程实现中必须分层对待：

  • 网络与传输层：连接成功、网络超时、连接被拒。
  • DNS 协议层：正常应答（NOERROR）、域名不存在（NXDOMAIN）、NOREC（解析库内部标明的无记录分类，并非线上标准 DNS 响应码）、服务端临时故障（SERVFAIL）。
  • 认证协议与调度层：前置检查跳过（白名单/本地网络）、语法或多重记录错误（PERMFAIL、BADPOLICY）、对齐通过（PASS）、临时故障（TEMPFAIL）。
  • 综合决议层：黑名单命中判定、DMARC 聚合处置。

SPF 状态映射与 DMARC 计数依赖

在发件人策略框架（Sender Policy Framework，SPF）检查中，Lua 层的入口回调 spf_check_callback 调用 rspamd_spf.resolve(task, spf_resolved_cb) 发起异步解析；拿到解析记录对象后，再调用 record:check_ip(ip) 针对当前发信 IP 执行匹配，最终将策略结果映射为符号。7 这表明系统并非对发信域缓存一个全局的最终结果，缓存下来的 SPF 记录依然用于针对本次具体 IP 进行运算。

在 C 语言核心解析逻辑 src/libserver/spf.c 中：8

  • 若响应码为 RDNS_RC_NOREC 或 RDNS_RC_NXDOMAIN，且为首次 DNS 请求，元素被赋予 RSPAMD_SPF_FLAG_NA（不适用/无记录）。
  • 若响应码既非无记录又非 NXDOMAIN，且非成功响应，则直接打上 RSPAMD_SPF_FLAG_TEMPFAIL 标记。
  • 在后续解析 redirect 修饰符时，若目标域名返回不存在，则状态会被置为 RSPAMD_SPF_FLAG_PERMFAIL。

在 Lua 层插件 src/plugins/lua/spf.lua 中，这些标志最终被映射为具体符号：R_SPF_ALLOW（+）、R_SPF_FAIL（-）、R_SPF_SOFTFAIL（~）、R_SPF_NEUTRAL（?）、R_SPF_DNSFAIL（对应 temp_fail）、R_SPF_PERMFAIL 以及 R_SPF_NA。9

关于模块协作，DMARC 的执行依赖 SPF 与 DKIM 的前置评估，配置层明确注册了依赖关系：10

-- 节选自 src/plugins/lua/dmarc.lua
rspamd_config:register_dependency('DMARC_CALLBACK', symbols['spf_allow_symbol'])
rspamd_config:register_dependency('DMARC_CALLBACK', symbols['dkim_allow_symbol'])

同时，在 src/plugins/lua/spf.lua 中维护着任务内存池变量 dmarc_checks 的计数，源码在此处留下 FIXME，提示这一计数并不等于真正执行了 SPF 认证。11 细读具体路径可知：若发信 IP 命中了白名单（whitelist）或被判定为本地/授权网络（is_skip_local_or_authed），函数在此前已经直接 return，不会递增该计数；而若缺少发信 IP 地址，虽然无法发起解析，却依然会向下执行递增该计数。DKIM 符号回调中也存在对 dmarc_checks 的递增操作。12 DMARC 插件在 dmarc_callback 中通过判断 dmarc_checks ~= 2 来确定是否已调度前置检查。13 这一计数的递增仅代表进入了特定调度路径，绝不代表 SPF 已经通过了验证或已完成实质性解析。

DKIM 密钥查询与错误码分类

域密钥识别邮件（DomainKeys Identified Mail，DKIM）的入口函数 dkim_symbol_callback 先按 DNS 键查公钥缓存；未命中时调用 rspamd_get_dkim_key，注册 dkim_module_key_handler。回调取得公钥或错误后调用 dkim_module_check 汇总签名结果，故函数发起查询后返回不等于认证已经结束。12

DKIM 的公钥存放在 selector._domainkey.domain 的 TXT 记录中。在 src/libserver/dkim.c 中，当 DNS 查询返回非 NOERROR 时：14

  • 若响应码为 RDNS_RC_NOREC 或 RDNS_RC_NXDOMAIN，设置内部错误码为 DKIM_SIGERROR_NOREC；
  • 其他非成功错误码则统一赋值为 DKIM_SIGERROR_NOKEY。

随后在 src/plugins/dkim_check.c 的 dkim_module_key_handler 回调中：15

  • 错误码等于 DKIM_SIGERROR_NOKEY 时，被归类为 DKIM_TRYAGAIN（临时故障，通常对应 DNS 网络超时或服务异常），促使上层产生临时未决状态；
  • 其余错误（包括记录不存在及公钥格式非法）则被归类为 DKIM_PERM_ERROR（永久错误）。

在签名结果汇总函数 dkim_module_check 中，系统遍历全部签名上下文，将状态码映射为对应符号与追踪标记：DKIM_CONTINUE 映射为允许（+）、DKIM_REJECT 映射为拒绝（-）、DKIM_PERM_ERROR 映射为永久失败（~）、DKIM_TRYAGAIN 映射为临时失败（?）。16 这一错误划分属于 Rspamd 该版本的内部实现决策，并非全部 DNS 协议的硬性通用规定。

DMARC 聚合策略与临时故障仲裁

基于域的消息认证、报告和一致性（Domain-based Message Authentication, Reporting, and Conformance，DMARC）比较可见 From 域与已通过认证的 SPF 域或 DKIM 的 d= 域。严格对齐要求完整域名一致，宽松对齐比较组织域。17

在 src/plugins/lua/dmarc.lua 的 dmarc_validate_policy 中，仲裁逻辑严格遵循 RFC 7489 原则：18

  1. 对齐通过优先于临时故障：只要 SPF 或 DKIM 中有一项通过且达到域对齐（spf_ok 或 dkim_ok 为真），即使另一项由于 DNS 超时遭遇了 tempfail，DMARC 仍判定为通过（DMARC_POLICY_ALLOW）。
  2. 临时故障保护发件人：只有当 SPF 与 DKIM 均未达成对齐通过，且其中至少一项遭遇了临时故障（spf_tmpfail 或 dkim_tmpfail）时，系统才会产出 DMARC_POLICY_DNSFAIL，而不会执行发件人声明的 reject 拦截。

在策略记录查询阶段，DMARC 需要解析 From 完整域及其组织域（通过 rspamd_util.get_tld 获取，非 DNS 根级顶级域）的 _dmarc. TXT 记录，并维护 dns_checks_inflight 计数，确保两次潜在查询全部返回后才触发最终校验。19

DNSBL 响应码与位掩码匹配机制

RBL 规则回调通过 task:get_resolver() 提交 resolve_a 请求，并把 gen_rbl_dns_callback 接到 rbl_dns_process；地址展开规则可能先经过额外 A/AAAA 解析阶段。20 在基于 IP 或域名的 DNSBL 检查中，发信 IP 经由特定规则反转拼接在查询域后。在 src/plugins/lua/rbl.lua 的 rbl_dns_process 函数中：21

  • 若返回错误为 requested record is not found 或 no records with this name，说明发信 IP 在本次查询的名单中未查得记录（未命中），函数直接返回。这仅代表当前名单未列入，不能以此推论整封邮件必然安全。
  • 若遇到其他非空错误（如超时或 SERVFAIL），插入 rbl.symbol .. '_FAIL' 符号标明服务不可用，而不判定发件人违规。
  • 当成功获取 IP 解析列表时：
    1. 若规则既未配置 returncodes 也未配置 returnbits，且定义了 symbol，则直接判定命中并插入该符号；
    2. 若配置了 returnbits，提取返回 IP 的整数值进行按位与运算；
    3. 若配置了 returncodes，把配置模式加上首尾锚点，再用 Lua 模式匹配返回地址；
    4. 若返回了未知代码，仅在显式配置 unknown = true 时才赋予主符号，否则仅记录调试信息。

缓存隔离与故障保留边界

为降低重复网络开销，Rspamd 2.7 采用了分模块的局部缓存设计：

  1. SPF 扁平化记录缓存：在 src/libserver/spf.c 中，展开后的记录存入 spf_hash（基于最近最少使用算法，Least Recently Used，LRU）。其存入条件为 flat->ttl > 0 && flat->flags == 0。22 记录缓存的生存时间（Time to Live，TTL）受 min_cache_ttl 兜底抬高，23 若策略中包含特定宏展开则可能阻止记录被缓存。24
  2. DKIM 公钥缓存：在 src/plugins/dkim_check.c 中，解析出的公钥存入模块独立的 dkim_hash，其淘汰策略同样采用带有 TTL 的 LRU 散列表。25
  3. DNS 临时故障缓存：src/libserver/dns.c 还保存 SERVFAIL，并定义了把该类别回传的 rspamd_fail_cache_cb。26 命中分支初始化定时器后返回，但仅凭这里的代码无法确认调度链是否完整工作；不能把它写成已验证的缓存重放。27 接入时应专门验证命中后回调、任务收尾与错误类别均正确。

自研反垃圾网关的工程设计与验证方案

基于对 Rspamd 2.7 的实现分析，自研邮件后端或网关在处理异步 DNS 探测时，应建立分层状态契约并配合严密的验证测试用例。

统一的异步身份认证状态机契约

自研网关在向综合评分模块输出判定时，建议将传输层网络状态与协议语义严格拆解，避免使用模糊的布尔值。以下给出单个检查对象的教学设计契约（注意：以下数据契约仅为工程设计推导与教学示意，未在实际生产系统运行，并非 Rspamd 原生 JSON 格式）：

{
  "task_id": "sim-task-20211226-001",
  "mechanism": "spf",
  "checked": true,
  "query_status": "timeout",
  "protocol_result": "temperror",
  "aligned": null,
  "complete": true,
  "cache": {
    "hit": false,
    "kind": "none"
  }
}

在工程扩展中，DKIM 多签名可单独存入对象数组；DNSBL 查询在无记录时记录 listed: false，在遇到 SERVFAIL 时则记录 listed: null；跳过执行时应显式标注 checked: false 与 skip_reason，避免用 null 冒充明确失败；同时应独立保留观测时间与过期时间，以便区分旧缓存与实时查询。

典型失败案例与工程验证方案

以下案例与测试方案均为教学推导演练，未在生产集群实际运行。

问题场景： 发件域 example.org 配置了 p=reject 策略。测试邮件带有有效的 DKIM 签名（d=example.org）且与 From 域严格对齐。在接收处理时，网关针对 SPF TXT 查询遭遇网络瞬态故障（例如解析器超时或 SERVFAIL）。若网关仅凭简单的非此即彼逻辑判定“SPF 校验未通过”，并将内部标志记为失败，可能错误地触发拒收动作。

测试桩注入与断言方案：

  1. 故障与缓存桩搭建：
    • 建立 Mock DNS 桩服务，将 SPF TXT 解析分别注入为独立的两组异常变量：一组注入人为延迟（产生 TIMEOUT），另一组直接返回 SERVFAIL 报文；
    • 预热本地 DKIM 公钥缓存，使其命中已存在的合法公钥记录；另设对照邮件，使用另一不对齐域的密钥重新生成有效 DKIM 签名，并为该域配置测试 DNS 公钥；保持 From 域不变。
  2. 多分支断言要求：
    • 基础用例：在 DKIM 预热命中且标识对齐的条件下，无论 SPF 遭遇 TIMEOUT 还是 SERVFAIL，SPF 模块均必须产出 tempfail 状态，DMARC 仲裁必须识别对齐通过并产出 pass，严禁触发 DMARC 拒收；
    • 对照用例：若改用不对齐域重新签名导致两项认证机制均无法对齐，且存在 SPF 临时故障，DMARC 仲裁必须产出 DMARC_POLICY_DNSFAIL（临时错误），而不得将其直接判定为明确永久违规；
    • 调度与收尾断言：在任务超时注销或 DNS 请求因参数非法未创建时，验证挂起会话计数是否正常清零、是否杜绝了重复回调及内存泄漏，并确保无记录响应与真实拦截得到清晰区分。这些断言仅用于验证认证分支的决议逻辑，最终邮件动作仍受其他综合评分规则和本地策略影响。
