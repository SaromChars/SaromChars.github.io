邮件中的 URL 检查、模糊指纹与附件扫描

2022年1月2日
|

在邮件系统的反垃圾风控与内容检测链路中，一封邮件在经过反病毒扫描器后返回未命中，是否就代表其附件内容已被完整扫描且毫无风险？正文里提取的超链接在名单服务中未查出记录，又是否意味着目标网页安全可信？

在自建邮件系统或开发安全网关适配层时，容易把统一资源定位符（Uniform Resource Locator，URL）检查误当成网页抓取或沙箱分析，或者把防病毒服务返回的无威胁误当成完整覆盖的安全保证。实际上，邮件过滤引擎针对正文与附件采用了分层的处理机制。结合 Rspamd 2.7 与 ClamAV 0.103.0 的开源实现，我们可以厘清 URL 名单查询、模糊指纹比对与附件流式防病毒扫描（Antivirus Scanning）各自回答什么问题、调用链路、资源预算与状态边界，并探讨在自研适配层中如何定义严密的数据契约。

三种机制的定位与回答边界

正文与附件的内容安全检查由三种定位不同的机制协同完成：

  1. URL 名单检查：回答“邮件中出现的链接主机或域名，是否被已知的基于域名系统（Domain Name System，DNS）的黑名单服务收录”。它只通过 DNS 查询特定域名的信誉，不抓取目标网页，也不在无头浏览器中渲染页面。
  2. 模糊指纹比对（Fuzzy Hashing）：回答“当前邮件的文本分块或图片附件，是否与已标记的批量样本相匹配”。文本部分可通过特征切片进行相似度匹配，但本版所读源码分支中的图片附件使用内容散列摘要做精确比对，并非所有媒体格式都能提取模糊相似度。
  3. 附件防病毒扫描：回答“附件文件（或解包提取出的内容）是否命中病毒库中的特征码、包含宏代码或触发特定启发式告警”。它受制于解包深度、文件体积与流式传输预算，返回的结果不仅有清洁与病毒，还包含加密、超限和格式异常。

清楚这三者的边界，才能避免将上层路由决策建立在错误的假设之上。

URL 提取与 DNS 名单查询链路

在 Rspamd 2.7 的 src/plugins/lua/rbl.lua 插件中，URL 检查的核心逻辑由 check_urls 函数组织。邮件正文解析完成后，引擎根据规则配置提取链接并转换为 DNS 查询请求 源码。

在 check_urls 中，系统调用 lua_util.extract_specific_urls 提取 URL 列表，参数中通过 requests_limit 限制单封邮件的最大提取数，并通过 esld_limit 限制每个有效二级域名下提取的链接数量，避免大量子域名耗尽解析队列。提取出的 URL 随后遍历调用 u:get_tld()。这里提取的并非严格意义上的顶级域名，而是通常用于分组的可注册域（如将 a.example.com 归入 example.com，具体逻辑受公共后缀列表与 url_compose_map 影响）。若配置了重组映射，则调用 url_compose_map:process_url 进行二次处理。

处理后的域名通过内部函数 add_dns_request 加入队列。该函数首先核对白名单：若匹配当前规则配置的白名单，或命中了同类型已缓存的白名单结果，则直接忽略。对未加入白名单的目标，若规则指定了哈希处理，则先计算哈希值，随后拼接为 <hash-or-domain>.<rbl-zone> 的形式，挂载到任务的 DNS 解析器发起异步查询。

从调用链路可以看出，整个过程仅包含邮件正文解析、字符串抽取与 DNS 名单查询。名单未命中仅说明在查询成功的前提下收到了名单服务定义的未收录响应；若遭遇 DNS 解析超时、网络错误、规则主动跳过，或者超出了最大提取数量限制而未发起查询的 URL，绝不能并入安全未命中的范畴。同时，该机制不发起 HTTP 或 HTTPS 网络请求，不跟踪网页重定向跳转，更不下载目标落地页内容，不代表该网站内容经过了动态分析。

模糊指纹机制：分流特征与状态语义

面对群发并频繁微调排版的垃圾邮件，Rspamd 在 src/plugins/fuzzy_check.c 中实现了模糊指纹比对 源码生成 源码分流。

在 fuzzy_generate_commands 函数中，引擎遍历邮件的多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）部分（task->parts）。针对文本分块，系统根据规则分支选择使用滑动窗口特征集合（shingles）或规范化文本摘要：短文本分支（short_text）对剥离后的 UTF 内容及主题计算哈希；而针对正常长文本的 shingles 生成分支，若通过分词提取后无法生成有效特征（sh == NULL），则直接返回 NULL（No shingles, no check），不产生检查指令。因此，不能认为所有文本在特征缺失时都会自动回退到摘要比对。而对于图像附件，源码直接读取父级图像分块的散列摘要（digest）进行精确哈希匹配，打上 FUZZY_CMD_FLAG_IMAGE 标记用于在模糊存储库中检索。

当模糊查询完成，结果进入 fuzzy_insert_result 函数 源码解析：

  • prob 与 value 的语义：后端响应结构体中包含 prob 与 value 字段。源码明确注释：当 prob > 0.5 时认定为匹配，此时 value 代表后端记录的匹配数量（Matches Count）；若未达到判定阈值，value 则用作错误码。prob 仅为匹配服务返回的浮点数字段，用于在文本 shingles 匹配时结合规则权重计算归一化分值，不能将其直接解释为“这封邮件是垃圾邮件的绝对概率”。
  • 超时与错误边界：在 fuzzy_check_timer_callback 中，当触发定时器且重传次数（retransmits）耗尽时，引擎记录错误日志并递减异步处理计数器。在适配层设计中，模糊服务请求超时是外部服务故障，不能推导为未命中。

ClamAV 防病毒集成与 INSTREAM 传输

邮件附件的病毒查杀通常交由外置引擎处理。Rspamd 通过 src/plugins/lua/antivirus.lua 与 lualib/lua_scanners/clamav.lua 驱动 ClamAV 守护进程 源码分块。

在 antivirus.lua 的规则构建函数 add_antivirus_rule 中，根据 rule.scan_mime_parts 的配置决定扫描范围：若开启分块扫描，则通过 common.check_parts_match 遍历匹配的 MIME 分块，对非空分块逐一调用 p:get_content() 与 p:get_digest() 传递给底层检测函数 cfg.check；若未开启分块扫描，则提取整封邮件的原始数据 task:get_content() 与全局摘要 task:get_digest() 发起扫描 源码分块。

进入 lualib/lua_scanners/clamav.lua 后，对于未命中本地缓存的请求，调用 clamav_check_uncached 建立套接字连接。ClamAV 支持通过套接字直接流式传输待检文件（INSTREAM 命令），客户端无需与扫描器共享本地文件路径 文档规范。协议允许多个数据块流式推送，而 Rspamd 2.7 此版适配器在实现上一次请求发送一个内容块及零块：首先发送以 zINSTREAM\0 打头的头部，后接 4 字节大端网络序整数表示的整块内容长度与数据本体；随后紧跟一个 4 字节的零长度块（\0\0\0\0）标记流结束。

服务端在 server-th.c 中循环读取 4 字节的 chunksize，若单块或累积数据超过 StreamMaxLength 设定的配额，clamd 会写入日志并返回 INSTREAM size limit exceeded.，随后关闭连接 源码处理。

响应解析与静态健壮性分析

当网络连接或传输本身报错时，Rspamd 在回调函数中捕获 err，将当前 upstream 标记为失败，并在重试次数允许内依据 rule.timeout 重发请求；若重试耗尽，则通过 common.yield_result 产出 fail 符号并终止扫描 源码交互。

当套接字成功收到远端文本响应时，进入另一分支：若响应为 stream: OK，记录清洁状态；若非 OK，代码执行 local vname = string.match(data, 'stream: (.+) FOUND') 尝试捕获病毒名称。在 Rspamd 2.7 源码中，紧接着直接调用 if string.find(vname, '^Heuristics%.Encrypted') then。这里只分析源码，未运行复现：若 ClamAV 返回了非 OK 且不包含 FOUND 格式的文本（例如直接返回 INSTREAM size limit exceeded. 或扫描器其他错误字符串），vname 的匹配结果将是 nil。此时未先对 vname 进行非空判断就直接调用 string.find，会在当前回调中引发 Lua 运行时异常。这提示我们在自研适配层中，必须先检查回复的整体语法结构与非空状态，再解析具体检测名称。

此外，ClamAV 返回的 FOUND 文本具有丰富的子类型：

  • Heuristics.Encrypted.*：指示文件受口令加密保护，内部内容无法展开。
  • Heuristics.OLE2.ContainsMacros：指示 Office 复合文档中检测到宏代码存在。
  • Heuristics.Limits.Exceeded：指示解包过程中触发了按配置报告的资源限制。 不能把所有带 FOUND 的响应都当作已知病毒特征对待，适配层应保留具体的特征名称（signature）与威胁类别（category），供策略层做细化动作分流。

资源预算、超时分层与缓存模型

无论是 URL 检查还是流式查毒，都受限于资源预算约束。

在 ClamAV 0.103.0 的 clamd.conf 中，定义了解包与递归控制的核心参数 配置流控 配置解包 配置告警：

  • StreamMaxLength：控制客户端单次允许推入的流总字节数 配置流控。
  • MaxFileSize：输入文件本身以及归档内部解压出的单个文件体积上限 配置解包。
  • MaxScanSize：单个输入文件递归解压分析的数据累积上限 配置解包。
  • MaxRecursion：压缩包递归嵌套的最大深度 配置解包。
  • MaxFiles：一个容器文件内允许扫描的最大子文件数量 配置解包。
  • AlertExceedsMax：该选项控制在触及 MaxFileSize、MaxScanSize 或 MaxRecursion 时，是否返回 Heuristics.Limits.Exceeded 配置告警。若该项未启用且未命中特征，引擎在解包截断后仍可能返回 stream: OK。因此，扫描器的 OK 响应绝不代表归档内所有层级的内容都被完整扫描。

在网关适配层设计中，针对超出最大体积阈值的输入，网关应当在独立入口处主动拒绝或跳过扫描并记录超限状态，而不是强行截断部分字节推给引擎并假定其完成了有效扫描。Rspamd lualib/lua_scanners/common.lua 中将 max_size 与 min_size 的校验放在 Redis 回调内部，在自研架构中更推荐将强制上限作为独立的入口防线。

在超时管理上，必须区分底层重传机制与端到端超时。Rspamd 内部的 retransmits 代表失败重传的次数，并不等于超时时长的简单累加；而上层网关的全局处理截止时间（Deadline）必须整体覆盖队列排队、连接重试与数据流传输的总耗时。当全局超时发生时，适配层应主动关闭底层连接释放套接字，同时依靠幂等处理机制确保迟到的响应不会污染后续处理状态。

在缓存设计方面，Rspamd 将检测结果以 prefix .. digest 为键存入 Redis，并赋予固定过期时间 源码缓存。在源码 need_check 函数中，若未命中可用缓存，系统在核对剩余的大小与动态条件后决定是否发起扫描；若因条件不符被跳过，系统亦应记录明确的跳过状态。在自研适配层中，建议将防病毒引擎版本、病毒库版本以及检测策略版本一并编入缓存键中，使库更新后的结果能自动失效隔离。

适配层数据契约设计与模拟注入

为了将底层安全组件与上游邮件分发、归档及拦截策略解耦，网关适配层应提供结构清晰、语义确定的一致性数据契约。这是自研建议字段，不是 Rspamd 或 ClamAV 原生协议字段。

数据契约示意

适配层产出的标准化检测记录示例如下：

{
  "request_id": "req-20220102-094102-f81a",
  "message_ref": "internal-msg-queue-89412",
  "part_id": "mime-part-2",
  "representation": "raw_content",
  "digest": {
    "algorithm": "sha256",
    "value": "placeholder-sha256-digest-value"
  },
  "scanner": {
    "engine": "clamav",
    "engine_version": "demo-0.103.0",
    "db_version": "db-demo",
    "policy_revision": "policy-demo-2022.01"
  },
  "status": "limit_exceeded",
  "coverage": "partial",
  "reason": "MaxScanSize reached; nested archive unpacking truncated",
  "cache_hit": false,
  "elapsed_ms": null
}

在该契约中：

  • 标识符使用内部生成的 message_ref，不直接使用可能被伪造的外来 Message-ID 邮件头。
  • digest、版本与耗时字段均使用占位或示意标识，避免将教学示例误当成真实测试数据。
  • 命中具体威胁时，由附加的 signature 与 category 字段分别保存特征名称与定性类别。
  • status 字段定义受限枚举：hit（特征命中）、no_match（当前条件下未匹配）、limit_exceeded（解包或体积超限）、timeout（超时）、skipped（依据策略主动跳过）与 error（协议或解析错误）。no_match 仅代表未检出特征，绝不能在适配层将其等价为 safe。
  • coverage 字段显式标注覆盖度：仅在具备确凿证据表明全部分块均已完整分析时置为 complete_for_policy，触碰解包深度或体积限制时标记为 partial，无法确定时标记为 unknown。

无害教学场景：错误注入与预期断言

在开发自研适配层时，可设计一套无害教学输入方案：邮件正文包含保留的测试域名（如 http://phish.example.invalid/login），附件为一个包含多层嵌套文件的纯文本 zip 压缩包。

下列是预期断言，本篇未运行扫描、解包或模拟测试，测试框架可通过 Mock 适配器向调用链注入以下模拟响应：

  1. 启发式超限注入：Mock 适配器注入 stream: Heuristics.Limits.Exceeded FOUND。预期断言：适配层正确映射为 status: "limit_exceeded"，且将 coverage 设为 partial，保留原始超限信息供策略层审计。
  2. 非 FOUND 错误回复注入：Mock 适配器注入协议合法的流大小超限回复 INSTREAM size limit exceeded.。预期断言：适配层正确将其识别为 status: "limit_exceeded"；随后注入未知的错误格式文本，断言适配层归类为 status: "error"，且不抛出 nil 变量相关异常。
  3. 超时与幂等验证：模拟在超时重传后底座连接超时断开。预期断言：网关记录 status: "timeout"，且在随后的延迟回复到达时能够被幂等丢弃，不改变该任务已固化的超时状态。
  4. 特征库版本失效验证：模拟扫描引擎升级，注入新的 db_version。预期断言：原缓存键失效，适配层重新调度扫描。

最终的处理动作由网关显式策略负责：在 SMTP 接收前会话阶段可返回 4xx 临时失败拒绝投递；在接收后确有责任方的条件下可放入隔离队列。适配层的核心职责是确保故障状态交给策略层，不被适配器篡改或假定为未命中。
