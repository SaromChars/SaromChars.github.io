Chromium 的桌面 User-Agent 缩减

2023年2月8日
|

早期 Web 中，用户代理请求标头（User-Agent，UA）用于向服务端说明客户端的浏览器名称与版本，以便服务端针对不同浏览器的解析特性下发兼容的 HTML 与样式。然而，随着桌面操作系统与浏览器版本的演化，UA 字符串逐渐堆叠了大量系统架构、构建补丁号与操作系统细分版本。这种细粒度的被动信息暴露，为网络追踪者提供了低成本的特征来源，成为浏览器指纹（browser fingerprinting）的重要组成部分。[W3C Fingerprinting Guidance §3][Chromium UA Reduction]

为了收敛被动指纹暴露，Chromium 团队提出了用户代理缩减（User-Agent reduction）计划，并在桌面平台逐步落地。本文结合具体网络请求与脚本调用示意，分析 Chromium 桌面端 UA 缩减的分阶段设计、低熵与高熵客户端提示（Client Hints，CH）的交互机制。

传统 UA 字符串的信息膨胀

在未执行缩减前，典型的 Chromium 桌面端请求标头包含详尽的软硬件环境细节：

GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 6.3; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/100.0.4896.127 Safari/537.36

该字符串在无交互、被动发起的网络请求中暴露了操作系统细分版本（如 Windows 8.1 对应的 Windows NT 6.3）以及完整的浏览器构建号与补丁号（100.0.4896.127）。细粒度的版本暴露为追踪脚本提供了差异化的特征，同时也增加了因正则解析脆弱而导致兼容性故障的风险。[Chromium UA Reduction Dates]

桌面端分阶段缩减方案

针对桌面端环境，Chromium 制定了分步递进的缩减计划，将默认发送的被动信息削减至通用形式：[Chromium UA Reduction]

1. 阶段 4：版本字段规范化

将浏览器版本号中的次版本号、构建号和补丁号归零，格式统一为 <major>.0.0.0。

  • 实施节点： Chrome 101 于 2022 年 4 月 26 日进入桌面稳定版，5 月 6 日开始面向少量用户灰度推送阶段 4；2022 年 6 月 13 日，通过 Chromium 实验分发框架（Chrome Variations / Finch）面向全部 Chrome 101+ 稳定版用户达到 100% 生效。
  • 表现示意： 各版本保留自身主版本。例如 Chrome 101 的 UA 版本字段显示为 Chrome/101.0.0.0。

2. 阶段 5：桌面平台字段规范化

将桌面操作系统及其架构版本字符串固定为默认占位符。在此阶段后，桌面端发出的标头不再体现底层系统的真实版本升级。

  • 实施节点： 2022 年 11 月 3 日，Chromium 针对 Chrome 107+ 桌面端启动阶段 5 的 1% 灰度测试；2023 年 2 月 7 日，随 Chrome 110 稳定版发布，通过 Finch 面向全部 Chrome 107+ 桌面用户全量推送（达到 100%）。对于需要维持兼容的组织，Chromium 提供了企业策略与反向源试用（Reverse Origin Trial）等过渡支持。
  • 表现规范： Windows 平台固定为 Windows NT 10.0; Win64; x64，Linux 平台固定为 X11; Linux x86_64。对于 macOS 平台，其字符串在此前（Chrome 90 时代）已固定为 Macintosh; Intel Mac OS X 10_15_7，并不归因于本次阶段 5 缩减。

需要明确的是，针对移动端（Android）平台的阶段 6 缩减属于后续独立规划，不在本次桌面阶段 5 范围内。

缩减前后的 HTTP 与 JavaScript 对比

缩减方案的落地改变了默认被动请求的内容。以下对比各阶段的差异：

1. 阶段 4 与阶段 5 前后 HTTP 请求标头对比

在传统阶段与阶段 4 中，以 Windows 8.1 为例（注意 Chrome 110 已不再支持 Windows 8.1，此处阶段 5 采用仍受支持时期的 Chrome 107 示意）：

缩减前传统状态（Windows 8.1 / Chrome 100 示例）：

GET / HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 6.3; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/100.0.4896.127 Safari/537.36

阶段 4 生效后（版本号规范化）：

GET / HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 6.3; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/101.0.0.0 Safari/537.36

阶段 5 生效后（桌面平台字段固定为 Windows NT 10.0，Chrome 107 示例）：

GET / HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/107.0.0.0 Safari/537.36

以上三份示意只展示 User-Agent 标头。Chrome 89 已开始支持用户代理客户端提示（User-Agent Client Hints，UA-CH）。支持且启用该功能的浏览器通常会在适用的安全请求中默认发送低熵提示，首个请求也可以携带这些字段。[Chrome UA-CH Support]

2. 客户端 JavaScript 属性表现

在 DOM 环境中，传统同步属性同步进行了对齐：

// 阶段 5 生效后的输出示例（以 Windows 桌面环境为例）
console.log(navigator.userAgent);
// 输出: "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/107.0.0.0 Safari/537.36"

console.log(navigator.appVersion);
// 输出中版本号亦对齐为 Chrome/107.0.0.0

console.log(navigator.platform);
// Windows 平台下仍保留 "Win32" 历史兼容占位符

User-Agent Client Hints 的主动协商机制

HTTP Client Hints 体系由 IETF RFC 8942（实验性规范，Experimental RFC）定义，规范了基于 Accept-CH 响应标头协商客户端提示的通用流程；而 User-Agent Client Hints（UA-CH）扩展规范则在 Chromium 推动下制定了具体字段定义。[RFC 8942 §3.1][Intent to Prototype and Ship: UA-CH API Updates]该机制将环境信息的传递从“默认被动泄露”重构为“按需主动协商”。

低熵提示通常随适用的安全请求发送。下表是支持 UA-CH 的 Chromium 浏览器发送的三项默认提示。

标头提供的信息
Sec-CH-UA浏览器品牌与主版本号
Sec-CH-UA-Mobile是否为移动设备形态（?0 或 ?1）
Sec-CH-UA-Platform操作系统大类（如 "Windows"、"macOS"）

高熵提示可通过 Accept-CH 请求，是否发送由浏览器按策略决定。

标头提供的信息
Sec-CH-UA-Platform-Version操作系统平台版本（Windows 10 及以上映射为 API 契约版本）
Sec-CH-UA-Full-Version-List浏览器完整品牌与版本列表 [Full-Version-List]
Sec-CH-UA-Arch底层 CPU 架构（如 "x86"、"arm"）
Sec-CH-UA-BitnessCPU 指令寻址位数（如 "64"）
Sec-CH-UA-Model终端设备型号（桌面端通常为空字符串）

1. 服务端标头协商流程（以 Windows 10 / Chrome 110 为例）

当服务端确实需要特定高熵信息（例如软件分发站点需要根据用户的实际 CPU 架构与平台版本下发正确的 64 位安装包）时，可以通过 HTTPS 响应中的 Accept-CH 标头告知客户端在随后的同源请求中包含这些高熵项：

HTTP/1.1 200 OK
Content-Type: text/html
Accept-CH: Sec-CH-UA-Arch, Sec-CH-UA-Bitness, Sec-CH-UA-Platform-Version, Sec-CH-UA-Full-Version-List

浏览器收到这个响应后，可按自身策略在后续同源 HTTPS 请求中发送所请求的高熵标头。以下示意假定浏览器选择发送：

GET /download HTTP/1.1
Host: example.com
Sec-CH-UA: "Chromium";v="110", "Google Chrome";v="110", "Not A(Brand";v="24"
Sec-CH-UA-Mobile: ?0
Sec-CH-UA-Platform: "Windows"
Sec-CH-UA-Platform-Version: "10.0.0"
Sec-CH-UA-Arch: "x86"
Sec-CH-UA-Bitness: "64"
Sec-CH-UA-Full-Version-List: "Chromium";v="110.0.5481.77", "Google Chrome";v="110.0.5481.77", "Not A(Brand";v="24.0.0.0"

需要说明的是，RFC 8942 仅定义了向同源响应声明 Accept-CH 的机制；对于跨源子资源的高熵标头传递，跨源委派需要依据客户端提示基础设施规范，通过权限策略（Permissions Policy）显式授权。[Client Hints Delegation Issue #134]

2. 客户端异步 API：getHighEntropyValues

除服务端网络协商外，页面前端脚本亦可通过异步接口查询高熵数据：

// 客户端主动查询高熵提示示例（独立于服务端的 Accept-CH）
if (navigator.userAgentData) {
  navigator.userAgentData.getHighEntropyValues([
    "architecture",
    "bitness",
    "platformVersion"
  ]).then(values => {
    // 根据架构与位数引导用户下载匹配的 64 位安装包
    console.log("CPU架构:", values.architecture);
    console.log("寻址位数:", values.bitness);
    console.log("平台版本契约:", values.platformVersion);
  }).catch(err => {
    console.warn("查询失败:", err);
  });
}

getHighEntropyValues() 是一个独立的异步 Promise 接口，其执行不要求服务端预先响应 Accept-CH 标头。该 API 允许脚本在有实际功能需要时异步调取高熵参数，但具体调用仍受客户端安全策略的约束。

隐私提升与工程约束

桌面端 User-Agent 缩减是 Web 平台收敛被动信息暴露的重要实践：

  1. 被动特征的实质性收敛： 将构建补丁号归零并固定操作系统版本，使得静态资源请求、普通导航与服务器访问日志默认减少接收高熵细节，大众用户的网络流量在特征层面实现了聚类。
  2. 主动探测的主导地位： 缩减 UA 仅限制了被动网络泄漏。对于具备脚本执行能力的页面，其仍可通过 Canvas、WebGL、音频与字体度量等客户端 API 组合指纹。UA 缩减必须与多层防御协同，才能应对多维度的追踪风险。
  3. 生态兼容考量： 大量遗留 Web 基础设施依然依赖 UA 字符串进行基本的平台识别。这也是 Chromium 采取多阶段演进、保留通用操作系统占位符与主版本号的核心考量。[Chromium UA Reduction Dates]
