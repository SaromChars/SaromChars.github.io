Dovecot 认证与用户信息查询

2021年11月14日
|

将自研账号目录接入 Dovecot 邮件存储服务时，后端系统需要完成两个截然不同的查询：一是判断客户端给出的凭据是否有效，二是确定该用户对应的系统运行身份与邮箱存储路径。

在 Dovecot 的模块化架构中，这两个职责由独立配置的流水线承担：密码数据库（password database，passdb）负责身份认证（authentication）与准入控制；用户数据库（user database，userdb）负责获取运行环境与存储位置。本文以 Dovecot 2.3.16 稳定版源码为依据，分析两者在 src/auth/ 内部的执行流水线、auth-worker 辅助工作进程的隔离边界、自研 SQL 对接字段契约，并给出一套覆盖禁用、改密与故障降级的工程验证方案。

两个查询的职责切分与流水线

在实际邮件收发中，认证与存储定位并不总是成对触发。区分两者的调用链是理解 Dovecot 设计的关键。

1. 登录协议调用链（IMAP / POP3）

当用户通过 IMAP 或 POP3 客户端登录时，请求首先由登录进程（imap-login 或 pop3-login）接收，并通过套接字转发给 auth 主服务。

此时系统按序执行两个阶段：

  1. passdb 凭据验证：主服务调用 passdb 模块验证密码。如果密码不匹配、账号不存在或处于禁用状态，认证失败，主服务向登录进程返回失败通知，由协议登录层向客户端给出错误响应。
  2. userdb 运行环境定位：如果 passdb 验证通过且不是代理（proxy）会话，auth 主服务会继续执行 userdb 查询（或利用 prefetch 缓存的字段），获取操作系统用户 ID（UID）、操作系统组 ID（GID）、家目录（home）与邮件存储路径（mail）。
  3. 主进程派生存储服务：认证成功后，登录连接移交给主服务（dovecot master），派生或分配专用的 imap 进程，切换到 userdb 指定的系统权限下打开邮件夹。

2. 邮件投递调用链（LMTP / LDA）

在邮件传输代理（Mail Transfer Agent，MTA）向本地邮箱投递进站信件时，调用的是本地邮件传输协议（Local Mail Transfer Protocol，LMTP）或本地投递代理（Local Delivery Agent，LDA）。

此时发件方无需提供收件人登录密码。LMTP 服务直接通过 src/lib-storage/mail-storage-service.c 中的 service_auth_userdb_lookup（存储服务查询源码），向 auth 服务发起 userdb 查询，解析收件人的存储目录并执行投递。在进站投递链路上，passdb 完全不参与工作。

核心调度、状态语义与链式流转

在 src/auth/auth-request.c 中，密码验证从 auth_request_verify_plain 入口开始，经策略检查转入 auth_request_default_verify_plain_continue。函数先尝试读取未过期的内存缓存；若未命中，请求状态才置为 AUTH_REQUEST_STATE_PASSDB。若底层模块标记为阻塞，流程进入 passdb_blocking_verify_plain，通过 auth_worker_call（阻塞认证调用源码）将请求发往工作进程执行实际的 iface.verify_plain，并在异步回调返回后通过引用计数维护请求对象的生命周期。

验证返回进入 auth_request_verify_plain_callback（验证回调与缓存回退源码），请求状态转为 AUTH_REQUEST_STATE_MECH_CONTINUE。在 src/auth/passdb.h（passdb 接口源码）中，结果由 enum passdb_result 建模：

  • PASSDB_RESULT_OK (1)：密码匹配成功。
  • PASSDB_RESULT_PASSWORD_MISMATCH (0)：密码不匹配。
  • PASSDB_RESULT_INTERNAL_FAILURE (-1)：底层数据库连接超时、查询语法错误或驱动异常。
  • PASSDB_RESULT_SCHEME_NOT_AVAILABLE (-2)：配置的密码哈希方案不可用。
  • PASSDB_RESULT_USER_UNKNOWN (-3)：账号目录中不存在该用户。
  • PASSDB_RESULT_USER_DISABLED (-4)：账号已被封禁或禁用。
  • PASSDB_RESULT_PASS_EXPIRED (-5)：口令已过期。
  • PASSDB_RESULT_NEXT (-6)：跳过当前 passdb 验证（例如设置了 noauthenticate）。

在 src/auth/auth-request.c 的 auth_request_handle_passdb_callback（passdb 回调分派源码）中，Dovecot 依据配置处理多 passdb 链条：

首先是黑名单库（deny = yes）的处理。在到达此分派函数后，黑名单库保证：只有查询结果明确为 PASSDB_RESULT_USER_UNKNOWN（用户不在黑名单中）时才允许继续处理后续 passdb；若查到用户，则无条件置为 PASSDB_RESULT_USER_DISABLED 并终止；如果黑名单库自身发生内部故障（INTERNAL_FAILURE），则直接视作致命错误阻断认证，绝不静默放行。

其次是普通 passdb 链条的失败处理。在 src/auth/auth-settings.c（认证配置源码）中，result_internalfail 的系统默认值是 continue。这意味着多认证后端并存且保持默认配置时，当前库若发生数据库脱机等内部故障，Dovecot 会尝试向后继续查询后续 passdb。如果后续库恰好包含该用户名，可能造成非预期的放行。因此，在单主账号目录场景下，工程配置通常应显式指定 result_internalfail = return-fail。

需要特别注意的是，result_internalfail = return-fail 只约束链式分派，无法阻止此前的过期缓存回退。当显式启用了认证缓存时，若底层数据库出现 INTERNAL_FAILURE，auth_request_verify_plain_callback 会检查是否存在已过期的历史缓存记录；如果存在，Dovecot 会记录日志并回退（fallback）使用过期缓存完成当前认证。

userdb 调度与环境装配

userdb 的接口定义在 src/auth/userdb.h（userdb 接口源码），状态仅有 USERDB_RESULT_OK、USERDB_RESULT_USER_UNKNOWN 与 USERDB_RESULT_INTERNAL_FAILURE。

主服务通过 auth_request_lookup_user 发起查询，根据配置走缓存、阻塞分流或直接调用 iface.lookup。在 src/auth/auth-request.c 的 auth_request_userdb_callback（userdb 链与回调源码）中，当配置要求继续查询下一项 userdb 时，成功查询留下的字段会保存快照，失败查询产生的字段会回滚，避免失败后端污染后续结果。若 userdb 数据库发生 INTERNAL_FAILURE，且启用了缓存，同样存在回退使用过期缓存记录的 fallback 逻辑。

当查询成功后，存储服务层 src/lib-storage/mail-storage-service.c 中的 user_reply_handle（存储应答处理源码）负责解析字段：

  • uid 与 gid：映射为存储进程运行时的 mail_uid 与 mail_gid。Dovecot 在代码中显式校验：若 uid 为 0（root），直接返回错误并拒绝初始化存储。
  • home 与 mail：分别设置用户家目录与邮件存储位置。需要特别注意，home 是用户的个人根目录（用于存放 Sieve 脚本等），不等于邮件文件的存放目录 mail。如果全局配置了统一的 mail_location，查询中无需强行返回 mail 字段。

auth-worker 进程模型与代理边界

高并发场景下，访问后端 SQL 或 LDAP 容易因网络延迟或慢查询导致卡顿。Dovecot 主 auth 进程基于单线程异步事件循环（ioloop），需要隔离外部数据库带来的阻塞调用。

auth-worker 的阻塞分流

Dovecot 采用多进程模型处理阻塞查询：

  1. 模块通过标记 blocking = yes 或 SQL 驱动自带的 SQL_DB_FLAG_BLOCKING 声明需要分流。
  2. 主 auth 进程通过本地 UNIX 域套接字向子进程池 auth-worker 派发请求。验证密码发送 PASSV <passdb_id> <password> <args...>，查询用户信息发送 USER <userdb_id> <args...>。
  3. auth-worker 进程内部执行同步数据库驱动调用（见 src/auth/auth-worker-client.c（工作进程客户端源码））。
  4. 查询返回后，结果通过套接字送回主进程并触发回调。

需要注意的是，auth-worker 是一个有限大小的进程池。将阻塞操作交由 worker 处理避免了主事件循环被单次慢 SQL 立即卡死，但如果大量请求同时发生数据库慢查询或死锁，worker 进程池被占满后，排队的后续认证请求依然会因等待超时而失败。它隔离的是主进程事件调度，不能替代数据库自身的高可用与查询优化。

代理边界：认证决策与流量中继

Dovecot 支持反向代理（proxy）机制。理解代理边界需要分清控制面与数据面：

  • 路由参数提取：在 src/auth/auth-request-handler.c 的 auth_request_handler_reply_success_finish（请求成功结束源码）中，若 passdb 返回了 proxy=y 及 host 字段，认证主服务在密码验证成功后将这些额外字段返回给前端登录进程。
  • 数据流量中继：auth 与 auth-worker 仅负责查出路由参数，不承担客户端与后端存储节点之间的 TCP 流量中继。真实的数据转发由 imap-login 或 pop3-login 进程接管。
  • userdb 旁路：当认证结果确定为远端代理节点时，本地网关无需在本地磁盘装配邮件环境，此时系统直接跳过本地 userdb 查询。

自研 SQL 接入配置与字段契约

自研账号系统与 Dovecot 对接时，通常利用 SQL 驱动模块。本节首先给出最小合法的配置段声明，再针对自研库列出字段契约。

1. 最小 passdb 与 userdb 配置结构

在 dovecot.conf 或 conf.d/auth-sql.conf.ext 中声明两段独立的数据库驱动，显式指定失败规则并关闭潜在的越权链条。本文先采用真实的独立 userdb，暂不启用 Prefetch 优化：

passdb {
  driver = sql
  args = /etc/dovecot/dovecot-sql.conf.ext
  result_internalfail = return-fail
  result_failure = return-fail
}

userdb {
  driver = sql
  args = /etc/dovecot/dovecot-sql.conf.ext
}

配置范围与部署限定： 上述配置片段展示了安全阻断故障的核心规则。生产部署时，args 对应的文件中仍需配置具体的数据库驱动（如 driver = pgsql）、连接串（包含用户、密码、主机与端口）以及套接字访问权限。这些敏感凭据与文件权限必须在受控隔离环境中独立配置。

2. passdb 字段契约 (password_query)

根据配置范例 doc/example-config/dovecot-sql.conf.ext（SQL 配置范例），password_query 用于返回凭据及准入属性。各字段的具体约定如下：

  • password（必须）：用户密码哈希。推荐带有密码存储方案前缀。若无前缀，回落至全局配置的 default_pass_scheme。 
    {BLF-CRYPT}$2y$05$xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
  • user（可选）：规范化后的用户名全称。用于在数据库大小写不敏感匹配时校正客户端传入的大小写异构。 
    alice@example.test
  • userdb_*（预取可选）：例如 userdb_home、userdb_uid 等。只有在配置中启用了 userdb { driver = prefetch } 查询模块时，才可据此省掉后续独立的数据库查询；而在独立的本地投递（LMTP/LDA）链路上，仍需真实的独立 userdb 进行查找。 
    /var/mail/vmail/example.test/alice

在自研数据库中阻断已封禁账号时，推荐在 SQL 条件中增加状态判断（如 status = 'ACTIVE'）。当账号禁用时查询返回 0 行，驱动将其直接映射为 PASSDB_RESULT_USER_UNKNOWN。在配置了 result_failure = return-fail 的单库环境下即可安全阻断登录。

PostgreSQL 查询配置示意：

password_query = \
  SELECT \
    password_hash AS password, \
    (account_name || '@' || domain_name) AS user \
  FROM accounts \
  WHERE account_name = '%n' \
    AND domain_name = '%d' \
    AND status = 'ACTIVE'

3. userdb 字段契约 (user_query)

用于独立邮件投递（LMTP/LDA）或登录通过后的存储环境装配。各字段具体约定如下：

  • uid（可选，须有来源）：访问邮件存储时 Dovecot 进程切换的目标操作系统用户 ID。若 SQL 不返回，必须在系统全局配置 mail_uid；代码中显式校验，严禁为 0（root）。 
    5000
  • gid（可选，须有来源）：访问邮件存储时切换的目标操作系统组 ID。若 SQL 不返回，必须在系统全局配置 mail_gid。 
    5000
  • home（可选，推荐）：用户的个人家目录。必须由可信服务派生生成，严禁直接拼接未经校验的客户端原始输入。 
    /var/mail/vmail/example.test/alice
  • mail（可选）：邮件数据的物理存储格式与位置。若缺省，使用系统全局配置的 mail_location 宏规则。 
    maildir:/var/mail/vmail/example.test/alice/Maildir

PostgreSQL 查询配置示意：

user_query = \
  SELECT \
    ('/var/mail/vmail/' || domain_name || '/' || account_name) AS home, \
    5000 AS uid, \
    5000 AS gid \
  FROM accounts \
  WHERE account_name = '%n' \
    AND domain_name = '%d' \
    AND status = 'ACTIVE'

业务授权与策略切分说明： 上述 password_query 与 user_query 均带有 status = 'ACTIVE' 条件，代表业务选择在账号停用时同时阻断客户端登录与收件投递。如果业务要求“允许离职账号继续接收信件，仅禁止用户登录”，则应在 user_query 中放宽条件。

此外，passdb 登录成功与 userdb 路径解析仅完成身份验证与本地存储挂载，并不自动赋予发件人权限、邮件外发中继权限、共享邮件夹访问权或管理端控制权限。发件人校验由简单邮件传输协议（SMTP）阶段的身份认证与传输策略决定，邮件夹细粒度授权由访问控制列表（ACL）或业务控制面独立判定（authorization）。

缓存机制、凭据变更与失效处置

Dovecot 的认证缓存（Auth Cache）由 auth_cache_size 控制。在 src/auth/auth-settings.c 中，其默认大小为 0（即默认关闭缓存）。当显式设置了大于 0 的缓存容量时，默认生存时间为 1 小时（auth_cache_ttl = 3600）。启用缓存后，必须配合严密的失效处置策略。

1. 账号封禁与缓存失效时序

当业务后台将账号置为禁用时，如果仅修改数据库字段：

  1. 新建连接风险：在 Dovecot 认证缓存尚未过期前，客户端仍可利用缓存成功发起新认证。
  2. 活跃长连接不受控：IMAP 协议具备持久连接特性。连接一旦建立，后续邮件操作直接在 imap 进程内进行，不会重复调用 passdb。

因此，自研后台处置封禁账号时，应依次执行两个步骤：

  • 步骤一（主动驱逐缓存）：调用 doveadm auth cache flush。其实现位于 src/doveadm/doveadm-auth.c 中的 cmd_auth_cache_flush（缓存刷新源码），通过向 auth-master 套接字发送命令清空全部或指定用户的认证缓存。
  • 步骤二（终止活跃会话）：调用 doveadm kick <user>。其实现位于 src/doveadm/doveadm-kick.c（踢出用户源码），通过查找会话并向对应的客户端处理进程发送信号终止连接。

2. 口令变更的多阶段推进

当用户修改密码时，由于系统跨越了关系型数据库、消息总线与多个 Dovecot 网关节点，无法建立跨组件的强原子事务。工程上应采用可重试的分阶段推进流程：

  1. 数据库更新与版本递增：在数据库中持久化新的密码哈希，同时增加账号凭据版本号（credential_version）。该版本号主要供自研系统内部追踪审计，Dovecot 本身并无自动识别和比对外部凭据版本的约定。
  2. 多节点逐台确认失效与重试：业务系统驱动各邮件接入网关执行 doveadm auth cache flush，并要求每个网关节点返回执行确认。若个别节点通信超时，必须进行重试。工程上决不能仅仅依赖 TTL 自然耗尽，因为在后端数据库短时故障时，Dovecot 存在回退读取过期缓存记录的容灾逻辑，单凭等待时间无法绝对杜绝过期凭据被再次使用。
  3. 选择性切断既有连接：如果安全合规要求改密后所有旧设备必须下线，可联动执行 doveadm kick。

待执行集成验证方案

以下验证案例为设计推导与测试方案，用于指导开发环境下的集成验收与测试编写，未在真实编译环境中直接运行。测试前需建立前置状态：在测试环境维持一条真实的 IMAP 长会话（如维持 IDLE 状态），并在开启认证缓存的前提下完成初始凭据预热。

验证 1：passdb 独立凭据检验（正常、错误与跨租户隔离）

验证 SQL 语句提取与密码哈希匹配是否正常，重点核验多租户场景下同名账号的隔离性。

  • 测试输入 1（有效凭据）：doveadm auth test -x service=imap alice@example.test（终端交互输入正确密码）。
    • 观察点：输出显示认证成功，提取出的 user 字段为规范化的全名 alice@example.test。
  • 测试输入 2（错误密码）：相同指令输入错误密码。
    • 观察点：输出显示认证失败，进程返回非零退出码。
  • 测试输入 3（跨租户同名账号验证）：分别测试 alice@tenant-a.test 与 alice@tenant-b.test。
    • 观察点：确认两者的认证记录在数据库中严格隔离，不能出现跨租户凭据混淆或默认截断域名匹配的情况。

验证 2：userdb 独立运行上下文查询

验证在无登录密码时（模拟 LMTP 投递路径），userdb 能够正确解析存储参数。

  • 测试输入：doveadm user alice@example.test。
  • 观察点与判据：
    • 输出中包含 home、uid 与 gid 字段。
    • 确认 uid 不为 0。
    • 确认解析出的 home 目录包含正确的租户与用户名路径结构（如 /var/mail/vmail/example.test/alice），杜绝路径跨租户越权。

验证 3：账号封禁、缓存清理与会话切断时序

  • 前置条件：开启认证缓存，通过客户端登录成功一次以预热缓存；保持一个活动的 IMAP 交互会话。
  • 步骤与操作：
    1. 在数据库中将 alice@example.test 状态置为 DISABLED。
    2. 在未清理缓存时立即测试 doveadm auth test -x service=imap alice@example.test，验证命中内存未过期缓存仍返回成功。
    3. 执行 doveadm auth cache flush 驱逐缓存。
    4. 再次执行 doveadm auth test，此时查询穿透至数据库，因 0 行记录返回失败。
    5. 检查此前保持的 IMAP 客户端，验证此时尚未断开；随后执行 doveadm kick alice@example.test，确认客户端连接被强行切断。

验证 4：口令变更的新旧凭据验证

  • 前置条件：账号当前密码为 PassA，预热缓存并建立 IMAP 连接。
  • 步骤与操作：
    1. 数据库更新密码哈希为 PassB。
    2. 在网关节点逐台执行 doveadm auth cache flush 并确认成功。
    3. 使用旧密码 PassA 执行 doveadm auth test，预期认证失败。
    4. 使用新密码 PassB 执行 doveadm auth test，预期认证成功。
    5. 执行 doveadm kick alice@example.test，迫使旧设备重新走新密码认证流程。

验证 5：后端数据库不可用时的降级与容灾行为

  • 测试场景 A（无缓存或缓存未启用）：
    • 操作：停止数据库服务，执行 doveadm auth test -x service=imap alice@example.test。
    • 观察点：Dovecot 日志记录密码查询失败与内部错误；在显式配置了 result_internalfail = return-fail 时，认证立即返回失败中断，严禁绕行到其他数据源。
  • 测试场景 B（启用了缓存且存在刚过期的缓存项）：
    • 操作：在缓存刚过期时断开数据库并尝试认证。
    • 观察点：检查日志是否输出 Falling back to expired data from cache，验证系统在数据库瞬时故障时的有限容灾保护机制。

验证 6：端到端登录与存储路径完整闭环（待组合验收）

需要指出的是，doveadm auth test 与 doveadm user 仅是独立的控制面查询工具，并不等同于完整协议交互与磁盘文件写入。完整的系统验收仍需组合下列待执行步骤：

  1. 真实协议登录：使用真实 IMAP 客户端连接 143/993 端口发起 LOGIN 命令，验证网络链路、TLS 握手及登录进程交接是否顺畅。
  2. 文件系统属主与读写闭环：登录成功后，验证系统在实际 mail_location 或 mail 解析出的内容目录及索引目录下能否正常建立文件，属主权限是否严格符合 userdb 给出的非 root UID/GID。
  3. 真实投递测试：通过本地 LMTP 端口投递一封测试邮件，验证进站信件能否根据 userdb 返回的路径正确写入磁盘。
