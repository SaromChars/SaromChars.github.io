SMTP 会话、信封与退信

2021年8月8日
|

在完成收件人域名的 DNS MX 解析并确定目标主机后，发送端邮件传输代理（Message Transfer Agent，MTA）会通过 TCP 25 端口与接收端建立网络连接。在这个传输通道上展开的交互，受 RFC 5321（简单邮件传输协议，Simple Mail Transfer Protocol，SMTP）规范约束。

邮件传输的可靠性建立在会话状态机、信封元数据与邮件内容的分离机制，以及结构化的响应状态码之上。理解这一阶段的关键，在于分清协议级接收与最终投递的语义边界：接收端在 DATA 数据传输结束后返回成功响应，仅代表该节点接管了这封邮件的后续传输或投递责任，并不等同于邮件已经安全放入了收件人的邮箱。

邮件信封与邮件内容的分离

在 SMTP 协议中，邮件由两层截然不同的部分组成：邮件信封（Envelope）与邮件内容（Content）。

  1. 邮件信封（Envelope）：在 SMTP 对话过程中由命令参数显式传递，包含反向路径（Reverse-Path，MAIL FROM:<reverse-path>，即退信与错误通知的目的地址）与正向路径（Forward-Path，RCPT TO:<forward-path>，即本事务指定的收件目标）。传输系统依据 RCPT TO 确定投递目的地，并在遭遇投递失败时将通知路由回反向路径。传输系统亦可通过检查邮件内容中的 Received: 头字段计数等方式辅助循环检测。
  2. 邮件内容（Content）：在 DATA 命令之后传输的数据块，由格式化邮件头字段（Header fields，如 From:、To:、Date:、Subject:）与正文（Body）组成。

这两者之间在协议层面保持独立。邮件头字段中的 To: 即使写着一个展示名称或完全不同的地址，MTA 也不会依据它来分发邮件；中间路由与本地投递依据信封中的 RCPT TO 进行。类似地，如果邮件在后续处理中发生投递失败，未送达通知依据信封中的反向路径（即 MAIL FROM 指定的地址）投递，而不会依据邮件头字段中的 From:。

SMTP 会话时序与核心命令

一次正常的 SMTP 事务遵循清晰的命令与响应时序。以下为单次事务的正常交互路径示意：

注：上图展示单次成功事务的主干交互。在实际会话中，RCPT TO 可多次重复以指定多个收件人；在 DATA 结束后，客户端可发出新的 MAIL FROM 启动下一个事务，或使用 RSET 重置状态、使用 QUIT 正常关闭连接。

1. 会话初始化（EHLO / HELO）

客户端连接至服务端口后，服务端首先返回 220 欢迎横幅。根据 RFC 5321 第 4.1.1.1 节，客户端在开始邮件事务之前必须发出 EHLO 或 HELO 命令。客户端通常应优先使用 EHLO（扩展 HELO，Extended HELLO）表明身份，并附带自身的完全限定域名（Fully-Qualified Domain Name，FQDN）；若客户端没有可用的有意义域名，则应当提供地址字面量（address-literal，如带方括号的 IP 地址）。

支持扩展特性的服务端会返回多行 250 响应，声明当前支持的服务扩展参数。如果服务端不识别或不支持 EHLO，客户端可回退至基础的 HELO 命令重新发起握手。

2. 事务启动与发件人声明（MAIL FROM）

MAIL FROM:<reverse-path> 标志着一次邮件事务的开始。服务端接收到该命令后，会清空内部的事务缓冲区（包括收件人列表与邮件内容数据）。参数中的反向路径被记录为退信与错误通知的接收地址。需要注意的是，根据 RFC 5321 语法，冒号两侧不允许出现空格。

3. 指定收件人（RCPT TO）与响应作用域

客户端紧随其后发送一个或多个 RCPT TO:<forward-path> 命令，每条命令指定一个信封收件人。服务端会对每个收件人独立给出响应。例如，同一个会话中，某个收件人可能返回 250 OK，而另一个不存在的用户则直接返回 550。只要有至少一个收件人被成功接受，客户端即可推进到数据传输阶段。

理解响应的作用域至关重要：在正常情况下，针对特定收件人的诸如 450 或 550 响应仅作用于当前这一个收件人，并不影响会话中其他已被成功接受的收件人。但若是收到 421（服务不可用并关闭传输通道）等连接级响应，则整个会话将直接终止；此时先前即使已有收件人收到 250 OK，也由于尚未经过 DATA 阶段最终确认而未发生责任移交，发送端必须在后续会话中保留未完成事务的投递责任。

4. 传输邮件内容与透明性填充（DATA）

客户端发出 DATA 命令。如果此前至少有一个收件人被接受且服务端准备就绪，会返回中间状态码 354 Start mail input; end with <CRLF>.<CRLF>。随后客户端开始按行发送邮件内容（包含头字段与正文）。

为了防止正文中恰好包含单独一行的英文句点（.）而被误判为数据传输结束，RFC 5321 第 4.5.2 节规定了点透明性填充程序（Transparency Procedure）：

  • 发送端填充：发送端在检查待发送的数据行时，如果发现该行的第一个字符就是句点 .，必须在该句点前面再额外插入一个句点 ..。
  • 接收端恢复：接收端读取一行数据时，先检查首字符。如果是句点且后续紧跟回车换行符（<CRLF>.<CRLF>），则判定数据传输结束；如果句点后还跟有其他字符，则剥除这第一个句点，将剩余字符还原为原始数据写入存储。

当收到合法的数据结束符并成功接收并可靠保存后，服务端针对整个事务返回 250 OK，正式确认接管投递责任。若此时服务端返回 4yz 或 5yz 响应，则代表该事务整体失败，接收端不得对该事务的任何收件人执行投递，发送端仍保留处理责任。

响应状态码分类与重试边界

SMTP 协议采用经典的三位数字响应码（RFC 5321 第 4.2 节）。首位数字决定了动作的基本结果与客户端的后续行为逻辑：

状态码类别语义定义客户端标准处置行为典型状态码示例
2yz积极完成响应（Positive Completion reply）请求的动作已顺利完成，客户端可继续推进下一步或发起新事务。220 服务就绪、250 操作成功完成
3yz积极中间响应（Positive Intermediate reply）命令已被接受，但服务端暂停操作等待补充数据。354 开始输入邮件内容
4yz临时失败响应（Transient Negative Completion reply）命令未被接受，但故障属于临时状态。客户端通常应当回到命令序列起点延后重试，无需变更命令内容。421 服务不可用并关闭传输通道、450 邮箱暂时锁定、451 处理异常、452 系统存储不足或收件人超限
5yz永久失败响应（Permanent Negative Completion reply）命令未被接受且当前形式通常不会成功。客户端不应原样立即重复请求；但排除原因或人工干预后可重新发起。500 语法错误、503 时序错误、550 邮箱不可达、552 超出存储分配（旧式收件人超限例外）

临时失败（4yz）与队列重试机制

当交互中出现 4yz 临时失败响应时，常规 MTA 通常会将该事务（或该收件人）放入本地等待队列延后重试。例如在 RCPT TO 阶段某个收件人遭遇 450，而另一个收件人被 250 接受并在 DATA 后成功交接，则队列只保留未成功交接的目标，避免向已完成的目标重复投递。

对于进入队列的邮件，RFC 5321 第 4.5.4.1 节给出了常见重试策略建议：

  • 初次失败后通常需推迟重试，重试间隔建议不少于 30 分钟（经验策略通常为首小时尝试 2 次，之后退避为每 2 至 3 小时一次）。
  • 队列放弃时限通常建议至少设置为 4 至 5 天，但所有重试参数在实现中必须支持配置。对于通知类邮件或投递状态通知，系统可配置更短的最大重试时限以避免资源无谓占用。当重试时限耗尽或满足放弃条件时，发送端才生成未送达通知。

永久失败（5yz）与兼容例外

收到 5yz 响应意味着当前命令在现有参数下无法被接受。虽然协议规定客户端不应在同一序列中原样重复相同请求，但这并不等于错误绝对不可逆——例如用户修改拼写错误、管理员恢复账号状态后，均可重新发起投递。

此外，RFC 5321 第 4.5.3.1.10 节明确指出了一项重要的向后兼容例外：部分历史实现会错误地使用 552 响应来表示单次事务中的收件人数超出了系统临时承载上限（标准新代码应为 452）。遇到这种情况时，客户端应当将其视为临时失败，将多出的收件人保留在队列中分批重试，而不是直接判定为永久退信。

增强邮件系统状态码（Enhanced Mail System Status Codes，RFC 3463）

为了解决原生三位数字状态码语义重载、跨语言诊断困难的问题，IETF 在标准跟踪文档 RFC 3463 中定义了 class.subject.detail 格式的增强状态码体系：

  • class（类别）：分为 2（成功）、4（持久临时失败，Persistent Transient Failure）与 5（永久失败，Permanent Failure）。
  • subject（主题类别）：对故障来源进行分类，例如 X.1.XXX（地址相关）、X.2.XXX（邮箱状态）、X.3.XXX（邮件系统状态）、X.4.XXX（网络与路由）、X.5.XXX（投递协议交互）、X.7.XXX（安全与策略）。
  • detail（明细）：标明细分原因，例如 5.1.1 代表目标收件人邮箱不存在，4.2.2 代表收件人邮箱暂时超出配额，5.3.4 代表邮件体积超出系统单信限制。

增强状态码提供了与具体自然语言无关的机器可读分类，显著减少了对自由文本描述的依赖，方便自动化程序根据主题与类别进行故障归类与处理。若客户端遇到未识别的明细代码，仍可回退至对应的主题类别与状态类别进行解释。

协议接收不等于最终送达

在邮件系统工程中，必须厘清一个核心边界：服务端在 DATA 数据传输结束后返回 250 OK，只代表该节点接管了这封邮件的后续责任，绝不等于邮件已被安全放入最终收件人的邮箱。

可能导致接收后仍发生投递失败的典型情况包括：

  1. 中继转发（Relaying）：接收端可能只是一台中继服务器或组织的外围边界网关。它在 SMTP 会话中接受邮件并落盘，但在后续尝试将邮件中继给下一跳或内部邮箱系统时，下游主机可能发生宕机、网络中断或拒绝接收。
  2. 延迟收件人校验：某些邮件系统可能不在 RCPT TO 阶段实时核验用户是否存在，而是在会话结束、邮件入队之后才由本地投递代理进行解析，此时才发现本地并无此收件人。
  3. 接收后的异步内容检查：接收端在会话确认接管后，可能会调用异步检查机制；若后续检测发现邮件包含恶意或严重欺诈内容，将触发异常处理流程。

退信与空反向路径

当服务端在通过 250 OK 确认接收邮件后，如果在后续处理中发生了不可恢复的投递失败，根据 RFC 5321 第 6.1 节的一般规定，该节点必须构建并发送一封投递状态通知（Delivery Status Notification，DSN），在失败场景下通常被称为退信（Bounce Message）。

然而，退信生成存在明确的限制与安全例外：

  1. 恶意与欺诈内容例外：根据 RFC 5321 第 6.2 节，如果接收后判定邮件包含严重的欺诈或敌意内容，系统默认应当避免盲目发送退信（除非确信通知能有效送达），甚至在具备极高确信度时可谨慎静默丢弃，以防止退信被滥用。
  2. 原始反向路径为空：如果最初接收到的邮件本身就带有空反向路径（即 MAIL FROM:<>），接收端绝对不得向其发送投递失败通知。

退信与空反向路径防循环机制

在退信发送机制中，最关键的风险是无限循环退信。假设主机 A 向伪造或无效的发件人地址发送了一封退信，若接收端针对这封失败的退信再次生成新的退信通知回传，两个系统之间可能陷入递归循环，严重浪费网络与系统资源。

为此，RFC 5321 第 3.7 节与第 4.5.5 节作出了严格规范：

  • 所有自动生成的未送达通知、投递状态通知（DSN）以及消息处置通知（Message Disposition Notification，MDN），在 SMTP 传输时，其信封发件人必须使用空反向路径（Null Reverse-Path）： 
    MAIL FROM:<>
  • 终止循环规则：任何 SMTP 节点在处理一封带有空反向路径（MAIL FROM:<>）的邮件时，如果该邮件在传输或投递中再次遭遇失败，严禁再次生成任何投递失败通知。该事件只能在系统本地进行记录、告警或交由管理员处理，从而在协议规则上彻底切断了退信递归循环的链条。
