Rspamd规则的调度与评分

2021年12月22日
|

在邮件过滤网关的规则体系中，如果规则 MY_AFTER 显式依赖了 MY_HEADER，调度器能够确保的仅仅是 MY_HEADER 已经完成执行，并不意味着 MY_HEADER 必定成功命中并插入了结果。反垃圾邮件过滤系统（Rspamd）通过规则符号（symbol）、符号缓存（symcache）、组合规则（composite）和指标扫描结果（scan result）把成百上千个检查单元组织起来，将离散的特征检测量化为分值，再转换为最终动作。

结合 Rspamd 2.7 的公开源码与官方发布记录 Release 公告，可以厘清规则注册、依赖拓扑、组合运算和动作裁决的具体流转与边界。

规则符号与依赖注册

在 Rspamd 中，每一个检查单元通常输出一个或多个符号。规则既可以通过底层 C 语言模块实现，也可以在 Lua 脚本中动态编写并挂载到引擎中。

规则编写与执行语义

编写 Lua 规则时，Lua 回调函数返回的布尔值代表该符号是否命中，而伴随的浮点数是权重倍率（weight multiplier），并不是绝对分值。最终计入指标的分值由符号在配置中的基准分数与该倍率相乘得出。

例如，定义一个检查测试头 X-Lab-Spam 的规则 MY_HEADER，基准分值设为 2.0，配置 one_shot = true；再定义后续规则 MY_AFTER，基准分值设为 1.0，同样配置 one_shot = true。MY_AFTER 显式依赖 MY_HEADER 执行完成，并在内部独立判定 MY_HEADER 是否真正命中。

-- 规则 1：检查指定头部，命中时返回 true 与倍率 1.0
rspamd_config:register_symbol({
  name = 'MY_HEADER',
  score = 2.0,
  one_shot = true,
  type = 'normal',
  callback = function(task)
    local hdr = task:get_header('X-Lab-Spam')
    if hdr and tostring(hdr):lower() == 'yes' then
      return true, 1.0, 'found lab spam header'
    end
    return false
  end
})

-- 规则 2：显式依赖 MY_HEADER
rspamd_config:register_symbol({
  name = 'MY_AFTER',
  score = 1.0,
  one_shot = true,
  type = 'normal',
  callback = function(task)
    -- 依赖关系仅保证调度完成，不代表 MY_HEADER 必定命中
    -- 因此下游必须通过 has_symbol 显式检查上游执行结果
    if task:has_symbol('MY_HEADER') then
      return true, 1.0, 'header matched upstream'
    end
    return false
  end
})

-- 注册依赖关系：MY_AFTER 依赖 MY_HEADER 先行完成
rspamd_config:register_dependency('MY_AFTER', 'MY_HEADER')

在这段配置中，register_dependency('MY_AFTER', 'MY_HEADER') 表达的是执行时序依赖。引擎调度器确保 MY_HEADER 彻底运行结束（无论是未命中、正常命中、还是报错终止），才会调度 MY_AFTER。如果下游规则需要上游产出的判定，必须显式调用 task:has_symbol 检查指标结果集。

注册调用链

从 Lua 层声明到引擎内部注册，配置经历清晰的调用链路：

  1. rspamd_config:register_symbol 映射到 C 层的 lua_config_register_symbol lua_config.c:1998。
  2. lua_config_register_symbol 解析传入的 table 参数，并调用 rspamd_register_symbol_fromlua lua_config.c:1502。
  3. 在 rspamd_register_symbol_fromlua 中，如果注册了 Lua 回调函数（ref != -1），系统分配 struct lua_callback_data 记录回调引用，同步规则指定 C 回调包装函数为 lua_metric_symbol_callback，随后调用 rspamd_symcache_add_symbol 写入缓存结构。
  4. 若声明了分值（score），lua_config_register_symbol 继续调用 rspamd_config_add_symbol 将基准分值与分组写入指标字典。
  5. 依赖注册函数 rspamd_config:register_dependency 映射到 lua_config_register_dependency lua_config.c:2287，调用 rspamd_symcache_add_delayed_dependency 将依赖关系记录在符号缓存的依赖图表中。

调度机制与异步生命周期

邮件进入扫描后，Rspamd 通过阶段划分和异步事件计数驱动整个流水线。

任务扫描阶段

在 src/libserver/task.c 的 rspamd_task_process 中，任务按预设阶段驱动 task.c:704：连接过滤器（CONNFILTERS）、解析与处理消息结构（READ_MESSAGE 与 PROCESS_MESSAGE）、预过滤（PRE_FILTERS）、主规则过滤（FILTERS）、统计分类（CLASSIFIERS）、组合规则（COMPOSITES）以及后置过滤（POST_FILTERS）。大部分正文与头部规则在 FILTERS 阶段由 rspamd_symcache_process_symbols 调度执行。

状态位与依赖检查

引擎在执行每个检查项时，依赖一系列状态位与计数器进行生命周期管理：

  • CHECK_START_BIT 与 SET_START_BIT：标识当前项是否已经启动执行。
  • CHECK_FINISH_BIT 与 SET_FINISH_BIT：标识当前项是否已经完成执行（不代表底层内存已释放）。
  • checkpoint->items_inflight：记录当前任务中正在并发执行的符号总数。
  • dyn_item->async_events：记录单个符号项关联的未决异步事件数。

在 rspamd_symcache_check_deps 中 rspamd_symcache.c:1848，系统检查目标符号的前置依赖 item->deps。若某个依赖项尚未完成（未置 CHECK_FINISH_BIT）：

  • 如果尚未启动（未置 CHECK_START_BIT），调度器递归检查并启动该依赖符号。
  • 如果已经启动但尚未结束，当前符号的执行被阻塞，调度器退出等待。
  • 检查过程中若递归层级超出预设上限（recursion > 20），调度器输出错误日志后直接返回，避免更深的递归。

同步包装与逆依赖唤醒

即使是在 Lua 中编写的同步规则，底层执行也通过统一的异步计数模型维护生命周期。

在 lua_metric_symbol_callback 中 lua_config.c:1194：

  1. 调用 lua_pcall 执行 Lua 回调前，先调用 rspamd_symcache_item_async_inc 将当前符号的 async_events 计数加 1。
  2. 执行成功后，若返回 true，提取倍率并调用 rspamd_task_insert_result 将符号记录插入扫描结果集。
  3. 函数末尾调用 rspamd_symcache_item_async_dec_check。

在 rspamd_symcache_item_async_dec_check_full 中，当 async_events 归零时触发终结函数 rspamd_symcache_finalize_item rspamd_symcache.c:3169：

  • 通过 SET_FINISH_BIT 标记完成；
  • 将检查点的 items_inflight 减 1；
  • 遍历该符号的逆向依赖列表 item->rdeps，检查等待该符号的下游项是否已满足启动条件。若前置依赖全部完成，立刻唤醒下游符号执行。

组合符号与指标评分

所有规则符号在 FILTERS 阶段产出的结果记录在指标结果集中。进入 COMPOSITES 阶段后，组合规则引擎开始介入求值。

组合规则策略

组合规则允许将多个原子符号以布尔表达式组合，并定义命中后的符号处置策略。假设教学配置如下：

composites {
  MY_COMBO {
    expression = "MY_HEADER & MY_AFTER";
    score = 3.0;
    policy = "remove_all"; # 教学配置参数，非全局唯一默认
  }
}

在 src/libserver/composites.c 中 composites.c:833：

  1. 表达式求值：若表达式为真，通过 rspamd_task_insert_result_full 插入组合符号 MY_COMBO（分值 3.0）。
  2. 符号清理：遍历表达式中的原子符号。若原子节点处于非运算（OP_NOT）分支下，跳过剔除逻辑；若策略为 remove_all 且无其他组合规则要求保留，系统从指标总分中扣除原符号分值，并将原符号标记为 RSPAMD_SYMBOL_RESULT_IGNORED。若策略配置为 leave，则原符号与分值均完整保留。

在没有其他符号命中、没有 settings 覆盖分值、grow_factor 保持 1.0、无组上限截断、未提前达到扫描上限且无直通动作的前提下：

  • 若 policy 为 leave：保留两基础符号分值，加上组合符号分值，总分为 2.0 + 1.0 + 3.0 = 6.0。
  • 若 policy 为 remove_all：扣除两基础符号分值（-2.0 与 -1.0），计入组合符号分值，总分为 2.0 + 1.0 - 2.0 - 1.0 + 3.0 = 3.0。

指标结果插入与限制

在 src/libmime/scan_result.c 的 insert_metric_result 中 scan_result.c:192：

  • 分组上限截断：若符号所属分组配置了 max_score > 0，该限制仅作用于正分增量。当组累积分达到上限时，正分增量被忽略；若累加后超出上限，正分增量被截断为补齐差额（负分不被正上限限制）。
  • 重复插入处理：若符号已被插入过，在 one_shot 约束下，同符号、同倍率的重复插入不会重复增加分值；只有当后续插入的绝对分值更大且符号方向相同时，才计算差额更新分值。
  • 动态阈值截断：在未设置 PASS_ALL 且满足 metric_limit 条件时，调度器可停止继续安排后续规则检查；此处触发提前终止的分数条件是严格大于所取 required score，与动作裁决的 score >= 阈值 逻辑不同。

动作裁决与系统边界

扫描结束后，引擎根据指标结果做出动作裁决。

动作选择与阈值匹配

动作裁决由 rspamd_check_action_metric 执行 scan_result.c:742：

  1. 直通动作优先（Passthrough Results）：若有白名单或速率限制模块注入了直通结果，且不带 LEAST 标记，引擎直接采纳该动作返回。
  2. 常规阈值匹配：在无直通结果时，引擎逆序遍历配置的阈值列表，比较条件为 scan_result->score >= sc && sc > max_score。等号包含在判定条件内，最终选取已达到的最高阈值对应的动作；若未达到任何阈值，返回默认的 noaction。

例如系统配置了动作阈值：add_header = 2.0，reject = 5.0。 若任务最终得分为 2.0，满足分值大于等于 2.0，裁决为 add_header；若最终得分为 5.0，精确达到 reject 阈值，裁决为 reject。

动作落地与系统接入

本节追踪的评分和动作选择函数只产生扫描结果；简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）接收/拒绝与邮件修改还要经过具体接入链路。自建时须核对动作名、邮件传输代理（Mail Transfer Agent，MTA，如 Postfix、Sendmail）响应与头字段修改配置，不能把得分当作投递完成。

异常失败路径与自研设计

Lua 运行时报错的表现

在 lua_metric_symbol_callback 中，Lua 回调受 lua_pcall 保护：

  • 若回调内部发生运行时错误（例如在任何结果插入前调用 error("lab failure")），lua_pcall 捕获该异常并打印错误日志。
  • 该错误分支不会向指标中插入任何符号结果。
  • 在函数退出时，末尾的 rspamd_symcache_item_async_dec_check 仍然正常执行。在没有其他关联异步事件挂起时，该符号完成执行并触发终结，逆依赖链依然会唤醒下游的 MY_AFTER。
  • 此时下游执行 task:has_symbol('MY_HEADER')，因指标集中无此记录而返回 false。
  • 此包装层不会自动追加 soft reject 或 clean；整封邮件仍按其他规则与动作策略处理。

自研网关的状态建模

自研邮件网关在设计规则抽象时，应将规则运行状态与最终动作裁决解耦。以下为教学设计的简短接口字段模型（明确与 Rspamd 原生 C 结构区分）：

RuleOutcome {
    rule_id: str,
    rule_version: str,
    status: str,          # PENDING, RUNNING, SUCCESS, FAILED, SKIPPED
    matched: bool,
    multiplier: float,
    error: Optional[str],
    observations: list[str]
}

需要注意的是，诸如 on_dependency_error 等依赖故障处置策略并非 Rspamd 原生支持的配置项。在自研系统或接入层编排中，必须由开发者根据规则版本与系统能力显式实现策略映射。

静态推导与状态验证

以下基于 Rspamd 2.7 源码逻辑，针对前述教学配置进行静态推导验证（未运行真实生产服务）：

  • 输入包含 X-Lab-Spam: yes： MY_HEADER 正常执行并命中，插入指标得 2.0 分；MY_AFTER 被唤醒，has_symbol('MY_HEADER') 为真，插入指标得 1.0 分；MY_COMBO 表达式成立，若策略为 remove_all，扣除两基础分并计入组合分 3.0，最终总分为 3.0，大于等于 2.0 且小于 5.0，裁决动作为 add_header；若组合分设为 5.0，最终总分为 5.0，精确达到阈值，裁决动作为 reject。
  • 输入无此头部： MY_HEADER 返回 false，不插入指标；MY_AFTER 被唤醒，但 has_symbol 检查为假，返回 false；MY_COMBO 表达式不成立；指标无加分，总分为 0.0，裁决动作为 noaction。
  • MY_HEADER 主动抛错（error("lab failure")）： lua_pcall 捕获异常，MY_HEADER 未插入指标；但调度终结仍唤醒 MY_AFTER；MY_AFTER 执行 has_symbol('MY_HEADER') 为假，未插入指标；MY_COMBO 不触发；总分维持 0.0，裁决动作为 noaction。
  • 同倍率重复插入验证： 在 one_shot = true 前提下，同一任务内对 MY_HEADER 再次尝试以相同 1.0 倍率插入时，分值不予累加；若后续出现更大绝对值的同号分值，系统仅按差额调整。
