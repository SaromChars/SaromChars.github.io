Dovecot 的 LMTP 本地投递

2021年11月17日
|

在邮件系统的分工中，边缘邮件传输代理（mail transfer agent，MTA）通常负责简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）的会话与重试队列。当邮件交由本地存储处理时，若继续使用标准 SMTP，单笔事务中包含多个收件人时数据阶段末尾只能返回单一应答码：地址在指令阶段被接受并不代表邮件已被实际保存，若部分收件人保存失败，调用方难以对不同收件人分别感知结果。

本地邮件传输协议（Local Mail Transfer Protocol，LMTP）由 RFC 2033 1 描述，适用于无需维护独立重试队列的投递子系统。LMTP 规定客户端使用 LHLO 替代 HELO/EHLO，且不得在 TCP 25 端口监听；在数据阶段终结符（<CRLF>.<CRLF>）之后，服务端必须针对此前校验通过的收件人，严格按照 RCPT TO 的发起顺序逐一返回独立状态回执。当服务端返回 2xx 肯定完成码时，即确认承担向该收件人投递或转交的责任。本文结合开源实现 Dovecot 2.3.16 的源码调用链，分析 LMTP 服务的调用权限、身份映射、投递提交与失败清理机制，并对自研邮件系统的状态设计给出工程推导 2。

地址校验与收件人上下文构建

在 Dovecot 2.3.16 中，LMTP 服务通常通过本地套接字或私有网络接收请求。当客户端发出 RCPT TO 指令时，src/lmtp/lmtp-commands.c 中的 cmd_rcpt() 调用 client_default_cmd_rcpt() 3。在本地模式下，该逻辑转入 lmtp_local_rcpt()（位于 src/lmtp/lmtp-local.c）执行实际地址处理 4。

在 lmtp_local_rcpt() 中，服务以 service = "lmtp"、目标用户名及会话标识构造参数，调用 mail_storage_service_lookup() 查询用户信息库（user database，userdb）：

  • 若查找返回负值，向客户端返回 451 4.3.0 Temporary internal error；
  • 若用户不存在（返回 0），返回 550 5.1.1 User doesn't exist: %s；
  • 若查找成功，注册 approved 与 destroy 回调钩子。当整条指令合法并被接受后，lmtp_local_rcpt_approved() 将收件人加入当前事务的合法收件人列表；连接断开或事务重置时，lmtp_local_rcpt_destroy() 负责取消未完成的并发查询、解除资源登记并释放引用。需要注意的是，即使在地址阶段配置了快速配额预检，此时返回的 250 OK 仅代表地址被接受，并不构成最终的落盘承诺。

逐收件人投递循环与状态回执

客户端发送数据终结符后，src/lmtp/lmtp-commands.c 的 cmd_data_finish() 触发 client_default_cmd_data()，本地模式由此调用 lmtp_local_data() 3。数据阶段的执行流程从 lmtp_local_deliver_to_rcpts() 步进到 lmtp_local_deliver()，按先前 RCPT TO 的登记顺序依次处理每个合法收件人。若本地原始报文输入流无法打开，服务直接对所有本地收件人返回 451。

lmtp_local_deliver() 先调用 mail_storage_service_next()，再经可替换的 client->v.local_deliver；默认实现 lmtp_local_default_deliver() 组装 mail_deliver_input 并进入 mail_deliver()：

  • 若切换用户环境失败，返回 451 4.3.0；
  • 经由投递流程尝试落盘。若 mail_deliver() 返回 0，服务格式化输出肯定回执：250 2.0.0 <session_id> Saved；
  • 若投递返回临时错误，输出 451 4.2.0 及临时错误说明；若被拒收，输出 552 5.2.0；内部异常则输出 451 4.3.0；
  • 若遇到配额不足错误（MAIL_DELIVER_ERROR_NOQUOTA），服务检查配置项 quota_full_tempfail：若开启则返回 452 4.2.2 配额超限临时失败，指示调用方稍后重试；若未开启则返回 552 5.2.2，触发调用方退信；
  • 收件人处理后，循环按结果停用用户上下文；不再需要的用户实例会被释放，为复用首个已存消息而保留的用户引用则延后清理。事务收尾再释放缓存消息的读取事务与相关邮箱资源。

在多收件人场景下，first_saved_mail 会保留当前事务中首个成功保存的消息引用，可能允许特定存储后端利用硬链接复用已有数据，但该机制仅作用于同一事务内的后续收件人。任何一个收件人发生失败，都不会导致前面已经独立完成投递的收件人被回滚。

存储事务提交、插件钩子与失败责任

实际存储写入由 src/lib-lda/mail-deliver.c 承载 5。mail_do_deliver() 调用 deliver_mail 钩子。钩子返回正值时按处理成功计算，即使未保存；返回非正值时，如果 ctx->saved_mail 已置位仍按成功处理，以免已经保存后再退信；否则按失败处理，并依临时错误和是否尝试过默认保存决定是否进入默认保存分支。

这一调用链带来几个关键的工程边界：

Saved 状态不等于收件箱新增：如果启用了投递扩展钩子，插件可能在自身逻辑中成功分流或处理该邮件，而无需在默认存储中新建邮件。只要钩子返回成功且未请求继续执行默认保存，LMTP 依然向客户端输出带 Saved 的 250 应答。因此，Saved 仅代表 LMTP 本地投递流程正常接管并处理完毕，不能据此直接断定收件箱（INBOX）中新增了邮件，具体插件行为需结合其扩展逻辑单独审计。

保存阶段与提交阶段的错误隔离：在 mail_deliver_save() 中，系统通过 mailbox_save_alloc() 分配保存上下文，通过 mailbox_save_using_mail() 写入报文数据。若写入阶段失败，系统主动调用 mailbox_transaction_rollback() 请求回滚；若写入完成，则调用 mailbox_transaction_commit_get_changes() 尝试提交。mailbox_transaction_commit_get_changes() 返回 0 后才设置 ctx->saved_mail = TRUE；默认保存路径以这个成功提交作为保存成功依据。若提交接口返回失败，流程按错误返回。物理临时文件的清理与存储索引的崩溃恢复由具体存储后端实现负责，本层接口调用无法证明任意物理后端的无残留状态。

耐久性界限：LMTP 服务在这一层只能观测到存储层 API 的返回值。API 提交成功表明存储驱动已接受该事务，但断电环境下的物理耐久性依赖于具体后端实现、操作系统同步机制（如 fsync）以及底层存储硬件的故障恢复策略，不能单凭 LMTP 层的 250 状态码认定数据已持久化到物理介质。

权限控制与自研服务工程推导

根据上述协议约束与 Dovecot 的实现逻辑，在自建或自研 LMTP 本地投递组件时，需要关注以下系统设计要点：

若 LMTP 服务监听在本地 UNIX 域套接字上，该套接字文件必须由实际发起投递的客户端进程访问。通常通过所属组与文件掩码（如 0660）实施隔离，禁止无权系统进程向本地投递接口直接注入未经验证的报文，具体权限配置须在实际部署环境中验证。投递进程必须依据受信任的用户信息库（user database，userdb）将收件人映射为对应的 uid、gid 及合法存储目录，并在操作用户信箱前切换至目标安全上下文，不接受信封参数中携带的任意外部文件路径。

自研系统不应仅依赖单次连接的内部标识。上游持久化队列应维护全局唯一的邮件任务标识（Message Task ID）与收件人任务标识（Recipient Task ID），并在跨连接重试期间保持不变；每次投递连接或尝试则分配独立的会话标识（Session ID）与尝试标识（Attempt ID），便于分布式链路追踪。RFC 2033 明确要求数据阶段后的回执流必须与早先已接受的 RCPT TO 指令顺序严格一致，而非按各收件人底层处理完成的先后顺序乱序输出。自研服务在多线程或异步保存时，必须由收集模块按照原始顺序排队发送回执。

当单笔事务中仅有部分收件人返回 4xx 临时失败，客户端必须保留已获 250 成功者的完成记录，并在后续重试调度中仅对临时失败或未获最终回执者发起新的投递事务；若收到永久性 5xx 失败，由上游记录失败并按既定退信或通知策略处理，不再自动重试。若服务端底层存储事务已提交成功，但在回传 250 期间网络中断或客户端超时断开，客户端因未收到确认回执，会将该收件人判定为投递未完成并在稍后发起重试。由于 Message-ID 仅为报文头元数据，重发或转发场景均可能产生相同取值，存储层不能仅凭 Message-ID 做粗暴去重；若需实现严格幂等，应在客户端与存储层协同约定传递持久化的投递流水标识。

教学推导方案：多收件人部分失败场景

本方案演示两个收件人在同一 LMTP 事务中分别遭遇成功与临时存储异常时的处理时序。注：本方案未在实际服务器中启动运行，属于待执行的教学推导方案。

客户端通过 LMTP 提交一封包含两个收件人的邮件，服务端的本地用户信息库已验证两位收件人均有效：

C: RCPT TO:<alice@example.test>
S: 250 2.1.5 OK
C: RCPT TO:<bob@example.test>
S: 250 2.1.5 OK
C: DATA
S: 354 Start mail input; end with <CRLF>.<CRLF>
C: [Message Content]
C: .
S: 250 2.0.0 <session-001> Saved
S: 451 4.2.0 Temporary failure

服务端在数据阶段结束后，按顺序输出两条回执：首条 250 对应 alice@example.test，表明其邮件已成功交由存储处理；第二条 451 对应 bob@example.test，表明其在保存阶段发生临时错误。

在实际测试或集成该场景时，可通过以下步骤执行验证：

  • 准备两个相互隔离的测试邮箱目录，配置投递客户端仅与本地 LMTP 套接字通信。
  • 在保存阶段注入模拟故障，使针对 bob 的存储写入触发模拟 IO 异常，而 alice 保持正常流程。
  • 检查客户端与服务端通信记录，确认服务端返回的第二行状态码严格对齐为 451，且首条 250 输出不受影响。
  • 检查两用户邮箱与上游队列状态，确认 alice 成功落盘一封邮件且投递任务标记为完成，bob 信箱中未出现半成品邮件；上游队列仅保留 bob 重试。恢复 bob 存储后触发重试，验证发起的全新事务中仅包含 bob，重试成功后仅 bob 信箱新增该邮件。
  • 在针对 alice 的 250 回执刚写入但客户端尚未完全读取时强行关闭连接，观察上游队列判定逻辑与重试时服务端产生的重复写入表现，据此评估幂等设计。
