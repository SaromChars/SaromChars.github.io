Postfix smtpd 的会话状态与收件人校验

2021年10月31日
|

在实现或运维简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）服务端时，一个常见的疑问是：当某个 RCPT TO 命令因未授权中继或收件人不存在被拒绝后，当前会话中的后续命令是否会受到污染？

在成熟的邮件传输代理（Mail Transfer Agent，MTA）如 Postfix 中，网络连接与单次邮件事务的上下文虽然保存在同一会话结构中，但两者的生命周期有着明确区分。一个收件人被拒绝，既不会递增已接受收件人计数，也不会将该收件人记录写入后端队列；在未触发通用错误计数超限等中断条件的前提下，客户端依然可以在该连接上继续发送后续合法的收件人指令。

本文基于 2021 年 7 月 24 日发布的 Postfix 3.6.2 稳定版源码 [1]，解析 smtpd(8) 服务中命令分派、会话状态流转、访问控制列表（Access Control List，ACL）评估时机以及事务清理链条，为自建服务配置核验与自研 SMTP 状态机提供参考。

连接与事务生命周期的区分

Postfix 的 smtpd 进程负责处理客户端的网络连接与协议交互。在启动初始化时，smtpd.c 的配置绑定机制通过 CONFIG_INT_TABLE 与 CONFIG_TIME_TABLE（如 VAR_SMTPD_RCPT_LIMIT 绑定内部变量 var_smtpd_rcpt_limit，VAR_SMTPD_TMOUT 即公开参数 smtpd_timeout 绑定 var_smtpd_tmout）完成参数装载。进入会话后，核心结构体 SMTPD_STATE（定义于 src/smtpd/smtpd.h [2]）同时管理着连接与事务两个不同生命周期的字段：

  • 连接级字段：贯穿整个客户端 TCP 连接的生命周期。例如客户端套接字流句柄 client、解析后的客户端主机名 name 与 IP 地址 addr、用于日志输出的 namaddr、HELO 握手参数 helo_name、累计错误次数 error_count 与错误掩码 error_mask 等。
  • 事务级字段：仅在单封邮件传输事务中有效，在事务重置或结束时回收。包括发件人地址 sender、首个收件人记录 recipient、已成功接受的收件人数量 rcpt_count、超出收件人上限后的探测计数 rcpt_overshoot、实际接收字节累计 act_size，以及通往后台队列处理进程的管道句柄 cleanup 和文件流封装 dest。

Postfix 通过判断发件人指针是否非空来识别当前是否处于邮件事务中：

/* src/smtpd/smtpd.h:336 */
#define SMTPD_IN_MAIL_TRANSACTION(state) ((state)->sender != 0)

这里的细节在于：只要 state->sender 非空指针，系统即判定当前事务已开启。对于系统退信等使用空反向路径（MAIL FROM:<>）的合法邮件，Postfix 会将其规范化为长度为 0 的空字符串并分配内存，因此 state->sender 指针依然非空，事务状态判定依然成立。

当客户端执行 RSET 命令，或者邮件正常进入提交并走完末尾回收路径时，服务端会调用 mail_reset(state) 与 rcpt_reset(state)。发件人字符串被释放、收件人计数被重置，但连接级别的 TCP 套接字和握手状态（如 helo_name）得以保留，客户端可在同一连接内开启下一封邮件传输。

命令分派与逐行同步处理

在本连接内，Postfix 的 smtpd 采用同步逐行读取与命令分派机制。连接建立后，协议主循环由 smtpd_proto（位于 src/smtpd/smtpd.c [3]）驱动，并在入口处调用 smtp_stream_setup(state->client, var_smtpd_tmout, ...) 设置 I/O 超时：

  1. 逐行读取与异常捕获：使用 vstream_setjmp(state->client) 捕获底层 I/O 异常。当客户端连接空闲超时触发 SMTP_ERR_TIME 时，服务端发送 421 4.4.2 Error: timeout exceeded 并关闭连接；检测到对端直接断开连接（SMTP_ERR_EOF）时，退出协议循环并清理状态。
  2. 命令查表分派：通过 smtpd_token 将输入行切分为参数数组，随后在命令表 smtpd_cmd_table 中匹配命令名，分派到对应的实现函数，如 mail_cmd、rcpt_cmd、data_cmd、rset_cmd 等。
  3. 流水线处理：虽然 ESMTP 支持流水线（PIPELINING），但服务端在处理逻辑上仍然按照读取到的行顺序逐条同步执行。若某条 RCPT TO 校验失败，服务端立即向网络缓冲区写入对应 5xx 或 4xx 响应，随后继续读取并独立评估下一行命令。

MAIL FROM：事务初始化与限制预检

当 mail_cmd 收到 MAIL FROM 命令时，首先执行协议阶段检查：

  • 阶段校验：若配置了 smtpd_helo_required = yes 且握手参数 state->helo_name == 0，拒绝并返回 503 5.5.1 Error: send HELO/EHLO first。
  • 嵌套事务防护：若 SMTPD_IN_MAIL_TRANSACTION(state) 已经为真，说明前一事务仍未重置，直接拒绝 503 5.5.1 Error: nested MAIL command。此时并不会重置既有事务，原有发件人依然保留。
  • 语法校验：解析参数是否以 FROM: 开头，地址格式是否符合协议规范。

在早退校验阶段，若客户端声明了 SIZE=n 扩展参数，函数会调用 smtpd_check_size 进行预检：若声明大小超过配置的 message_size_limit，立即返回 552 5.3.4 Message size exceeds fixed limit。同时，smtpd_check_queue 会检查本地队列存储空间，若剩余空间不足 queue_minfree，提前返回临时错误 452 4.3.1 Insufficient system storage。

只有当所有前置检查全部通过并成功分配发件人内存后，新的事务才推进到开启阶段。在配置为立即打开队列流（var_smtpd_delay_open == 0）时，若紧接着执行的 mail_open_stream(state) 失败，系统会立即调用 mail_reset(state) 回滚发件人并返回错误；只有全部成功并向客户端输出 250 2.1.0 Ok，才代表新事务在外部边界上正式确立：

/* src/smtpd/smtpd.c:2703-2720 */
GETTIMEOFDAY(&state->arrival_time);
state->sender = mystrdup(STR(state->addr_buf));
/* ... 初始化 instance 与协议扩展属性 ... */
if (var_smtpd_delay_open == 0 && mail_open_stream(state) < 0) {
    mail_reset(state);
    return (-1);
}
smtpd_chat_reply(state, "250 2.1.0 Ok");
return (0);

如果在检查过程中发现语法或策略错误早退，mail_cmd 直接返回 -1，新发件人不会被写入 state->sender。

RCPT TO：访问控制、中继限制与目录检查

rcpt_cmd 是反垃圾策略与收件人校验的核心。客户端发送 RCPT TO 时，处理流程分为前后两个阶段：

1. 延迟限制与中继评估顺序

Postfix 默认启用 smtpd_delay_reject = yes。这意味着即使客户端在连接、握手或发信人阶段触发了拒绝规则，Postfix 也会将拒绝推迟到收到第一个 RCPT TO 时才生效并输出响应。这样设计的目的是尽可能将客户端 IP、发件人和收件人完整记录在同一条拒绝日志中，便于事后排查分析。

在进入具体的收件人策略前，smtpd_check_rcpt（位于 src/smtpd/smtpd_check.c [4]）会先回放延迟的检查：

/* src/smtpd/smtpd_check.c:5078-5082 */
if (var_smtpd_delay_reject)
    if ((err = smtpd_check_client(state)) != 0
        || (err = smtpd_check_helo(state, state->helo_name)) != 0
        || (err = smtpd_check_mail(state, state->sender)) != 0)
        SMTPD_CHECK_RCPT_RETURN(err);

随后评估收件人限制。在 Postfix 架构中，中继限制（smtpd_relay_restrictions）与收件人限制（smtpd_recipient_restrictions）被拆分为两个独立的限制列表。两者的评估顺序由源码内部变量 var_relay_before_rcpt_checks（对应公开配置参数 smtpd_relay_before_recipient_restrictions）决定，并结合兼容性等级（compatibility_level）的警告分支综合计算得出：

/* src/smtpd/smtpd_check.c:5112-5114 */
rcpt_index = (var_relay_before_rcpt_checks
              && !warn_compat_break_relay_restrictions);
relay_index = !rcpt_index;

中继限制的核心规则由 reject_unauth_destination（定义于 src/smtpd/smtpd_check.c:1748）实现：

/* src/smtpd/smtpd_check.c:1748-1768 核心流程截取 */
static int reject_unauth_destination(SMTPD_STATE *state, char *recipient,
                                      int reply_code, const char *reply_dsn)
{
    /* ... 调试日志输出 ... */
    if (permit_auth_destination(state, recipient) == SMTPD_CHECK_OK)
        return (SMTPD_CHECK_DUNNO);

    return (smtpd_check_reject(state, MAIL_ERROR_POLICY,
                               reply_code, reply_dsn,
                               "<%s>: Relay access denied",
                               recipient));
}

这里需要将授权中继目的地址与合法收件人目录清晰区分：

  • reject_unauth_destination 解决的是域名路由归属问题，判断本站是否有权为该收件人域名进行邮件转发；
  • reject_unlisted_recipient 调用的 check_recipient_rcpt_maps 解决的是收件人真实存在性问题。它会按收件人地址类别选用相应目录进行核验：本地域查询本地收件人表（local_recipient_maps），虚拟别名域查询虚拟别名表（virtual_alias_maps），虚拟邮箱域查询虚拟邮箱表（virtual_mailbox_maps），中继域查询中继收件人表（relay_recipient_maps）。注意中继目录用于核验下一跳收件人合法性，并不表示账户在本机存储。

2. 状态保护与计数递增

在校验过程中若任何规则产生拒绝（例如返回 554 5.7.1 Relay access denied 或 550 5.1.1 User unknown），rcpt_cmd 执行以下分支：

/* src/smtpd/smtpd.c:2996-2999 */
if (err != 0) {
    smtpd_chat_reply(state, "%s", err);
    return (-1);
}

直接向对端输出错误文本后返回 -1。此时，state->rcpt_count 不会递增，更不会向后端的 cleanup 队列写入任何收件人数据。

只有当地址通过所有 ACL 检查，并且队列流或代理连接准备完毕后，才会执行真正的状态提交：

/* src/smtpd/smtpd.c:3061-3085 */
state->rcpt_count++;
if (state->recipient == 0)
    state->recipient = mystrdup(STR(state->addr_buf));
if (state->cleanup) {
    rec_fputs(state->cleanup, REC_TYPE_RCPT, STR(state->addr_buf));
    vstream_fflush(state->cleanup);
}
smtpd_chat_reply(state, "250 2.1.5 Ok");
return (0);

一个被拒绝的 RCPT 仅记录在日志并更新协议错误统计，不会增加已接受收件人总数。只要连接累计的错误数未达到硬限阈值（smtpd_hard_error_limit），客户端完全可以在当前会话中继续发送下一个合法收件人。

针对收件人数量配额，Postfix 区分了常规上限 smtpd_recipient_limit 与超限容忍缓冲 smtpd_recipient_overshoot_limit。当已接受收件人数达到上限后，首批超限的探测在 rcpt_overshoot 未超出缓冲时，函数虽然回复 452 4.5.3 Error: too many recipients 但依然返回 0，暂不计入通用错误预算；只有连续超出容忍阈值后，才返回 -1 并记录策略错误，最终可能导致连接因达到错误硬限而断开。

DATA 处理与落地确认

当客户端发出 DATA 命令时，data_cmd 首先检查 state->rcpt_count 是否大于 0：

  • 若不在事务中，回复 503 5.5.1 Error: need RCPT command；
  • 若处于事务中但没有成功接受任何收件人，回复 554 5.5.1 Error: no valid recipients 并阻断数据传输。

通过后，服务端回复 354 End data with <CR><LF>.<CR><LF> 并进入 receive_data_message 读取正文：

  1. 实际大小累计：虽然在 MAIL FROM 阶段可能做过 SIZE 声明预检，但正文传输过程中 Postfix 会逐行累加 state->act_size。若累计大小超过 message_size_limit，状态置为 CLEANUP_STAT_SIZE 并记录警告日志。
  2. 字节流消费边界与异常保护：当在正文传输中途检测到大小超限或写入错误时，Postfix 并不会立刻关闭连接，而是继续循环读取，直至遇到标准的行尾终结点 \r\n.\r\n。若在读取流中途发生 I/O 超时或对端断开，底层捕获后转入连接清理；若连接正常保持，排空至终结点保证了命令流同步，防止未消费完的邮件内容被当作后续新的 SMTP 指令误解析。
  3. 确认落盘与响应：读取完终止符后，进入 common_post_message_handling。向 cleanup 服务写入 REC_TYPE_END 结束标记，并等待后端队列文件处理完成。只有收到 cleanup 服务返回的写入成功状态（state->err == CLEANUP_STAT_OK），才向客户端发送最终的队列接收确认： 
    250 2.0.0 Ok: queued as 4St8xyz...
  4. 清理回收与早退例外：在常规的收尾退出路径中，服务端会执行清理函数： 
    /* src/smtpd/smtpd.c:3758-3759 */
mail_reset(state);
rcpt_reset(state);
    需要指出的是，在 Postfix 3.6.2 的源码实现中，存在一个特殊早退分支：如果在 smtpd_check_eod（数据段结束检查）阶段被策略拒绝，函数在关闭流后直接返回，未能走入末尾的 mail_reset 与 rcpt_reset。这提醒我们在进行自研状态机设计时，应当在事务终结出口统一进行清理，避免条件分支遗漏。

自建配置核验与自研设计指引

自建 Postfix 配置核验要点

  1. 分离中继与本地收件人策略： 在 main.cf 中建议明确将中继权限与本地反垃圾策略分离： 
    # 控制中继权限（防止沦为外部中继）
smtpd_relay_restrictions =
    permit_mynetworks,
    permit_sasl_authenticated,
    reject_unauth_destination

# 控制本地收件人及反垃圾检查
smtpd_recipient_restrictions =
    reject_unauth_pipelining,
    reject_non_fqdn_recipient,
    reject_unknown_recipient_domain,
    permit
  2. 规则评估顺序与中继安全：smtpd_recipient_restrictions 按照列表自上而下评估，首个明确匹配的规则（permit 或 reject）生效。需要注意：在现代 Postfix 中，即使收件人规则中包含了无条件 permit，只要 smtpd_relay_restrictions 依然独立运行并包含 reject_unauth_destination，非本地中继依然会被阻断。只有当管理员为了向后兼容将中继检查完全依赖于收件人列表且无独立中继防护时，在收件人列表中过早配置无条件 permit 才会造成开放中继漏洞。
  3. 保持 delay_reject 默认开启：保留 smtpd_delay_reject = yes 可以在收件人阶段汇总获得客户端 IP、发件人和收件人，为日志审计与安全分析提供完整的上下文。

自研 SMTP 服务端状态机设计推导

在自行实现 SMTP 接收端或网关时，建议参考以下状态处理原则：

  1. 生命周期分离：网络连接上下文（TCP 套接字、握手信息）与邮件事务上下文（发件人、收件人列表、临时文件句柄）应当独立封装。事务对象可在接收完成或 RSET 时迅速销毁，不影响长连接保持。
  2. 收件人错误隔离：单次 RCPT TO 校验失败时，仅返回对应的状态码，切勿更改连接级正常状态，也绝不能将失败的收件人压入队列记录中。
  3. 超限流消费边界：在 DATA 阶段检测到尺寸超限时，服务端有两种合理的工程选择：
    • 若选择复用该连接，则在未发生超时或断线的前提下持续读取并消费输入流直至遇到行尾终结点 \r\n.\r\n，然后再发送 552 响应，确保连接后续能够继续接收 RSET 或新命令；若读取过程中触发超时则直接关闭连接并清理；
    • 若选择直接返回错误并关闭连接（发送带 421 状态码或直接断开连接），则必须彻底终结该会话，禁止在未消费完邮件正文的情况下继续将后续字节作为 SMTP 命令解析。
  4. 外部查询异常与 4xx 降级：当后端数据库或目录服务发生超时、内部错误时，状态机应返回 4xx 临时失败状态码（如 451），切忌误报为 550 User unknown 永久拒绝，以免造成合法邮件被发件方系统退信。

开发验证方案（未执行测试）

以下给出一套可用于验证 SMTP 状态机逻辑的工程测试设计（注：本方案为基于协议规范与源码逻辑设计的测试用例，未在实际环境中执行）：

验证用例 1：被拒 RCPT 隔离与后续合法 RCPT 提交

  • 测试目的：验证非法收件人被拒绝后，会话状态与计数器未被污染，后续合法收件人能正常提交。
  • 前置设定：服务端已配置中继限制 reject_unauth_destination；测试客户端未认证且不在受信任网段；example.com 为本地域且 good@example.com 在目录中有效存在；无其他策略拒绝，目录查询均成功，测试期间无网络超时和异常断线。
  • 输入序列：
    1. 连接并完成 EHLO test.client。
    2. 发送 MAIL FROM:<tester@client.test>。
    3. 发送外部非中继域收件人：RCPT TO:<bad@external.invalid>。
    4. 发送合法本地收件人：RCPT TO:<good@example.com>。
    5. 发送 DATA，写入标准测试正文并以 \r\n.\r\n 结尾。
  • 预期观察：
    • 第 3 步返回 554 5.7.1 ... Relay access denied。
    • 第 4 步返回 250 2.1.5 Ok；此时观测服务端内部状态，rcpt_count 准确为 1。
    • 第 5 步 DATA 命令返回 354，正文提交后返回 250 2.0.0 Ok: queued as ...。普通收尾后服务端 rcpt_count 与发件人被重置为 0/空。
    • 后端队列记录与计数状态异步观测：后端队列文件中仅包含 good@example.com 一条收件人记录，被拒绝的收件人不进入队列。

验证用例 2：DATA 长度超限与流同步边界

  • 测试目的：验证当消息体超过配额时，服务端是否在消费完终结符后才反馈错误，且连接能通过 RSET 恢复。
  • 前置设定：服务端配置限制 message_size_limit = 10240（10 KB）；good@example.com 存在；测试期间无网络超时。
  • 输入序列：
    1. 发送 MAIL FROM:<tester@client.test> 与 RCPT TO:<good@example.com>。
    2. 发送 DATA，收到 354 响应后，连续发送累计 20 KB 的多行短文本数据，紧接着发送 \r\n.\r\n。
    3. 不断开连接，紧接着发送 RSET 与新的 MAIL FROM:<tester2@client.test>。
  • 预期观察：
    • 在正文数据发送过程中连接不被对端强制重置，服务端在完整接收到终结符后返回 552 5.3.4 Message size exceeds fixed limit。
    • 随后的 RSET 成功返回 250 2.0.0 Ok。
    • 新的 MAIL FROM 成功返回 250 2.1.0 Ok，证明数据流解析完全同步，未发生粘包或命令错位。
