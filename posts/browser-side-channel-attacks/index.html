浏览器中的侧信道攻击与防御

2022年6月12日更新于: 2026年11月10日
|

在日常浏览网页时，本地 HTTP 缓存能够缩短重复资源的获取耗时。然而，这种因缓存命中带来的时间差异，在安全视角下也可能成为一条泄露用户隐私的侧信道（side-channel）：在资源允许缓存且处于同一可复用分区等前置条件下，攻击者无需攻破同源策略（Same-Origin Policy，SOP）直接读取跨源报文内容，只需测量跨源资源请求的事件派发时序波动，便可能推断目标资源是否已存在于本地缓存中，进而推断用户是否曾访问过特定页面。[Felten 2000 §2][W3C Same-Origin Policy]

侧信道攻击（side-channel attack，SCA）关注的通常不是越界数据读写，而是计算任务在底层硬件或共享资源上产生的物理与逻辑副作用，如执行耗时、微架构缓存争用以及排队延迟等。[Kocher 1996 §1]与用于识别或重新识别访问浏览器的无状态指纹（browser fingerprinting）相比，侧信道分析是一种推断内部机密或跨源状态的方法；而在底层测量中，计时等侧信道同样可以为浏览器指纹提供高熵特征信号。[W3C Fingerprinting Guidance §1.1, §3]

计时基石与隐式时钟构造

Web 环境中的侧信道分析，通常依赖对操作耗时的度量。无论是微架构缓存组的命中状态，还是跨源资源的加载反馈，都会在时间轴上产生微秒乃至纳秒级的差异。[Kocher 1996 §2]

早期 Web 标准为页面提供了显式高精度计时接口 performance.now()。该接口最初用于评估渲染性能与帧率。在微架构漏洞披露后，浏览器厂商对未隔离环境下的显式时钟实施了粗化与抖动限制：例如，WebKit 在 2018 年的应急缓解中将常规上下文的计时精度降至 1 毫秒；其他主流浏览器也根据是否处于跨源隔离环境及隐私设置，对显式时钟实施了不同程度的精度粗化。[WebKit Timing Defenses]

然而，降低显式 API 的精度并不能彻底切断相对时间基准。利用浏览器运行时的并发执行与异步调度原语，攻击者可以构造出具有较高分辨能力的隐式时钟（implicit timers）：[Schwarz 2017 §3]

  1. 共享内存并发计数器： 在支持的环境中，脚本利用 Web Workers 结合共享内存数组（SharedArrayBuffer，SAB）。攻击者在独立的 Worker 线程中运行循环，持续推进 32 位整数计数；主线程在受测任务执行前后读取该计数。尽管计数器的增量受即时编译（just-in-time compilation，JIT）优化、CPU 频率调度与多核缓存一致性影响，并不严格等同于固定频率的硬件时钟周期，但在短时间内仍可作为灵敏的相对时间代理。
  2. 异步任务队列排队时钟： 在缺乏共享内存的受限环境下，脚本还可以利用异步事件循环测量粗粒度的执行或排队差异。例如向 MessageChannel 任务队列分发空消息，通过测量事件派发间隔或堆叠任务清空耗时，结合多次采样统计均值降低调度抖动。这种方案的时钟分辨率取决于具体事件调度周期与浏览器环境，通常无法直接匹敌共享内存计数器的精细粒度。
// 基于 SharedArrayBuffer 与 Atomics 的隐式计数器示意（阐述原理）
// 假设主线程已完成 Worker 启动并确认就绪

// worker.js: 辅助线程持续推进共享计数
self.onmessage = function(e) {
  const sharedBuffer = e.data;
  const view = new Int32Array(sharedBuffer);
  Atomics.store(view, 1, 1);
  while (true) {
    Atomics.add(view, 0, 1);
  }
};

// main.js: 主线程利用计数器增量作为相对耗时代理
function measureRelativeTime(targetTask, sharedBuffer) {
  const view = new Int32Array(sharedBuffer);
  const startTick = Atomics.load(view, 0);
  
  targetTask(); // 执行同步待测任务
  
  const endTick = Atomics.load(view, 0);
  return (endTick - startTick) >>> 0;
}

上述代码假定受测任务为同步执行且真实增量严格小于 232 步；若任务涉及异步操作，该同步结构仅能测量到任务发起的耗时。此外，若长时间执行导致计数器发生多次完整回绕，则无法单凭差值直接判断真实耗时。[Schwarz 2017 §4]

JavaScript 中的缓存侧信道

现代中央处理器（central processing unit，CPU）采用多级分层缓存体系（L1、L2 与末级缓存 last-level cache，LLC）缓解处理器计算速度与动态随机存取内存（dynamic random-access memory，DRAM）访问延迟之间的差距。在典型现代微架构中，访问 L1 缓存通常只需 4 至 5 个时钟周期，若逐级未命中最终必须通过总线访问 DRAM，耗时可能跃升至数十甚至数百周期。

在系统级原生环境中，攻击者可通过汇编指令管理缓存行。而在沙箱隔离的 JavaScript 运行时中，既不存在显式缓存清理指令，代码也无法直接获知操作系统的虚拟地址或物理页分布。Yossef Oren 等人在 2015 年的研究证实，填装+探测（Prime+Probe）侧信道攻击可以在无特权的纯浏览器 JavaScript 环境中实施：[Oren 2015 §2]

处理器末级缓存通常采用组相联（set-associative）结构，内存地址按照特定哈希规则映射到固定的缓存组（Cache Sets）。Prime+Probe 的基本过程如下：[Oren 2015 §3]

  1. 构造驱逐集（Eviction Sets）： 攻击者在堆中分配大尺寸数组（如数十兆字节的 ArrayBuffer）。虽然其在高级语言层表现为连续的数组索引，但在操作系统底层并不对应连续物理内存。攻击者通过按步长访问并结合计时反馈与集合缩减算法，反复筛选出一组在 LLC 中恰好竞争相同缓存组的数组偏移与访问位置，形成驱逐集。
  2. 填装阶段（Prime）： 攻击者访问驱逐集中的所有内存项，将自身数据载入目标缓存组，促使该组中原有的其他数据被替换失效。
  3. 等待受害者执行（Wait）： 攻击者让出主线程或诱导目标活动。若受害者在执行期间访问了映射到同一缓存组的数据，CPU 会将受害数据载入该组，使攻击者的部分缓存行被替换失效。
  4. 探测阶段（Probe）： 攻击者再次按特定间隔与顺序访问驱逐集并度量耗时。若某一缓存组的读取耗时偏高，表明在等待期间该组发生过访存竞争。

需要指出的是，单次 Probe 变慢只反映当前缓存组发生过置换干扰，可能由操作系统调度或后台任务引起。同时，JavaScript 运行时的垃圾回收（garbage collection，GC）暂停、JIT 即时编译的动态优化与硬件预取器，都会引入噪声。攻击者通常需要大量重复测量与统计信号处理，才能在特定实验条件下还原出粗粒度的访问模式。[Oren 2015 §5]

推测执行与瞬态指令窗口

缓存侧信道揭示了微架构资源竞争的可测性，而推测执行（speculative execution）漏洞则表明，仅依靠高级语言层面的类型检查与软件边界判断，无法阻止微架构层面的跨边界数据读取。[Kocher 2019 §1]

现代高性能 CPU 广泛采用分支预测（Branch Prediction）技术保持流水线满载。在条件分支尚未完成实际判断前，CPU 的硬件结构会依据历史记录超前推测执行预测路径上的指令；若后续确认预测错误，硬件会撤销架构层面的寄存器写入。

2018 年披露的 Spectre 变种 1（绕过边界检查，Bounds Check Bypass，CVE-2017-5753）指出，推测执行在分支预测错误回滚时，通常不会撤销已经发生的微架构缓存行填充：[Kocher 2019 §2]

// Spectre 变种 1 概念原理示意（依赖特定 JIT 编译生成的机器指令条件）
// array1 为经过边界检查的合法数组，array2 为攻击者构造的离散探针数组
if (x < array1.length) {
  // 当 x 超出合法边界，但分支预测器误判进入时：
  // 1. CPU 推测性执行越界读取该渲染进程虚拟地址空间中的字节（secret = array1[x]）
  // 2. 以 secret 为索引计算虚拟偏移，访问 array2 跨缓存行的特定项（例如 512 字节步长）
  value = array2[array1[x] * 512];
}

在概念攻击模型中，操作通常包含以下阶段：[Kocher 2019 §3]

  1. 训练预测器： 连续传入小于 array1.length 的合法索引 x 调用该代码段，使分支预测器建立该条件分支大概率成立的历史状态。
  2. 制造分支延迟： 构造使 array1.length 远离缓存的访存环境，迫使 CPU 耗时从更低层级缓存或主存读取边界值。
  3. 推测越界读取： 传入一个指向进程内其他虚拟地址的恶意偏移量 x。在长度读取未完成的时间窗口内，CPU 推测性执行分支内指令，越界读取进程虚拟地址空间内的数据，并以此为偏移触发 array2 对应项的缓存填充。
  4. 测量还原机密： CPU 得到边界检查结果后回滚架构状态，正常控制流并未抛出越界异常；但 array2 对应的微架构缓存状态已经改变。攻击者随后探测 array2 各位置的读取时延，尝试推测窗口中加载的字节值。[Kocher 2019 §4]

上述 JavaScript 代码仅为概念机制说明。实际利用严格依赖 JIT 引擎生成的机器指令排布、内存寻址方式以及 CPU 微架构的推测深度。此外，推测读取的范围受限于当前渲染进程所能访问的虚拟地址空间；由独立网络服务或主进程隔离保管的敏感凭据（如 HttpOnly Cookie）并不一定常驻于当前渲染进程中。

Spectre 表明，仅依赖软件边界检查无法保证同进程内内存的绝对安全。各大浏览器在 2018 年初禁用了 SharedArrayBuffer，并在 JIT 编译中引入了索引掩码（index masking）与推测屏障，同时推进由操作系统强制执行的进程地址空间隔离。[Reis 2019 §1]

跨站泄漏：宏观 Web 侧信道

侧信道并不仅限于微架构底层。Web 平台的网络协议、状态机制与渲染排版中存在的资源共享，同样构成了一系列信息信道，统称为跨站泄漏（Cross-Site Leaks，XS-Leaks）：[Knittel 2021 §1]

1. 总体网络与加载时序

在测量跨源资源时，HTML 媒体元素与异步 fetch() API 在同源策略下的表现存在差异：

  • HTML 媒体元素加载事件： 页面可以通过创建 <img> 标签并监听其 onload 与 onerror 事件测量时序。从在 DOM 或 JavaScript 中设置资源地址到事件最终派发，所测耗时不仅包括网络传输或本地缓存读取，还包含浏览器内部任务排队、事件循环调度与解码准备等环节，并不直接等同于屏幕渲染完成的时间点。
  • fetch API 与跨源限制： fetch() 默认采用 cors 模式发起请求。对于需要预检的请求，预检未通过时浏览器不会发送实际请求。对于已经发出的请求，响应未通过跨源资源共享（Cross-Origin Resource Sharing，CORS）检查时，浏览器不会把响应交给脚本，fetch() 返回的 Promise 会以 TypeError 拒绝。即使采用 no-cors 模式发起请求，请求成功时前端仅能获得不透明响应（opaque response），无法读取响应体、状态码或响应头，但脚本仍可观察 fetch() 返回的 Promise 结算时机。
  • Resource Timing API 的精度限制： 在没有 Timing-Allow-Origin（TAO）标头授权的情况下，跨源资源的 Resource Timing 接口仍会暴露总耗时（如 duration），但细粒度的网络阶段耗时（如 DNS 查询、TCP 握手、TLS 协商与请求/响应传输细节）会被限制或清零。[W3C Resource Timing Level 2]
  • 服务端处理时延差异： 若目标应用对不同参数或登录状态执行了复杂度差异明显的后端逻辑，其响应耗时可能呈现统计可区分的差距，甚至可通过图像等跨源资源的 onerror 事件派发时序进行推断。[Bortz 2007 §4]

2. HTTP 缓存状态探测

在资源允许被浏览器本地缓存且攻击者页面与受害者请求能够命中同一个缓存分区的前提下，从本地磁盘或内存中读取已缓存资源的时间通常低于经历跨网络往返的时间。攻击者可通过触发跨源资源获取，依据加载延迟推断目标资源是否已在用户本地缓存中。[Felten 2000 §2]

探测还需要能预测候选资源的 URL。

3. 渲染管线与排版时序

浏览器的图形排版引擎同样存在开销差异。历史上，攻击者曾尝试在包含 CSS :visited 伪类的超链接上施加特定排版变化，试图通过测量页面重绘（repaint）与布局时序反推链接的访问历史。现代浏览器通过限制 :visited 可改变的样式属性、让脚本样式查询统一返回未访问状态，并减少已访问与未访问链接在样式解析和布局中的执行差异，缓解了部分历史时序探测。[Mozilla :visited Fix]

现代浏览器的纵深防御体系

面对分布在微架构、网络栈与渲染层的侧信道风险，现代浏览器推行了面向系统架构的纵深防御：

1. 站点隔离（Site Isolation）

在推测执行漏洞面前，同一进程内的虚拟内存无法依赖语言虚拟机实现绝对隔离。Chromium 的站点隔离（Site Isolation）与 Firefox 的 Project Fission 将隔离边界上移至操作系统进程级别：[Reis 2019 §1]

启用完整站点隔离时，浏览器将属于不同带协议的站点（schemeful site，由协议与可注册域 eTLD+1 构成）的文档，分配到各自独立的操作系统渲染进程中。跨站的 <iframe> 被实现为进程外 iframe（out-of-process iframe，OOPIF）。每个站点进程拥有独立的虚拟地址空间与内存管理单元（memory management unit，MMU）页表映射。[Reis 2019 §2]

选择性站点隔离也会为符合条件的站点分配隔离进程。此外，站点隔离的核心防护效果建立在“目标敏感数据未进入攻击者所在渲染进程”的前提下。若跨站文档被分配在独立进程中，即便恶意页面利用 Spectre 读取自身渲染进程内可访问的数据，也无法触及受操作系统进程边界保护的其他站点内存。

在部署范围上，不同平台与浏览器存在实现差异：

  • Chromium： 在桌面平台自 Chrome 67 起默认启用完整站点隔离，并在后续版本中将浏览器扩展的进程隔离进一步完善；而在 Android 移动平台，受设备内存资源限制，初期主要针对用户登录过的站点实施隔离，直至 Chrome 92（2021 年 7 月）根据 Charlie Reis 与 Alex Moshchuk 发布的公告，进一步为高内存 Android 设备上的 OAuth 交互及声明了跨源开放者策略（Cross-Origin-Opener-Policy，COOP）的站点启用选择性隔离。[Chrome Site Isolation Update]
  • Firefox： Firefox 在桌面平台于 Firefox 95（2021 年 12 月）全面默认启用了基于进程隔离的 Fission 架构。[Firefox 95 Release Notes]

此外，Chromium 的跨源读取阻塞（Cross-Origin Read Blocking，CORB）协同生效，在跨源响应从网络进程传输至渲染进程前进行内容嗅探，阻止未授权的敏感内容类型（如特定 HTML、XML 及 JSON）进入可能被恶意控制的渲染进程地址空间。[Reis 2019 §3.5]

2. 跨源隔离上下文（Cross-Origin Isolation）

为了在 WebAssembly、图形渲染与多线程计算场景下安全恢复 SharedArrayBuffer，现代浏览器通过 COOP 与 COEP 标头确立了跨源隔离上下文机制：[Firefox 79 Cross-Origin Isolation]

页面必须在安全上下文（通常为 HTTPS 或受信任的本地环境）中，并在顶级响应标头中声明安全策略，典型配置如下：

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
  • 跨源开放者策略（Cross-Origin-Opener-Policy，COOP）： 声明 same-origin。当页面与跨源窗口相互打开时，若双方策略不匹配或不同源，浏览器会将其分配到不同的顶级浏览上下文组，切断对窗口对象（window.opener）的直接交互引用。
  • 跨源嵌入者策略（Cross-Origin-Embedder-Policy，COEP）： 声明 require-corp 时，页面所加载的跨源 no-cors 子资源必须通过跨源资源策略（Cross-Origin-Resource-Policy，CORP）获得显式许可；而自 Chrome 96 起正式支持的 credentialless 指令，允许跨源 no-cors 子资源在省略请求凭据（如 Cookie）的条件下加载，无需服务端具备 CORP 标头。[Chrome COEP Credentialless]对于跨源 iframe，依然需要子框架自身明确声明相应的隔离策略。

在满足上述策略的跨源隔离环境中，window.crossOriginIsolated 属性为 true，允许分配 SharedArrayBuffer，其显式计时精度也依具体浏览器实现得到恢复。[Chromium SAB Timeline]

3. 网络状态分区（Network State Partitioning）

针对 HTTP 缓存状态的 XS-Leaks，主流浏览器推进了网络状态分区：

  • Chromium： 自 Chrome 86 起全面启用 HTTP 缓存分区，将由顶层站点与当前框架站点构成的二元网络隔离键（Network Isolation Key，NIK）与资源 URL 组合为最终缓存键。[Chrome HTTP Cache Partitioning]
  • WebKit： WebKit 在 ITP 机制中针对 HTTP 缓存推行了双键模型，以第一方可注册域（eTLD+1）与第三方资源源（origin）作为隔离键，阻断跨第一方站点的缓存共享。[WebKit ITP 2.1]

4. 获取元数据请求标头（Fetch Metadata）

由浏览器网络层在向可信 URL 发起请求时统一注入获取元数据请求标头（Fetch Metadata Request Headers），页面前端脚本无法自行设置或篡改：[web.dev Fetch Metadata][Firefox 90 Fetch Metadata]

  • Sec-Fetch-Site：标明请求发起关系，包括 same-origin、same-site、cross-site 以及用户直接通过地址栏输入或书签访问时的 none。
  • Sec-Fetch-Mode：标明请求模式（例如 navigate、cors、no-cors）。
  • Sec-Fetch-Dest：标明资源的目标载体（例如 document、image、script）。

服务端可在请求处理的最前置逻辑中校验这些标头。若收到非预期的跨站请求，服务端可在执行耗时的数据库查询或业务计算前直接拒绝，从而缓解基于加载时延的探测尝试；对于不支持该特性的浏览器或合法跨站请求，服务端通常配置安全放行或备用策略。

对抗边界与工程权衡

侧信道防御的演进展现了系统安全在安全性、性能与通用性之间的平衡：

  1. 进程模型与物理开销： 站点隔离将跨站 iframe 拆分为独立的操作系统进程，提供了可靠的虚拟内存隔离，但显著增加了进程内存常驻占用与进程间通信（inter-process communication，IPC）成本。在内存紧缺的移动终端设备上，各浏览器通常需要针对内存阈值与站点重要度实施精细化的渐进隔离策略。[Reis 2019 §4]
  2. 常数时间执行在高级语言中的局限： 在专门的密码学库中，常数时间算法（constant-time execution）旨在确保控制流分支与内存访问索引独立于机密数据。然而在通用 Web 平台中，高级语言具有动态类型、JIT 即时编译优化以及运行时垃圾回收；要求通用业务逻辑在编译与调度层面消除一切数据相关的微小时间波动是不现实的。
  3. 隔离策略的重心迁移： 只要多个安全域的代码共享底层的 CPU 执行单元、缓存组与物理总线，完全消除微架构上的时间相关性就极其困难。因此，现代浏览器通过进程隔离减少跨站敏感数据与不受信任代码在同一地址空间中共存，并通过网络状态分区减少可跨站观察的共享状态。这些措施显著收紧了攻击条件，但并未消除跨进程的底层微架构资源竞争。
