浏览器中的侧信道攻击与防御

2026年11月9日
|

在探讨浏览器指纹（browser fingerprinting）时，核心问题通常是服务端或客户端探测脚本如何收集终端在硬件配置、图形渲染管线与音频实现中暴露的差异，从而组合为一个具备统计辨识度的特征向量。指纹关注的是概率性地识别访问设备，度量的是软硬件环境在不同客户端之间的配置与实现差异。[W3C Fingerprinting Guidance §1.1]

与之相比，侧信道攻击（side-channel attack，SCA）关注的通常不是设备身份，而是计算任务在底层硬件或共享资源上产生的物理与逻辑副作用。Web 客户端的安全基石建立在由协议、主机名与端口构成的同源策略（Same-Origin Policy，SOP）之上。[W3C Same-Origin Policy] 侧信道分析不要求通过常规架构可见的内存越界读写获取机密，而是度量时间消耗、缓存争用或网络排队等客观物理特征，推断受害者在其他源（origin）中的敏感数据或状态。[Kocher 1996 §1]

两种技术在底层并不孤立：同一种高精度计时或资源竞争测量手段，既可作为辨识设备环境的高熵输入，也可作为刺探跨源私有状态的信息信道。两者的关键区别在于分析目标、受害对象与信息暴露的边界。

计时基石与隐式时钟构造

本文讨论的许多侧信道分析，都依赖对操作耗时的精确度量。密码学运算中的分支跳转、微架构缓存的命中状态以及跨源资源的加载反馈，都会在时间轴上留下微秒甚至纳秒级的差异。[Kocher 1996 §2]

早期 Web 标准为页面提供了显式高精度计时接口 performance.now()。该接口最初用于评估渲染性能与动画帧率，随后成为前端时序测量的通用基准。在微架构漏洞披露后，浏览器厂商对未隔离环境下的显式时钟实施了粗化与限制措施：例如，WebKit 在 2018 年的应急缓解中将常规上下文的计时精度降至 1 毫秒；其他浏览器也根据版本、是否跨源隔离及隐私设置，对显式时钟采用不同程度的精度粗化。[WebKit Timing Defenses]

然而，截断显式 API 并不能阻止攻击者获得时间基准。利用浏览器运行时的并发与异步调度原语，攻击者可以构造出具有亚微秒辨识能力的隐式时钟（implicit timers）：[Schwarz 2017 §3]

  1. 共享内存并发计数器： 利用 Web Workers 结合共享内存数组（SharedArrayBuffer，SAB）。攻击者在独立的 Worker 线程中运行紧凑循环，持续推进 32 位整数计数；主线程在受测任务执行前后读取该计数。尽管计数器的增量受即时编译（just-in-time compilation，JIT）优化、CPU 频率调度与多核缓存一致性影响，并不严格等同于固定频率的硬件指令周期，但在短时间内仍可作为灵敏的相对时间代理。
  2. 异步任务队列排队时钟： 在缺乏共享内存的受限环境下，脚本还可以利用异步事件循环测量粗粒度的执行或排队差异。例如向 MessageChannel 任务队列分发大量空消息，通过测量事件派发的平均间隔或堆叠任务清空总耗时，结合多次采样统计均值滤除部分调度抖动。这种方案的时钟分辨率取决于具体事件调度周期与浏览器环境，通常无法直接匹敌共享内存计数器的精细粒度。
// 基于 SharedArrayBuffer 与 Atomics 的隐式计数器示意（仅阐述原理）
// 假设主线程已完成 Worker 启动并确认就绪

// worker.js: 辅助线程持续推进共享计数
self.onmessage = function(e) {
  const sharedBuffer = e.data;
  const view = new Int32Array(sharedBuffer);
  // view[0] 作为计数单元，view[1] 标记就绪状态
  Atomics.store(view, 1, 1);
  while (true) {
    Atomics.add(view, 0, 1);
  }
};

// main.js: 主线程利用计数器增量作为相对耗时代理
// 前置条件：调用前主线程已通过异步握手或就绪信号确认 Worker 正常循环；以下省略启动与就绪等待逻辑
function measureRelativeTime(targetTask, sharedBuffer) {
  const view = new Int32Array(sharedBuffer);
  const startTick = Atomics.load(view, 0);
  
  targetTask(); // 执行同步待测任务
  
  const endTick = Atomics.load(view, 0);
  // 单次测量真实增量严格小于 2^32 时，返回模 2^32 的无符号相对增量
  return (endTick - startTick) >>> 0;
}

需要说明的是，上述代码假定受测任务为同步执行且真实增量严格小于 232 步；若任务涉及异步 Promise，该同步结构仅能测量到任务发起的耗时，而非最终完成耗时。此外，若长时间执行导致计数器发生多次完整回绕，则无法单凭差值直接判断真实耗时。[Schwarz 2017 §4]

JavaScript 中的缓存侧信道

现代中央处理器（central processing unit，CPU）采用多级分层缓存体系（L1、L2 与末级缓存 last-level cache，LLC）缓解处理器计算速度与动态随机存取内存（dynamic random-access memory，DRAM）访问延迟之间的差距。在典型现代微架构中，访问 L1 缓存通常只需 4 至 5 个时钟周期，若逐级未命中最终必须通过总线访问 DRAM，耗时可能跃升至数十甚至数百周期。

在系统级原生环境中，攻击者可通过汇编指令直接管理缓存行。而在沙箱隔离的 JavaScript 运行时中，既不存在显式缓存清理指令，代码也无法直接获知操作系统的虚拟地址或物理页分布。Yossef Oren 等人在 2015 年的研究证实，填装+探测（Prime+Probe）侧信道攻击可以在无特权的纯浏览器 JavaScript 环境中实施：[Oren 2015 §2]

处理器末级缓存通常采用组相联（set-associative）结构，内存地址按照特定哈希规则映射到固定的缓存组（Cache Sets）。Prime+Probe 的基本过程如下：[Oren 2015 §3]

  1. 构造驱逐集（Eviction Sets）： 攻击者在堆中分配大尺寸数组（如数十兆字节的 ArrayBuffer）。虽然其在高级语言层表现为连续的数组索引，但在操作系统底层并不对应连续物理内存。攻击者通过按步长访问并结合计时反馈与集合缩减算法，反复筛选出一组在 LLC 中恰好竞争相同缓存组的数组偏移与访问位置，形成驱逐集。
  2. 填装阶段（Prime）： 攻击者访问驱逐集中的所有内存项，将自身数据载入目标缓存组，促使该组中原有的其他数据被替换失效。
  3. 等待受害者执行（Wait）： 攻击者让出主线程或诱导目标活动。若受害者在执行期间访问了映射到同一缓存组的数据，CPU 会将受害数据载入该组，使攻击者的部分缓存行被替换失效。
  4. 探测阶段（Probe）： 攻击者再次按特定间隔与顺序访问驱逐集并度量耗时。若某一缓存组的读取耗时显著偏高，表明在等待期间该组发生过访存竞争。

需要指出的是，单次 Probe 变慢只反映当前缓存组发生过置换干扰，可能由操作系统调度或后台任务引起。同时，JavaScript 运行时的垃圾回收（garbage collection，GC）暂停、JIT 即时编译的动态优化与去优化、以及硬件预取器（hardware prefetcher），都会引入显著噪声。攻击者通常需要成千上万次重复测量与统计信号处理，才能在特定实验条件下还原出粗粒度的访问模式。[Oren 2015 §5]

推测执行与瞬态指令窗口

缓存侧信道揭示了微架构资源竞争的可测性，而推测执行（speculative execution）漏洞则表明，仅依靠高级语言层面的类型检查与软件边界判断，无法阻止微架构层面的跨边界数据读取。[Kocher 2019 §1]

现代高性能 CPU 广泛采用分支预测（Branch Prediction）技术保持流水线满载。在条件分支尚未完成实际判断前，CPU 的模式历史表（Pattern History Table，PHT）等硬件结构会依据历史记录超前推测执行预测路径上的指令；若后续确认预测错误，硬件会撤销架构层面的寄存器写入。

2018 年披露的 Spectre 变种 1（绕过边界检查，Bounds Check Bypass，CVE-2017-5753）指出，推测执行在分支预测错误回滚时，通常不会撤销已经发生的微架构缓存行填充：[Kocher 2019 §2]

// Spectre 变种 1 概念原理示意（依赖特定 JIT 编译生成的机器指令条件）
// array1 为经过边界检查的合法数组，array2 为攻击者构造的离散探针数组
if (x < array1.length) {
  // 当 x 超出合法边界，但分支预测器误判进入时：
  // 1. CPU 推测性执行越界读取该渲染进程虚拟地址空间中的字节（secret = array1[x]）
  // 2. 以 secret 为索引计算虚拟偏移，访问 array2 跨缓存行的特定项（例如 512 字节步长）
  value = array2[array1[x] * 512];
}

在概念攻击模型中，操作通常包含以下阶段：[Kocher 2019 §3]

  1. 训练预测器： 连续传入小于 array1.length 的合法索引 x 调用该代码段，使分支预测器建立该条件分支大概率成立的历史状态。
  2. 制造分支延迟： 构造使 array1.length 远离缓存的访存环境，迫使 CPU 耗时从更低层级缓存或主存读取边界值。
  3. 推测越界读取： 传入一个指向进程内其他虚拟地址的恶意偏移量 x。在长度读取未完成的几十个时钟周期窗口内，CPU 推测性执行分支内指令，越界读取进程虚拟地址空间内的机密数据，并以此为偏移触发 array2 对应项的缓存填充。
  4. 测量还原机密： CPU 得到边界检查结果后回滚架构状态，正常控制流并未抛出越界异常；但 array2 对应的微架构缓存状态已经改变。攻击者随后探测 array2 各位置的读取时延，尝试还原推测窗口中加载的字节值。[Kocher 2019 §4]

需要强调的是，上述 JavaScript 代码仅为概念机制说明。语言虚拟机本身并不会在正常执行中返回越界数据，实际利用严格依赖 JIT 引擎生成的具体机器指令排布、内存寻址方式以及 CPU 微架构的推测深度。此外，攻击者能推测读取的范围受限于当前渲染进程所能访问的虚拟地址空间；由独立网络服务或主进程隔离保管的敏感凭据（如 HttpOnly Cookie）并不一定常驻于当前渲染进程中。

Spectre 表明，仅依赖可被错误推测绕过的软件边界检查无法保证同进程内内存的绝对安全。各大浏览器在 2018 年初紧急禁用了 SharedArrayBuffer，并在 JIT 编译中引入了索引掩码（index masking）与推测屏障，同时加速推进由操作系统强制执行的进程地址空间隔离。[Reis 2019 §1]

跨站泄漏：宏观 Web 侧信道

侧信道并不仅限于微架构底层。Web 平台的网络协议、状态机制与渲染排版中存在的资源共享，同样构成了一系列宏观信息信道，统称为跨站泄漏（Cross-Site Leaks，XS-Leaks）。本文选择其中几类典型的测量路径展开说明：[Knittel 2021 §1]

XS-Leaks 不依赖 CPU 硬件设计漏洞，而是测量浏览器各子系统在处理跨源请求时的行为与状态差异：[Knittel 2021 §2]

1. 总体网络与加载时序

攻击者页面可通过 <script>、<img> 或 fetch 等方式发起跨源资源请求。尽管同源策略阻断了直接读取响应报文体，且 Resource Timing API 受到同源及 Timing-Allow-Origin 标头的严格约束，但网页仍能观察到事件触发的总耗时：[Felten 2000 §2]

  • 权限检查与数据库查询差异： 若服务端对不同权限或不同检索结果的请求执行了复杂度差异明显的数据库操作，或进入了耗时不同的权限检查路径，加载完成事件（onload 或 onerror）的总时延可能呈现统计可区分的差距。
  • 凭据与状态依赖： 这类测量通常要求请求携带用户的登录凭据，因而高度依赖浏览器当前的 Cookie 发送策略（例如 SameSite 属性与第三方 Cookie 限制）。

2. 连接池排队争用

在基于 HTTP/1.1 协议的传统网络环境中，浏览器对同一目标主机通常设有并发 TCP 连接上限（例如常见限制为 6 个连接）。历史研究指出，在目标请求与探针请求确定共享同一单主机连接配额的前提下，攻击者可维持 N-1 个长连接占满绝大部分可用配额；当目标跨站敏感操作被诱导触发并占用最后一个空闲槽位时，随后发出的探针请求将因无可用连接而被迫进入本地队列排队。通过度量探针请求从发出到最终完成的时延波动，攻击者得以间接推断受害者跨源请求的发生与持续耗时。[Knittel 2021 §3]

该模型高度依赖单主机的全局连接配额机制。而在现代 Web 广泛采用 HTTP/2 或 HTTP/3 连接复用与多路复用（Multiplexing）、以及浏览器推行网络状态分区的背景下，该攻击的成立条件已受到显著限制。

3. HTTP 缓存状态探测

当用户曾经访问过某个特定的私有或半公开资源且该资源允许缓存时，它会保存在本地浏览器的 HTTP 缓存中。由于本地读取耗时通常显著低于经历完整网络往返的请求，攻击者可通过发起跨源探测请求，依据加载延迟推断目标资源是否已在用户本地缓存中。[Felten 2000 §2]

这种攻击要求候选资源的 URL 具备可预测性且允许本地缓存，并且未受到现代网络隔离分区的约束。

4. 渲染管线与排版时序

浏览器的图形排版引擎同样存在开销差异。历史上，攻击者曾尝试在包含 CSS :visited 伪类的超链接上施加特定排版变化，试图通过测量页面重绘（repaint）与布局时序反推链接的访问历史。现代浏览器通过限制 :visited 可改变的样式属性、让脚本样式查询统一返回未访问状态，并减少已访问与未访问链接在样式解析和布局中的执行差异，缓解了多类历史探测与部分时序攻击。[Mozilla :visited Fix]

现代浏览器的纵深防御体系

面对分布在微架构、网络栈与渲染层的侧信道风险，现代浏览器厂商推行了面向系统架构的纵深防御：

1. 站点隔离（Site Isolation）

在推测执行漏洞面前，同一进程内的虚拟内存无法依赖语言虚拟机实现绝对隔离。Chromium 的站点隔离（Site Isolation）与 Firefox 的 Project Fission 将隔离边界上移至操作系统进程级别：[Reis 2019 §1]

浏览器将属于不同带协议的站点（schemeful site，由协议与可注册域 eTLD+1 构成）的文档，强制分配到各自独立的操作系统渲染进程中。跨站的 <iframe> 被实现为进程外 iframe（out-of-process iframe，OOPIF）。每个站点进程拥有独立的虚拟地址空间与内存管理单元（memory management unit，MMU）页表映射。[Reis 2019 §2]

需要明确的是，MMU 提供的是虚拟地址空间与访问权限隔离，各进程在物理层面仍共享 CPU 缓存与内存总线。站点隔离的核心收益在于阻断跨站进程内存共存：即使恶意页面在自身渲染进程内利用 Spectre 读取全部进程地址空间，也无法读到被操作系统隔离在其他进程中的跨站文档与凭据。结合跨源读取阻塞（Cross-Origin Read Blocking，CORB），浏览器进一步限制了非法的跨站敏感响应进入攻击者进程。

2. 跨源隔离上下文（Cross-Origin Isolation）

为了在 WebAssembly、图形渲染与多线程计算场景下安全恢复 SharedArrayBuffer 与较高精度的计时能力，WHATWG HTML 规范确立了跨源隔离上下文机制：[WHATWG Cross-Origin Isolation]

页面必须在安全上下文（通常由 HTTPS 或受信任的本地开发环境提供）中，并在顶级响应标头中声明以下策略：

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
  • 跨源开放者策略（Cross-Origin-Opener-Policy，COOP）： 声明 same-origin。当页面与跨源窗口相互打开时，只有双方同源且均使用该策略时才保留同一浏览上下文组；否则浏览器会分离顶级浏览上下文组，切断对窗口对象（window.opener）的直接交互引用。
  • 跨源嵌入者策略（Cross-Origin-Embedder-Policy，COEP）： 支持不同限制级别的指令。当声明 require-corp 时，页面所加载的跨源 no-cors 子资源必须通过跨源资源策略（Cross-Origin-Resource-Policy，CORP）获得显式许可，cors 请求必须通过跨源资源共享（Cross-Origin Resource Sharing，CORS）获得许可；当声明 credentialless 时，跨源 no-cors 子资源可以在省略请求凭据（如 Cookie）的条件下直接加载，不强制要求响应具备 CORP 标头；其他请求模式仍适用相应检查。

当文档声明并满足上述安全策略及 Permissions Policy 约束后，环境会将 window.crossOriginIsolated 属性置为 true，允许分配 SharedArrayBuffer 并提供微秒级显式计时接口。

3. 网络状态分区（Network State Partitioning）

针对 HTTP 缓存与连接状态的 XS-Leaks，主流浏览器推进了网络状态分区（Network State Partitioning）：不同浏览器对 HTTP 缓存、连接状态与本地存储推行了各异的分区策略。例如 Chromium 将 HTTP 缓存键由单一 URL 扩展为包含顶层站点、当前框架站点与资源 URL 的三元组；[Chrome HTTP Cache Partitioning] WebKit 则推行了第一方与资源来源的双键缓存模型。[WebKit Intelligent Tracking Prevention 2.1] 连接状态也逐步采用基于顶层站点等键的分区，以减少不同站点之间对连接状态的共享与观察；具体效果取决于浏览器实现及相关配额的作用范围。而对于 Cookie，浏览器主要依靠第三方 Cookie 限制机制与独立的分区存储（如 CHIPS）进行约束。

4. 获取元数据请求标头（Fetch Metadata）

W3C 规范制定了由浏览器网络层统一注入、前端 JavaScript 无法伪造的获取元数据请求标头（Fetch Metadata Request Headers）：[W3C Fetch Metadata]

  • Sec-Fetch-Site：标明请求发起关系，包括 same-origin、same-site、cross-site 以及用户直接在地址栏输入的 none。
  • Sec-Fetch-Mode：标明请求模式（如 navigate、cors、no-cors）。
  • Sec-Fetch-Dest：标明资源的目标载体（如 document、image、script）。

服务端可在请求处理的最前置逻辑中统一校验这些标头。当收到非预期的跨站请求时，服务端可在执行敏感业务计算或查询数据库前直接拒绝，从应用入口阻断基于加载时序的探测尝试。

对抗边界与工程权衡

侧信道防御的演进展现了系统安全在安全性、性能与通用性之间的平衡：

  1. 进程模型与物理开销： 站点隔离将跨站 iframe 拆分为独立的操作系统进程，提供了可靠的虚拟内存隔离，但显著增加了进程内存常驻占用与进程间通信（inter-process communication，IPC）成本。在内存紧缺的移动终端设备上，各浏览器通常需要针对内存阈值与站点重要度实施精细化的渐进隔离策略。[Reis 2019 §4]
  2. 常数时间执行在高级语言中的局限： 在专门的密码学库中，常数时间算法（constant-time execution）旨在确保控制流分支与内存访问索引独立于机密数据。然而在通用 Web 平台中，高级语言具有动态类型、JIT 即时编译优化以及运行时垃圾回收；要求通用业务逻辑在编译与调度层面消除一切数据相关的微小时间波动是不现实的。
  3. 隔离策略的重心迁移： 只要多个安全域的代码共享底层的 CPU 执行单元、缓存组与物理总线，完全消除微架构上的时间相关性就极其困难。因此，现代浏览器通过进程隔离减少跨站敏感数据与不受信任代码在同一地址空间中共存，并通过网络状态分区减少可跨站观察的共享状态。这些措施显著收紧了攻击条件，但并未消除跨进程的底层微架构资源竞争。
