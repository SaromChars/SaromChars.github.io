Rspamd的MIME解析与任务生命周期

2021年12月15日更新于: 2026年11月12日
|

邮件字节流已完整送入过滤引擎后，域名系统（Domain Name System，DNS）查询与黑名单检查仍可能挂起。挂起事件完成后，任务状态机可以继续推进。过滤阶段首次超时会清理挂起事件并继续推进，二次超时则终止任务。判定回写与内存释放各有触发条件。在底层网络事件与上层业务规则交织的场景下，理清报文投影、对象归属与事件生命周期，是网关开发者编写异步插件或排查超时故障的必要前提。

本文基于 2021 年 1 月发布的 Rspamd 2.7 稳定版公开源码，深入剖析扫描任务（scan task）生命周期核心机制。

报文输入通道与内存切片投影

扫描任务由工作进程接收网络请求后建立。在 task.c 的 rspamd_task_load_message 中，系统支持多通道报文输入#：

  1. 共享内存（Shared Memory，shm）：读取 shm、shm-offset 与 shm-length 请求标头，调用 shm_open 打开共享内存段，并经 mmap 进行只读映射（PROT_READ、MAP_SHARED）。
  2. 本地文件直接映射（file / path）：读取 file 或 path 标头，直接对指定磁盘文件调用 open 与 mmap。
  3. Zstandard（zstd）流式解压：若标头指定 compression: zstd，调用 ZSTD_decompressStream 动态扩容堆缓冲区进行全量解压。
  4. HTTP 报文体：标准 HTTP POST 请求直接复用网络层读取的 chunk 缓冲区指针。

服务端配置项中的 max_message 是由 worker.c 在 rspamd_http_connection_set_max_size 中施加给 HTTP 连接传输层的限制#。它不能限制本地文件映射或共享内存引入的数据体量，也无法在网络流解压前约束 Zstandard 解压后展开的总内存膨胀。

装载完成后，task->msg.begin 与 task->msg.len 确立报文范围。随后 rspamd_message_parse 执行两项前置处理：调用 g_ascii_isspace 跳过前导空白字符，以及跳过 Exim 邮箱格式的 From 标头行#。

  • task->msg.begin 在解析前会被向后移动；
  • task->msg 不能被视作永久逐字保留的原版邮件镜像。若网关下游需要保真投递或归档，应在输入网关处独立保留原始副本。

对象分层与内存池（Memory Pool）所有权

在 Rspamd 内部，任务处理涉及三个生命周期与所有权不同的核心结构：

+------------------------------------+
| rspamd_task (扫描任务)             |
|  task_pool (rspamd_mempool_t)      |
|   - 析构链: unmapper/g_free/conn-- |
|                                    |
|  msg (rspamd_task_data_storage)    |
|   - begin/len: 输入缓冲区切片      |
|                                    |
|  message (struct rspamd_message *) |
|   - ref: ref_entry_t 独立引用计数  |
|   - parts (GPtrArray):             |
|      part[i]->raw_data (切片)      |
|      part[i]->parsed_data (解码)   |
+------------------------------------+

每个任务通过 rspamd_task_new 分配，默认持有独立的内存池（memory pool，task_pool）#。内存池不仅聚合分配任务结构与临时字符串，还作为析构清理链表：

  • 通过 rspamd_mempool_add_destructor 注册清理动作（如 munmap 解除映射、释放 zstd 缓冲区、递减工作进程连接计数）#。
  • 当任务在 rspamd_task_free 终结时，只要持有 RSPAMD_TASK_FLAG_OWN_POOL，调用 rspamd_mempool_delete 会一次性触发所有析构钩子并归还内存。

语义容器 struct rspamd_message 虽然采用 ref_entry_t 进行独立引用计数管理（rspamd_message_ref / rspamd_message_unref），但在 rspamd_message_new 中，其结构体本身及包含的部件大部分仍直接分配自 task->task_pool#。因此：

  • 独立的引用计数主要用于任务执行过程中模块间传递及防止提前释放；
  • 不能脱离任务生命周期在 task_pool 销毁后继续持有这些切片指针，否则会造成访问野指针。

MIME 实体树解析与容错边界

进入 RSPAMD_TASK_STAGE_READ_MESSAGE 阶段后，mime_parser.c 递归解析多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）结构#：

递归深度与越界处理

mime_parser.c 中定义了静态常量：

static const guint max_nested = 64;

解析器在处理 multipart 时维护 st->nesting，边界判断为 st->nesting > max_nested#。

  • 该常量是 Rspamd 防范栈溢出的内部防御阈值，不能简单等同于 RFC 协议限制或外部邮件客户端可观测到的 MIME 树精确层数；
  • 递归触发 RSPAMD_MIME_PARSE_NESTING 时，系统发出告警并打上 RSPAMD_TASK_FLAG_BROKEN_HEADERS 标志，解析器不会中断任务，而是继续使用当前已识别的顶层部件向下扫描；
  • 仅当解析遭遇 RSPAMD_MIME_PARSE_FATAL 致命错误时，系统才会检查配置项 allow_raw_input。若未开启该选项，则报错中断；若开启，则擦除 MIME 标志，进入 rspamd_message_from_data 创建单一数据部件，利用 Content-Type 标头或通过 lua_magic 探测类型后继续扫描，并非必定退化为纯文本#。

内容传输编码（Content-Transfer-Encoding，CTE）解码与部件视图

每个 struct rspamd_mime_part 提供多层切片投影#：

  • raw_data：直接指向输入缓冲区中的原始切片；
  • parsed_data：经内容传输编码（Content-Transfer-Encoding，CTE）解码（如 Base64、Quoted-Printable 或 8bit）后的二进制或文本内容；
  • 特化解析：后续 rspamd_message_process 阶段会继续执行图片尺寸提取、文本词元切分及正文超链接发现。

任务状态机推进与异步会话协作

任务推进由阶段位图驱动，核心状态推进流如下：

rspamd_task_process(task, stages)
  │
  ▼
select_processing_stage: 选取未完成 stage (如 FILTERS)
  │
  ▼
执行规则匹配与插件调用 (可能调用 add_event_full 注册 finalizer)
  │
  ▼
检查完成条件 (pending 与 all_done 三分支):
  │
  ├── [1] pending > 0:
  │         退出 process 函数，暂停推进，等待外部事件回调
  │
  ├── [2] pending == 0 且 all_done == false:
  │         不置位当前 stage，尾递归再次重试当前 stage
  │
  └── [3] pending == 0 且 all_done == true:
            标记当前 stage 完成 (processed_stages |= st)
            尾递归调用 process 进入下一 stage

三分支推进约束

调度函数 rspamd_task_process 执行某阶段（如 RSPAMD_TASK_STAGE_FILTERS）时，对挂起计数与完成状态的判定严格遵循三个分支#：

  1. 若 rspamd_session_events_pending(task->s) > 0：仍有挂起的外部事件未完成，函数立即退出，等待事件触发或超时；
  2. 若 pending == 0 但 all_done == false：当前阶段虽无挂起 I/O，但规则或符号仍需继续处理，系统直接尾递归重试当前阶段，决不等待不存在的外部事件；
  3. 唯有当 pending == 0 且 all_done == true 同时满足时，当前阶段才被打上完成位图标记，并尾递归推进至下一阶段。

异步会话（Asynchronous Session）生命周期

任务通过 task->s（rspamd_async_session）协调异步操作#：

  • 事件终结回调：调用 rspamd_session_add_event_full 时传入的 fin 函数是指事件终结/清理回调（event finalizer），在正常调用 remove_event 以及异常调用 cleanup 时均会被执行，绝不能将其与底层套接字网络读取成功的数据回调混淆；
  • 会话清空重入：当最后一个异步事件被移除、挂起事件数清零时，rspamd_session_pending 触发 session->fin（即 rspamd_task_fin），由其重新触发 rspamd_task_process 推进状态机；
  • 终止与响应标志：RSPAMD_TASK_STAGE_DONE 仅表示任务处理流程到达终点（可由成功跑完所有阶段置位，亦可由解析失败或超时强行打标终止）；RSPAMD_TASK_STAGE_REPLIED 则是在 protocol.c 中发起异步写操作 rspamd_http_connection_write_message 后立即置位，作为防止重复写响应的内部标志，并不代表网络客户端已完整接收响应字节#。

超时兜底、异常断连与插件责任

阶梯式超时强行收敛

任务在 worker.c 中绑定全局定时器 task->timeout_ev，触发 rspamd_task_timeout#：

  • 第一阶段（规则过滤超时）：若超时发生且尚未完成 RSPAMD_TASK_STAGE_FILTERS，系统会检查配置 soft_reject_on_timeout。仅当显式开启该配置项且当前动作尚未达到拒信级别（action_type != METRIC_ACTION_REJECT）时，系统才注入临时拒信（soft_reject）；随后强行标记 FILTERS 阶段完成，调用 rspamd_session_cleanup(task->s) 清理挂起事件，并再次调用 rspamd_task_process 尝试执行后置处理#。由于后续仍可能执行后置阶段与协议响应生成，客户端并不会在超时触发时刻保证瞬间收到响应；
  • 第二阶段（后置处理超时）：若第二次超时触发，系统直接标记 RSPAMD_TASK_STAGE_DONE 并终止任务。

断连防护与会话销毁定序

task->guard_ev 监听连接套接字事件。若收到客户端 EOF，通常会调用 rspamd_session_destroy 销毁会话；但在非 CMD_CHECK_V2 且配置了 enable_shutdown_workaround 时，为兼容客户端的 shutdown(SHUT_WR) 半关闭，仅停止防卫事件而不会立刻杀死任务#。

在销毁会话 rspamd_session_destroy 时，执行顺序严格固定：

  1. 遍历挂起事件，逐个调用其清理回调 ev->fin(ev->user_data)；
  2. 清空事件哈希表；
  3. 执行注册在会话上的全局清理函数 session->cleanup（在 worker.c 中为 rspamd_task_free）。

插件开发者责任：异步插件必须在 fin 清理回调中主动注销挂在底层事件循环或第三方异步库上的回调指针。单靠任务内存池的释放无法阻断操作系统底层已排队的套接字网络事件。若外部网络库在任务释放后继续回调，可能访问已释放对象。

教学数据契约与验证设计

说明：以下契约属于自研网关接入层的概念教学设计，不是 Rspamd 的原生 C 结构或原生 HTTP JSON 协议字段；字段中的 budget 亦非 Rspamd 内置提供的自动保护配额，需由网关层自行编码约束。

1. 扫描输入上下文契约设计

{
  "scan_input": {
    "raw_ref": {
      "channel": "shm | file | zstd_stream | plain_http",
      "path": "/var/spool/mmap_tmp_xyz",
      "length": 1048576
    },
    "envelope": {
      "helo": "mail.example.com",
      "from": "sender@example.com",
      "rcpt": ["recipient@example.com"],
      "client_ip": "192.0.2.1"
    },
    "budget": {
      "max_time_seconds": 5.0,
      "max_decompressed_bytes": 10485760
    }
  }
}

2. 判定结果输出契约设计

{
  "scan_result": {
    "execution": {
      "completed": true,
      "timed_out": false,
      "final_stage": "POST_FILTERS"
    },
    "coverage": {
      "mime_parsed": true,
      "broken_headers": false,
      "parts_count": 2,
      "unknown_or_skipped_sections": false
    },
    "action": {
      "verdict": "no_action | soft_reject | reject",
      "symbols": ["R_SPF_ALLOW", "BAYES_SPAM"]
    }
  }
}

契约中 coverage 字段显式分离了部分解析与未知区间。网关二次开发时，不得把“未解析”或“解析跳过”盲目等同于“内容干净”。

3. 未运行失败案例与验证设计：超时晚回调与对象生命周期错位

  • 场景描述：在显式开启 soft_reject_on_timeout 且尚未产生 reject 动作的配置下，某异步插件发起外部查询，并将上下文绑定至 task->s。当外部响应迟缓触发首次任务超时时，rspamd_task_timeout 调用 rspamd_session_cleanup 强行清空挂起事件并进入后置阶段。若该插件的 fin 回调未能及时注销注册到底层事件循环中的回调指针，在任务被释放后迟到的数据包触发底层回调，由于绑定的 task 上下文已被释放，将导致读取已注销内存。
  • 3 步验证方案设计（尚未执行）：
    1. 构建受控模拟环境：在测试模块中显式开启 soft_reject_on_timeout，发起一个故意延迟响应的异步模拟事件，绑定带有注销断言的 fin 清理回调。
    2. 观测超时清理与响应终结：触发扫描并等待任务进入超时路径，检查 fin 清理回调是否被准确调用且仅调用一次；验证在经历后置处理后最终写出的响应中包含 soft_reject，且 RSPAMD_TASK_STAGE_REPLIED 至多置位一次。
    3. 延迟回包并监测内存完整性：在任务彻底释放后由 Mock 端注入延迟响应，借助 AddressSanitizer（ASan）监测进程，验证迟到回调是否已被安全阻断，确认不会再次解引用已释放的 task 对象指针。

工程推导：内存占用与资源规划

本文分析的 Rspamd 2.7 源码范围中未提供统一的全局任务总内存或 CPU 配额。高并发网关的容量规划必须基于各部分开销进行计量，并在实测后针对最坏输入设定上限：

  • 输入缓冲区：若使用 shm 或 file mmap 映射，数据驻留于页面缓存；若为 HTTP 直传或 Zstandard 解压，则在堆中保留解压全量字节；
  • MIME 部件解码展开：每个 MIME 部件若存在 Base64 解码与 UTF-8 转码，会在内存池中额外分配解码缓冲区（parsed_data）和规范化文本容器（utf_content）；
  • 对象指针与运行时结构：任务结构体、标头表、正则运行时缓存与统计词元数组均需占用内存，必须结合邮件结构体复杂度进行上限控制；
  • 切片指针共享：raw_data 仅是指向原始输入的轻量切片指针，不额外拷贝数据，但各部件解码展开副本与多语言分析可能显著放大内存。

网关设计必须在网络入口处对报文尺寸、解压体积、部件展开上限、执行时间以及外部异步并发数分别设立独立预算，并在插件扩展中严格落实注销机制。
