DKIM 的邮件签名与验证

2021年9月12日
|

在电子邮件的传输路径中，信封地址由简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）会话维护，而邮件内容中的头部与正文则由互联网邮件格式（Internet Message Format，IMF，即 RFC 5322）规范。然而，传统 SMTP 缺乏在报文内容层面证明责任主体或防止非授权篡改的通用密码学手段。

为了在现存邮件基础设施上为报文建立可验证的组织责任关联，互联网工程任务组（Internet Engineering Task Force，IETF）制定了域名密钥识别邮件（DomainKeys Identified Mail，DKIM）标准。其核心规程定义于 2011 年发布的 RFC 6376，并在 2018 年由 RFC 8301 实施了针对哈希算法与密钥长度的正式安全更新。

协议定位与核心目标

DKIM 并非端到端的端用户保密通信工具，其机制与设计目标具有明确边界：

  1. 组织责任主张：DKIM 允许拥有签名域名的主体（可以是发信组织、传输中继或其代理）通过数字签名（Digital Signature）声明对邮件承担责任。
  2. 签名身份与作者身份解耦：RFC 6376 明确将签名域标识符（Signing Domain Identifier，SDID）与 RFC 5322 中声明的邮件作者（From: 字段）区分开来。签名有效仅代表指定域名声称对该报文负责，并不要求签名域必须与发件人邮箱后缀完全一致。
  3. 基于 DNS 的公钥发布：DKIM 无需依赖传统的层级式公钥基础设施（Public Key Infrastructure，PKI）或第三方数字证书（Digital Certificate）认证中心（Certificate Authority，CA），而是直接复用域名系统（Domain Name System，DNS）的 TXT 资源记录分发用于验证数字签名（验签，signature verification）的公钥。
  4. 报文无损穿越：签名数据直接封装为名为 DKIM-Signature: 的邮件头字段（Header Field），不需要修改邮件正文结构，对传统邮件用户代理（Message User Agent，MUA）和中间传输代理透明。
  5. 不提供传输加密与长期归档保证：DKIM 仅提供针对被签名内容的完整性验证（Data Integrity）与签名者身份认证（authentication），不涉及邮件内容加密（Encryption），也不以长期报文归档为目标。

协议要素与关键标签

在 DKIM 架构中，签名信息在邮件头部以 DKIM-Signature: 字段承载，而公钥则通过 DNS 记录发布。两者均采用基于分号分隔的 tag=value 标签列表语法。

1. DKIM-Signature 头部字段标签

根据 RFC 6376 第 3.5 节，DKIM-Signature: 常见标签如下：

标签全称与含义是否必需说明与规范要求
v=版本（Version）必需目前固定为 1。若版本不匹配，验签方必须返回永久失败（PERMFAIL）。
a=签名算法（Algorithm）必需格式为 key-alg-hash-alg。RFC 6376 原定义 rsa-sha1 与 rsa-sha256；RFC 8301 更新后禁止使用 rsa-sha1，必须使用 rsa-sha256。
b=数字签名数据（Signature Data）必需对头部哈希的数字签名结果，采用 Base64 编码。计算时需删除本字段内 b= 的值及其周围所有折叠空白，具体处理见下文计算步骤。
bh=正文哈希（Body Hash）必需经规范化并截断（若指定 l=）后的正文哈希摘要，Base64 编码。
c=规范化算法（Canonicalization）可选格式为 header/body，可选 simple 或 relaxed，缺省默认值为 simple/simple。
d=签名域标识符（SDID）必需声称对邮件承担责任的域名，用于定位 DNS 公钥检索路径。
s=选择器（Selector）必需用于将域名的密钥命名空间细分，支持多密钥共存与独立轮换。
h=签名包含的头部字段（Signed Headers）必需冒号分隔的头部字段名列表。必须包含 From 字段。
i=代理或用户标识符（Agent or User Identifier，AUID）可选格式为 local-part@domain，缺省为 @d。其域名部分必须是 d= 域或其子域。
l=正文长度限制（Body Length）可选参与哈希计算的正文字节数。缺省包含全部正文。存在严重安全风险，需谨慎使用。
t=签名时间戳（Timestamp）推荐签名创建的 UTC 秒数（自 Unix 纪元起）。
x=签名过期时间（Expiration）推荐绝对时间戳。若验签所用时间已超过该时间，验签方可判定签名失效。能可靠取得时，验签时间应采用邮件首次进入验签方管理域的接收时间，否则采用当前时间。若与 t= 同时存在，其值必须大于 t=。该标签不是防重放机制。
z=头部字段副本（Copied Headers）可选签名时选定头部的原始副本，仅供诊断分析使用。

2. 选择器与 DNS 公钥记录

为了支持单域名下部署多组密钥（例如区分部门、外包投递渠道或平滑进行密钥轮换），DKIM 引入了选择器（Selector）机制。

公钥存放在 _domainkey 专用子域名下的 TXT 记录中。当验签方解析 d=example.com 且 s=jun2021 时，发起的 DNS 查询名称为：

jun2021._domainkey.example.com

根据 RFC 6376 第 3.6.1 节，DNS TXT 记录内容示例如下：

v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC3...
  • v=DKIM1：公钥记录版本（推荐）。若出现必须位于首位；若版本值不匹配，验签方必须丢弃该记录。
  • k=rsa：密钥算法类型，默认为 rsa。
  • p=：Base64 编码的公钥数据。若 p= 值为空字符串（即 p= 后无内容），表示该密钥已被吊销（Revoked），验签方必须判定签名失败。
  • t=：标志位列表。y 表示发信域处于测试阶段（Testing Mode），验签失败不应直接作为拒收依据；s 表示约束 i= 标签域名必须与 d= 严格完全一致（禁止子域）。

规范化算法机制

在电子邮件从发件人传输到收件人的中继链路中，邮件传输代理（Message Transfer Agent，MTA）可能会调整头部折行、替换空格与制表符，或者统一行尾换行符。直接对原始文本计算哈希极易因无关紧要的空白变化导致验签断裂。

DKIM 提出了规范化（Canonicalization）算法，在将数据送入哈希函数（hash function，也称散列函数）之前将其转换为确定格式。RFC 6376 为头部和正文分别定义了 simple 和 relaxed 两种算法（用 c=header/body 声明）。

1. 头部规范化

  • simple 头部规范化：完全不改变头部文本。字段名大小写保持原样，字段内的空格、折行回车换行（CRLF）与制表符完全不改动。
  • relaxed 头部规范化：
    1. 将所有字段名转换为小写（字段值内容大小写不变）；
    2. 展开所有折叠行（Unfold），将字段值内部的 CRLF WSP 中的 CRLF 剥除，仅保留空白字符；
    3. 将字段值内部连续的一个或多个空白字符（WSP，即空格或制表符）压缩为单个 ASCII 空格（SP）；
    4. 清除冒号前后残留的所有空白字符（保留冒号分隔符）；
    5. 删除字段值末尾的所有空白字符；
    6. 严格保留行尾的单个 CRLF。

2. 正文规范化

  • simple 正文规范化：
    • 忽略正文末尾的所有空行（空行指剥离换行符后长度为 0 的行）；
    • 将正文末尾的所有连续空行转换为单个 CRLF；
    • 若正文完全为空或末尾缺少换行符，补齐单个 CRLF（即空正文的规范化输出固定为 2 字节的 CRLF）。
  • relaxed 正文规范化：
    • 压缩行内所有连续空白字符为单个空格，并删除行尾的所有空白字符（保留行尾换行 CRLF）；
    • 忽略正文末尾的所有空行；
    • 若正文非空但未以 CRLF 结尾，补齐一个 CRLF。完全为空的正文规范化后输入长度为 0 字节。

签名生成与验证流程

DKIM 采用双哈希计算架构：先计算正文哈希并填入 bh= 标签，再将它与选定头部一起纳入数字签名。

1. 签名生成流程

发信方签名步骤如下：

  1. 正文哈希计算：
    • 提取正文，按照 c= 声明的正文规范化算法处理；
    • 若设置了 l= 标签，截取指定字节数；
    • 使用 a= 选定的哈希算法（RFC 8301 规定必须为 SHA-256）计算摘要，进行 Base64 编码，填入 bh= 标签。
  2. 头部哈希计算：
    • 按照 h= 标签中列出的字段名顺序，依次提取邮件头字段；若同名字段出现多次，遵循 RFC 6376 规定的自底向上规则；
    • 对提取出的头部字段按 c= 声明的头部规范化算法逐一处理，每个字段末尾以 CRLF 结束；
    • 构造即将插入的 DKIM-Signature: 头部，包含所有其余标签（包含刚计算出的 bh= 值）；删除 b= 的值及其周围的所有折叠空白（即把 b= 的值视为空字符串，保留 b= 标签本身）；
    • 对该 DKIM-Signature: 头部同样进行规范化（签名计算时末尾不追加 CRLF），追加到待签头部数据末尾；
    • 对拼接后的整个头部数据流计算哈希摘要。
  3. 数字签名生成：
    • 使用发信域的 RSA 私钥对头部哈希摘要进行数字签名；
    • 将签名输出 Base64 编码，填入 b= 标签；
    • 将完整的 DKIM-Signature: 字段插入到邮件头部顶端。

2. 验签与结果判定

收件端验签方在收到邮件后，执行逆向验证：

  1. 语法与参数解析：提取 DKIM-Signature:，严格检查是否包含 v=, a=, b=, bh=, d=, h=, s= 等必需标签；检查 h= 中是否包含 From 字段。缺失必需项则直接判定为 PERMFAIL。
  2. 公钥检索：向 s._domainkey.d 发起 DNS 查询获取 TXT 记录。
    • 若 DNS 返回记录不存在，判定为 PERMFAIL；
    • 若 DNS 查询发生临时超时或服务不可达，可返回 TEMPFAIL；
    • 若记录中 p= 为空，判定为密钥已吊销（PERMFAIL）。
  3. 正文哈希比对：对接收到的正文按 c= 声明重新规范化并截断，计算哈希值，与报文中的 bh= 标签比对。若不匹配，则判定验证失败（PERMFAIL）。
  4. 头部验签：根据 h= 列表提取头部并追加删除 b= 值及周围空白后的 DKIM-Signature:，计算头部摘要，结合 DNS 查得的 RSA 公钥验证 b= 签名值。

密钥生命周期与安全边界

1. 密钥轮换工程实践

为了防止私钥长期暴露引发泄露风险，发信方应当定期进行密钥轮换（Key Rotation）。在私钥未泄露的正常轮换场景下，发信方可通过双公钥过渡保持平滑验证：

  • 重叠过渡期（Dual-Key Staging）：由于邮件在传输链路、队列重试或收件方延后处理过程中存在时间差，在正常维护中，发信方通常在启用新私钥签名的同时保留旧选择器的公钥记录，避免在途邮件在送达验签时因找不到公钥而失效。但如果发生私钥泄露，则应优先立即吊销或移除对应公钥，而非维持旧邮件验签。
  • 工程切换流程：
    1. 生成新密钥对，分配新选择器（如 202109._domainkey.example.com）并在 DNS 中发布新公钥记录；
    2. 根据权威 DNS 生效情况及相关缓存 TTL（包括负缓存）确定生效条件后，发信系统开始使用新私钥与新选择器签名；
    3. 旧选择器的公钥记录在 DNS 中继续保留一段时间，具体时长取决于预估的邮件传输延迟与本地重试队列上限；
    4. 待在途邮件投递生命周期结束后，从 DNS 移除旧记录，或发布 p= 为空的吊销记录。

2. 签名算法与密钥长度要求（RFC 8301）

随着密码学计算能力的提升，早期标准允许的算法显露出安全隐患：

  • 禁止 SHA-1：RFC 6376 时代允许 rsa-sha1 与 rsa-sha256。2018 年发布的 RFC 8301 正式更新了规范，明确将 rsa-sha1 置为历史废弃状态（Historic）。发信方严禁使用（MUST NOT） rsa-sha1 进行签名，验签方也严禁使用（MUST NOT）该算法验证，遇到 rsa-sha1 必须视作永久失败。
  • 密钥长度下限：RFC 6376 原先允许验证 512 位短密钥。RFC 8301 明确规定发信方所有密钥长度必须至少为 1024 位（MUST），且推荐至少使用 2048 位（SHOULD）；验签方严禁将小于 1024 位的密钥视为有效签名（MUST NOT）。

3. 常见安全陷阱与边界

A. 头部重放与注入攻击（Header Injection）

RFC 6376 指出，若签名仅覆盖了现有头部中的某个字段（例如出现了一次 Subject: 且 h=subject），攻击者或恶意中继可在传输途中向头部上方再插入一个新的 Subject: 字段。部分宽松实现的 MUA 可能会优先显示新插入的顶部字段，而底层 DKIM 依然验证通过。

  • 防护机制（Over-signing）：发信方可在 h= 列表中将该字段多列出一次（例如 h=from:from:subject:subject）。根据规范，如果某字段在报文中仅出现一次，而在 h= 中声明了两次，计算哈希时第二次将被视为空输入。若中间人额外插入了同名字段，验签时该字段就会参与哈希计算，导致哈希不匹配从而使签名失效。

B. 正文长度标签（l=）的滥用风险

l= 标签初衷是允许邮件列表在正文末尾追加退订链接而不破坏原签名。然而 RFC 6376 第 8.2 节警告，任何位于 l= 指定长度之后的数据均未受密码学保护。恶意攻击者可利用这一空隙在末尾追加任意伪造正文，甚至通过注入多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）分隔符或 HTML 闭合标签彻底颠覆原始邮件的展示。

在实际安全运营中，通常强烈建议省略 l= 标签，对整封正文实施完整保护。

C. 验签成功与内容可信的边界

在邮件安全架构中，DKIM 具有明确的语义界限：

  • 验签通过的真实含义：验签通过仅表示所选头部和正文受保护部分在指定规范化规则下与签名时一致，以及声称的签名域名 d= 确实对该邮件主张了组织责任。它并不代表报文在逐字节层面完全未变（规范化允许的空白、折行等微小变动仍可通过）。
  • 内容与作者可信度：DKIM 并不证明发件人邮箱真实可信，不能阻止发信域自身发送钓鱼或垃圾邮件，也无法单独保证 From: 作者身份未被伪造（在后续架构中，需进一步结合发件人策略框架（Sender Policy Framework，SPF）与基于域的消息身份认证、报告与一致性（Domain-based Message Authentication, Reporting, and Conformance，DMARC）机制进行多维对齐判定）。内容与信誉判定仍须依赖发信域名的历史信誉评估（Reputation System）与反垃圾安全引擎综合决策。
