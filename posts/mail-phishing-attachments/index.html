钓鱼邮件、冒名与恶意附件

2021年9月26日
|

一封邮件在收件网关处即使获得发件人策略框架（Sender Policy Framework，SPF）、互联网域名密钥识别邮件（DomainKeys Identified Mail，DKIM，RFC 6376）以及基于域的消息认证、报告与一致性（Domain-based Message Authentication, Reporting, and Conformance，DMARC，RFC 7489）的认证通过判定，仍可能包含钓鱼诱导或恶意附件。

从协议定义来看，身份认证（Authentication）不等于内容信誉或意图良善。SPF 仅检验简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）信封中的客户端 IP 是否获得发送域授权；DKIM 仅在签名覆盖范围内，验证经规范化处理的头部字段与正文哈希是否保持完整，并确认签署域的责任；DMARC 则要求邮件头部 RFC 5322 From: 中的作者域（Author Domain）必须与 SPF 或 DKIM 验证通过的标识达成身份对齐（Identifier Alignment）。

如果攻击者自行注册合法域名并配置 SPF 记录与 DKIM 签名，或者利用已被盗用的合法发信账号，其发出的邮件完全可能在协议认证分支上获得通过。然而，认证通过仅意味着邮件来源符合所声明域名的技术检验，接收端仍可依据本地内容安全策略、信誉评估或杀毒规则对其执行隔离或拒绝。

攻击者依然可以在终端可见交互、域名视觉差异、正文超链接以及附件处理等环节实施欺骗。本文结合 RFC 7489、RFC 6376 以及多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）呈现规范 RFC 2183，剖析协议认证通过后的关键安全盲区与防御边界。

邮件认证层与内容安全层的职责边界

在邮件处理流程中，底层传输认证与内容安全评估存在明确的职责划分。RFC 7489 第 2.2 节、第 4.2 节与第 6.7 节明确指出，DMARC 的评估对象是域级别的身份对齐，协议本身不分析邮件内容；RFC 6376 第 2.5 节与第 2.7 节同样强调，DKIM 的输出是签署域标识符（Signing Domain Identifier，SDID），仅代表该域对报文承担责任，对正文信誉与后续处理的评估属于身份评估器（Identity Assessor）或内容过滤引擎的职责范围。

因此，协议认证通过仅表明特定技术标识在传输中通过了校验，绝不代表邮件正文或附件本身无害。

显示名仿冒

在 RFC 5322 规范中，邮件头部的 From: 字段常采用包含显示名（Display Name）与地址规范的格式（name-addr 形式）：

From: "Security Center" <attacker-alert@example.net>

1. 协议机制的局限

DMARC（RFC 7489 第 3.1 节）在执行身份对齐时，提取并校验的是尖括号内的邮箱地址规范部分（Addr-Spec）中的域名（如 example.net）。若实际发送路径、签名及对齐条件满足要求，攻击者使用自身控制域名的邮件也可能通过接收端 DMARC 检查。

然而，部分邮件用户代理（Message User Agent，MUA）为了界面紧凑，在消息列表或预览区域可能只突出展示双引号内的显示名，而折叠或隐藏真实邮箱地址。如果界面只显示“Security Center”，收件人容易误以为该邮件来自正规管理机构。

RFC 7489 第 12.4 节对此作了专门的安全考量（Display Name Attacks）：

  • 机制外范围：规范指出，显示名攻击在 DMARC 核心机制的设计范围之外，属于滥用防范中需要进一步探索的领域。
  • 潜在缓解手段与局限：
    • 若显示名包含邮箱地址，则对该地址的域名执行 DMARC：例如显示名为 "admin@example.com via Portal"。但攻击者只要不在显示名中包含标准邮箱格式即可绕开；且该做法会影响合法的代理发送场景。
    • 仅当 DMARC 通过时才展示显示名：但攻击者在自己控制的域名上同样可以使 DMARC 检查通过，此方法无法防范仿冒。
    • 仅当 DMARC 通过且验证后的地址位于已知联系人列表中时才展示显示名：结合了协议验证与本地白名单，但对于初次通信的合法外部来信会带来体验限制。

2. 客户端与网关的工程处理

由于协议标准不规范 MUA 界面的具体展示方式（RFC 6376 附录 D），防御显示名仿冒主要依赖本地实现的工程策略：

  • 界面并列展示：MUA 可以在阅读界面中同时显式呈现显示名与完整的规范邮箱地址，避免用单一名称遮蔽真实来源域名。
  • 外部来信提醒：入站网关若具备规则比对能力，可检测外部来信的显示名是否与内部重要角色名称重名；若存在重名风险，可在正文顶部插入警示信息。需要注意的是，正文修改可能会破坏原始邮件的 DKIM 签名完整性，影响下游中继节点的验签。

域名视觉混淆与相似域

当攻击者在邮箱地址域名部分实施欺诈时，通常使用与受信任域名外观近似的相似域（Look-alike Domain）。

1. 常见视觉混淆形式

在教学演示中，相似域欺诈常表现为以下几类字符串构造方式（以下均基于保留域名命名空间示意）：

  1. 错别字与拼写混淆：在保留域名标签中调换、增删字符，例如对比 brand.example.com 与 brnad.example.net。
  2. 字符替换混淆：利用数字或相似字母替换，例如在示例中使用 service.example.net 与 serv1ce.example.net。
  3. 国际化域名（IDN）形式：利用国际化域名（Internationalized Domain Names，IDN）中不同脚本字符的视觉相似性。为了在基于 ASCII 的域名系统（Domain Name System，DNS）体系中兼容传输，国际化域名的 ASCII 标签（A-label）以 xn-- 为前缀，其非 ASCII 字符由 Punycode 编码表示。如果界面缺乏适当的转码展示，不同字符集在屏幕上的字形可能产生混淆。

2. 认证状态与防护要求

相似域在 DNS 体系中是完全独立的域名实体。攻击者若为自身控制的相似域配置了相应的 DNS 记录与签名，并在符合发信条件时发送邮件，这些邮件在收件端同样可能通过基础协议认证。

防范相似域不能依赖单一的协议检查：

  • 域名信誉与历史数据：如果接收系统接入了域名注册时间或信誉数据，可将新出现的域名列入关注范围，按本地风险容忍度调整扫描级别。相关阈值必须经过实测与误判评估，不可直接假定存在普遍固定的判定天数。
  • 界面 Punycode 展示：MUA 在渲染混合语言脚本或易混淆的国际化域名时，可选择直接展示原始 Punycode 字符串，帮助用户识别底层真实域名。

正文链接与目标地址

钓鱼邮件通常利用超文本标记语言（Hypertext Markup Language，HTML）正文诱导用户点击恶意链接。

1. 锚文本与目标 URL 不一致

HTML 邮件中的超链接允许将锚文本（Anchor Text）与真实的统一资源定位符（Uniform Resource Locator，URL）分离：

<a href="http://login.service.example.net/auth">https://mail.example.com/login</a>

在界面渲染中，收件人直观看到的蓝色文字是 mail.example.com，但点击后实际发起的请求却指向 login.service.example.net。

2. 防护策略与注意事项

  • 悬停预览与跨域提示：MUA 在用户将鼠标悬停在链接上时，可浮动展示实际的 href 目标地址。若检测到可见锚文本具有域名外观但与底层目标域名不一致，可在点击时弹出确认提示。
  • 点击时检查（Time-of-Click）：由于邮件正文中的外部链接所指向的页面可能在邮件投递之后发生篡改或切换，具备 URL 代理能力的网关系统可选择对正文链接进行转换，以便在用户实际发起点击时重新评估目标页面的安全性。这种机制同样属于本地增值实现，需要权衡用户体验与外发重写对内容完整性的影响。

文件名参数与安全风险

邮件正文通过 MIME 组织，其中各个部件根据标准轨道规范 RFC 2183《The Content-Disposition Header Field》声明呈现意图。

1. Content-Disposition 呈现语义

Content-Disposition 是一个可选头部字段。当字段缺失时，MUA 可以自行决定展示方式（RFC 2183 第 2 节）。规范定义了两种基础处置类型：

  • inline（第 2.1 节）：表达该部件应当在展示邮件时自动展开呈现给用户的意图（should be displayed automatically）。
  • attachment（第 2.2 节）：表达该部件独立于邮件主体，其展示应当依赖于用户的进一步操作（contingent upon some further action of the user），例如通过图标或附件列表供用户点击。

需要说明的是，Content-Disposition 仅表达发件方的呈现意图，它不是文件真实格式的证明，也不提供恶意代码过滤能力。接收端如何处置附件依然取决于客户端软件的实现与本地安全设置。

2. 文件名参数与安全考量

在 Content-Disposition 中，发送方可通过可选的 filename 参数建议保存时的文件名（RFC 2183 第 2.3 节）。但规范在第 2.3 节与第 5 节明确提出了安全告诫：

  1. 不可盲目采纳建议文件名：接收端 MUA 绝不应盲目使用发送方建议的文件名（The receiving MUA not blindly use the suggested filename）。建议的文件名应当（SHOULD）接受校验并允许针对本地文件系统规则进行修改，避免覆盖现有文件。
  2. 忽略目录路径信息：接收端 MUA 不应采纳建议文件名中可能包含的任何目录路径（SHOULD NOT respect any directory path information），建议文件名应当仅作为末端纯文件名组件处理，防范利用相对路径或绝对路径对系统目录发起穿越。
  3. 防范非预期执行与系统文件覆盖：RFC 2183 第 5 节列举了多种严重风险，包括利用文件名诱导创建或覆盖系统启动文件（如 UNIX 环境下的 .login）、系统核心文件（如 /etc/passwd）、将可执行文件写入系统命令搜索路径（如 ~/bin/more）或送入管道（如 | sh）。规范要求接收端 MUA 不应以导致文件在未经用户明确操作的情况下被解释或执行的方式来命名或放置文件。

网关与客户端的防护分工

防范邮件欺诈需要传输验证、网关过滤与客户端界面的协同配合，各层承担不同的防护职责：

+-----------------------------------------------------------------+
|                        入站邮件接收                             |
+-----------------------------------------------------------------+
                                |
                                v
+-----------------------------------------------------------------+
| 1. 协议认证层 (SPF / DKIM / DMARC)                              |
|    - 检验客户端 IP、签名完整性与 From 域对齐                    |
|    - 依赖接收端实际执行；抑制对严格配置域名的直接仿冒           |
+-----------------------------------------------------------------+
                                |
                                v
+-----------------------------------------------------------------+
| 2. 可选网关过滤层 (信誉评分 / 内容过滤 / 链接检测)              |
|    - 结合域名注册时间等信誉数据评估风险                         |
|    - 识别高风险外部发件人重名并可插入警示                       |
|    - 具备条件时在点击时重新检查正文外部链接                     |
+-----------------------------------------------------------------+
                                |
                                v
+-----------------------------------------------------------------+
| 3. 客户端界面与操作系统策略 (MUA / 本地安全设置)                |
|    - 同时呈现显示名与完整规范邮箱地址                           |
|    - 遵循 RFC 2183 忽略附件目录路径，校验建议文件名             |
|    - 悬停展示真实目标 URL，防止界面混淆                         |
+-----------------------------------------------------------------+
  1. 协议层作为基础标识检验：SPF、DKIM 与 DMARC 能够有效验证发信域与消息签名的技术合法性。当域所有者发布了严格的处置策略（如 p=reject）且接收端严格执行时，能够阻断外部直接冒用该域名的发信行为。
  2. 网关层提供内容与行为检测：通过本地策略规则、外部信誉数据库以及深度解析引擎，对认证通过背后的文本语义、外部跳转与附件载荷进行动态筛查。
  3. 客户端承担呈现保护与用户交互：MUA 遵循 RFC 2183 的建议对附件文件名进行本地规范化，拒绝自动执行潜在风险文件；在界面上清晰呈现完整邮件地址与链接目标，避免单一视图遮蔽网络标识，帮助用户作出正确的安全判断。
