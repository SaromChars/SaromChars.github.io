邮件头、正文与 MIME 编码

2021年8月11日
|

在简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）的会话中，客户端通过 DATA 命令发送的数据块，在协议语义上被称为邮件内容（Content）。这块数据在进入具体传输通道之前，必须遵循严格的报文格式规范。

定义纯文本邮件报文格式的基础标准是 RFC 5322（互联网邮件格式，Internet Message Format，IMF）。为了使邮件支持多国语言字符集、非文本多媒体内容与复杂多部件结构，RFC 2045 与 RFC 2046（多用途互联网邮件扩展，Multipurpose Internet Mail Extensions，MIME）系列规范与 RFC 5322 报文格式配合使用，补充了内容描述与编码机制（MIME 规范最初针对 RFC 822 制定）。

信封地址与邮件头字段的语义分离

邮件系统中存在两套职责不同的地址与元数据体系：信封元数据（Envelope Metadata）与邮件头字段（Header Fields）。

  • 信封地址（Envelope Address）：由 SMTP 会话中的 MAIL FROM（反向路径，用于退信通知）与 RCPT TO（正向路径，用于路由与投递）命令显式声明。SMTP 事务的本次投递目标完全取自信封，显示地址不直接决定本事务的路由。
  • 邮件头字段（Header Fields）：位于邮件内容的头部区域，以可打印字符构造，供邮件用户代理（Message User Agent，MUA）展示给用户阅读，或供过滤规则归档分类。

RFC 5322 明确指出，它只规范邮件内容的格式，不规范信封。这种语义分离带来了关键工程机制：

  1. 密送（Blind Carbon Copy，Bcc）的实现：当发件人密送给某个收件人时，发信组件根据收件人列表构造信封并在发送前准备相应副本。在最终递送给其他公开收件人的邮件内容中，Bcc: 字段会被剥除，或者向密送收件人单独投递副本。
  2. 显示与路由分离：在 MUA 界面看到的 From: 是邮件头字段，它在协议上可以与 SMTP 传输中的信封 MAIL FROM 不一致。

RFC 5322 的头部结构与字段约束

根据 RFC 5322 第 2.1 节，一封合法的邮件由头部区域（Header Section）与可选的正文（Body）构成，两者之间严格以一个空行（即回车换行，Carriage Return and Line Feed，CRLF）分隔。

Field-Name: Field-Body<CRLF>
Another-Field: Field-Body<CRLF>
<CRLF>
Here is the message body text...

1. 行长限制与头部折叠（Folding）

RFC 5322 第 2.1.1 节对邮件内容的每一行施加了两项长度约束：

  • 强制硬性上限：每行字符数不得超过 998 个字符（不包含行尾 CRLF）。若单行超过 998 字符，该报文可能被某些传输代理拒收或无法被正确处理。
  • 推荐行长：每行建议不超过 78 个字符（不包含 CRLF），以便在窄屏终端平整展示。

为了在单行长度受限的前提下表达较长字段，RFC 5322 第 2.2.3 节定义了头部折叠（Folding）机制： 在允许出现折叠空白符（Folding White Space，FWS）的语法位置，可以在空白符（空格 Space，SP 或水平制表符 Horizontal Tab，HTAB）之前插入一个 <CRLF>。

接收端在解析头部字段时执行展开（Unfolding）程序： 删除后面紧跟空格或制表符的 <CRLF>，保留这些空白字符；再按具体字段的语法进行解析。

例如，一个长收件人字段在物理传输时被折叠为两行：

To: alice@example.com,
    bob@example.net

解析端展开后，折行处的 CRLF 被移除，第二行开头的缩进空格保留，由地址解析器继续按逗号和空白切分。

2. 核心头部字段与出现基数约束

RFC 5322 第 3.6 节对各类字段的语义与出现次数作出了规定：

头部字段语法基数要求语义定义与协议边界
Date:必须且仅允许 1 个发件人完成邮件编写并交付外发系统的源起时间（RFC 5322 第 3.6.1 节），非网络传输时间。
From:必须且仅允许 1 个标明对邮件负有著作责任的作者邮箱（可为多个邮箱地址组成的列表）。
Sender:0 个或 1 个标明实际执行代理发信的邮箱（RFC 5322 第 3.6.2 节）。当 From: 包含多个邮箱地址时，Sender: 必须（MUST）出现且只能有单个邮箱。
Reply-To:0 个或 1 个建议收件人回复时的目标地址列表。缺失时，MUA 默认回复给 From:。
To: / Cc:0 个或 1 个To: 为主要接收人；Cc: 为抄送接收人。二者语法允许包含多个邮箱地址。
Message-ID:0 个或 1 个（强烈推荐）机器可读的唯一报文标识符（RFC 5322 第 3.6.4 节），格式为 <id-left@id-right>。
In-Reply-To:0 个或 1 个标识当前回复所对应的一封或多封父报文的 Message-ID。
References:0 个或 1 个记录可用于构造会话关系的一组报文标识；通常继承父邮件的 References 并追加父 Message-ID，不保证历史完整。
Subject:0 个或 1 个非结构化短文本，指明邮件主题。

MIME 内容描述与 RFC 2045

基础的 RFC 5322 格式使用美国信息交换标准代码（American Standard Code for Information Interchange，ASCII，本文特指 US-ASCII，字符值 1 至 127）。RFC 2045 定义了标准头部字段，使得邮件可以在保持 RFC 5322 报文格式兼容的前提下承载丰富内容。

1. MIME 标识与默认继承

遵循 MIME 规范的报文在顶层头部包含版本声明（RFC 2045 第 4 节）：

MIME-Version: 1.0

在协议解析中，不同字段的缺省语义有所区别：

  • 缺少 Content-Type 时：RFC 2045 第 5.2 节规定默认采用 text/plain; charset=us-ascii。
  • 缺少 MIME-Version 时：RFC 2045 第 4 节明确指出不能确认该报文遵循 MIME 规范，接收端可能按本地约定解释正文，不能据此反推实际编码或字符集。

2. 媒体类型与字符集参数

Content-Type 字段（RFC 2045 第 5 节）的语法形如 type/subtype; parameter=value：

  • 主类型（Type）：定义数据的基本类别。RFC 2046 初始定义了五类离散类型（text、image、audio、video、application）与两类复合类型（multipart、message）。
  • 字符集参数（charset）：针对 text 类型，charset 参数指明字节序列对应的字符编码（如 utf-8 或 gb2312）。

内容传输编码（Content-Transfer-Encoding）

由于早期 SMTP 传输通道主要为 7 位 US-ASCII 短行设计，若直接传输 8 位字节或任意二进制流，可能在老旧网关处遭遇高位被剥除或控制符被过滤的风险。RFC 2045 第 6 节为此定义了 Content-Transfer-Encoding 传输编码机制。

规范定义了五类核心机制：

  1. 7bit：数据本身由不超过 998 字节的短行 US-ASCII 字符组成，编码前后字节不变，是协议的默认状态。
  2. 8bit：数据由短行构成但包含大于 127 的字节，编码前后字节不变，需传输通道支持 8 位传输。
  3. binary：允许任意字节流，行长不受 CRLF 限制，编码前后字节不变。
  4. quoted-printable：面向大部分为可打印 ASCII 字符、少量非 ASCII 字节的文本。
  5. base64：面向任意二进制或非 ASCII 密集型数据。

Quoted-Printable 编码规则（RFC 2045 第 6.7 节）

Quoted-Printable（简称 QP）旨在保持文本的人类可读性，编码按如下顺序应用：

  1. 可打印字符与内部空白：ASCII 值 33 到 60 以及 62 到 126 的字符可直接保留（= 字符除外）；行内的空格（SP）与制表符（HTAB）也可直接保留。
  2. 特殊字节与非 ASCII 字节转义：等号 = 以及大于 126 的字节必须转义为 = 紧跟两位大写十六进制数（例如等号编码为 =3D）；其他控制字节也必须按 =XX 编码（例如换页符为 =0C）。
  3. 行末空白保护：行尾的空格与制表符必须转义（如 =20、=09），避免在传输中途被中继剔除。
  4. 文本真实换行：文本数据规范形式中的 CRLF 换行在 QP 编码中保留为 CRLF。
  5. 软换行（Soft Line Break）：编码后每行长度不得超过 76 个字符。若单行过长，在行末插入一个单独的等号 = 并换行（即 =CRLF），解码端还原时剥除该等号并将前后行拼接。

Base64 编码规则（RFC 2045 第 6.8 节）

Base64 将连续的字节流按每 3 个字节（24 位）为一组，转换为 4 个 6 位的索引，并映射到 64 个安全打印字符（A-Z, a-z, 0-9, +, /）：

  • 体积变化：不含 CRLF 时，输入 n 个字节会产生 4 × 向上取整(n ÷ 3) 个编码字符。短数据受填充影响明显；较长数据的字符数趋近于原字节数的 4/3（约增 33%）。每行编码字符不超过 76 个（不计行末 CRLF）。
  • 尾部填充（Padding）：当输入字节数不能被 3 整除时，尾部用 0 补足 6 位组，并在输出末尾补充 =（余 1 字节输出 2 字符加 ==；余 2 字节输出 3 字符加 =）。

复合实体与 multipart 边界（RFC 2046）

当邮件需要同时承载排版正文、备用纯文本以及附件时，需使用复合媒体类型 multipart（RFC 2046 第 5.1 节）。

1. multipart 边界语法

multipart 类型必须在 Content-Type 声明中指定 boundary 参数：

Content-Type: multipart/mixed; boundary="simple-boundary-123"

其边界处理遵循以下规则：

  • 边界分隔行：每个子实体部件（Body Part）开始前，独立成行插入 -- 加上边界字符串，即 --simple-boundary-123<CRLF>。
  • 结束分隔行：最后一个部件结束后，两端均带双连字符，即 --simple-boundary-123--<CRLF>。
  • 位置与约束：边界字符串最长不超过 70 个字符（不计前导两个连字符）。子部件内部的数据不得在行首出现与边界分隔符冲突的行。分隔符行前的 CRLF 在语义上隶属于分隔符本身，不属于上一部件的正文数据。
  • 前导语与后记（Preamble and Epilogue）：首个边界行之前与结束边界行之后的数据，MIME 解析器予以忽略。

2. 常见 Multipart 子类型的语义分工

复合子类型规范定位语义解析逻辑与部件顺序要求
multipart/mixedRFC 2046 第 5.1.3 节各部件互相独立且按顺序捆绑。通常前部为主正文，后续为各类文件附件。
multipart/alternativeRFC 2046 第 5.1.4 节各部件内容互为等价替代版本。发送端必须按保真度升序排列（从简单纯文本到丰富排版）。接收端通常优先选择最后一个自身能正常显示的部件，但也可由用户自行切换查看。
multipart/digestRFC 2046 第 5.1.5 节邮件摘要集合。与 mixed 语法相同，但子部件默认的 Content-Type 为 message/rfc822。

报文结构示例与解析流程

下面是自编的 MIME 嵌套结构示例。假设报文各物理行均使用 CRLF 结束；它用于说明解析过程，不是生产邮件抓包：

Date: Wed, 11 Aug 2021 09:30:00 +0800
From: Alice Author <alice@example.com>
To: Bob Recipient <bob@example.net>
Subject: Project Status and Document
Message-ID: <20210811013000.A1B2C3@mail.example.com>
MIME-Version: 1.0
Content-Type: multipart/mixed; boundary="frontier_mixed_01"

This is a multi-part message in MIME format.
--frontier_mixed_01
Content-Type: multipart/alternative; boundary="frontier_alt_02"

--frontier_alt_02
Content-Type: text/plain; charset=utf-8
Content-Transfer-Encoding: quoted-printable

Hello Bob,

Please inspect the attached status report.
--frontier_alt_02
Content-Type: text/html; charset=utf-8
Content-Transfer-Encoding: quoted-printable

<p>Hello Bob,</p><p>Please inspect the <b>attached status report</b>.</p>
--frontier_alt_02--
--frontier_mixed_01
Content-Type: application/octet-stream; name="data.bin"
Content-Transfer-Encoding: base64

AQIDBAUGBwg=
--frontier_mixed_01--

本例的一种解析顺序

当软件模块接收并处理该报文时，通常采用如下处理步骤：

  1. 切分头部与正文：按行扫描至首个出现的空行（CRLF），上方归为邮件头字段，下方进入正文解析。
  2. 顶层 MIME 识别：检查 MIME-Version: 1.0，解析 Content-Type 为 multipart/mixed 并提取外层边界 frontier_mixed_01。
  3. 外层边界拆分：忽略第一个 --frontier_mixed_01 之前的导语，提取各子部件数据，直至闭合边界 --frontier_mixed_01--。
  4. 递归下降解析：
    • 第一部件识别为 multipart/alternative，依内层边界 frontier_alt_02 进一步拆分为 text/plain 与 text/html。假设本地显示策略选择 HTML，MUA 采纳排在最后的 HTML 部件，执行 Quoted-Printable 解码后送入渲染引擎排版。
    • 第二部件识别为 application/octet-stream，读取 Content-Transfer-Encoding: base64 声明，对数据 AQIDBAUGBwg=（8 字节输入编码为 12 字符，含一个 = 填充）执行 Base64 解码，恢复原始二进制字节（十进制数值 1 至 8）。

协议约束下的工程实现边界

在实现邮件生成与解析模块时，需注意以下协议约束与工程实现边界：

  1. 边界选取与前缀隔离：生成 multipart 的 boundary 时，必须确保其值不会在封装部件的行首作为边界分隔符出现，内层边界也不得与外层边界产生冲突。工程上通常采用随机字符串结合格式前缀的方式降低冲突概率，并在封装前核验正文行首特征。
  2. 换行符规范化（CRLF）：RFC 5322 规定报文行以 CRLF 结束。在采用单纯换行符 LF（\n）的操作系统中，发信模块在将数据交给传输层之前，应完成换行符的规范化转换，避免因网关兼容性差异引起解析异常。
  3. 头部非 ASCII 字符约束：在本文讨论的 RFC 5322 基础格式中，邮件头字段仅允许 US-ASCII 字符，不能直接填入未经转义的原始多字节字符。邮件头部的国际化与字符编码扩展遵循专门的头部扩展规范。
