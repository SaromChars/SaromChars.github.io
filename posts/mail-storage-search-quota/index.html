邮箱存储、检索与配额

2021年8月25日
|

在互联网邮件访问体系中，当邮件由投递代理（Mail Delivery Agent，MDA）写入用户的后端存储区后，如何让客户端有序组织文件夹、检索特定邮件并遵守容量边界，构成了邮箱存储服务（Message Store）的核心职责。

本文讨论互联网消息访问协议第 4 版修订版 1（Internet Message Access Protocol - Version 4rev1，IMAP4rev1，RFC 3501）访问接口下的邮箱组织。配合 IMAP4 配额扩展（IMAP4 QUOTA extension，RFC 2087）以及专用邮箱列表扩展（IMAP LIST Extension for Special-Use Mailboxes，RFC 6154），服务端在网络层提供了层级目录、结构化检索能力、多邮箱共享配额以及语义化文件夹识别机制。

需要指出的是，协议本身定义的是网络交互中可观察的逻辑语义（如消息属性、可变标志与查询响应），并不指定底层的具体存储引擎、文件格式或索引数据库结构。

邮箱层级模型与专用文件夹语义

在 IMAP4rev1 架构中，邮箱（Mailbox）指的是存放消息的远端容器或文件夹。规范允许服务端实现任意层级的命名空间，并通过层级分隔符（Hierarchy Delimiter）将路径串联。

本文中的客户端与服务端交互片段均为教学简化示意，客户端请求以 C: 标出，服务端响应以 S: 标出。

1. 命名空间、通配符与状态探测

客户端在枚举服务端目录时，主要通过 LIST 与 LSUB 命令配合两类通配符（RFC 3501 第 6.3.8 节）：

  • *（星号）：匹配零个或多个字符，能够跨越层级分隔符向下递归匹配所有子目录。
  • %（百分号）：匹配零个或多个字符，但不匹配层级分隔符。当 % 位于参数末尾时，仅展开当前层级的直属子目录；若匹配到的某一层级本身不可被 SELECT 选中（例如仅作为中间目录节点存在），服务端在响应中需附带 \Noselect 属性。

RFC 3501 规定特殊邮箱名称 INBOX 不区分大小写；若服务端支持某用户的 INBOX，在 LIST 输出中必须采用大写形式 INBOX（RFC 3501 第 6.3.8 节）。此外，服务端允许对特定路径隐藏通配符匹配（例如类 UNIX 系统服务端可限制 * 不匹配首字符为 / 的路径）。

以下为分层枚举的简化示意：

C: A101 LIST "" "%"
S: * LIST (\Noselect) "/" "Archive"
S: * LIST () "/" "INBOX"
S: A101 OK LIST completed
C: A102 LIST "" "Archive/%"
S: * LIST () "/" "Archive/2021"
S: A102 OK LIST completed
C: A103 STATUS "Archive/2021" (MESSAGES UNSEEN UIDNEXT UIDVALIDITY)
S: * STATUS "Archive/2021" (MESSAGES 142 UNSEEN 3 UIDNEXT 501 UIDVALIDITY 1629850000)
S: A103 OK STATUS completed

当客户端需要探测未选中邮箱的状态时，可发出 STATUS 命令查询特定数据项（RFC 3501 第 6.3.10 节）：

  • MESSAGES：邮箱内的总消息数。
  • RECENT：带有 \Recent 标志的消息数。
  • UIDNEXT：预测分配给下一封新消息的唯一标识符（Unique Identifier，UID）。它仅作为指示值，并非下一封可用 UID 必然取该值的强保证。
  • UIDVALIDITY：邮箱的唯一标识符有效性数值。
  • UNSEEN：未设置 \Seen 已读标志的消息数。

针对 STATUS 命令的调用，RFC 3501 第 6.3.10 节给出了明确的性能边界与行为禁令：

  1. STATUS 命令不保证返回速度；在部分后端实现中，服务端可能需要在内部以只读方式打开对应存储才能汇总数据，因此客户端不应预期连续大量调用该命令仍能保持良好响应性能。
  2. 鉴于当前处于已选中状态（Selected State）的邮箱其内部状态已可通过会话常规更新获取，客户端不应（SHOULD NOT）对当前已选中的邮箱执行 STATUS 命令。
  3. 客户端严禁（MUST NOT）将 STATUS 命令作为检查已选中邮箱新邮件到达的手段；已选中邮箱的新消息发现应依赖空闲 NOOP 等常规交互中服务端主动返回的未加标签通知。

2. 专用邮箱（Special-Use Mailboxes）与语义统一

在多客户端共存的环境中，各客户端往往对草稿箱、已发送箱、垃圾箱或废件箱采用不同名称（例如 Sent、Sent Messages、已发送邮件）。为消除硬编码路径造成的歧义，RFC 6154 引入了专用邮箱属性。

在基础 LIST 响应中，支持该扩展的服务端可直接在邮箱属性列表中返回语义属性；而在支持扩展 LIST（RFC 5258）时，客户端可通过 SPECIAL-USE 选项进行精准过滤（RFC 6154 第 2 节与第 3 节）：

属性名称语义与规范说明（RFC 6154 第 2 节）典型服务端行为或客户端处理
\All呈现用户存储中的所有邮件通常作为虚拟视图（Virtual Mailbox），可能排除垃圾与废件
\Archive归档存储，移出收件箱但长期保留具体的归档策略与触发条件由服务端定义
\Drafts存放草稿（正在撰写尚未发送的邮件）可为独立文件夹，或汇聚带有 \Draft 标志邮件的虚拟视图
\Flagged呈现所有标记为重要的邮件通常为汇总带有 \Flagged 标志邮件的虚拟视图
\Junk存放被判定为垃圾邮件的消息服务端过滤引擎自动投递，或向客户端垃圾邮件模块提供建议位置
\Sent保存已发送邮件的副本发信流程完成后自动或手动通过 APPEND 归档
\Trash存放已删除或标记待清理的邮件供不采用 IMAP \Deleted 标志覆盖模型的客户端作为废件箱

RFC 6154 强调所有上述属性均为可选（OPTIONAL）。若服务端在 CAPABILITY 中通告了 CREATE-SPECIAL-USE，客户端可在 CREATE 命令中使用 USE (...) 参数为新建文件夹指定属性；若无法按所指定用途创建，服务端不得（MUST NOT）创建该邮箱，并必须（MUST）返回标记 NO；如果失败原因与用途属性相关，应当（SHOULD）在该 NO 响应中附带 USEATTR 响应码（RFC 6154 第 3 节）：

C: A201 CREATE "Spam" (USE (\Junk))
S: A201 OK CREATE completed
C: A202 CREATE "VirtualAll" (USE (\All))
S: A202 NO [USEATTR] \All not supported

消息寻址、存储解耦与服务端检索

在邮件存储的工程实践中，为了兼顾高频访问效率与协议规范要求，系统通常将邮件体、元数据标志与检索索引进行分层维护。

1. 存储分层与 UID 稳定性（工程示意）

RFC 3501 并不强制特定的物理存储结构，但从协议的可观察语义出发，一种典型的工程分层模型可示意如下：

  • 整信内容（Message Content）：包含信头（Header）与正文（Body），通常以静态文件或对象形式持久化，并记录协议内部日期（INTERNALDATE）。
  • 可变元数据（Flags & State）：包括 \Seen、\Flagged、\Deleted 等状态标志。多客户端并发修改标志时仅变更轻量元数据记录。
  • 检索索引与配额统计：为加速 SEARCH 与容量统计构建的辅助结构。索引可由整信内容异步解析生成，并在损坏时重建。

在会话生命周期内，消息序号（Message Sequence Number）会随着邮件的移除发生动态重排；因此，跨连接、跨离线重同步的邮件身份必须依赖邮箱名、UIDVALIDITY 与 UID 的三元组合进行确认（RFC 3501 第 2.3.1 节）。UID 在同一邮箱内单调递增但不一定连续。只要 UIDVALIDITY 未发生变化，已分配的 UID 便具有全局稳定对应关系；若服务端发生重建或迁移导致 UID 无法沿用，服务端必须更新 UIDVALIDITY，客户端收到后必须废除旧有的本地 UID 缓存并重新建立同步。

2. SEARCH 命令语法与布尔逻辑

客户端在已选中状态下通过 SEARCH 命令发起检索（RFC 3501 第 6.4.4 节）。当给出多个检索键（Search Keys）时，默认求所有条件的交集（AND 逻辑）。若需使用析取（OR）或否定（NOT），需显式声明前缀操作符：

C: A301 SEARCH FLAGGED SINCE 1-Aug-2021 NOT FROM "notifications@example.com"
S: * SEARCH 12 15 48
S: A301 OK SEARCH completed

服务端匹配成功后，在未加标签的 * SEARCH 响应中返回符合条件的消息序列号；若以 UID SEARCH 发起，则返回对应的 UID 集合。RFC 3501 并不对返回的数字列表做强制升序保证。

常用检索键在 RFC 3501 第 6.4.4 节中的定义如下：

  • 标志状态：ALL（默认全集）、ANSWERED/UNANSWERED、DELETED/UNDELETED、FLAGGED/UNFLAGGED、SEEN/UNSEEN、RECENT/OLD（OLD 等价于 NOT RECENT）。此外，NEW 严格等价于 (RECENT UNSEEN)。
  • 信头字段与子串匹配：FROM <string>、TO <string>、CC <string>、BCC <string>、SUBJECT <string>。此类匹配针对 IMAP 从邮件头字段解析出的 ENVELOPE 结构（并非 SMTP 传输阶段的 MAIL FROM/RCPT TO 信封参数）进行子串比对，且不区分大小写（case-insensitive）。若需匹配任意自定义信头，使用 HEADER <field-name> <string>。
  • 正文与全文内容：
    • BODY <string>：匹配邮件正文（Body）文本中包含指定子串的邮件。
    • TEXT <string>：匹配邮件信头（Header）或正文（Body）中包含指定子串的邮件。
    • 规范明确允许：服务端实现可以（MAY）在执行检索匹配时，排除多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）中终端媒体类型非 TEXT 与 MESSAGE 的实体部分（例如二进制附件）。
  • 日期对比范围：
    • 区分内部接收日期（BEFORE、ON、SINCE，以协议内部日期 INTERNALDATE 为准，忽略时分秒与时区；该日期可通过 APPEND 显式指定或由系统接收时赋予，并非统一的磁盘落盘时间）与发件人信头日期（SENTBEFORE、SENTON、SENTSINCE，解析邮件信头的 Date: 字段）。
  • 容量对比：LARGER <n> 与 SMALLER <n>，按邮件的八位组字节数（RFC 2822 大小）进行筛选。

3. 字符集声明与解码约束

在处理非纯 ASCII 文本时，客户端可在检索条件前置 CHARSET <registered-charset>。

RFC 3501 第 6.4.4 节作出了严格的兼容性规范：

  1. 服务端必须（MUST）支持美国信息交换标准代码（American Standard Code for Information Interchange，ASCII，具体为 US-ASCII）字符集；对其他字符集（如 UTF-8 或 GB2312）的支持为可选（MAY）。
  2. 在比对非 US-ASCII 字符集前，服务端必须（MUST）先将邮件内容传输编码（Content-Transfer-Encoding，如 Base64 或 Quoted-Printable）以及信头中的 MIME 编码字（RFC 2047 格式）解码为原生字符序列，再进行文本匹配。
  3. 若客户端请求了服务端未实现的字符集，服务端必须（MUST）返回标记 NO 响应（而不得返回语法错误的 BAD），并且该响应中应当（SHOULD）包含 BADCHARSET 响应码，其参数可列出服务端当前支持的字符集列表。

以下为探测字符集支持情况的教学简化示意：

C: A302 SEARCH CHARSET GB2312 TEXT "query"
S: A302 NO [BADCHARSET (US-ASCII UTF-8)] Unsupported charset

邮箱配额体系：RFC 2087 QUOTA 扩展

随着邮件系统的长期运行，存储膨胀与资源耗尽是邮件服务器面临的主要风险。在服务端通告了 QUOTA 功能能力（CAPABILITY）的前提下，RFC 2087 为 IMAP4 提供了配额管理机制。

1. 配额根（Quota Root）与资源抽象

RFC 2087 的核心设计在于解耦“具体邮箱路径”与“配额计算实体”：

  • 配额根（Quota Root）：服务端内部定义的资源限制命名实体。一个配额根拥有零个或多个资源限制。配额根的名称由实现定义，不必然（do not necessarily have to）与现实存在的邮箱名称重合（RFC 2087 第 3 节）。
  • 多邮箱共享：每个邮箱隶属于零个或多个配额根。凡是共享同一个配额根的所有邮箱，共同消耗该配额根下的资源额度。

RFC 2087 第 3 节列举了两类标准资源原子名称作为解释示例（服务端并不被强制必须实现这两类）：

  1. STORAGE：所有邮件的 RFC822.SIZE 累计总和，以 1024 字节（1024 octets） 为基本度量单位。
  2. MESSAGE：当前配额根覆盖范围内的消息数量，用于限制总消息数。

2. 配额查询与响应指令

客户端通常通过 GETQUOTAROOT 命令探测某个具体邮箱绑定的配额信息（RFC 2087 第 4.3 节与第 5 节）：

C: A401 GETQUOTAROOT "INBOX"
S: * QUOTAROOT "INBOX" ""
S: * QUOTA "" (STORAGE 20480 102400 MESSAGE 150 1000)
S: A401 OK GETQUOTAROOT completed

在此交互过程中，服务端先返回未加标签的 QUOTAROOT 响应，指明 INBOX 关联的配额根名称（此示例假设服务端实现使用空字符串 "" 命名共享个人配额根，并非标准强制的通用命名规则）；随后紧跟对应的 QUOTA 响应，给出该配额根下的各资源三元组：(资源名称 当前用量 资源上限)。

在上述示例中，当前已使用 20480 单位（即 20480 × 1024 字节，整 20 MiB），上限为 102400 单位（整 100 MiB）。若某资源未在三元组列表中列出，则表示该配额根对该项资源不作限制（RFC 2087 第 5.1 节）。管理员权限用户还可以使用 SETQUOTA 动态重置限额；若指定配额根原先不存在，服务端实现可按需创建该根（RFC 2087 第 4.1 节）。

并发、消息清理与异常边界

邮件存储层必须在多客户端长连接、断网重连以及后台清理并发发生的场景下，维系状态一致性与稳定的异常边界。

1. 消息永久移除与并发会话同步

在 IMAP4rev1 中，删除邮件分两阶段完成：首先通过类似 STORE 12 +FLAGS (\Deleted) 为指定消息打上待删除标志，随后由客户端显式触发清理。

从邮箱中永久移除（Permanent Removal）带有 \Deleted 标志的邮件存在两种方式，其在协议通知行为上有所区分（RFC 3501 第 6.4.2 节与第 6.4.3 节）：

  1. EXPUNGE 命令：发起该命令的会话在收到最终的标记 OK 前，服务端必须针对每封被移除的邮件返回未加标签的 * <seq> EXPUNGE 通知。需要注意的是，EXPUNGE 会永久移除当前邮箱中所有带有 \Deleted 标志的消息，而不仅限于当前会话打上标志的邮件，这在多客户端并发操作时具有清理扩散风险。对于其他并发打开了该邮箱的会话，RFC 3501 第 7 节规定服务端应当（SHOULD）发送对应的更新通知，但受限于第 7.4.1 节的时序限制，服务端不得在无命令执行期间或响应 FETCH/STORE/SEARCH 等指令的中途随意插入 EXPUNGE，因此其他会话通常在自身发出后续命令时才会接收到序号重排通知。
  2. CLOSE 命令：从当前邮箱中永久移除带有 \Deleted 标志的邮件，并使当前连接从已选中状态退回已认证状态。与 EXPUNGE 不同，CLOSE 不会（No untagged EXPUNGE responses are sent）向当前连接发送任何未加标签的 EXPUNGE 响应。因此，在需要清理大量消息时，CLOSE 能有效减少网络逐条通知开销。但协议仅定义了邮件在逻辑邮箱视图中的永久移除，并不保证底层分布式存储、快照或备份系统的物理磁盘块被即刻释放。
Caution

依据 RFC 3501 第 6.4.2 节规范，如果邮箱是通过 EXAMINE 指令打开（只读模式）或底层存储处于只读保护状态，执行 CLOSE 绝对不会（No messages are removed）移除任何邮件，且服务端不会报错，直接返回 OK 并退回已认证状态。客户端若依赖 CLOSE 移除邮件，必须预先确认会话具备读写权限。

2. 配额超额与写入失败边界

当配额耗尽或存储空间不足时，邮件写入操作的失败模式需严格界定：

  • IMAP 追加与复制：当客户端通过 APPEND 向满额邮箱追加邮件，或执行跨邮箱 COPY 导致目标配额根溢出时，服务端必须返回标记 NO，并可在未加标签的诊断文本中向用户提示空间紧张（RFC 3501 第 7.1.2 节给出了 * NO Disk is 98% full 的告警示例）。
  • 投递写入与责任边界推导：RFC 2087 仅约束 IMAP4 交互，并未定义底层投递传输时的返回状态。基于本系列前篇对 RFC 5321 投递协议的探讨进行工程推导：在服务端尚未发送最终确认响应（如 250 OK）之前，如果 MDA 预先判定或在写入时发现配额溢出，可通过适宜的 4xx（临时失败）或 5xx（永久失败，如 552 Requested mail action aborted: exceeded storage allocation）拒绝接收，此时投递责任仍在发信前一跳；若服务端已向发送方发送了最终成功确认（正式接受投递责任），之后因存储落盘崩溃且无法进入重试队列导致交付失败，接收方必须独立承担退信责任，此时若向原始反向路径生成失败通知，该通知自身的信封发件人必须为空（MAIL FROM:<>），且如果原始信件的反向路径本身为空，则严禁发送退信，以阻断无限循环弹跳。
