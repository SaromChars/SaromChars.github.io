配额、并发写入与部分失败

2021年12月1日
|

当两个投递进程几乎在同一瞬间为同一个邮箱写入信件时，配额系统的边界会被立刻暴露出来。假设用户的剩余存储空间仅剩 10 MiB，两个进程分别试图存入一封 8 MiB 的邮件。如果检查余额与实际落盘之间存在时间差，两个进程在第一步读取到的剩余空间都满足要求。若缺乏全局的互斥或预留机制，两封信件便可能同时落盘并成功提交，导致邮箱最终额外增加 16 MiB 存储，打破预设的配额上限。

本文基于 2021 年 8 月发布的 Dovecot 2.3.16 源码与 RFC 2033 LMTP 备忘录，剖析配额（quota）子系统在“检查容量、底层存储提交、统计服务提交”三阶段中的具体控制流与失败处理。文中涉及的时序推导与并发场景为基于源码逻辑的机制分析，未在物理集群中执行压力测试。

配额根与计量口径

在 Dovecot 的配额插件中，限制规则挂载在配额根（quota root）之上。每个配额根可以定义不同的范围（例如整个用户的主命名空间，或特定的一组邮箱文件夹），并同时维护两项独立的度量指标：存储字节数与邮件封数。

根据 src/lib-storage/mail-storage.h 的接口定义，这两项度量指标与操作系统底层的物理资源有着明确的口径边界：

在字节计量方面，系统默认获取的是物理尺寸（physical size），即 mail_get_physical_size() 返回的底层流读取长度（mail_get_stream），它反映邮件文件流的大小，并不等同于文件系统在磁盘上实际占用的数据块（disk blocks）。当配置开启了虚拟大小（virtual size，quota_vsizes = yes）时，系统转而使用 mail_get_virtual_size()，它度量的是读者视角的邮件内容体积，其中所有行换行符均严格按回车换行（CRLF）双字节计。

在封数计量方面，系统度量的是邮箱中逻辑邮件实体的数量，而不是底层存储目录中的文件数量。封数限制在逻辑层防止邮件无序积压，但不能替代文件系统的 inode 配额；底层文件系统的空间耗尽（ENOSPC）或 inode 耗尽属于操作系统层面的物理故障，配额子系统无法在用户态为其提供完整阻断。

当邮箱事务（transaction）开始时，调用 quota_transaction_begin() 初始化配额事务上下文 struct quota_transaction_context。在 quota_transaction_set_limits() 中，系统遍历所有可见的配额根，读取限制并设置当前事务允许的增量阈值（bytes_ceil 与 count_ceil）。该函数通过 limits_set 布尔标志确保在同一个事务上下文中只计算一次并缓存。如果当前处于本地邮件传输协议（Local Mail Transfer Protocol，LMTP）或本地投递代理投递会话（包含 MAILBOX_FLAG_POST_SESSION 标志），算法还会计入配置的宽限额外字节（last_mail_max_extra_bytes，在配额根规则中配置为例如 quota_grace = 0 时不分配宽限）。

写入生命周期与两次检查

在本地投递的普通保存流程（mail_deliver_save）中，配额检查通过钩子函数挂载在底层存储操作的前后两端：

mailbox_transaction_begin()
  -> quota_mailbox_transaction_begin()
       -> quota_transaction_begin()
mailbox_save_alloc()
mailbox_save_using_mail()
  -> quota_save_begin()
  -> super.save_begin()
  -> [底层存储流式写入数据]
  -> super.save_finish()
  -> quota_check()
       -> quota_try_alloc()
mailbox_transaction_commit()
  -> quota_mailbox_transaction_commit()
       -> super.transaction_commit()
       -> (void)quota_transaction_commit()

上述调用链展示了投递时的 save 分支；mailbox_save_using_mail() 在实际运行时也可能经由 copy 分支完成，具体由底层存储后端选择，此时配额插件会走独立的 quota_copy() 路径进行检查。而在一般的流式保存路径下，quota_save_begin() 在流式写入前估算输入流大小，quota_check() 在写入完成流关闭后核验实际尺寸，最后由 quota_mailbox_transaction_commit() 协调存储驱动落盘与统计更新。

1. 开始保存阶段：输入流估算

在 quota_save_begin() 中，如果输入流（istream）的大小在调用前已知且事务未处于失败状态（!qt->failed），系统通过 quota_test_alloc() 提前试探剩余额度。

这一步的作用是提前拦截注定超额的超大邮件，避免无意义的磁盘 I/O。但由于网络流中的 CRLF 与磁盘保存时的换行差异，或者存储格式跳过特定头部，流长度与最终物理尺寸可能存在微小偏差。

当试探分配返回临时失败（QUOTA_ALLOC_RESULT_TEMPFAIL）或后台正在重算（QUOTA_ALLOC_RESULT_BACKGROUND_CALC）时，Dovecot 仅记录错误日志，并放行保存（saving mail anyway），以尽量避免单点统计故障阻断合法邮件投递。

2. 结束保存阶段：实际尺寸核验

在底层存储完成数据流写入并执行 super.save_finish() 之后（参见 quota_save_finish()），系统进入 quota_check()，调用 quota_try_alloc()。

保存检查的相关分支如下：

  • 若事务之前已被标记为失败（qt->failed == TRUE），在 quota_check() 中直接返回 0。这表示跳过配额判定，并不表示整个保存必然失败或用量已更新；
  • 进入 quota_try_alloc() 后，首先调用 quota_transaction_set_limits() 确保上限已初始化，若配置为无需更新配额（ctx->no_quota_updates == TRUE）则直接返回成功；
  • 尝试获取邮件物理尺寸或虚拟大小；若获取大小失败，且错误不是源邮件已被删除（MAIL_ERROR_EXPUNGED），则返回 QUOTA_ALLOC_RESULT_TEMPFAIL；若此时放行，邮件虽然落盘但用量暂未准确计入本事务上下文；
  • 调用 quota_test_alloc() 对尺寸进行最终核验。若超过单封邮件最大限制（max_mail_size），返回 QUOTA_ALLOC_RESULT_OVER_MAXSIZE 并映射为 MAIL_ERROR_LIMIT；若超过总配额，返回 QUOTA_ALLOC_RESULT_OVER_QUOTA 并映射为 MAIL_ERROR_NOQUOTA；
  • 在 quota_check() 中，若判定结果为 TEMPFAIL 或 BACKGROUND_CALC，系统记录日志后同样返回 0 放行保存；只有明确超额时，才调用 quota_set_storage_error() 并返回 -1；
  • 检查通过后，调用 quota_alloc() 将邮件尺寸累加到本事务私有上下文（ctx->bytes_used += size; ctx->count_used++;）。

提交、回滚与统计后端的解耦

一封邮件在底层存储驱动中的持久化落盘，与配额计数在外部统计介质（如数据库字典）中的递增，属于不同的控制流。在 quota_mailbox_transaction_commit() 中：

super.transaction_commit(ctx) < 0
  |-- 是 --> quota_transaction_rollback(&qt) -> return -1
  +-- 否 --> (void)quota_transaction_commit(&qt) -> return 0
  1. 底层存储驱动提交优先：系统先执行底层存储与索引的提交（super.transaction_commit）。若底层驱动因权限、磁盘空间或格式错误返回失败，配额上下文通过 quota_transaction_rollback() 释放内存结构，函数直接向调用者返回 -1。但这仅代表配额子系统清理了事务状态，底层磁盘上是否存在部分写入的临时残留碎片，取决于对应存储后端的崩溃恢复与回滚实现。
  2. 统计失败不回滚已存邮件：如果底层存储提交成功，紧接着调用 quota_transaction_commit()。在 src/plugins/quota/quota.c 的实现中，即便各个配额根的后端更新（roots[i]->backend.v.update）返回失败并在日志中记录 Failed to update quota，外层依然强制忽略返回值（void），对调用者返回 0。

以字典存储驱动为例，在 src/plugins/quota/quota-dict.c 的 dict_quota_update() 中，系统通过 dict_atomic_inc() 发送增量指令，并通过异步事务 dict_transaction_commit_async() 提交。其异步回调函数 dict_quota_update_callback() 展现了两种降级机制：

  • 若行记录不存在（result->ret == 0），安排定时器重新计算当前配额；
  • 若底层数据库报错或网络断开（result->ret < 0），仅在日志中输出警告：Quota update failed: ... - Quota is now desynced。

由此可见，在底层存储已提交成功的前提下，Dovecot 优先保障已存信件的投递确认，允许统计服务在异常时处于失步（desynced）状态，而不会因为外部统计后端暂时脱机撤销已落盘邮件。

并发写入与全局超额

在多进程投递环境下，这种分阶段设计带来了一个典型的并发竞态推导。

假定邮件尺寸均按同一计量口径度量，且系统未配置额外宽限额度、未引入外部写串行化机制。用户配额设为 100 MiB，当前用量为 90 MiB，剩余可用 10 MiB。外部进程 P1 与 P2 几乎同时为该用户写入一封 8 MiB 的信件：

  1. 时序推导：
    • P1 与 P2 分别启动独立的投递进程，进入 quota_transaction_set_limits()；
    • 两者分别从字典后端查询当前用量，由于对方均未提交，两者均读取到当前用量 90 MiB，各自在私有上下文中缓存上限阈值 bytes_ceil = 10 MiB，并将 limits_set 标记为 TRUE；
    • P1 写入 8 MiB 数据，在 quota_check() 时，P1 本地初始 bytes_used = 0，试探分配满足 8 <= 10 MiB，核验通过后更新私有计数 bytes_used = 8 MiB；
    • P2 几乎在同一时刻写入 8 MiB 数据。在 P2 独立的进程上下文中，其私有 bytes_used 初始同样为 0，核验自身 8 MiB 同样满足本地缓存的 bytes_ceil = 10 MiB，核验通过并更新自身私有计数；
    • P1 执行底层驱动 super.transaction_commit() 成功，完成物理落盘；
    • P2 执行底层驱动 super.transaction_commit() 成功，完成物理落盘；
    • 随后 P1 与 P2 分别向字典后端发起 dict_atomic_inc 异步提交。假定外部字典服务正常处理了两次原子加法操作，数据库中的配额数值最终累加为 106 MiB。

在这个流程中，数据库的原子递增操作确保了并发加法不会丢失计数；但在应用层面，单字段的原子增量并不等于“检查余额、预留空间与落盘提交”的跨进程排他事务。两个并发进程依据相同的时间切片余额进行决策，导致新写入的数据量达到 16 MiB，用户存储用量最终超出预设限制。

LMTP 协议与多收件人部分失败

当上游邮件传输代理（Mail Transfer Agent，MTA）通过 LMTP 投递给多个本地收件人时，RFC 2033 第 4.2 节规定：在邮件数据结束符（.）之后，服务端必须为每个之前成功的 RCPT TO 命令按原有顺序返回独立的响应状态码。

在 Dovecot 的 src/lmtp/lmtp-local.c 中，每个收件人都会进入 lmtp_local_default_do_deliver() 函数，由它负责调用 mail_deliver()：

  • 投递成功时，返回 250 2.0.0 <session_id> Saved；
  • 底层存储临时故障（MAIL_DELIVER_ERROR_TEMPORARY）时，返回 451 4.2.0 <error>；
  • 配额满额错误（MAIL_DELIVER_ERROR_NOQUOTA）时，进入 lmtp_local_rcpt_reply_overquota()。若配置项 quota_full_tempfail = yes，返回临时错误 452 4.2.2；若为默认的 no（参见 lda-settings.c），返回永久错误 552 5.2.2。

如果启用了 RCPT 阶段的预检（lmtp_rcpt_check_quota = yes，参见 lmtp_local_rcpt_check_quota()），系统在接收数据前会以 size = 0 调用状态查询。根据 src/plugins/quota/quota-util.c 中的判断逻辑，size = 0 既不预留空间，也不检查即将传入的信件体积，仅当历史用量已明确超出限额（bytes_over > 0）或封数配额已用尽时才会判定超额。若该阶段实际执行了统计查询且后端报错，系统向该收件人返回 451 4.3.0 Temporary internal error。而在后续保存阶段，统计后端异常本身并不直接导致拒绝，只要底层存储驱动提交成功，该收件人依然可以获得 250。

逐场景结果对照

在包含多个本地收件人的单次会话中，LMTP 允许针对不同目标返回混合状态：

  • 场景 A（正常收件人写入成功）：服务端返回 250 2.0.0 Saved。该收件人的投递责任已明确移交给存储服务，上游队列管理器从本地队列中清除收件人 A 的投递任务。
  • 场景 B（目标收件人配额超限）：若配置了 quota_full_tempfail = yes，返回 452 4.2.2，上游队列保留该任务等待稍后重试；若为默认的 no，返回 552 5.2.2，上游队列终止对 B 的投递，按发件人反向路径规则决定是否生成投递状态通知。
  • 场景 C（目标收件人底层存储故障）：因目录权限或磁盘异常导致底层驱动提交失败，返回 451 4.2.0 Storage failure。上游队列将其记录为临时失败，保留在队列中等待下一次轮询重投。
  • 场景 D（存储落盘成功但统计异步失败）：底层邮件已成功提交落盘，服务端向客户端确认 250 2.0.0 Saved。上游队列清除任务，下游字典后端记录日志告警，由离线对账机制校准失步数据。

结合 RFC 2033 第 5 节关于网络中断的处理语义：客户端逐行读取响应。若服务端已返回收件人 A 的 250，但在输出后续响应时网络连接意外中断，客户端必须将已收到确认的收件人记录为成功，未收到响应的收件人视为临时失败（4xx）。上游在后续轮次中重投未确认的收件人是符合规范的容灾行为。若网络中断发生在服务端已落盘但客户端尚未读到 250 的瞬间，后续重试将引发重复写入。在下游存储层中，防重逻辑不能仅依赖易伪造或可能缺失的 Message-ID 头部，而应结合上游受信投递任务标识与收件人地址进行幂等排重；若系统未暴露该接口，则必须在业务层面容忍偶发的重投消息。

自研硬配额与对账设计推导

对于需要实施严格硬配额（不允许并发微量超限）的自研邮件存储系统，无法单纯依赖“先存信、后加计数”的弱隔离模式。从工程推导来看，实现严格配额有两种主要实现路径：

一种路径是统一所有写入口，将 LMTP 接收、本地进程导入和 IMAP 追加写入统一交由单点协调器处理，按配额根实施严格的排他锁，串行化执行检查与最终落盘。这种方式结构直观，但在单用户高频写入时会形成明显的排队瓶颈。

另一种路径是引入原子余额检查与额度预留。如果邮件尺寸在流式传输前已知，可一次性申请预留；若尺寸未知，可在接收过程中分段申请，或在底层存储最终提交前完成最终额度核验。预留凭证必须具备全局唯一的预留标识（reservation ID），在协调中心记录预留中、已提交和已释放等状态，并通过租约超时（TTL）避免客户端崩溃导致额度永久泄漏。

需要特别指出的是，存储提交与公开必须在验证预留依然有效的前提下才能执行，过期的旧持有者不得完成使信件变为用户可见的提交步骤。如果仅在存储提交后才检查计数后端，超额邮件已经持久化落盘，配额防御便已失效；协调中心必须具备拒绝过期写入者的有效性校验机制。此外，额度的提交确认与释放必须以 reservation ID 保证幂等；若因网络异常导致提交结果未知，该预留必须保持在待核对状态，待恢复程序根据真实邮件实体核验对账后再行转正或释放，不能单凭租约超时就将其当作垃圾额度粗暴回收。

在对账层面，离线校准必须基于所选存储后端中的真实邮件实体，按照既定的物理尺寸或虚拟大小规则重新统计，以修正因统计网络异常而产生的数值漂移，保证配额长期收敛。

待执行验证方案

为在工程环境中复现并检验上述机制边界，设计以下受控的验证方案（待在隔离测试环境中部署执行）：

  1. 并发竞态与超额复现：
    • 配置测试账号配额为 10 MiB，指定该配额根宽限为零（quota_grace = 0），显式配置 lmtp_rcpt_check_quota = no，将当前用量初始化为 2 MiB（剩余 8 MiB）；
    • 在服务端或代理层设置测试拦截点，确保两个并发投递进程均已完成用量读取并获取到相同的剩余配额后，再同时放行后续写入；
    • 两个连接各自投递一封 6 MiB 的信件。观察两者在终结符 . 后的返回码、最终生成的邮件 UID、数据库中的用量数值以及服务器日志，验证是否均返回 250 Saved 且总用量实际达到 14 MiB。
  2. 多收件人响应截断与独立恢复：
    • 配置收件人 A 配额充足，收件人 B 配额已满且 quota_full_tempfail = no，收件人 C 模拟目录权限错误产生存储故障；
    • 第一轮测试：发送包含 A、B、C 的 LMTP 会话，完整读取响应，验证是否依次返回 250、552 5.2.2、451 4.2.0；
    • 第二轮测试：重置测试环境并更换测试邮件，发送新的会话。客户端在读取到收件人 A 的第一行 250 确认后，立即发送 TCP RST 强制断开连接。检查上游队列管理器的持久化状态，验证收件人 A 是否已被标记为成功移除，而 B 和 C 是否仍保留在待投递任务中。
  3. 统计后端故障分级注入：
    • 在开启 lmtp_rcpt_check_quota = yes 的环境下注入字典后端不可用，验证 RCPT 阶段实际执行查询且错误可达时是否返回 451 4.3.0；
    • 在保存开始阶段注入字典服务异常，验证日志中是否记录 saving mail anyway 且信件在底层存储正常提交时仍能获得 250；
    • 在提交回调阶段注入字典服务网络中断，验证日志中是否精确出现 Quota is now desynced，且 LMTP 依然向客户端返回 250 Saved。
