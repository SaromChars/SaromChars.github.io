证书明明没过期，浏览器为什么还说不安全？——从 CRL、OCSP 到吊销检查策略

2018年8月15日更新于: 2026年11月7日
|

访问 HTTPS 网站遇到红色的“连接不安全”告警时，许多人的第一反应是“证书是不是过期了”。打开证书详情一看，Validity 字段可能写着半年后才到期。

有效期只是证书签发时写进结构体的一纸静态声明。在握手过程中，客户端除了校验证书有效期，还会按顺序核验服务器域名与数字证书（digital certificate）名称是否匹配、证书链是否能追溯到受信任的本地信任锚（trust anchor）、密钥用法是否允许当前协议握手，以及数字签名（digital signature）算法和密钥长度是否依然满足安全基准。RFC 5280 §6 证书路径验证 · RFC 2818 §3.1 域名匹配

即便这些检查全部通过，也不能保证证书仍然有效。如果服务器私钥在签发次日不幸泄露、域名所有权发生变更，或者 CA 发现签发过程存在违规，这张证书就必须被提前作废。数字证书是一旦签发出厂便无法由 CA 远程修改或销毁的离线数据文件，无法在各个客户端的存储介质上直接擦除它。要通知各方这张证书已作废，公钥基础设施（public key infrastructure，PKI）体系依靠的是另一套独立机制——证书吊销（Certificate Revocation）。

但另一个常见的现象是：即使证书已经被 CA 标记吊销，某些浏览器在访问时却未必立即将其拦截；而在另一些环境下，网络稍有抖动页面就会报错中断。要理解这种表现，需要从 CRL、OCSP、OCSP Stapling 的技术机制，以及客户端对吊销状态的取舍策略说起。

证书怎么声明作废：CRL 机制与它的传播时延

让客户端知道证书作废，常见方法之一是由签发该证书的 CA 定期发布一份作废列表，这就是证书吊销列表（Certificate Revocation List，简称 CRL）。RFC 5280 §5 CRL 格式与处理

在 X.509 标准中，CA 签发证书时通常会在扩展字段写入 CRL 分发点（CRL Distribution Points，crlDistributionPoints）。当客户端拿到证书后，可以根据该 URL 下载对应的 CRL 文件。

客户端获取证书 ──> 读取 crlDistributionPoints URL
                          │
                          ▼
                   下载 CA 签名的 CRL 文件
                          │
                          ▼
            校验证书序列号是否在 Revoked Certificates 列表中

校验一份 CRL 并不是简单查看里面有没有目标证书的序列号。为了防止中间人伪造作废列表或用过期列表实施回滚攻击，客户端在处理 CRL 时需要执行结构验证：

  1. 验证签名与签发权限：确认该 CRL 确由负责签发该证书的 CA（或具有 CRL 签发授权的专用实体）私钥签名，且所用公钥受信任。
  2. 检查适用范围：核验该 CRL 的分发点适用范围（例如证书分段、原因范围，以及增量 CRL 与其对应基准 CRL 的配合检查）。
  3. 核验生效与更新时间：按 RFC 5280，CRL 包含 thisUpdate（本期发布时间）和 nextUpdate（下一份 CRL 最晚发布时间）。客户端应检查当前时间和适用的有效时间窗口，超过 nextUpdate 的旧 CRL 不能直接作为当前未吊销的充分依据。

只有当 CRL 签名有效、时间未超过预定窗口、适用范围匹配时，客户端才会遍历其内的被吊销证书序列号列表（Revoked Certificates）。

这里存在一个容易被忽略的逻辑前提：“目标证书不在某份 CRL 中”，并不等于“证书未被吊销”。只有当客户端获取到了由该证书对应权威签发者发布的、涵盖该证书所在范围的有效最新 CRL 时，未列入其中才能作为未吊销的凭据。

CRL 最核心的工程考量在于传播延迟与体积膨胀。大型公共 CA 签发的证书量较大，累计的吊销列表体积可能达到数兆甚至更大。CA 通常会设定固定的发布周期（即通过 nextUpdate 指明下期预期时间）。这意味着：

  • 如果一张证书的私钥泄露，即便 CA 在后台将其标记吊销，也往往需要等待 CA 生成并发布包含该更新的下一期 CRL，客户端拉取后才能获知。虽然 RFC 5280 允许 CA 在遇到紧急吊销等情况时提前发布新的 CRL，但客户端获取并识别仍取决于具体拉取时机。
  • 客户端与网络中间代理为了性能往往会缓存已获取的 CRL。在本地缓存过期或触发刷新前，客户端通常不会频繁重新发起网络请求，这导致吊销信息的传递存在时间差。

单张快速查询：OCSP 与响应语义的边界

为了避免客户端每次验证都要下载整份庞大的黑名单，IETF 推出了在线证书状态协议（Online Certificate Status Protocol，简称 OCSP）。RFC 6960 在线证书状态协议

在支持 OCSP 的证书中，扩展字段包含 Authority Information Access（AIA），其中给出了 OCSP 响应服务器（OCSP Responder）的查询 URL。客户端在需要且本地没有可接受的缓存状态证据时，可向该 Responder 发送一个包含目标证书序列号等标识的小型请求，由响应者返回针对该证书状态的数字签名响应。

OCSP 响应明确定义了三种状态代码：

  • good：表示响应器查询了该证书的状态信息，目前未收到该证书被吊销的正向记录。
  • revoked：明确表示该证书已被吊销。响应中会附带吊销时间（revocationTime），有时还包含具体吊销原因（revocationReason）。
  • unknown：表示响应器不知道这张证书的状态（例如该证书不是由此 CA 签发，或者响应器负责的数据范围中没有该序列号的数据）。

需要注意，在 RFC 6960 标准中，good 仅仅是最低语义——只表示“没有查到针对此序列号的吊销信息”。它既不证明证书目前尚未过期，也不保证该证书曾被合法签发，更不证明证书链能通过本地信任锚校验或域名相符。这些基础检查依然是客户端路径验证的独立责任。

同时，客户端收到 OCSP 响应后，通常会按协议规则核查：

  1. 响应者授权与签名：响应通常由签发该证书的 CA 直接签名，或者由持有该 CA 颁发、且带有专用扩展用途（id-kp-OCSPSigning）的委派 OCSP 响应者证书签名，或由客户端本地配置直接信任的受托实体签名。
  2. 目标匹配与时间范围：响应中的 CertID 必须与查询目标匹配；核查 thisUpdate，并在存在 nextUpdate 时检查其截止时间，或者结合本地策略评估响应新鲜度。需要说明的是，时间检查有助于限制陈旧响应的使用，但并不能完全排除合法时间窗口内的网络重放。

值得一提的是，unknown 属于响应器正常返回的应用层状态码，与因网络阻断、DNS 解析失败或连接超时的“查询失败”在性质上不同。而在 revoked 状态中，吊销原因包括私钥泄露（keyCompromise）、CA 泄露（cACompromise）、从属关系变更（affiliationChanged）、被取代（superseded）、停止营运（cessationOfOperation）以及证书暂扣挂起（certificateHold）。certificateHold 是一种可临时暂停、允许被解挂（removeFromCRL）的特殊状态，因此不能将所有被标记为 revoked 的情况都一概称为永久不可逆的终结。

OCSP Stapling：让服务端携带状态证明

虽然 OCSP 的单次响应体比 CRL 小得多，但直连查询存在一些工程代价：

  1. 连接延迟：每次建立 TLS 握手时，客户端若暂停握手等待第三方向 CA 的 OCSP 服务器建立 HTTP 连接，会增加连接建立耗时。
  2. 访问关联暴露：客户端在访问具体站点前直连 CA 响应器，会向响应者暴露被访问的目标证书及客户端来源 IP，产生访问痕迹关联。
  3. 依赖第三方服务稳定性：一旦 CA 的 OCSP 服务遭遇故障或网络拥堵，依赖该服务的客户端可能受到影响。

为了改善这些问题，TLS 扩展机制引入了证书状态请求（Certificate Status Request），即通常所说的 OCSP Stapling（OCSP 装订）。RFC 6066 §8 证书状态请求扩展

(以 TLS 1.2 状态请求为例；服务端通常提前向 CA 预取并缓存响应，在握手中作为独立 CertificateStatus 紧随 Certificate 之后返回，非逐消息串行等待)
客户端                                     服务端                                CA OCSP 响应器
  │                                          │                                         │
  │── ClientHello (status_request) ─────────>│                                         │
  │                                          │── 预取/缓存授权响应 (带时间戳) ────────>│
  │                                          │<── 返回签名的 OCSP Response ────────────│
  │                                          │
  │<── ServerHello + Certificate + OCSP ─────│
  │    (由服务端直接在握手报文中装订返回证明) │
  ▼                                          ▼
客户端验证该 OCSP 响应签名、授权、目标与新鲜度

在 OCSP Stapling 机制下：

  1. 服务端自主向授权的 OCSP 响应器发起请求，获取并缓存一份带有数字签名的 OCSP 响应。
  2. 客户端在 TLS 握手的 ClientHello 中携带 status_request 扩展，告知服务端自己支持接收装订状态。
  3. 服务端在握手报文中直接将这份已签名的 OCSP 响应连同证书一起发回给客户端。

客户端拿到装订的 OCSP 响应后，按照前述规则验证签名者授权、响应签名、目标 CertID 及时间新鲜度。由于响应由授权响应者签名防篡改，服务端即便想伪造也无法成功；客户端无须自行向第三方发起网络请求，有助于减少延迟与访问关联暴露。

需要强调的是，在常规握手规则下，“服务端未提供 Stapled OCSP 响应”并不等于“证书已被吊销”。很多站点未配置 Stapling，服务端完全有权不装订响应；客户端在未收到装订数据时，通常只会退回到本地已有策略或决定是否发起查询。

为了明确要求证书必须携带装订响应，RFC 7633 提出了 TLS Feature 扩展（常称 OCSP Must-Staple）。RFC 7633 TLS Feature 扩展。若证书的 TLS Feature 扩展中列出了 status_request 等特性，即声明该证书在握手中应当提供装订响应。遵循该标准的客户端依据 RFC 7633 §4.3.3 判断证书有效性；当客户端的安全策略要求证书必须完全有效时，未收到合规装订且无法从其他来源（如本地缓存或实时查询，参见 RFC 7633 §4.2.3.1）取得有效状态凭证的握手必须予以拒绝。不过，该约束依客户端对 RFC 7633 的解析支持而定，在未适配该扩展的客户端中不会被强制执行。

检查失败了怎么办：Soft-fail 与 Hard-fail 的两难博弈

如果客户端发起了在线吊销查询，但由于目标服务器故障、DNS 解析失败或网络拥塞，客户端没有拿到任何可被接受的状态证据（无论是 CRL 还是 OCSP），客户端该如何决策？

这就是 PKI 体系中常见的可用性与安全性考量：

  • Soft-fail（软失败）：当客户端无法连接到吊销服务器，或者拿不到有效签名、未过期的状态响应时，允许握手继续。
  • Hard-fail（硬失败）：当客户端无法在规定条件内取得合法的吊销凭据时，将连接视为不可靠并阻断通信。

这两个概念需要明确其边界：

  • Soft-fail 并不是“已经收到了明确的 revoked 状态依然放行”。只要收到合法的 revoked 证据，遵循规范的客户端均会予以拦截。Soft-fail 指的是在“拿不到证据、状态未知”时的容错降级。
  • Hard-fail 也并不意味着“每次握手都必须实时发起全新的网络通信”。如果本地拥有仍在有效窗口内的可用缓存响应，或者服务端提供了合法的 Stapling 响应，同样可以满足检查要求，只有在缺乏有效凭证时才会阻断连接。

在网络环境下，在线查询常受跨网路由或偶发波动影响。若客户端无条件开启 Hard-fail，一旦网络出现波动或响应服务器故障，就可能导致大批站点无法访问；同时，攻击者也可以通过网络丢包制造阻断。而 Soft-fail 虽然保障了可用性，但在遇到具备网络控制能力的攻击者（例如伪造热点并丢弃吊销查询流量）时，查询超时降级可能导致吊销拦截失效。

浏览器机制与协议分开：分发清单与生态现实

必须将“密码学协议定义的能力”与“各款浏览器及平台实际启用的行为”区分开来。

在桌面与移动端生态中，面对延迟与软失败缺陷，不同产品采取了不同路径：

  • Chromium 团队探讨了在线 OCSP 带来的延迟与降级问题，在部分场景下结合离线推送机制进行补充。例如，其设计的 CRLSet 机制通过后台更新向客户端推送覆盖特定证书（如受关注的中级 CA 或特定应急范围）的紧凑吊销清单。Chromium 官方设计文档：CRLSets。这种离线清单更新时不增加连接延迟，但其收录范围并非全网所有被吊销证书。
  • 不同的操作系统底层网络库、浏览器分支版本、企业环境策略（如针对受管设备的集中策略配置），均会影响吊销检查是否开启以及失败时如何处理。

同一个站点在不同环境下表现出不同的拦截结果，往往正是这些平台机制、版本分支与本地安全策略不同所致。

用 OpenSSL 探查证书链与 Stapling

在排查服务端证书配置时，命令行工具 OpenSSL 能够帮助我们观察服务端握手时返回的材料。

在 OpenSSL 1.0.2 与 1.1.0 版本中，s_client 工具提供了证书链输出与状态扩展请求选项。OpenSSL 1.1.0 s_client 手册

# 发送 SNI 与主机名，并请求 OCSP Stapling 状态（命令在 OpenSSL 1.0.2 / 1.1.0 中可用）
openssl s_client \
  -connect example.com:443 \
  -servername example.com \
  -verify_hostname example.com \
  -verify_return_error \
  -showcerts \
  -status

这条命令各参数的作用如下：

  • -connect example.com:443：指定建立 TCP 连接的目标地址与端口。
  • -servername example.com：在 TLS 握手报文中发送 Server Name Indication（SNI）扩展。
  • -verify_hostname example.com：核验服务器证书的主机名（该选项在 OpenSSL 1.0.2 中引入）。
  • -verify_return_error：在证书路径校验失败时返回错误退出。
  • -showcerts：打印握手中服务端出示的所有证书内容。
  • -status：在 ClientHello 中携带 status_request 扩展，并输出服务端是否返回装订响应及相应内容。

如果服务器配置并返回了装订响应，命令输出中通常包含类似如下的示意输出：

OCSP response:
======================================
OCSP Response Data:
    OCSP Response Status: successful (0x0)
    Response Type: Basic OCSP Response
    Version: 1 (0x0)
    Responder Id: ...
    Produced At: Aug 14 06:12:00 2018 GMT
    Responses:
    Certificate ID:
      ...
    Cert Status: good
    This Update: Aug 14 06:00:00 2018 GMT
    Next Update: Aug 21 06:00:00 2018 GMT
======================================

必须注意：OpenSSL s_client -status 的作用是发送请求并打印返回内容，命令返回成功或打印出 successful / good，并不等同于客户端已对该 OCSP 响应完成完整的签名授权校验、目标匹配和时效验证。此外，该工具的验证逻辑不能等同于桌面浏览器的复杂策略。

如果遇到浏览器信任而终端报错，往往不是吊销状态差异，而是客户端自身没有安装签发该证书的机构根证书。关于 Java、Linux、Windows 与 macOS 系统如何维护信任锚与导入自签根证书，请参考下一篇：《浏览器能访问，Java 却报证书错误？——Java、Linux、Windows 与 macOS 信任库配置》。
