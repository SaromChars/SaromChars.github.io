关于邮箱反垃圾技术的研究

2021年10月13日
|

邮件接收网关处理入站流量时，需要确定各层检测信号进入判定的时机，按综合评分选择处置动作，并在抑制垃圾邮件（Spam）的同时严格控制对正常邮件（Ham）的误判。简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）在基础传输设计上不强制验证发件人真实意图，任何对端主机都能尝试建立传输连接。如果在会话早期直接阻断连接，能够节约本地计算开销，但会失去后续深层特征审计的机会；若将邮件接收后再做离线处置，虽然具备灵活的纠偏缓冲，却需承担存储堆积与被动投递的风险。

评估与构建反垃圾引擎的难点，往往不在于单项特征的堆砌，而在于理解信号生效的协议上下文、避免离线评测中的未来数据泄漏，并根据业务能承受的非对称代价设定阈值。

分层信号的获取时序与判定输入

反垃圾网关获取检测信号的过程与 SMTP 会话阶段紧密绑定。在报文传输的不同时点，系统所能掌握的信息维度是动态递增的，各项信号在进入评分器时必须明确标注其状态是命中（Hit）、未命中（Miss）还是未知（Unknown/Error）。

在传输控制协议（Transmission Control Protocol，TCP）握手建立及客户端发送 HELO 或 EHLO 命令阶段，系统仅能获取对端网络协议（Internet Protocol，IP）地址及客户端声称的主机名。此时系统可针对发信 IP 执行基于域名系统（Domain Name System，DNS）的名单（DNS-Based List，DNSBL，RFC 6471）查询，并基于发信频次实施速率控制（RFC 2505）。当客户端给出 MAIL FROM 与 RCPT TO 信封地址时，系统可对发件人策略框架（Sender Policy Framework，SPF，RFC 7208）进行初步授权检验，并根据收发地址组合实施灰名单（Greylisting，RFC 6647）等行为观测。在信封阶段，邮件头及正文尚未传输，任何基于正文词元或附件特征的检测均处于不可用状态。

当客户端执行 DATA 命令并将整封邮件头与邮件体完整送达后，系统才能展开全文深层解析。此时接收端可以提取域名密钥识别邮件（DomainKeys Identified Mail，DKIM，RFC 6376）签名并执行密码学公钥验签，校验被签名的邮件头字段及规范化且按签名覆盖的正文哈希（Hash）是否遭到篡改。紧接着，系统提取用户可见的 From: 头部域名，执行基于域的消息认证、报告和一致性（Domain-based Message Authentication, Reporting, and Conformance，DMARC，RFC 7489）对齐校验，按宽松或严格规则检查可见域是否与至少一项已通过验证的 SPF 发件域或 DKIM 签名域达成对齐。同时，正文分词处理产生的词元（Token，指经过切分后用于统计分类的基础特征单元）、统一资源定位符（Uniform Resource Locator，URL）域名名单比对，以及启发式语法规则也在此阶段集中输出。

SMTP 会话阶段与特征可用性时序：
1. TCP 连接与 HELO/EHLO -> 发信 IP、客户端主机名、DNSBL 信誉、连接速率控制
2. MAIL FROM / RCPT TO  -> 信封发收地址、SPF 授权初步校验、灰名单重试状态
3. DATA 内容传完，最终响应前 -> DKIM 签名核验、DMARC 对齐、正文 Token/URL、启发式规则

在工程架构中，网络解析超时或服务降级是常态。例如当查询 DNSBL 出现超时无响应时，该特征在判定上下文中必须作为“未知”记录，既不能等同于命中黑名单而误阻断，也不能静默视作无风险良性。

综合评分与处置动作分离

将多维信号转化为系统决策时，常见的架构缺陷是将特征检查与硬编码动作直接绑定。例如一旦命中某项外部名单就直接在底层触发连接断开，这会导致系统失去全局风险权衡的灵活性。本文采用一种教学化的“特征提取-综合评分-动作映射”分层架构设计。底层检测模块既可输出连续分值或模型估算概率，也可输出符号化的结构状态，且局部估算概率并不直接等同于已完全校准的线上真实恶意率。

身份认证（authentication）、外部信誉与内容统计信号在本质上反映了不同层面的客观事实，彼此之间既不能相互替代，也不能简单线性叠加：

  1. 身份认证通过不等于内容良性：SPF 仅证明当前连接 IP 获得了信封发件域授权，DKIM 仅证明被签名的头部字段和覆盖正文自私钥签名后未遭篡改，DMARC 仅证明可见发件域与已通过验证的 SPF 或 DKIM 身份域按规则对齐。垃圾邮件发送者同样可以自行注册正规域名，并配置合规的 SPF、DKIM 和 DMARC 记录来发送诈骗或仿冒邮件。
  2. 多层命中可能相关而非简单累加：例如一封钓鱼邮件的发信 IP 命中了某黑名单，其信封域名与正文链接也可能分别命中了对应名单。这表明多项检测信号可能存在关联，但同一服务商提供的不同名单并不必然代表完全重合的证据；系统应当通过共同触发样本与历史错误分类样本来评估是否存在冗余计分，不能盲目机械叠加，也不能在缺乏证据时随意抹去独立检测信号。
  3. 分值（Score）与动作（Action）解耦：底层检测模块输出连续分值或结构化判定结果，最终处置动作由外层策略引擎基于全局配置的业务阈值统一决定。

根据简单邮件传输协议标准规范（RFC 5321 第 6.1 节），邮件传输代理（Message Transfer Agent，MTA）一旦在 DATA 命令结束时返回了 250 OK 确认码，即在传输协议语义上承担后续投递或中继责任，不能再通过已经确认接受的那次 SMTP 事务向原发端追溯拒收。在会话内直接拒收时，接收端告知失败状态，由发端 MTA 按协议条件和反向路径规则承担后续通知处理；若反向路径为空，发信方可能不会产生退信。因此，网关通常将判定动作严格区分为不同级别：

  • 会话内拒绝（Reject，5xx 响应）：在 SMTP 会话期间直接返回永久失败代码，阻断传输，发端 MTA 按其协议配置与条件承担后续通知处理；
  • 临时延缓（Defer，4xx 响应）：要求发送方暂存并在稍后重试，多用于灰名单或系统资源过载保护；
  • 接受后标记（Tag/Flag）：在邮件头注入检测明细字段，正常投递至收件箱供客户端规则过滤；
  • 接受后隔离（Quarantine）：接收邮件但转存入系统集中隔离区，需要单独的授权审核接口才能释放；这与直接投递到用户个人垃圾邮件箱不同，后者依赖终端用户在客户端内自行翻查。

统计模型训练、标签来源与评估边界

在引入朴素贝叶斯（Naive Bayes）等统计分类方法时，模型将文本切分后的 Token 视为概率信号，基于历史已标注的正常样本与垃圾样本计算特征条件概率。然而，离线训练与评测环节若设计不严密，常会引入数据泄漏（Data Leakage），导致测试指标良好而线上应用效果下滑。

在文本检索会议（Text REtrieval Conference，TREC）的公开评测报告《TREC 2007 Spam Track Overview》（Cormack, 2007 第 1 至 3 页）中，作者阐述了邮件过滤评测的经典范式：评测严格依照邮件到达的时间序列推进，模型对当前邮件做出预测（Classify）之后，评测框架才根据设定的反馈延迟提供真实基准标签（Gold Label）；评测框架严格区分分类接口与训练更新（Train）接口，由评测流程在得到真实标签后显式调用训练，并基于真实正常邮件与垃圾邮件各自的独立总量来统计误判比例，从而绘制出不同阈值下的权衡曲线。

以下为针对评估线上新流量的工程建议，并不代表学术研究中禁止其他分析方法：

第一，时间切分与模型冻结原则。为了评估模型对未来线上新流量的拦截能力，训练集、超参数与阈值调优验证集、最终留出测试集必须严格按照邮件物理到达的时间先后进行切分。在冻结离线比较时，必须冻结模型权重、规则库、判定阈值以及外部信誉快照，并关闭自动在线学习；在验证集上选定最优阈值后，最终留出测试集仅用于一次性评估，不得再反向微调参数。若需测试在线学习能力，必须单列评测流程，严格遵守先预测后按 label_available_at 实际反馈可用时间注入学习的时序。

第二，近重复活动与去重边界。现实中同源群发或相似活动在时间轴上自然延续并不必然等同于泄漏。为了评估模型对未见新型活动的泛化能力，离线评测时应当分开报告纯时间切分序列表现与按活动去重后的评测表现，不能为了消除重复而随意将未来时间段的样本调配到过去时间段中。

第三，历史外部状态回放失真。反垃圾系统依赖动态 DNSBL 与域名声誉等外部数据源。在进行历史邮件回放评测时，若直接使用当前时刻的最新 DNSBL 列表去查询多月前的发信 IP，本质上是在用历史未知的“未来网络信誉”评估旧邮件，直接造成严重的评测失真。若无法保证高保真的历史声誉快照，评测时应剥离动态外部查询信号，仅针对静态文本和协议结构进行模型验证。

第四，事件标签与抽样复核。系统运行中的放行通过、用户点击举报以及隔离区人工释放，本质上仅记录了业务事件与候选线索，并不直接等同于无瑕疵的真实标签。若将所有用户举报机械地作为垃圾正样本灌入训练集，容易污染分类特征。为了控制数据质量，必须通过独立分层抽样进行人工复核来校验真实标签；在评测统计中，未经标注确认的样本不能简单归入正常邮件，必须明确报告样本覆盖度与不确定性。在有限测试样本中未观察到误判，绝不证明线上实际环境的误杀率为零。

误杀与漏杀的非对称代价及评估指标

反垃圾系统的判定错误可划分为两类：

  • 误杀（False Positive，FP）：将真实的正常邮件误判为垃圾邮件并予以拦截或隔离；
  • 漏杀（False Negative，FN）：未能识别垃圾邮件，使其进入用户的收件箱。

在量化评估中，分子与分母的口径必须严格对齐：

误杀率 (False Positive Rate, FPR) = 误杀数量 (FP) / 真实正常邮件总数 (N_legit)
漏杀率 (False Negative Rate, FNR) = 漏杀数量 (FN) / 真实垃圾邮件总数 (N_spam)

漏杀垃圾邮件带来的主要成本是用户的阅读干扰、邮件存储占用以及潜在的安全风险（如涉及高危钓鱼与木马凭据盗取）；而误杀正常邮件往往会中断关键业务协作。反垃圾系统的阈值调优并非在任何场景下都盲目追求固定不变的误杀指标，而是需要结合具体邮件类型及漏杀、误杀的实际业务成本动态权衡。

更为重要的是，系统评估必须针对具体执行的处置动作分别统计指标。例如将一封邮件“直接会话拒收（Reject）”与“转入系统隔离区（Quarantine）”若均计为判定垃圾，其对应的误杀代价完全不同：前者直接阻断传输，收件方拿不到邮件，发件方需依赖失败状态和后续通知排查；后者则保留了后续由管理员授权审核释放的通道。若不区分动作级别混为一谈，评估数据将无法反映系统的实际业务风险。

待执行的两个教学检查与数据规范

为说明分层特征评估、动作映射与误判统计口径，以下给出两项待执行的教学设计检查（本示例采用构造数据用于展示接口设计与分值流转，并非实际运行记录，也不代表检测率承诺）。

检查一：分层判定与结构化日志示例

假设网关接收到一封入站邮件，在进入判定时设定如下教学规则：

  • 发信 IP 命中轻量 DNSBL 列表（dnsbl.example.invalid）：赋予风险分 +2.0；若查询超时则标记为 DNSBL_TIMEOUT，状态为 UNKNOWN，不直接赋予正负分。
  • 身份认证：SPF 校验 scope=mailfrom，结果为 PASS；DKIM 校验 domain=example.org，结果为 PASS；DMARC 校验可见域与 DKIM 域对齐，结果为 PASS。本教学设计中，认证通过仅记录为上下文状态，不直接执行减分。
  • 朴素贝叶斯分类器：正文提取出的 Token 经模型计算输出分值 +4.0（该分值基于模型预测，不直接作为线上真实恶意概率保证）。
  • 动作阈值：总分达到 7.0 时会话拒收；总分达到 4.0 且低于 7.0 时接受后转入系统隔离区；低于 4.0 时放行。

网关在 DATA 结束但尚未向客户端返回响应阶段（phase=data_end_before_reply），导出的教学日志结构如下：

{
  "evaluation_id": "eval-20211013-001",
  "message_id": "<demo-001@example.org>",
  "timestamp": "2021-10-13T09:45:00+08:00",
  "phase": "data_end_before_reply",
  "client_ip": "192.0.2.42",
  "envelope_from": "bounces@example.org",
  "header_from": "billing@example.org",
  "engine_version": "v1.4.2-eval",
  "rule_set_version": "20211010-rules",
  "model_snapshot": "bayes-20211010-v1",
  "thresholds": {"reject": 7.0, "quarantine": 4.0},
  "signals": [
    {"name": "DNSBL_CHECK", "status": "HIT", "source": "dnsbl.example.invalid", "score": 2.0},
    {"name": "SPF_AUTH", "status": "PASS", "scope": "mailfrom", "identity": "example.org", "score": 0.0},
    {"name": "DKIM_AUTH", "status": "PASS", "domain": "example.org", "score": 0.0},
    {"name": "DMARC_ALIGNMENT", "status": "PASS", "domain": "example.org", "score": 0.0},
    {"name": "BAYES_TOKEN_SCORE", "status": "HIT", "score": 4.0}
  ],
  "evaluation": {
    "aggregate_score": 6.0,
    "selected_action": "QUARANTINE",
    "reason": "Score 6.0 reached quarantine threshold [4.0, 7.0)"
  }
}

综合评分计算为 2.0 + 4.0 = 6.0，系统选择将其转入系统隔离区。若在测试中将发信 IP 查询模拟替换为超时无响应，输入状态应明确记录为 UNKNOWN，日志中须包含 unknown_count 或依赖失败标记，并交由网关预设的外部故障降级策略决定动作，而不能静默视作无风险良性通过。

检查二：按动作划分的误判计数验算方案

为了验算不同处置动作下的评估口径，构造一个包含 1000 封真实正常邮件与 200 封真实垃圾邮件的离线留出测试集（数字仅用于展示分母与计算口径，不代表业务系统目标）：

  • 正常邮件（1000 封）：系统判定 2 封会话拒收、5 封系统隔离、993 封正常放行；
  • 垃圾邮件（200 封）：系统判定 120 封会话拒收、60 封系统隔离、20 封正常放行。

在统计时，若将拒收与隔离均视作判定为垃圾，则整体评估指标为：

  • 误杀率 FPR = (2 + 5) / 1000 = 0.7%；
  • 漏杀率 FNR = 20 / 200 = 10%。

进一步按具体执行动作拆解误判分布：

  • 会话拒收误杀率 = 2 / 1000 = 0.2%；
  • 系统隔离误杀率 = 5 / 1000 = 0.5%。

两者面临的业务挽回成本完全不同，必须分开统计展示。

在系统落地实践中，日志记录必须遵循最小必要与受控访问原则：对包含敏感信息的邮件头与正文特征进行去标识化脱敏，限制审计字段的留存周期。训练样本仅在获得明确授权的范围内采集与使用，保障系统数据链路的规范与安全。
