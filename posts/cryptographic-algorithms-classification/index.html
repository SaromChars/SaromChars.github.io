密码算法分类笔记：加密、哈希、签名与密钥协商

2018年8月21日更新于: 2026年11月7日
|

在梳理 TLS 历史版本与握手流程 以及 国密双证书体系 时，经常会遇到一长串算法名称：AES、RSA、ECDSA、ECDH、SHA-256、HMAC、ChaCha20、Poly1305、SM2、SM3、SM4。如果把它们混在一个清单里，容易产生困惑：为什么有的地方说 RSA 既能加密又能签名，有的地方又说签名绝对不能叫加密？为什么 SHA-256 不能用来保护传输内容的保密性，算出的哈希值发给对方又为什么不能直接防止篡改？

密码算法不是按单个“强度榜单”排列的，它们是为解决不同的通信与安全目标而设计的工具。把零散算法放回各自解决的核心问题中，才能看清它们的分工与组合方式。

两个交织的分类维度

梳理密码算法时，最容易引起混淆的是把不同维度的划分混在同一棵树里。工程中常见的分类维度有两个：

  1. 按密码学功能划分：即该机制究竟要解决通信中的什么问题——是防偷看的保密性（对称加密与公钥加密），防损坏的单向摘要，有共享密钥的消息认证码（message authentication code，MAC），公开可核验且抗抵赖的数字签名（digital signature），在公开信道上生成共识秘密的密钥协商（key agreement），还是把主秘密化整为零的密钥派生函数（key derivation function，KDF）。
  2. 按密钥结构与对称性划分：参与运算的各方使用的是相同（或可轻易互推）的秘密密钥，还是数学上成对出现、职责分离的公钥与私钥。

这两个维度是正交交织的，不能把它们生硬地嵌套。比如，“哈希算法”本身不需要密钥，它既不是对称加密，也不是非对称加密，硬把它塞进“非对称算法”分支是概念错位；同样，“公钥密码”是一个技术家族，其数学体系可以用来构造公钥加密方案、数字签名方案或密钥协商协议，但不能把这三者统称为“公钥加密”。

对称密码：分组密码与流密码

对称密码的特点是加解密双方使用相同的秘密密钥（或由同一主密钥直接推导出的对等密钥）。按处理明文的数据流形态，通常分为分组密码（Block Cipher）与流密码（Stream Cipher）。

分组密码不是完整的消息加密方案

分组密码以固定长度的“块”（Block）为单位进行变换。例如，AES（Rijndael）的固定块大小为 128 位（16 字节），支持 128、192、256 位密钥长度FIPS 197 §1；SM4 的块大小同样为 128 位，密钥长度为 128 位draft-ribose-cfrg-sm4-10 §1；早期的 DES 块大小为 64 位（56 位有效密钥），3DES 采用三重执行扩充了密钥长度，但块大小依然受限在 64 位。这些旧算法列出仅供维护识别，不代表推荐选用。

分组密码本身只定义了单个固定块的变换算法。现实中的报文或文件通常远超 128 位，且不一定是 16 字节的整数倍。因此必须引入工作模式（Mode of Operation）：

  • ECB（电子密码本模式）：将每个明文块独立加密。相同的明文块永远输出相同的密文块，不仅暴露统计特征与数据轮廓，还容易受到块重排与替换攻击，在工程场景中应严格避免。
  • CBC（密文分组链接模式）：每一个明文块在加密前先与前一个密文块进行异或，第一块引入初始化向量（initialization vector，IV）。CBC 要求输入为整块；若明文未对齐需按选定方案处理，采用 PKCS#7 时即使已整块也会追加整块填充，且 IV 必须不可预测。更重要的是，单纯的 CBC 模式无法防止密文被篡改，填充错误容易暴露出侧信道隐患（例如 Padding Oracle 问题）。
  • CTR（计数器模式）：通过加密逐次递增的计数器生成密钥流，再与明文逐位异或。CTR 把分组密码转换为流模式运行，无需填充，支持并行处理。但 CTR 对 IV/nonce 的唯一性要求明确，一旦在相同密钥下计数器发生重复，密钥流重叠会导致明文差分泄露。

在配置中使用 AES 时，不能脱离工作模式、初始化向量与认证机制只谈算法名称。

流密码

流密码直接生成连续的伪随机密钥流（Keystream），将其与明文逐位或逐字节异或来完成加解密。

  • ChaCha20：由 Daniel J. Bernstein 设计，并在 RFC 8439 中标准化的流密码RFC 8439 §2.4。它基于 256 位密钥与 96 位 nonce，内部维护一个 4x4 矩阵状态，通过 20 轮基于加法、旋转和异或（ARX）的运算生成 64 字节的密钥流块。相比老旧的 RC4（存在偏差弱点，列出仅作旧系统识别），ChaCha20 结构清晰，在缺乏专用硬件 AES 指令集的设备上拥有稳定且良好的软件执行表现。
  • 流密码的关键约束在于 带 nonce 构造（如 ChaCha20）中 Nonce 绝不可在相同密钥下重复。如果两段不同的明文使用了相同的密钥与 nonce，两段密文进行异或后密钥流将相互抵消，使得攻击者能直接得到两份明文的异或结果。

密码学哈希函数：单向摘要，不是“不可逆加密”

密码学哈希函数（cryptographic hash function）接收任意长度的输入，输出固定长度的指纹（digest / 摘要）。 代表算法包括：

  • SHA-2 家族：包括 SHA-224、SHA-256、SHA-384、SHA-512 等，基于 Merkle-Damgård 迭代结构FIPS 180-4 §4.1。SHA-256 是目前网络基础设施与安全通信中最通用的哈希基石。
  • SHA-3 家族：基于 Keccak 海绵结构（Sponge Construction），提供 SHA3-224 至 SHA3-512 以及可变长输出函数 SHAKEFIPS 202 §1。其内部设计与 SHA-2 完全不同，能够提供独立的算法多样性冗余。
  • SM3 密码杂凑算法：输出长度为 256 位，采用类似 Merkle-Damgård 的压缩函数结构draft-oscca-cfrg-sm3-00 §1。

关于哈希算法，有两个极易混淆的概念需要厘清：

第一，哈希不是“加密”。加密的目的是保密传输，前提是存在明确的逆过程——持有正确私钥或对称密钥的人能够还原原始明文。而哈希函数是信息压缩映射，从原理上不存在确定的还原映射。将其称为“不可逆加密”混淆了加密与摘要的职责。

第二，无密钥哈希不能单独防止恶意篡改。如果仅将一段明文计算一个 SHA-256 摘要附在文本后面发送，攻击者在链路中间截获后，不仅可以修改明文，还可以为修改后的明文重新计算一个 SHA-256 摘要并同时替换。接收方重新核算哈希只会显示匹配。要检测恶意篡改，必须引入双方共有的秘密材料（MAC）、数字签名，或者依赖带外受信任信道提供的摘要比对。

对于历史算法（如 MD5 与 SHA-1，列出仅作兼容排查参考），还需区分碰撞（Collision）与原像抗性（Pre-image Resistance）。产生碰撞是指找到两段不同的输入使其哈希值相同，这会危及依赖抗碰撞性的签名应用；但这并不等同于能够从给定摘要反推出原始明文，也不等同于基于这些哈希构造的 HMAC 机制立即全部失效。

消息认证码（MAC）：共享密钥下的完整性

如果通信双方已经事先安全地共享了一个对称密钥，他们希望在不加密或加密的同时，确保消息在传输过程中既没有被篡改，又确实来自持有共享密钥的一方，这时就需要使用消息认证码（Message Authentication Code，简称 MAC）。

代表构造与算法：

  • HMAC（基于哈希的消息认证码）：通过 RFC 2104 标准化，可以配合任意密码学哈希函数工作（例如 HMAC-SHA-256）RFC 2104 §1。它在底层哈希结构外层引入了两次带填充密钥的混合迭代，规避了单纯级联哈希容易遭遇的“长度扩展攻击（Length Extension Attack）”。
  • AES-CMAC：基于分组密码 AES 构造的消息认证码RFC 4493 §1，适合在已经内置 AES 引擎、希望复用硬件实现的系统中使用。
  • Poly1305：由 D. J. Bernstein 设计的高性能一次性密钥 MAC 算法RFC 8439 §2.5，针对模数 2¹³⁰ − 5 进行多项式求值计算。

使用 MAC 时需关注其边界：

  1. MAC 不能提供公开可验证的不可抵赖性。通信双方拥有相同的对称密钥，Alice 能算出的 MAC，Bob 也能计算出来。Bob 可以向自己证实消息来自持有该密钥的对端，但他无法向第三方证明该消息必定不是由自己伪造的。
  2. Poly1305 具有一次性密钥约束。计算 Poly1305 标签必须使用单次唯一的 256 位一次性密钥（通常由流密码配合独立 nonce 临时派生）；如果相同密钥被用于多次消息认证，多项式结构会给攻击者恢复内部参数、伪造后续认证标签提供机会。

认证加密（AEAD）：保密与认证的有机结合

早期的密码工程实践中，开发者常常将加密（如 AES-CBC）与认证（如 HMAC-SHA-256）自行组合拼接。这种手工组合若处理不当，容易在实现中引入填充错误或时序漏洞。

现代密码学普遍推行带关联数据的认证加密（authenticated encryption with associated data，AEAD）。 AEAD 将保密性加密与完整性认证在一个标准接口中完成，并支持同时对无需保密的附加认证数据（additional authenticated data，AAD）进行防篡改校验。

代表方案：

  • AES-GCM（Galois/Counter Mode）：将 CTR 模式加密与基于 Galois 域 GF(2¹²⁸) 的 GHASH 认证结合NIST SP 800-38D §5。在主流具备硬件加速指令支持的平台上执行效率很高。
  • ChaCha20-Poly1305：在 RFC 8439 中标准化，由 ChaCha20 提供加密，由 Poly1305 提供 16 字节认证标签（Tag）RFC 8439 §2.8。
明文 (Plaintext) ─────────┐
                         ▼
关联数据 (AAD) ────────> [ AEAD 运算引擎 ] ──> 密文 (Ciphertext)
                         (密钥 Key + Nonce)   └──> 认证标签 (Tag)

在理解与使用 AEAD 时需注意：

  • AEAD 不对 AAD 提供保密性：关联数据可以作为协议明文字段传输，也可以由通信双方根据上下文环境各自生成。AEAD 负责保证 AAD 与密文的完整性绑定，并不隐蔽 AAD 的内容。
  • Tag 匹配不代表现实实体认证：校验 Tag 成功仅证明密文和 AAD 确实是由持有当前对称密钥的一方生成的，并不代表现实中的机构身份。要证明远端主体的合法性，仍需依赖握手初期的数字证书或公钥签名。
  • Nonce 的唯一性要求依然明确：例如 AES-GCM 若在相同密钥下复用了 Nonce，GHASH 的多项式特性可能使攻击者恢复认证信息并伪造标签，严重破坏安全性。

公钥密码：加密、签名与协商的职责区分

公钥密码体制（Asymmetric Cryptography）利用了适当的数学难题构造：每一方拥有一对密钥——公钥（Public Key）公开供所有人使用，私钥（Private Key）由持有者严格保密。

公钥密码覆盖了截然不同的安全机制，不能将其与某一种具体运算直接画等号。

RSA 基础运算与具体方案

RSA 基于大整数素因数分解难题。在数学层面，RSA 具有幂模运算的形式，但在工程标准中必须区分基础数学变换与具体安全方案：RFC 8017 §7、§8

  • 公钥加密方案（RSAES-OAEP）：发送方使用接收方的公钥，结合基于哈希的最优非对称加密填充（OAEP）对数据进行加密，只有持有对应私钥的接收方能够解密。公钥加密常用于保护较短的对称密钥材料，不适合直接加密海量数据。
  • 数字签名方案（RSASSA-PSS）：签名者使用私钥，结合基于概率特征的随机化填充（PSS）生成签名。在相应哈希/掩码函数假设及随机预言机模型下，PSS 方案具有紧致的密码学安全归约，将伪造签名的难度直接归约到反演 RSA 难题上。旧式的确定性填充方案（RSASSA-PKCS1-v1_5）则需格外防范填充检查不严带来的风险。

ECC 是技术家族，不是单个替代算法

椭圆曲线密码学（elliptic curve cryptography，ECC）是一类基于有限域上椭圆曲线离散对数难题的技术家族，而不是单个具体算法。不同的曲线参数与构造方程用于完成完全不同的密码学功能：

  • 签名功能：包括 ECDSA 以及在 RFC 8032 中标准化的 Ed25519（EdDSA 方案）RFC 8032 §5.1。EdDSA 采用确定性签名机制，避免了传统 ECDSA 因每次签名所需随机数生成不当或偏置而带来的私钥暴露风险。SM2 签名同样基于椭圆曲线体系。
  • 密钥协商功能：包括 ECDH 以及在 RFC 7748 中标准化的 X25519 点乘协议RFC 7748 §5。
  • 公钥加密功能：例如 SM2 公钥加密机制，同样属于椭圆曲线体系下的独立方案。
  • 国密 SM2 算法集：SM2 算法集包含数字签名、密钥交换与公钥加密三种独立功能机制；这里参考其在 IETF 讨论的个人说明草案draft-shen-sm2-ecdsa-02 §4、§6、§7。

澄清概念边界

  1. “数字签名就是用私钥加密”是概念误解。虽然 RSA 基础幂模运算在形式上类似，但在现代密码工程中，签名方案与加密方案使用不同的填充与验证机制。在 ECDSA、EdDSA、SM2 等现代椭圆曲线体制中，签名生成与公钥验证使用的是完全不同的点乘方程，根本不存在“用私钥把明文加密包裹起来”的物理过程。
  2. 签名不提供保密性。签名附在明文数据之后，任何人都能阅读明文，也能用公钥核验签名。签名防伪造，但不防窥视。
  3. 公钥本身需要身份绑定。任何人都可以生成合法的公钥和私钥并完成签名计算。因此，公钥必须通过受信任的数字证书（PKI 机制）或预置受控配置绑定到明确的实体上，签名才有现实信任意义。
  4. 未认证的独立 DH 无法抵御中间人攻击（man-in-the-middle，MITM）。如果攻击者劫持了信道，他可以分别与通信双方各自完成一次独立的协商。因此生产协议中，密钥协商参数必须结合数字证书签名或预共享密钥（pre-shared key，PSK）进行上下文绑定认证。
  5. 协商出的共享秘密不直接作为业务传输密钥。点乘计算出的原始坐标数值分布不均匀，必须送入密钥派生函数（KDF）处理后，再派生出相互隔离的对称工作密钥。X25519 的设计便于构造恒定时间实现，但具体实现仍须避免与秘密相关的分支、访存和算术时序RFC 7748 §5.1。

密钥派生函数（KDF）：用途隔离与口令防护

密钥派生函数（Key Derivation Function）用于从源秘密材料（Input Keying Material）导出伪随机、定长且在密码学上相互独立的工作密钥。

根据源材料的熵（随机性与不可预测性）差异，KDF 分为两类应用场景：

1. 高熵主密钥派生：提取与扩展（HKDF）

在安全协议握手过程中，密钥协商通常已经建立了一个高熵共享秘密。为了从中派生出通信所需的客户端加密密钥、服务端加密密钥、初始化向量等参数，需要使用提取-扩展结构的 KDF。

  • HKDF（RFC 5869）：基于 HMAC 构造的标准 KDFRFC 5869 §2。
    • HKDF-Extract：使用一个可选的盐（Salt）将可能存在分布偏差的输入材料“提取”为一个伪随机密钥（PRK）。
    • HKDF-Expand：以 PRK 为基础，加入包含应用上下文与用途说明的 info 标签和计数字节，扩展出指定长度的独立子密钥材料。

2. 低熵口令派生：慢哈希抗暴力破解

用户设置的口令通常熵值有限。慢 KDF 并不能增加口令本身的原始熵，它的目标是通过算法设计增加离线穷举的成本。通过引入不可预测的盐（Salt），防止不同口令记录复用预计算结果；通过调整成本参数（如迭代轮数或内存开销），成倍提高单次猜测尝试的计算代价：

  • PBKDF2（RFC 8018）：通过指定盐与迭代轮数（Iteration Count），重复执行成千上万次底层的 HMAC 运算，提高猜测尝试的计算耗时RFC 8018 §5.2。
  • scrypt（RFC 7914）：引入“内存硬度（Memory-hard）”设计，在计算过程中要求随机访问大块不可预测的内存区域，增加了专用硬件并行破解的实现成本RFC 7914 §2。

不能把网络流处理中追求吞吐率的快速哈希算法当作口令慢哈希来存储口令；同样，口令慢哈希也不适用于网络通信主路径上的快速报文派生。

常见外围概念的边界澄清

在开发排查中，有些机制经常与密码算法并列出现，但它们处于不同的技术层次：

  1. Base64 与字符编码：Base64 是一种将二进制数据转换为 64 个可见字符的数据表示编码，完全公开可逆，没有任何密钥参与，不提供任何机密性或完整性防护。
  2. CRC32 与校验和：循环冗余校验（CRC）是为检测偶发性随机噪声或比特翻转设计的线性校验算法，不具备抗恶意篡改能力。检测恶意篡改需使用 MAC、签名或 AEAD；无密钥哈希需有可信信道提供的摘要等额外信任前提。
  3. 数字证书与 PKI：数字证书（如 X.509）本身不是密码算法，而是携带主体公钥、主体身份信息、有效期及 CA 签名的标准数据结构容器，解决公钥的可信绑定问题。
  4. TLS / HTTPS：TLS 是综合安全传输协议，按具体版本与套件组合身份认证、密钥建立、密钥派生以及数据保密与完整性保护等机制。

串联协作：混合密码系统的示意逻辑

在一次典型的安全通信建立过程中（非完整 TLS 握手时序），上述算法按功能依赖关系协同运作：

[ 阶段一：身份认证与密钥协商 ]
1. 客户端核验服务端 X.509 证书链 (RSA / ECDSA / SM2 签名验证)
2. 验证对端对本次协商参数或握手上下文的签名/认证证明，防止中间人替换
3. 双方在公开信道交换公钥参数，执行密钥协商 (X25519 / ECDH / SM2 交换)
4. 双方独立计算出相同的共享秘密 (Shared Secret)

                      │
                      ▼
[ 阶段二：密钥提取与用途分离 ]
5. 将共享秘密送入 KDF (如 HKDF)，结合双方随机数进行提取与扩展
6. 派生出方向隔离的对称加密工作密钥、初始化向量与认证参数

                      │
                      ▼
[ 阶段三：传输数据保密与认证 ]
7. 应用数据由 AEAD 方案 (如 AES-GCM 或 ChaCha20-Poly1305) 加密保护
8. 协议上下文或报文头关联数据 (AAD) 保持明文，但一同参与计算认证标签 (Tag)
9. 对端核验 Tag，只有认证通过才向应用层交付明文，防止窥视与篡改

把算法放回协作链条中，各项职责清晰对应：签名或认证机制负责确立身份并绑定本次会话，协商机制负责在公开信道产生共同秘密，KDF 负责把秘密加工成用途分离的工作钥匙，而 AEAD 则在数据传输过程中同时把守机密性与防篡改底线。分清各自的分工与限制，在架构设计与系统排错时才能选对工具、看懂日志。
