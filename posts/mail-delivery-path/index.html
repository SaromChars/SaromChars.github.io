一封邮件的投递路径

2021年8月1日
|

在日常软件开发中，发送电子邮件常被封装为一个简短的接口调用。在底层网络与协议层面，一封邮件的生命周期则由不同逻辑角色协作完成，跨越不同管理域实现状态流转与责任移交。

理解互联网邮件体系的关键在于厘清两点：一是各个系统组件的分工与责任移交边界；二是传输协议中的“信封（Envelope）”与被传输的“邮件内容（Content）”之间的职责隔离。在 RFC 5598 阐述的互联网邮件架构（Internet Mail Architecture）中，邮件处理系统（Message Handling System，MHS）被划分为清晰的功能角色；而在 RFC 5321 中，简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）规范了逐跳中继通信与会话处理规则。

邮件架构的核心角色

根据 RFC 5598，邮件系统由若干协同工作的逻辑代理构成。这些逻辑代理可以部署在不同主机上，也可在同一系统中合并实现。

图中箭头表示邮件在逻辑角色之间的流转，提交点和投递点标出两处责任移交。这是架构示意，各角色可合并部署；邮箱存储与收件人 MUA 仍承担不同职责。

1. 邮件用户代理（Message User Agent，MUA）

MUA 代表用户进行操作。

  • 发件人 MUA：负责根据用户输入创建邮件内容（含邮件头与正文），并提交给下一阶段。
  • 收件人 MUA：负责从邮箱存储中读取已投递的邮件，向收件人呈现内容，并处理用户的阅读、分类与回复操作。

2. 邮件提交代理（Mail Submission Agent，MSA）

RFC 5598（第 4.3.1 节）定义了邮件提交代理（MSA）。

  • MSA 处于用户环境与邮件传输网络之间，执行托管该服务的管理域（Administrative Domain，ADMD）策略与访问授权规则。
  • MSA 会检查提交报文是否符合协议格式规范；在具备配置授权时，它也可以协助补齐必要的字段（例如格式化时间戳或生成消息标识符 Message-ID:）。
  • 当 MSA 确认接收该邮件并纳入处理体系后，责任正式从发件用户环境移交到邮件处理系统（MHS），该责任转换环节在架构中被称为提交（Posting，标记为 S 点）。

3. 邮件传输代理（Message Transfer Agent，MTA）

邮件传输代理（MTA）承担传输中继职能（RFC 5598 第 4.3.2 节），类似网络层的路由交换节点：

  • MTA 检查信封上的目标地址，借助域名系统（Domain Name System，DNS）查询目标域的邮件交换（Mail Exchanger，MX）记录，将邮件推向下一跳节点。
  • 出站 MTA（Outbound MTA）：发件方边界 MTA，负责向外部管理域中继推送。
  • 入站 MTA（Inbound MTA）：接收外部网络传入流量并路由到本地投递环境的边界 MTA。
  • MTA 在中继转发过程中不解析和重构邮件内容的语义，只依据信封参数路由，并在完成下一跳责任移交前维持可靠持有状态。

4. 邮件投递代理（Mail Delivery Agent，MDA）与邮箱存储（Message Store，MS）

邮件到达目标域内部后进入终态投递：

  • 邮件投递代理（MDA）：RFC 5598 第 4.3.3 节定义了从 MHS 到收件人邮箱的移交操作，该事件称为投递（Delivery，标记为 D 点）。MDA 获取充分的目标地址属性信息后，将邮件脱离传输中继网络并存入收件人邮箱存储。若配置了过滤指令，过滤逻辑亦可在投递阶段运行。
  • 邮箱存储（MS）：负责邮件的持久化保存与组织。收件人 MUA 后续通过访问机制读取存储并展现给用户。
逻辑角色核心责任架构中的责任转换
MUA内容创建、编辑呈现与用户交互处于 MHS 外部两端
MSA提交检查、合规处理与访问授权提交点（S点）：用户环境移交至 MHS
MTA逐跳路由、DNS MX 查询与存储转发在 MHS 内部实施逐跳中继
MDA目标地址解析、本地过滤与落盘移交投递点（D点）：MHS 移交至收件人环境
MS邮件对象持久化保存与检索支持属于收件人存储端

信封与邮件内容的职责解耦

在邮件投递路径中，“地址”存在于不同层次。在 SMTP 会话中，存在两组职责不同的数据体系：协议信封（Envelope）与邮件内容（Content）。

1. 路由依据：SMTP 信封

在 RFC 5321 第 3.3 节中，规范了由一系列 SMTP 状态命令构成的信封事务。在 TCP 连接建立后，中继交互的简化示意如下：

S: 220 mx.example.net ESMTP Service ready
C: EHLO client.example.com
S: 250-mx.example.net greets client.example.com
S: 250 ENHANCEDSTATUSCODES
C: MAIL FROM:<bounce@example.com>
S: 250 2.1.0 Sender OK
C: RCPT TO:<carol@example.net>
S: 250 2.1.5 Recipient OK
C: DATA
S: 354 Start mail input; end with <CRLF>.<CRLF>
C: From: "Alice" <alice@example.com>
C: To: "Bob" <bob@example.com>
C: Date: Sun, 01 Aug 2021 02:00:00 +0000
C: Subject: Project Update
C: Message-ID: <unique-12345@example.com>
C: 
C: Hi Bob, here is the updated document.
C: .
S: 250 2.0.0 Ok: queued as 4St8Wq08P3z9Klx
C: QUIT
S: 221 2.0.0 Bye

从上述交互中可以观察到两者的解耦：

  • MAIL FROM:<bounce@example.com>：信封发件人（Reverse-Path，反向路径）。该路径主要供投递失败时发送投递状态通知（Delivery Status Notification，DSN）等退信；在某些特定场景（如退信通知本身）中，Reverse-Path 可以显式设为空（<>）。
  • RCPT TO:<carol@example.net>：信封收件人（Forward-Path，正向路径）。传输中继与投递代理仅依据信封中的 Forward-Path 决定本轮投递的目标路由。
  • DATA：客户端收到 354 中间响应后开始发送邮件内容（Content），以单独一行的点号（<CRLF>.<CRLF>）作为数据结束标记；该结束标记本身属于传输层面的终止信号，不属于邮件内容本体。

2. 邮件内容：头字段与正文

在 DATA 阶段传输的数据属于邮件内容（Content），由头字段（Header Fields）和正文（Body）两部分构成（RFC 5598 第 4.1 节）：

  • From: "Alice" <alice@example.com>：标明作者身份。
  • To: "Bob" <bob@example.com>：标明预期接收者。

头字段不仅呈现给读者阅读，也是诸多下游服务处理的元数据。然而，在协议层面上，头字段中的 To: 或 From: 并不决定本次 SMTP 事务中邮件被路由给谁。在上述简化示意中，信封投递地址是 carol@example.net，而头字段声明的是 bob@example.com。中继 MTA 只负责按信封指令推进，不依据邮件头字段更新传输路由。

3. 跨层信息的沉淀记录

信封信息在传输过程中会转化为内容中的追踪头字段保留：

  1. Received: 追踪头：SMTP 服务器在接收邮件用于中继或最终投递时，会在内容顶部插入一条 Received: 追踪字段（RFC 5321 第 4.4 节）。该字段通常记录客户端在 EHLO 中声明的名称、从 TCP 传输连接直接确定的来源 IP 地址以及接收时间戳。需要说明的是，EHLO 提供的仅为主机声明名称，并不等同于强认证身份。
  2. Return-Path: 落地写入：当邮件完成最终投递（D点）并交付收件人环境时，投递服务负责将本次事务信封中的 Reverse-Path 提取出来，生成 Return-Path: 头字段写入邮件最前端，用于记录该次投递确定的退信路径。

逐跳传输中的责任移交与失败边界

邮件服务采用存储转发（Store-and-Forward）模式，逐跳交互具有明确的责任判定边界。

1. 责任移交点：250 状态码

在 SMTP 事务中，DATA 结束后的响应状态码是责任移交的核心分界线：

  • 接收端在向发送端返回 250 OK 之前，必须已经可靠地接受了该邮件，并具备履行后续中继或投递责任的能力；将报文持久化到故障可恢复队列中是工业实现中的常见做法。
  • 返回 250 OK 代表接收端正式接管该邮件的后续处理责任。发送端收到 250 后方可解除本地发件任务的承运责任。需要明确的是，250 OK 仅代表当前传输节点接管责任，并不等同于邮件已经送达最终收件人的邮箱收件箱。
  • 接收端接管责任后若在后续处理中发生不可恢复错误，通常应向信封 Reverse-Path 构造投递状态通知进行告警；但若原信封 Reverse-Path 为空（<>），则绝不能再发起通知，以避免失败通知循环与回散（Backscatter）。此外，RFC 5321 第 6.2 节对判定为高置信恶意的特定邮件也允许进行受控的静默丢弃例外处理。

2. 失败分类与处理边界

根据 RFC 5321 第 4.2.1 节，SMTP 响应码的首位数字区分了不同的失败性质：

  • 4yz（临时失败，Transient Negative Completion）：表明服务当前处于不可用的临时条件中（如接收方资源紧张或临时限流）。
    • 处理边界：发送方通常将任务保留在重试队列中适时重试。RFC 5321 第 4.5.4.1 节建议客户端策略可配置，且通常建议重试保留期至少为 4 至 5 天；但这并不排除管理域根据业务需要向用户提前通报暂缓状态。
  • 5yz（永久失败，Permanent Negative Completion）：表明该请求存在永久性拒绝条件（如目标邮箱不存在或命令语法非法）。
    • 处理边界：发送端通常不应原样重复发起完全相同的失败请求。处理逻辑需根据当前具体命令（如在 RCPT TO 阶段还是 DATA 阶段）、该收件人是否为多收件人之一、以及 Reverse-Path 是否有效等具体边界分别判定，而非无差别删除全量任务。

3. 网络异常边界与重复邮件现象

在分布式网络传输中，一种常见的边界故障出现在 DATA 确认阶段：

  1. 发送方顺利传送完内容数据及结尾的点号；
  2. 接收方完成报文接管，并向网络发出了 250 OK 确认报文；
  3. 此时网络连接发生突发中断或超时，该响应未能在预定超时内被发送端收到（RFC 5321 第 4.5.3.2.6 节）。

此时产生了一种状态不一致：接收方已经履行接管并继续向下游投递；而发送方判定本次传输超时未成功，将任务退回本地队列择机重试。 当发送方后续重新投递时，收件端便会收到两封内容重复的邮件。这是分布式存储转发环境中产生重复邮件的一种典型原因。
