Postfix qmgr 的队列调度

2021年11月7日
|

在基于简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）的邮件系统开发中，系统接收客户端提交的邮件并返回成功应答之后，邮件可能会因为网络对端状态、目的地限流或队列堆积而延迟送达；而在包含多个收件人的邮件中，也可能出现部分收件人送达而另一部分进入暂缓重试的混合结果。

在邮件传输代理（Mail Transfer Agent，MTA）Postfix 3.6.2 的体系中，负责这一调度逻辑的核心是队列管理器（Queue Manager，即 qmgr 守护进程）。理解 qmgr 的内部调度数据结构、队列文件流转与逐收件人状态维护，是定位邮件投递延迟与队列堆积的关键基础，也为自研高可靠邮件投递引擎提供了成熟的工程参考。

一、调度器与投递代理的权责划分

在 Postfix 的模块化体系中，qmgr 与投递代理（Delivery Agent，例如负责远程 SMTP 投递的 smtp、负责本地投递的 local 或管道投递的 pipe）职责边界明确：qmgr 负责消息队列文件的状态迁移、内存批次规划与并发调度，不执行远端 SMTP 对话，也不负责目标邮箱的具体存储写入。网络连接的建立、协议交互及具体收件人邮箱的写盘，全部由对应的投递代理进程完成。

1.1 核心内存数据结构

在 src/qmgr/qmgr.h 中，qmgr 使用了四层核心内存结构来组织待投递任务：

内存结构名称组织维度与核心职责
QMGR_MESSAGE对应处于活动队列（active）中的一封邮件文件。持有队列标识（queue_id）、文件内正文数据偏移量（data_offset）、未处理收件人计数（rcpt_unread）及关联任务列表 源码。
QMGR_JOB消息与传输通道（Transport）层面的聚合单元。若同一封邮件包含多个不同传输通道（如外域 smtp 与本地域 local），会为不同通道分别分配 QMGR_JOB。
QMGR_PEER关联特定传输通道与目标队列（QMGR_QUEUE，对应下一跳目的地）的调度节点，衔接上层 Job 与底层待投递条目。
QMGR_ENTRY一次具体的进程间通信（Inter-Process Communication，IPC）投递单元。持有收件人批次列表 rcpt_list，挂载在对应队列的就绪链表（todo）或投递中链表（busy）上 源码。

1.2 投递批次的分组与目的地概念

当 qmgr 在 src/qmgr/qmgr_message.c 中执行 qmgr_message_assign() 时，会将邮件内的有效收件人打包分配进 QMGR_ENTRY。为降低网络交互开销，解析至相同传输通道与相同目的地的收件人会合并在同一个 QMGR_ENTRY 中发送给投递代理 源码。

但合并受传输通道的收件人限制（recipient_limit）约束。一旦当前条目的收件人数量达到限制，或者启用了单收件人投递（single_rcpt），qmgr 就会调用 qmgr_entry_create() 创建新的 QMGR_ENTRY。

需要特别说明的是目的地（Destination）的定义：在 src/qmgr/qmgr_message.c（第 1245–1301 行）中，目的地队列名称 queue_name 默认取自解析出的下一跳主机 nexthop；但对非 error 与 retry 通道，当投递代理的 recipient_limit 为 1 时，代码可按去除地址扩展后的 localpart 与 nexthop 建立队列（即 localpart@nexthop）源码。因此，Postfix 中的目的地并不绝对等同于目标域名或 MX 主机，而是由传输通道与下一跳配置共同决定的调度隔离单元。

工程推导提醒：
一次 IPC 投递尝试（即一个 QMGR_ENTRY）只是运行时的临时内存结构，并不等同于持久化的投递任务记录。在自研分布式邮件系统时，通常会在数据库中建立“消息记录（Message ID）”、“收件人记录（Recipient ID）”与“投递尝试记录（Attempt ID）”三张关系表；这是工程设计的规范化抽象，Postfix 内部并没有这三张独立的关系表，其持久化状态是以紧凑格式记录在单个队列文件中的。

二、队列生命周期与执行主链

Postfix 的队列目录结构明确，文件在磁盘上的状态迁移由 qmgr、cleanup 与投递代理协同完成。

2.1 队列目录状态流转

  1. incoming 队列：由 cleanup 守护进程在此目录创建并写入队列文件。当邮件接收完成、地址规范化处理完毕并满足权限与完整性检查后，文件在 incoming 目录等待调度。
  2. active 队列：受内存预算控制的活动水位池。只有通过检查并移入 active 目录的文件，qmgr 才会为其在内存中分配 QMGR_MESSAGE 及下属数据结构 源码。
  3. deferred 队列：当投递过程中遇到暂时性故障（如对端返回 4xx 状态码或网络连接超时），邮件从 active 被重命名移入 deferred 目录，并设置未来的修改时间戳进行退避等待。

2.2 源码级调用主链

在主事件循环 qmgr_loop()（src/qmgr/qmgr.c）中，qmgr 按照以下异步调用链驱动调度：

  1. 排空活跃队列（qmgr_active_drain）：调用 qmgr_transport_select() 挑选有待发邮件的传输通道，并通过 qmgr_transport_alloc() 异步申请对应的投递代理进程 源码。
  2. 读入新邮件（qmgr_active_feed）：当当前内存中的消息计数未达限制（qmgr_message_count < var_qmgr_active_limit）时，扫描器提取待处理文件，通过 mail_open_ok() 检查权限与完整性，随后通过 mail_queue_rename() 将文件原子重命名移入 active 目录 源码。
  3. 消息解析与分配（qmgr_message_alloc / qmgr_message_assign）：调用 qmgr_message_alloc() 读取信封数据与有效收件人，再通过 qmgr_message_assign() 将收件人切分挂载至各 QMGR_ENTRY。
  4. 派发投递请求（qmgr_deliver_send_request）：在 src/qmgr/qmgr_deliver.c 中，qmgr 通过 UNIX 域套接字向投递代理发送请求属性列表，包含队列目录、队列标识（queue_id）、正文偏移量（MAIL_ATTR_OFFSET）及收件人列表 源码。投递请求不会在 IPC 中拷贝整封邮件的正文。投递代理端在 src/global/deliver_request.c（第 351 行）通过 mail_queue_open() 以读写模式（O_RDWR）打开该队列文件并获取共享锁，随后依据偏移量读取邮件正文并具备回写完成记录的能力 源码。
  5. 异步状态更新（qmgr_deliver_update）：投递代理完成尝试后通过 IPC 回传状态（如成功、暂缓或代理崩溃）。qmgr 取消看门狗定时器，执行 qmgr_entry_done() 释放当前条目占用的内存 源码。
  6. 收尾与迁移（qmgr_active_done_3_generic）：当一封邮件的所有投递条目均处理完毕，若仍有未送达且需重试的收件人，计算退避延迟并赋予文件未来的修改时间戳，随后重命名移入 deferred 目录；若所有收件人均已处理完毕（成功送达或彻底退信），则调用 mail_queue_remove() 从磁盘删除该队列文件 源码。

三、持久性机制、崩溃恢复与投递语义

邮件系统在确认接收邮件与执行投递时，必须依赖严谨的文件系统交互来保障数据完整性。

3.1 入队确认与写屏障

负责接收邮件并建立初始队列文件的是 cleanup 服务，而不是 qmgr。在 src/cleanup/cleanup_api.c 与 src/global/mail_stream.c 中，邮件在向客户端返回接收成功应答前，必须通过 mail_stream_finish_file() 完成落盘检查 源码。

代码在刷新用户空间缓冲区 vstream_fflush() 之后，会在编译时定义 HAS_FSYNC 的平台上调用 fsync()，并检查文件关闭（close）的返回状态。只有在这一系列操作均未报告错误的情况下，接收阶段才会返回成功。qmgr 并不负责 SMTP 接收阶段的确认逻辑；它在从 incoming 扫描文件时，依然会调用 mail_open_ok() 校验文件属主、权限与常规文件属性，而不是盲目信任目录内容。而在缺少物理写屏障支持或硬件遭遇不可恢复故障的边界下，依然存在数据损坏的物理风险。

3.2 逐收件人标记：deliver_completed

当一封邮件包含多个收件人时，若投递代理成功将邮件送达给其中某一个收件人，系统会通过逐收件人标记避免后续重复投递。

在 src/global/deliver_completed.c 中，投递代理获取到该收件人在队列文件中的记录偏移量 offset，执行记录覆盖 源码：

/* src/global/deliver_completed.c */
void deliver_completed(VSTREAM *stream, long offset)
{
    if (offset == -1)
        return;
    if (offset <= 0)
        msg_panic("%s: bad offset %ld", myname, offset);
    if (rec_put_type(stream, REC_TYPE_DONE, offset) < 0
        || vstream_fflush(stream))
        msg_fatal("update queue file %s: %m", VSTREAM_PATH(stream));
}

投递代理通过原地覆盖的方式，将该偏移量处的记录类型直接改写为 REC_TYPE_DONE，并调用 vstream_fflush() 刷新流缓冲区。

核心细节辨析：
此处调用的是用户态缓冲区冲刷函数 vstream_fflush()，而不是强行执行内核写屏障的 fsync() 系统调用。这意味着修改已离开投递代理的进程缓冲区并写入操作系统内核页缓存，但若此时主机突然掉电，仍可能丢失尚未刷入磁盘介质的更新。

当 qmgr 后续重新加载该队列文件时，src/qmgr/qmgr_message.c 在读取信封记录时若识别到记录类型为 REC_TYPE_DONE，会递减 message->rcpt_unread 并跳过该收件人 源码。若该完成记录已可靠保存且读取有效，重新调度时便不会为该收件人再次生成投递条目。

3.3 崩溃恢复与投递语义边界

若远端 SMTP 服务端已经接受邮件，但本地投递代理在调用 deliver_completed() 成功写盘之前发生系统崩溃或网络断开：

  • 冷启动与未决邮件处理：在 qmgr_post_init()（src/qmgr/qmgr.c）中，Postfix 重新启动时会将所有残留在 active 目录中的文件移回 incoming 目录并设置当前时间戳，等待重新扫描；而原本已处于 deferred 队列的文件则继续保留在 deferred 目录中等待周期扫描，并不会被移入 incoming 源码。
  • 并发锁保护：当 qmgr 再次通过 qmgr_active_feed() 处理该文件时，若原有的投递代理进程尚未完全退出且仍持有文件锁，qmgr_message_alloc() 会返回 QMGR_MESSAGE_LOCKED。qmgr 不会强制接管，而是将其推回 incoming 延迟 60 秒后再试 源码。
  • 投递语义边界：只要远端已成功接收邮件，而本地将收件人标记为 REC_TYPE_DONE 的操作未可靠落盘，系统在重启重试时就可能再次安排该收件人的投递，从而产生重复邮件。恢复机制容许重复投递，不能承诺端到端恰好一次，也不保证每封邮件最终送达。

四、流量调度：并发控制、退避与饥饿预防

在高并发邮件外发场景中，若缺乏合理的流量控制，偶发的对端故障可能引发资源耗尽。qmgr 内部实现了一套细粒度的流控机制。

4.1 内存预算与输入控制

qmgr 通过配置参数对内存使用进行保护：

  • var_qmgr_active_limit：限制处于 active 内存中的最大邮件文件数量。
  • var_qmgr_rcpt_limit：限制处于内存中的最大收件人总数。

在事件循环中，qmgr_loop() 每次仅从待处理队列导入一封邮件进入 active（“We import one message per interrupt”），以平滑系统调用开销与内存分配压力 源码。

4.2 目的地并发、慢启动与限流挂起

在 QMGR_QUEUE 结构中维护了并发控制窗口 window 源码：

  • 慢启动与增窗：对某一目的地持续成功投递时，累加 success 反馈，逐步增大并发窗口 window，直至达到该通道配置的最大目的地并发限制。
  • 限流挂起（Throttle）：当投递代理报告目的地故障且反馈统计达到阈值时，qmgr_deliver_update() 会调用 qmgr_queue_throttle() 将目标队列挂起，并启动退避定时器，暂停调度该目的地的新任务；而当投递代理自身发生异常崩溃（DELIVER_STAT_CRASH）时，则触发对整个传输通道的挂起操作（qmgr_transport_throttle）源码。

目的地级故障由投递代理状态报告与 qmgr 反馈规则决定，不可只看一个 4xx 便断言整域不可用。例如收件人邮箱暂时已满，属于单个收件人的暂缓，并不会直接触发整个目的地的退避挂起。

4.3 轮询公平性与指数退避

在扫描待处理邮件时，qmgr_loop() 在 incoming 与 deferred 队列之间进行交替轮询（Round-robin）源码。这一策略减少了因 deferred 队列大量积压而导致新进邮件长时间无法调度的风险。

对于进入 deferred 队列的文件，src/qmgr/qmgr_active.c 中的 qmgr_active_done_3_generic() 会计算重试延迟时间 源码：

/* src/qmgr/qmgr_active.c */
if (message->create_time > 0) {
    delay = event_time() - message->create_time;
    if (delay > var_max_backoff_time)
        delay = var_max_backoff_time;
    if (delay < var_min_backoff_time)
        delay = var_min_backoff_time;
} else {
    delay = var_min_backoff_time;
}
qmgr_active_defer(message->queue_name, message->queue_id,
                  MAIL_QUEUE_DEFERRED, delay);

延迟时间取决于当前时间与邮件创建时间 create_time 的差值，并被限制在 var_min_backoff_time 与 var_max_backoff_time 之间。随后通过 utime() 将文件的修改时间 st_mtime 设置为当前时间加上 delay。

需要指出的是，周期扫描机制不保证在到期的那一秒立即触发。deferred 队列的扫描由定时器驱动，若未到达扫描周期，即便某个文件的 st_mtime 已经过期，它也会等待下一次扫描器运行时才会被读入。

五、教学场景分析与尚未执行的验证方案

5.1 教学场景：三收件人双目的地投递

假设系统接收了一封通过 smtp 传输通道投递的邮件，包含三个收件人：

  1. alice@domain-a.example
  2. bob@domain-a.example
  3. charlie@domain-b.example

在调度执行时：

  1. 任务切分：qmgr_message_assign() 为这封邮件创建同一个 smtp Job，但下设两个 Peer：一个关联 domain-a.example 队列，另一个关联 domain-b.example 队列。若传输通道收件人上限至少为 2，alice 与 bob 被合并打包在同一个 QMGR_ENTRY 中；charlie 挂载在独立的 QMGR_ENTRY 中。
  2. SMTP 交互与部分完成：
    • 投递代理连接 domain-a.example，在 SMTP 会话中按序发送 RCPT TO 命令：对端服务器接受了 alice（返回 250），但拒绝了 bob（返回 452 4.2.2 Mailbox full 临时错误）。随后投递代理发送 DATA 内容，并在邮件正文传输完毕且对端返回最终 250 应答后，才判定 alice 成功。此时投递代理调用 deliver_completed() 将 alice 在队列文件中的记录原地更新为 REC_TYPE_DONE 并执行 fflush。
    • 投递代理连接 domain-b.example 时网络不通，TCP 连接超时，整个条目失败。
  3. 状态汇总与暂缓：qmgr 收到反馈后，alice 标记完成，bob 与 charlie 均需重试。该邮件文件不会被删除，而是被重命名移入 deferred 目录，并更新未来的修改时间戳。
  4. 系统重启后的状态：若此时邮件服务重启，处于 deferred 目录的该文件继续由 deferred 扫描器负责；当退避时间到达且扫描器读入该文件时，解析代码检测到 alice 的记录已为 REC_TYPE_DONE 并直接跳过，仅为 bob 与 charlie 分配调度条目重新尝试。

5.2 尚未执行的验证方案

为在隔离测试环境中验证上述机制，设计以下验证方案（本方案在当前写作环境中尚未执行运行）：

  • 测试输入：构造包含上述三个收件人的标准 MIME 邮件，通过本地提交接口注入邮件系统。
  • 故障注入手段：
    • 在受控网络环境中，将 domain-a.example 指向本地模拟的 SMTP 接收器，配置其对 alice 接受、对 bob 的 RCPT TO 返回 452 并在 DATA 结束后返回 250；
    • 对发往 domain-b.example 的连接进行受控丢弃，并核实客户端记录的具体超时原因；
    • 借助测试断点或测试钩子控制实例：在投递代理向 alice 执行完毕 deliver_completed() 且 domain-b.example 报错后，通过隔离测试管理器停止并重启整个测试实例；
    • 类似地，通过测试钩子精确命中“远端 DATA 确认后但在本地执行 deliver_completed() 之前”的极短故障注入窗口。
  • 预期证据与观测点：
    1. 重启前，使用 postqueue -p 观察到队列文件中仍记录有该 queue_id，且状态标记为延迟；
    2. 使用分析工具检查队列文件内部记录，确认 alice 对应的记录类型已变更为 REC_TYPE_DONE；
    3. 服务重启后检查投递代理日志与模拟接收器的事务记录，确认仅针对 bob@domain-a.example 与 charlie@domain-b.example 发起了新的连接与投递交互，未向 alice 重复发送连接与投递；
    4. 若在第二种精确钩子注入窗口下中止测试实例，重启后日志与模拟端应观察到针对 alice 的重复投递尝试，用以证实非端到端恰好一次的理论边界。

5.3 队列堆积定位建议

当遇到邮件已接收但未送达的情况时，应结合日志与队列状态有序排查：

  • 检查日志生命周期：根据客户端收到的 queue_id 在系统日志中检索。若包含 status=deferred，记录具体的对端返回码与原因；若仅有接收记录而无 qmgr 调度日志，需检查 active 队列水位与调度器状态。
  • 检查物理队列位置与等待状态：通过队列工具检查文件位于 incoming、active 还是 deferred。若文件已在 active 中却未送出，需核查该目的地的并发窗口是否降为 0、对应 transport 的可用性以及是否达到进程并发上限（maxproc）；若停留在 deferred，可查看文件的修改时间是否处于未来的退避窗口中。此外，应结合具体的写失败日志核查 spool 目录所在磁盘容量、inode 是否耗尽以及目录权限；仅凭目录或队列计数不能直接认定系统故障。
  • 理性对待队列重试：切勿将全量强制重试（postqueue -f）作为日常运维手段。全量强制冲刷只是请求尽早重试队列，但新进入调度的批次仍受 active 容量与传输通道并发预算约束；在对端网络或服务故障尚未恢复时，强制冲刷不仅不能消除根本问题，反而会加剧本地与网络负载。

六、自研邮件投递系统的设计借鉴

Postfix 3.6.2 的调度设计为自研邮件投递与消息推送系统提供了重要的架构参考：

  1. 多级实体建模：在数据建模时，建议将全局消息实体、单个收件人投递单元与具体的网络尝试批次进行解耦拆分，使得单个收件人的成败状态能够独立流转，避免因部分收件人失败导致整批任务重复投递。
  2. 明确落盘屏障：在向上游客户端返回成功应答前，必须完成必要的文件刷盘与存储持久化校验，不能在易失性缓存中暂存即返回。自建系统的队列 spool 容量、底层存储可靠性以及意外崩溃后的恢复与备份流程，均需要部署与设计团队自行实施严格的工程验证与测试。
  3. 基于目的地的并发与退避：调度系统应按下一跳目的地维度聚合并发控制与退避状态，当某一目标域由于网络超时或频控而发生故障时，仅对该目的地实施熔断与降频，避免影响其他正常目的地的投递进度。
