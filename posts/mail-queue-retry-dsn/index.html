邮件队列、重试与投递状态通知

2021年8月22日
|

在简单邮件传输协议（Simple Mail Transfer Protocol，SMTP，RFC 5321）定义的分布式存储转发模型中，发送端邮件传输代理（Message Transfer Agent，MTA）并不能保证一封邮件在网络中“实时到达”或“端到端恰好一次投递”。网络抖动、目标主机宕机、临时负载过高或是收件人策略拦截，都是互联网跨域邮件传输的常态。

为了在不可靠的网络环境下提供高可用的传输保证，MTA 普遍依赖本地出站邮件队列（Outgoing Mail Queue）与退避重试机制（Backoff Retry Strategy）。而当多次重试耗尽或是遭遇不可恢复的致命错误时，系统则依靠投递状态通知（Delivery Status Notification，DSN，RFC 3464）向发件人反馈投递结果。

邮件队列与状态流转

当用户或上游系统通过邮件提交服务将一封邮件送达 MTA 后，MTA 并不一定立即完成对远端目标服务器的最终投递。一旦首轮实时连接尝试未果，邮件就会被写入出站队列，转化为异步重试状态。

队列项的核心构成

在典型的系统设计中，出站队列项通常持久化记录以下几类传输元数据（具体的字段命名与数据结构属于各软件的实现细节，而非协议固定的数据模型）：

  1. 信封反向路径（Reverse-Path）：即 MAIL FROM 中声明的原始发件人地址或空路径 <>。它是后续生成投递失败通知时的唯一合法路由目的地。
  2. 信封正向路径集合（Forward-Paths）：即未完成投递的 RCPT TO 地址列表。对于包含多个收件人的邮件，MTA 通常维护每位收件人的独立投递状态（已送达、临时延期、永久失败）。
  3. 邮件内容（Message Content）：符合 RFC 5322 格式规范的原始邮件头与正文数据。
  4. 调度状态元数据：入队时间戳（Arrival Date）、最近一次尝试时间（Last-Attempt-Date）、已尝试次数、当前重试退避间隔以及下一次计划调度时间。

队列项状态机

邮件在队列内部的生命周期涉及多个收件人与分步交互，其典型状态转移如下：

队列状态触发条件下一步动作
就绪（Ready / Active）新入队邮件或重试计时器到期分配传输连接通道，发起 SMTP 投递事务
延期（Deferred）遇到网络超时或远端返回 4yz 临时错误计算下一次退避延迟时间，保留未完成收件人并移入延期等待区
本跳移交成功（Relayed / Transferred）远端主机在完整接收 DATA 内容后返回 250 OK 并正式接管责任标记对应收件人已移交；若所有收件人均已处理完毕，释放正文持久化资源，记录投递审计日志
过期/永久失败（Expired / Failed）收到 5yz 致命错误或累计重试时间超限标记该收件人终结；若信封反向路径非空且非恶意邮件，生成并投递 DSN 退信通知；所有收件人终结后移除队列项

在多收件人场景下，同一封邮件的正文在队列中通常被多个收件人共享。只有在 DATA 阶段结束后远端返回针对整封内容的最终 250 OK，本跳的移交责任才告完成；如果仅是某个 RCPT TO 命令返回 250，仅代表该地址被远端初步接受，并不免除发信责任。同理，当某个收件人遭遇 5yz 失败时，MTA 仅标记该特定收件人失败，而不能丢弃其他处于等待或重试状态的收件人。

重试退避策略与时限约束

如果客户端在遇到连接失败或临时错误后立即盲目重试，不仅会白白耗尽本地计算资源与网络连接池，还容易导致同一时间集中重连，对处于恢复期的目标服务器造成二次冲击。为此，RFC 5321 对出站队列的重试策略给出了明确的协议规范与推荐指引。

1. 协议推荐的重试节奏

依据 RFC 5321 第 4.5.4.1 节规定：

  • 重试退避间隔：发送方在一次投递尝试失败后，必须（MUST）延迟对该特定目标的下一次重试。协议建议常规重试间隔应（SHOULD）至少为 30 分钟。但当客户端能识别具体的失败原因时，可以采用更精细的动态退避策略。
  • 故障初期的重试建议：工程经验表明，很多网络抖动与目标进程重启属于短时间故障。RFC 5321 推荐在入队后的首个小时内可尝试 2 次连接，随后逐步退避到每 2 至 3 小时尝试一次。
  • 超时放弃时限（Give-up Time）：对于普通邮件，在目标持续不可达或反复返回临时错误时，发送端放弃重试并判定最终失败的时限通常需要（needs to be）至少 4 至 5 天。
  • 参数可配置性：重试算法中的各项调度参数必须（MUST）支持管理员灵活配置。

2. 目标主机隔离与负向缓存边界

面对拥有大量排队邮件的高负载系统，如果每轮重试都针对同一个故障主机的数百封邮件逐一建立 TCP 连接，将导致严重的本地线程阻塞与无谓的网络等待。

  • 不可达主机列表（Host Unreachable List）：RFC 5321 第 4.5.4.1 节建议客户端维护一份当前无法连通的主机名单及其连接超时记录，避免针对每个队列项重复探测已知宕机的主机。
  • 负向缓存的严苛限制：与此同时，客户端在缓存服务端的负向响应时应当（SHOULD）极其谨慎。RFC 5321 明确要求：绝对禁止（MUST NOT）缓存针对 MAIL 命令返回的 5yz 响应。因为邮件系统可能随时调整账户策略或清理配额，跨事务盲目复用发件人拒绝状态会导致合法的后续发信被误判。

3. 多 MX 记录与地址回退

在解析目标域名的域名系统（Domain Name System，DNS）记录时，MTA 往往会获得多个按照优先级排列的邮件交换记录（Mail Exchange，MX）记录，或单个主机名解析出多个互联网协议第 4 版（Internet Protocol version 4，IPv4）或第 6 版（Internet Protocol version 6，IPv6）地址。

  • 优先级排序：RFC 5321 第 5.1 节规定，发送方必须（MUST）按 Preference 数值从小到大排序；对于数值相同的记录，在没有明确理由偏好特定目标时，必须（MUST）随机打乱以分摊负载。
  • 尝试与回退要求：发送端必须（MUST）能够依序尝试并重试列表中相关的目标地址，直到投递成功；客户端应（SHOULD）至少尝试两个地址。实现时可支持配置备用地址尝试的数量上限，避免无限耗尽资源。

投递状态通知：RFC 3464 报文剖析

当邮件因为超时、地址不存在或策略拒绝等原因彻底无法送达时，MTA 不能将其静默丢弃（除非原信封反向路径为空，或有充分证据表明其属于欺诈或攻击流量，见 RFC 5321 第 6.1 与第 6.2 节），而是应生成退信通知。传统的退信通常是一段纯文本，格式因厂商而异，自动化系统极难结构化解析。为此，RFC 3464 规范了机器可读的投递状态通知（Delivery Status Notification，DSN）。

1. MIME 报文顶层组织

多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）为非美国信息交换标准代码（American Standard Code for Information Interchange，ASCII；此处使用 US-ASCII）文本与多部件邮件提供了通用结构。符合 RFC 3464 规范的 DSN 是一封标准 MIME 邮件，其顶层媒体类型必须设置为 multipart/report，并包含参数 report-type=delivery-status。它由两到三个核心子部件（Part）构成：

multipart/report; report-type=delivery-status
  ├── Part 1: text/plain
  │     （面向普通用户的自然语言解释，说明为何投递受阻或失败）
  ├── Part 2: message/delivery-status
  │     （严格按照格式定义的机器可读状态字段，供用户代理或自动化系统解析）
  └── Part 3: message/rfc822 或 text/rfc822-headers [可选]
        （退回的原始邮件全文或仅保留的原始邮件头信息）

依据 RFC 3464 第 2.1 节规定，第二部件 message/delivery-status 属于机器状态数据，各字段必须采用 7 位 ASCII 字符表示。

2. message/delivery-status 核心字段

第二部件的内容分为两部分：首先是一组全局每邮件字段（Per-Message Fields），随后由空行分隔，跟随一组或多组每收件人字段（Per-Recipient Fields）。

全局每邮件字段（Per-Message Fields）

  • Reporting-MTA: dns; mailout.example.com：必选。执行该次投递尝试、中继或网关转换的 MTA 主机标识（通常在 DNS 语法下保留通用名称的大小写表示）。需要注意，Reporting-MTA 是执行该尝试的节点，不一定等同于最终组装格式化 DSN 报文的边界网关。
  • Received-From-MTA: dns; client.example.net ([192.0.2.10])：可选。接收该原始邮件的上游节点声明的主机名与客户端 IP 地址（SMTP 场景建议在括号中附带客户端 IP）。
  • Arrival-Date: Wed, 18 Aug 2021 14:20:00 +0800：可选。原始邮件到达本 Reporting-MTA 的时间戳。

每收件人字段（Per-Recipient Fields）

  • Final-Recipient: rfc822; invalid-user@example.com：必选。本组状态所对应的最终收件人信封地址。
  • Original-Recipient: rfc822; alias-user@example.com：可选。发件人最初指定的原始收件人地址（若在别名展开或中继转发前记录了该信息）。
  • Action: <failed | delayed | delivered | relayed | expanded>：必选。Reporting-MTA 针对该特定收件人所采取或报告的处理动作。
    • failed：终态动作，表示 Reporting-MTA 已放弃对该特定收件人的此次投递尝试，本节点不会再为该收件人生成后续通知（但这并不意味着该邮件的所有副本或其他收件人均未送达）。
    • delayed：非终态动作，邮件已被延迟排队重试，后续可能成功或最终失败。
    • delivered：终态动作，邮件已成功放入收件人邮箱或投递到邮件列表。
    • relayed：邮件已转交给下游不承担回传成功投递状态通知责任的下一跳系统（通常见于异构网关或不支持 DSN 的中继）。
    • expanded：邮件已投递至别名展开器，且 Reporting-MTA 已继续向展开后的多个子地址进行转发分发。
  • Status: <class>.<subject>.<detail>：必选。三段式增强状态码（Enhanced Status Code），按 RFC 3464 第 2.3.4 节定义，由状态类别（2、4 或 5）、主题与具体细节三部分数字组成（如 5.1.1、4.4.1）。它与 SMTP 传统的三位回复码具有不同的结构与语法，不可直接将普通数字字面量机械拼装。
  • Remote-MTA: dns; mx.example.com：可选。如果错误是在与下游远端服务器交互时发生的，在此记录远端服务器主机名。
  • Diagnostic-Code: smtp; 550 5.1.1 User unknown：可选。传输协议层捕获到的原始诊断行（以 smtp; 开头注明协议类型）。

3. Action 与 Status 的解耦

许多开发者容易混淆 Action 与 Status 字段。RFC 3464 第 2.3.3 节特别强调：这两者并不等价，且不可互相替代。 最典型的例子是临时错误重试：

  • 当邮件因目标网络不可达延期时，MTA 发送阶段性通知提醒发件人，此时 Action: delayed，Status: 4.4.1。
  • 若数天后重试耗尽宣告放弃，MTA 发送最终退信，此时 Action: failed，而 Status 依然是 4.4.1（记录导致放弃的根本原因仍是临时网络超时）。

4. 重复投递与 DSN 的结论边界

由于 SMTP 协议基于分步确认机制，且网络连接可能在任意时刻异常中断，系统无法保证“恰好一次投递”：

  • DATA 确认丢失导致的重复：当接收端 MTA 已经完整接收了邮件 DATA 内容并写入本地存储，正准备向发送端返回 250 OK 时，底层网络发生瞬断或超时；发送端因未收到最终 250 确认，只能判定此次尝试未完成并将任务保留在队列中延期重试。随后的重试可能使同一封邮件再次到达，从而产生重复投递。
  • failed DSN 并不证明所有副本都未送达：依据 RFC 3464 第 4.3 节，收到 Action: failed 的通知仅表明报告该事件的 Reporting-MTA 对该收件人的某次投递尝试宣告失败。如果之前的某次尝试实际上已经完成了内容写入（仅仅是确认回复丢失），或者邮件经过不同路由产生了多个副本，就可能出现收件人既收到邮件正文、发件人又收到退信通知的情况。因此，单凭 failed DSN 或邮件标头中的 Message-ID，并不能在协议层面证明收件人绝对没有收到该邮件。

邮件循环与回散风暴防范

在分布式邮件投递链条中，如果错误处理机制设计不当，容易在两台服务器之间形成死循环，甚至在遭遇伪造发件人垃圾邮件时引发严重的“退信回散（Backscatter）”。

1. 空反向路径与通知循环

RFC 5321 第 4.5.4 节与第 4.5.5 节以及 RFC 3464 第 2 节确立了错误通知的防环机制：

  • DSN 的空反向路径（Null Reverse-Path）：发送端在通过 SMTP 投递 DSN 或其他非送达通知时，其信封中的反向路径必须（MUST）设为空路径（即 MAIL FROM:<>）。
  • 禁止向空路径回退：任何接收端 MTA 在处理信封为 MAIL FROM:<> 的邮件时，一旦该邮件自身遭遇投递失败，绝对禁止（MUST NOT）再为其生成并发送任何退信通知（RFC 5321 第 6.1 节）。此时系统只能就地丢弃、记录本地日志或交由系统管理员人工分析。这一规定从协议层面切断了错误通知彼此退回形成的死循环。在转发包含空路径的邮件时，中继节点通常不应（SHOULD NOT）为其擅自填充或改写反向路径。

2. 避免无端回散攻击（Backscatter）

在垃圾邮件伪造发件人的场景下，如果外发或中继 MTA 不加甄别地“先接收、后退信”，会引发回散风险：

  1. 攻击者发送伪造垃圾邮件，信封写 MAIL FROM:<victim@example.net>，发往 non-existent@example.com。
  2. 目标 MTA 如果在 SMTP 会话期间返回 250 OK 接管邮件，随后在本地处理时发现用户不存在，再向 victim@example.net 发送 DSN 退信。
  3. 此时，无辜的 victim@example.net 就会遭到来自各大邮件服务器的海量退信轰炸，而目标 MTA 也沦为了攻击者的反射源。

工程边界与防御准则：

  • 边界前移与收件人校验：若能在 SMTP 会话中可靠判定收件人无效，接收端 MTA 应当（SHOULD）在 RCPT TO 命令时直接返回 550 等错误拒绝该收件人。此时连接并未强行中断，会话仍可继续处理其他收件人或发起重置（RSET），而接收端无须为该被拒收件人生成出站退信。但需要注意，RFC 5321 第 6.1 节指出，在某些情况下（如临时 DNS 软错误、收件人为邮件列表或需要中继至内部异构网关），接收端无法立即完成同步校验，仍可能需要先接管邮件再做后续处理。
  • 高置信度静默丢弃：依据 RFC 5321 第 6.2 节与第 7.8 节，尽管互联网传统期望邮件“要么送达、要么退回”，但当 MTA 拥有极高置信度确认该邮件属于恶意的垃圾邮件或病毒伪造信件时，允许直接静默丢弃而不发送通知。

3. 自动应答（RFC 3834）的防护边界

对于自动回复软件（例如“外出休假自动回复”、群组过滤回执），RFC 3834 做出了规范：

  • 信封发件人地址选择：与 DSN 必须使用空路径不同，RFC 3834 第 3.3 节规定，个人或群组自动应答器在投递自动回复时，可以使用空反向路径 <>，也可以选择使用一个经过专门配置的、不会再产生自动回复的非空回信地址。对于专门的服务应答器（Service Responder），则可依其特定服务规范定义信封地址。
  • 目标地址限制：投递后生成的个人或群组自动回复，通常不应（SHOULD NOT）发送至除原始邮件 Return-Path: 字段之外的任何地址（RFC 3834 第 4 节）；在投递前处理时则使用传输信封的反向路径。特别地，通常不应向 From: 或 Reply-To: 发送非预期的自动回复，以防将自动回执投递给邮件列表的全部订阅者。服务应答器如有专门规范可遵循其特定规则。
  • 标记自动生成：自动回复邮件头应（SHOULD）携带 Auto-Submitted: auto-replied 字段（RFC 3834 第 3.1.7 节与第 5.2 节）。对于 DSN，该字段在 RFC 3834 第 5.2 节属于可选（MAY），但在实际中常被包含以辅助识别。
  • 防环路与限频：如果接收到的邮件头部中已经包含了除 no 以外的 Auto-Submitted 字段，自动应答器通常不应（SHOULD NOT）对其产生回复（第 2 节）。此外，针对提示发件人自己无法阅读或回复的个人/群组自动应答，建议（SHOULD）对同一发件人在特定周期内（建议默认 7 天）仅回复一次。

DSN 结构与队列处理示例

1. 自编 DSN 报文结构示意

以下展示了一个自编的多部件 DSN 报文结构示例。该示例基于 RFC 3464 规范构造，用于说明各个子部件的组织方式。此处假设传输信封的反向路径为 MAIL FROM:<>，原始邮件的信封发件人地址为 alice@example.com，物理行均采用标准网络换行符回车换行（Carriage Return and Line Feed，CRLF）终止。

为符合 RFC 3464 第 2.1 节及 MIME 顶层默认 7bit 传输要求，示例第一部分用户通知采用 ASCII 文本表示，避免引入额外的 8 位传输扩展（8BITMIME）协商前提：

Date: Wed, 18 Aug 2021 16:30:00 +0800
From: Mail Delivery System <MAILER-DAEMON@mailout.example.com>
To: alice@example.com
Subject: Undelivered Mail Returned to Sender
Auto-Submitted: auto-replied
MIME-Version: 1.0
Content-Type: multipart/report; report-type=delivery-status;

2. 队列重试与退避流程示意

在出站队列的工程实现中，核心状态流转围绕单收件人投递尝试的结果判断展开。以下 Python 伪代码展示了一个高度简化的单收件人状态判定流程，重点说明本跳移交责任、延期重试计算、空路径抑制及终态退信处理逻辑（该代码仅为概念示意，其中的外部函数为明确标注的概念调用，省略了实际持久化事务与网络 I/O 细节；实际执行器仍需在每次实际发送前核验业务截止时限）：

import time
from typing import Optional

class SingleRecipientQueueItem:
    def __init__(self, msg_id: str, reverse_path: str, recipient: str):
        self.msg_id = msg_id
        self.reverse_path = reverse_path          # 信封 MAIL FROM，可能为 ""
        self.recipient = recipient                # 本任务负责的单一信封 RCPT TO
        self.arrival_time = time.time()
        self.retry_count = 0
        self.next_attempt_time = self.arrival_time

    def compute_next_retry(self, base_delay: int = 1800, max_giveup: int = 432000) -> Optional[int]:
        """
        计算下一次重试调度时间戳。
        - 基础间隔建议至少 30 分钟 (1800s)，放弃时限通常至少 4~5 天 (432000s)。
        - 均须支持系统可配置。执行器在实际发起重试前仍需核验当前时间是否超出业务截止。
        """
        now = time.time()
        if (now - self.arrival_time) > max_giveup:
            return None  # 超过最长重试时限，判定放弃
        
        # 示意算法：前两次重试后逐步拉长退避间隔
        delay = base_delay * (self.retry_count + 1)
        self.retry_count += 1
        self.next_attempt_time = now + delay
        return int(self.next_attempt_time)

def process_delivery_attempt(item: SingleRecipientQueueItem, target_mx: str):
    """
    处理与目标 MTA 完成完整会话后的结果判定。
    注意：只有 DATA 阶段结束且远端返回 250 时，才代表本跳移交完成。
    """
    # 模拟外部概念调用：返回是否成功移交、增强状态码及诊断信息
    outcome = execute_smtp_transaction(target_mx, item)
    
    if outcome.status == "TRANSFERRED":
        # DATA 阶段结束，远端 250 接管责任；本跳移交成功
        mark_as_completed(item)
        remove_from_queue(item)

    elif outcome.status == "TRANSIENT_FAILURE":
        # 临时故障（如 4yz 响应或连接建立超时）
        next_time = item.compute_next_retry()
        if next_time is not None:
            schedule_deferred_retry(item, next_time)
        else:
            # 超过放弃时限，终态处理：检查反向路径后生成超时退信
            if item.reverse_path:
                emit_dsn(item, action="failed", status="4.4.7", diagnostic=outcome.diagnostic)
            remove_from_queue(item)

    elif outcome.status == "PERMANENT_FAILURE":
        # 永久致命错误（如 5yz 明确拒收该收件人），不再重试
        if item.reverse_path:
            # 使用合法映射的增强状态码，非简单拼接字符串
            emit_dsn(item, action="failed", status=outcome.enhanced_status, diagnostic=outcome.diagnostic)
        remove_from_queue(item)

    else:
        # 遇到未决结果（如 DATA 接收后 250 丢失导致的网络断开），
        # 发送端无法确认责任是否移交，必须保留在队列中按延期重新尝试，不能视为已完成。
        next_time = item.compute_next_retry()
        if next_time is not None:
            schedule_deferred_retry(item, next_time)
        else:
            if item.reverse_path:
                emit_dsn(item, action="failed", status="4.4.2", diagnostic=outcome.diagnostic)
            remove_from_queue(item)

协议要求与工程权衡

下表汇总了规范约束（MUST / SHOULD）与系统工程实践的边界对比：

机制维度RFC 规范基线要求系统工程考量与策略示意
重试间隔必须（MUST）延迟重试；建议（SHOULD）间隔至少 30 分钟（RFC 5321 §4.5.4.1）协议允许识别故障原因后采用精细退避。系统可在公网退避与针对特定可恢复故障的初期微调间寻求平衡
重试放弃时限对普通邮件建议（needs to be）至少持续尝试 4 至 5 天（RFC 5321 §4.5.4.1）公网常规信件应遵循 4 至 5 天基线；针对特定业务时效邮件（如过期作废的动态验证码），运营策略可自编较短的专用队列时限，并明确其偏离公网基线的权衡
DSN 投递信封发送 DSN 时必须（MUST）使用空反向路径 MAIL FROM:<>（RFC 3464 §2）发送端基础设施强制锁定空路径；中间转发系统通常不应（SHOULD NOT）篡改或填充该反向路径
对空路径的响应若收到的邮件为 <>，失败时绝对禁止（MUST NOT）发通知（RFC 5321 §6.1）遇到投递阻断时就地丢弃或记录审计日志，切断退信循环
收件人校验时机允许接管后异步退信（RFC 5321 §6.1）若能在会话中可靠判定收件人无效，建议在 RCPT TO 阶段直接拒绝该收件人，接收端不为其生成退信；若存在邮件列表或软错误等无法立即验证的情况，再转入后续处理
