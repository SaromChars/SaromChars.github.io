域、账号与路由配置的管理模型

2021年10月24日
|

在邮箱系统后端开发中，协议交互构成了数据面（data plane）的传输与存取逻辑，而管理员配置怎样可靠生效则是控制面（control plane）的核心问题。当管理员开通一个域、新增一个邮箱或修改别名（alias）转发规则时，系统需要判定主体权限，验证路由拓扑合法，并将变更一致地推送到负责认证、接收、投递与过滤的各个后台组件中。若控制面缺乏清晰的状态与版本定义，多组件间的配置时差容易引发别名循环或路由混乱。

本文建立一套面向邮箱管理控制面的实体模型、路由图约束与配置发布流程，并基于 sales@example.test 从旧邮箱切换到新邮箱的教学场景，说明配置版本推进、失败降级与补偿回退的工程边界。需要说明的是，本文提供的数据模型、应用程序编程接口（Application Programming Interface，API）与状态机均为工程教学设计；文中所引用的跨域身份管理系统（System for Cross-domain Identity Management，SCIM）仅作为身份模型与实体生命周期的参考，并非邮箱配置的标准规范。

实体关系与生命周期边界

邮件管理后端通常需要支撑多租户隔离。如果直接将外部可见的域名或邮件地址作为数据库主键，一旦发生改名、域解绑或邮箱转让，历史审计与权限索引就会断裂。因此，控制面应借鉴 RFC 7643 第 3.1 节的做法，为每个实体分配稳定且不可重新指派的内部标识符（internal ID），并在所有引用链上执行租户归属校验。

租户 (Tenant: tenant_id)
  ├─ 域名 (Domain: domain_id, fqdn, status)
  ├─ 账号 (Account: account_id, username, status, account_version)
  │    ├─ 凭据 (Credential: credential_id, version, secret_hash)
  │    └─ 授权关系 (AccountMailboxGrant: account_id, mailbox_id, roles, grant_version)
  ├─ 邮箱 (Mailbox: mailbox_id, storage_node, status)
  └─ 地址路由 (AddressRoute: route_id, domain_id, local_part_norm, targets: [{type, ref}])

在这个模型中，各个实体的职责与生命周期保持解耦：

  1. 租户（Tenant）与域名（Domain）：域名必须全局唯一归属于一个租户。在开通域名时，控制面需要执行所有权资格校验（例如 DNS TXT 记录挑战）。域名停用属于期望策略变更，已加载该策略的边界节点应拒绝新邮件，但在多节点完全同步前，仍可能存在短暂的生效时差；属于该租户的历史邮件数据并不随域名停用而物理销毁。
  2. 账号（Account）与邮箱（Mailbox）：账号是登录身份认证（authentication）与审计的主体，邮箱则是存放邮件的物理或逻辑存储单元。二者通过多对多授权（authorization）关系关联。一个账号可以拥有多个邮箱的访问权（如兼管公共客服邮箱），一个共享邮箱也可以授权给多个业务账号。这种分离使得人员交接时只需调整授权关系或更新账号状态，无需迁移底层邮箱目录。
  3. 地址路由（AddressRoute）：定义进站邮件如何映射到具体目标。它与物理邮箱并非等同概念，允许将同一个本地部分映射到内部邮箱、嵌套别名或外部转发地址。
  4. 生命周期阶段的控制：当账号出现安全事件或员工离职时，“禁止登录”、“撤销令牌”、“暂停收信”与“删除历史邮件”是四个独立的操作级别。禁止登录用于在认证阶段阻断新的协商；撤销访问令牌（token）使依赖该令牌的请求在校验周期内失效；暂停收信需要将路由规则置为拒收或临时排队；而删除物理邮件则属于不可逆的数据擦除，受到独立归档保留策略的约束。

本地域地址解析与路由图约束

当邮件传输代理（Mail Transfer Agent，MTA）接收到外部进站邮件时，控制面必须提供确定性的地址匹配机制。在 RFC 5321 第 2.3.11 节定义了邮箱地址由本地部分与域名组成；而在第 2.4 节中明确规定，主机名或域名部分不区分大小写，但邮箱地址的本地部分（local-part）可能具有大小写敏感性，其解释权完全归属于接收主机的本地域。

因此，控制面在存储和匹配地址时，不能在入库前盲目做全网统一的强制小写转换（lowercase），而应保留创建时的原始形式。本域控制面可以定义本地域内的规范化匹配键（例如本域统一约定不区分大小写时的规范化散列或小写索引 local_part_norm），并以此施加“本地域内地址规范化键唯一”的数据库约束。

在别名与转发的设计中，目标数组（targets）中的每一个目标都必须明确类型并逐个校验租户归属：

  • 内部邮箱（mailbox）：目标直接指向系统内分配的 mailbox_id，投递发生在本地存储服务内部。
  • 嵌套别名（alias）：目标指向同一个域内的另一个路由项，支持多对多别名展开。
  • 外部转发（forward）：目标为外部邮件地址，邮件需要重新经过入队与出站中继。
进站地址: sales@example.test
               │
               ▼ [AddressRoute 查表]
       ┌───────┴───────┐
       ▼               ▼
内部投递 (mb_2)     外部转发 (external@partner.test)
       │               │
       ▼               ▼
本地邮箱写入         出站传输 (重新鉴别并防范外发滥用)

别名嵌套可能导致本地循环投递。在 RFC 5321 第 6.3 节提出了规避循环的原则。控制面在录入或变更路由时应施加静态拓扑检查，依据本系统的教学设计参数，对别名展开深度与目标总数设置硬性阈值（例如展开深度不超过 5 层，展开目标累计不超过 50 个）。在同一租户的内部别名依赖图中，通过有向图环路检测算法即可在配置校验阶段发现成环并拒绝写入。

但对于涉及外部地址的转发，远程外部系统可能再次配置转发回本域地址，这种跨域动态回环在静态配置阶段无法完全证明。因此，运行时仍需依赖传输头中的跳数计数（如 Received 字段超限）进行动态熔断。

另外，收件别名不能自动推导为发件地址授权。用户即使能接收发往 sales@example.test 的邮件，也不代表其可以直接以该地址签署发送。发件地址授权必须在控制面中作为独立的提交权限另行配置，以防范越权身份仿冒。

管理接口与用户接口的边界

控制面应严格区分管理员运维接口与终端用户自服务接口，防止权限越界：

  • 管理 API（Admin API）：供租户管理员调用，负责域名生命周期、账号分配、邮箱配额、路由拓扑及异步发布任务查询。
  • 用户 API（User API）：借鉴 RFC 7644 第 3.11 节的 /me 命名空间理念，仅供已登录终端主体查询自身授权与配置、修改个人凭据或提交受限委托发信，不能将其视为完整的 SCIM 兼容实现。读取邮件、检索/分页和提交发信须先校验账号到邮箱授权，再委托底层存储访问或外发提交组件；管理 API 成功不代表邮件已发送。用户接口严禁修改底层路由表或邮箱归属。

无论前端传入何种参数，后端服务都必须从已认证的主体上下文中提取租户归属，不能信任请求体中的 tenant_id。

在别名图变更中，如果对单个别名路由分散更新，两名管理员并发修改不同别名可能在各自看似合法的局部检查下组合出闭环。因此，控制面应将同一租户的本地路由依赖图视为一个聚合配置资源，并基于 RFC 7232 第 3.1 节与第 4.2 节采用强实体标签（strong entity-tag，strong ETag）与 If-Match 机制防范并发冲突。如果客户端持有的图版本已过时，服务器直接返回 412 Precondition Failed。

同时，控制面通过幂等机制支持网络重试。系统以 (tenant_id, operation, idempotency_key) 为数据库唯一约束，并将请求载荷的哈希值（payload_hash）作为校验字段保存在同条记录中。整个并发控制与幂等判定执行如下流程：

  1. 权限前置检查：无论是否为重试请求，后端必须首先基于当前认证主体进行租户管理授权检查；若已被撤销权限，即使携带有效幂等键也会在入口被拦截拒绝，杜绝借由旧键探查任务状态。
  2. 幂等查询：在通过授权后，系统在事务内查询幂等记录。若命中且 payload_hash 一致，直接返回既有任务状态与期望版本，不重复评估已过期的 If-Match；若命中但 payload_hash 不一致，返回 409 Conflict 拒绝非法重用。
  3. 并发版本比对与锁：若未命中既有幂等记录，系统必须锁住当前租户的路由配置根行（或采用带版本比对条件的原子更新/可串行化事务隔离级别），以防止两名并发写者在常见隔离级别下同时读到旧版本。取得根行锁后须再次读取同键幂等记录；若另一请求已提交，则按第 2 步处理并跳过旧 If-Match 检查（锁策略之外的条件更新或可串行化冲突重试分支，也须在冲突重试后重新执行幂等查询再判 ETag）。在锁保护下确认 If-Match 强 ETag 匹配后，执行拓扑与深度校验，持久化新配置版本并插入发布任务。若并发插入导致唯一键冲突，败者事务回滚并重新读取胜出者记录，比对载荷哈希后返回对应任务快照。

以 sales@example.test 的路由修改为例，管理员将目标从旧邮箱 mb_1 改为新邮箱 mb_2。此处使用 PATCH 方法表示基于教学定义的自定义 JSON 局部更新格式，而非标准 JSON Patch 规范：

PATCH /api/v1/admin/tenants/t_1/routing-config HTTP/1.1
Host: mail-admin.example.test
Authorization: Bearer <admin_token>
If-Match: "v14-a9f8b2"
X-Idempotency-Key: 7b3d9c-20211024-001
Content-Type: application/json

{
  "update_routes": [
    {
      "route_id": "rt_sales_998",
      "local_part": "sales",
      "targets": [
        { "type": "mailbox", "ref": "mb_2" }
      ]
    }
  ]
}

校验通过后，服务器持久化新版本期望配置并排队发布任务，返回 202 Accepted：

HTTP/1.1 202 Accepted
ETag: "v15-c3d4e5"
Content-Type: application/json

{
  "tenant_id": "t_1",
  "desired_version": 15,
  "task_id": "task_pub_20211024_1001",
  "task_status": "pending",
  "updated_at": "2021-10-24T02:00:00Z"
}

客户端持有的新 ETag 对应了租户在控制面持久化的最新期望配置版本，具体的组件生效进度则通过轮询 task_id 查询。

凭据接口、认证分离与缓存失效契约

在 RFC 7643 第 4.1.1 节与第 9.2 节的设计中，用户密码属性被定义为敏感的只写字段，系统绝不在任何读取或查询接口中返回密码明文或存储哈希（secret hash）。

控制面的凭据服务应仅暴露写入与校验契约：

  1. 凭据变更接口：客户端提交新密码，后端使用专用口令哈希方案计算哈希值入库，仅返回递增的 credential_version 与更新时间，不向外暴露任何密码哈希。
  2. 认证服务查询与存储分离：MTA 或认证守护进程向目录服务发起验证时，仅查询账号状态（是否启用、被锁定）及凭据匹配结果。认证服务在本例中不承担邮件物理存储节点寻址或配额查询，后者由数据面内部的独立定位逻辑处理。

在分布式邮件系统中，接入网关常对认证结果或令牌做本地缓存。一旦管理员执行了“禁用账号”、“重置密码”或“调整授权”，控制面必须有明确的缓存撤销机制：

  • 缓存记录必须同时绑定 credential_version 与账号状态版本（account_version），权限关系变更则需推进 grant_version 使邮箱访问授权缓存失效，并统一设置严格的生存时间（Time To Live，TTL）。
  • 当凭据、状态或授权变更时，控制面主动广播失效通知。若网络分区导致广播未达，控制面不得向管理员虚假宣称“已即时撤销”，而是提示存在最长可达 TTL（例如 120 秒）的旧缓存窗口。在此期间，依赖旧缓存的节点可能继续接受验证；若敏感节点无法连接目录服务，应按配置策略临时拒绝。
  • 新旧会话分界：账号被禁用且节点确认获取新状态后，新发起的认证将被拒绝。对于已经通过互联网消息访问协议（Internet Message Access Protocol，IMAP）建立的长连接，不会因 HTTP 令牌失效而自动断开，必须依赖底层的会话心跳检查或调用连接管理接口显式断开指定 account_id 的所有活跃 TCP 连接。

配置变更全生命周期与发布状态机

在邮件系统中，配置变更需要同步到负责接收的 SMTP 服务、负责认证的 Auth 守护进程及负责投递的代理进程。多进程与多服务重载无法依赖单一数据库事务实现跨组件原子性。

因此，控制面采用“期望状态与观测状态分离”的发布模型：

[管理员提交] 
    │
    ▼
[授权与拓扑校验] ──(校验不通过)──> 400 Bad Request (直接终止)
    │
    ▼
[同库事务保存] ──> 写入 desired_version 与发布任务 (pending)
    │
    ▼
[组件配置生成与预检] ──(语法/结构不符)──> 标记 failed (保持原线上版本)
    │
    ▼
[分发部署与重载信号] 
    │
    ▼
[探测读回组件 observed_version] 
    │
    ├─ 全部满足 ──> 标记 applied
    └─ 部分失败/不可判定 ──> 标记 degraded (暂停本租户后续发布并启动补偿)

发布任务的状态机包含明确的语义转移：

  • pending：变更已由控制面事务持久化，生成待发布任务。
  • validated：生成的各组件专用配置通过了语法和完整性预检。
  • applying：控制面正在向各个服务节点分发配置或发送重载（reload）指令。
  • applied：所有目标节点均已由控制面通过功能探测确认实际运行版本（observed_version）达到期望版本，且关键验证通过。仅各组件重载返回成功不足以断言此状态。
  • failed：仅在已明确确认所有组件均未改变线上运行版本（如预检阶段未通过）时标记，系统确认保持原版本运行。
  • degraded：部分节点成功应用，或部分节点由于探测超时等原因导致状态不可判定。针对每个组件，控制面必须明确记录 last_confirmed_version、观测时间 observed_at 以及具体错误 apply_error。在探测超时时，当前 observed_version 绝不冒用最后已知值，而是置为 unknown，并保留已确认版本；此时系统处于中间状态，必须暂停当前租户后续的所有新发布任务，并启动补偿重试。
  • rolling_back：正在执行回退补偿任务。
  • rolled_back：仅当补偿新版本在所有目标组件上均已应用并通过功能探测确认后，原失败任务方可置为此状态。若补偿过程再次出现异常，任务继续保持 degraded。

在审计日志（Audit Log）记录中，控制面应记录操作主体（actor）、请求追踪号（request_id）、操作耗时、差异摘要及生效版本号，严禁记录密码明文、哈希串或任何邮件正文。

当发生回退时，控制面不能用旧快照盲目覆盖后续的合法配置变更。系统在回退前必须检查租户当前版本与变更锁。正确的回退流程是以历史已知安全版本的配置快照，重新生成一个新的递增版本号（例如从版本 15 回退，应生成新版本 16，其内容与 14 一致），再次经过完整的校验、分发、重载与读回探测。

更重要的是，配置回滚绝不能撤销已经落盘的数据。在版本 15 生效期间已经投递入库的邮件属于客观业务事实，回退到版本 16 不会触发对历史邮件的删除。如果遇到配置异常，控制面可以通过在边界路由上返回 SMTP 4xx 临时失败阻断新邮件流入，给修复争取时间，但绝不能丢失队列中已接收的邮件。

场景验证与异常推导案例

以下基于 sales@example.test 由 mb_1 切换到 mb_2 的场景，整理未运行实测验证的工程推导案例。这些案例明确列出各项操作在理想状态下的预期行为与系统状态字段，用以指导控制面实现时的断言测试：

并发修改竞争

两名管理员同时基于版本 14 提交聚合路由更新。先到达的处理流在数据库事务中锁住租户路由配置根行并通过校验，成功将期望版本推进至 15；后到达的处理流因持有的强 ETag 已落后，在版本比对时被直接拒绝，避免产生未知环路。

先到达者响应: HTTP 202 Accepted
先到达者版本: desired_version = 15
后到达者响应: HTTP 412 Precondition Failed

重复请求提交

客户端因网络超时重发具有相同请求体与幂等键的请求。控制面在执行租户管理授权检查通过后，优先命中数据库已持久化的幂等记录，不再重复评估客户端携带的旧 ETag，直接返回既有发布任务的最新进展。

响应结果: 返回既有任务快照
任务标识: task_id = task_pub_20211024_1001
任务状态: task_status = pending (或 applying)

配置生成预检失败

别名解析生成了非法路径或引用的目标邮箱在系统中不存在。控制面在生成各组件配置后的预检阶段捕获错误，主动终止发布流程；所有线上运行组件保持原有版本不变，杜绝破损配置流入生产。

任务状态: task_status = failed
运行版本: component.observed_version = 14
校验错误: validation_error = "E_TARGET_NOT_FOUND"

多组件部分重载失败

SMTP 节点成功加载并应用了版本 15，但负责本地投递的节点在探测时超时未响应。控制面禁止将发布任务标记为成功，而是置为降级状态并暂停当前租户后续发布队列，保留投递组件最后确认的版本与时间并启动补偿重试。

任务状态: task_status = degraded
传输节点: smtp.observed_version = 15
投递节点: lmtp.observed_version = unknown
投递确认: lmtp.last_confirmed_version = 14

账号凭据紧急禁用

管理员紧急冻结异常账号并广播缓存失效通知。已确认获取新状态的边缘认证节点立即拒绝后续新连接的握手；而已建立的长连接存活状态取决于底层的定期会话检查或显式断连指令执行进度。

账号状态: account.status = suspended
广播状态: cache_invalidation_sent = true
活跃连接: active_sessions = pending_inspection

配置故障补偿回退

发布处于降级状态后，管理员或编排引擎基于版本 14 的安全快照生成新版本 16 执行补偿发布链。版本 16 在所有目标组件上均通过验证与功能探测后，原失败任务置为回退终态；在版本 15 期间已落盘至 mb_2 的历史邮件完整保留，回退绝不触发数据删除。

原发布任务: original_task.status = rolled_back
补偿任务: compensation_task.status = applied
期望版本: desired_version = 16
数据保留: mb_2.messages_retained = true
