证书链与主机名校验怎样决定信任

更新于:2026年11月7日
|

在上一篇关于 TLS 握手组件的复盘中，我们看到服务端在握手期间向客户端出示了一张 X.509 数字证书。客户端通过验证这张证书，确认了服务端的公钥。

然而在工程实践中，常常有人认为“只要证书被受信任的机构签了名，连接就安全了”；或者误以为“证书路径验证通过了，服务端就一定是合法站点”。这是对公钥基础设施（public key infrastructure，PKI）与互联网 X.509 公钥基础设施（Internet public key infrastructure using X.509，PKIX）信任机制的巨大简化。

在一次真实的 TLS 连接建立中，信任是由两个既独立又交织的核心环节共同决定的：

  1. 证书链（certificate chain）路径验证（Path Validation）： 证明这张数字证书（digital certificate）在密码学与策略层面上是否有效、是否源自受信任的颁发机构。
  2. 主机名服务身份校验（Service Identity Verification）： 证明当前连接的目标域名（例如 example.com）是否真正被授权绑定在这张证书上。[RFC 5280 §6.1] · [RFC 6125 §1.4]

信任锚：信任从来不来自远端报文

一个最常见的误解是：服务端发来了一整套证书（从叶子证书、中间 CA 到根 CA），客户端只要校验这一串证书“上级签了下级”就能建立信任。

这是极其危险的逻辑。 如果客户端无条件信任服务端发来的根证书，那么任何攻击者都可以自己生成一套自签名根证书并向你签发假证书。

RFC 5280 和 RFC 6818 明确指出：证书路径验证的起点是信任锚（Trust Anchor）。[RFC 5280 §3.2] · [RFC 6818 §1]

  • 信任锚是由客户端通过受信任的带外配置（Out-of-band Configuration）接受的信任信息（包括受信任名称、公钥及相关参数）。在常见操作系统、浏览器或独立应用程序中，它们通常保存在受保护的本地信任库（Trust Store）中。[RFC 5280 §6.1.1]
  • 服务端在 TLS 握手中发送的，通常是叶子证书（End-Entity Certificate） 以及若干张中间证书（Intermediate CA Certificates）。
  • 服务端不需要在握手报文中发送自签名的根证书，作为信任锚的自签名证书本身不属于待验证的目标路径，客户端必须在自己受信任的本地配置中对接信任信息。我们在早期的《信任库配置》中探讨的正是这一本地边界。

证书路径的构建与验证：RFC 5280 核心算法

拿到服务端出示的证书序列后，客户端根据 RFC 5280 §6.1 执行路径验证状态机：[RFC 5280 §6.1]

  1. 候选路径构建（Path Building）： 客户端在本地缓存、信任锚库以及服务端提供的中间证书中搜寻匹配证书，组合形成一条从待验证叶子证书到某个信任锚的候选链路：Root Anchor → Intermediate CA → Leaf Cert。RFC 4158 指出，实际构建算法可以采用自顶向下、自底向上等多种图搜索策略。[RFC 4158 §1]
  2. 签名链数学检验： 沿着待验证链路中的每一个节点，逐级使用颁发者公钥验证签名。
  3. 多维策略与约束检查： 链路中的每个待验证证书节点，还必须经受一系列标准扩展属性与策略规则的严格审问：
    • 时间有效性（Validity Period）： 当前时间必须落在 notBefore 与 notAfter 所构成的闭区间内（两端均包含，Inclusive）。[RFC 5280 §4.1.2.5]
    • 基本约束（Basic Constraints）： 链路中签发下级的 CA 证书必须具备 cA: TRUE；且其 pathLenConstraint（不计叶子证书，计算非自颁发的中间 CA）必须满足最大深度限制。[RFC 5280 §4.2.1.9]
    • 用途限制（Key Usage & EKU）： 若存在 Key Usage，CA 证书必须允许 keyCertSign；若存在 Extended Key Usage（EKU），其声明的用途必须允许当前 TLS 目标服务（例如仅带有 id-kp-emailProtection 邮件保护的证书不能充当服务端证书）；若两者同时存在，必须同时满足各自约束。[RFC 5280 §4.2.1.12]
    • 名称约束与关键扩展： 必须遵守上级 CA 施加的名称约束（Name Constraints）；遇到标记为关键（Critical）的未知扩展时必须拒绝该证书。[RFC 5280 §4.2.1.10]
    • 吊销状态检查（Revocation Status）： 检查证书是否已被 CA 吊销。若状态已证实为 revoked，连接必须拒绝；若因网络波动或服务不可用而无法获取证明，该状态属于未确定，是否继续取决于客户端配置的软失败（Soft-Fail）或硬失败（Hard-Fail）安全策略（详见早期的《证书吊销策略》）。

主机名校验：服务身份匹配与 SAN

即使上述全部路径验证 100% 完美通过，也不能单独证明当前通信是安全的！

设想这样一个场景：攻击者合法申请了一张属于他自己域名 evil.com 的正规证书。当你在浏览器中访问 bank.com 时，攻击者劫持了 DNS 并把流量导向他的服务器，并向你出示那张合法的 evil.com 证书。

  • 此时整条证书链都是真实的，根 CA 是受信任的，签名无误，时间有效，没有吊销。
  • 如果系统只做证书链验证，就会误以为连接完全可信！

这就是为什么主机名服务身份校验具有决定性否决权。[RFC 6125 §1.4]

RFC 6125 为基于 PKIX 证书验证 TLS 服务身份提供了通用指导（具体应用仍遵循自身上层协议规定）：[RFC 6125 §1.4] · [RFC 6125 §6]

  1. 使用者备用名称中的出示标识符与参考标识符比对：
    • 在 HTTPS 场景中，客户端根据用户期望访问的目标构造参考标识符（reference identifier），并将其与证书 subjectAltName（使用者备用名称，subject alternative name，SAN）扩展中出示的标识符（presented identifier，主要是 dNSName，即 DNS-ID）进行匹配。[RFC 5280 §4.2.1.6] · [RFC 6125 §6.4]
    • RFC 6125 §6.4.4 规定：如果证书出示的标识中包含了客户端支持的应用标识符类型（如 DNS-ID），客户端不应再回退检查 Common Name（CN）。
  2. 通用名称（CN）的历史回退限制：
    • 只有在出示的标识符中完全不包含客户端所支持的应用标识类型时，作为向后兼容历史实现的过渡手段，规范才允许在受限条件下检查 Subject 字段中的 CN。[RFC 6125 §6.4]
    • 依赖 CN 验证主机名是历史遗留做法，现代规范普遍建议迁移淘汰对 CN 的匹配。
  3. 通配符（Wildcard）的匹配建议：
    • 本文以完整最左标签的通配符作为保守匹配示例：.example.com 可匹配 foo.example.com，不跨级匹配 sub.foo.example.com；RFC 6125 §6.4.3 也允许客户端支持左标签内的部分通配（例如 baz.example.net），具体应用协议与客户端实现规则可更为严格。[RFC 6125 §6.4]

总结：决定信任的双重防线

在完整的 TLS 客户端实现中，信任判定需要双层防线共同闭环：

[接收服务器出示证书序列]
       |
       v
[步骤一：PKIX 证书链验证 (RFC 5280)]
  + 本地信任锚（Trust Anchor）带外对接
  + 待验证路径节点逐级验签
  + notBefore / notAfter 闭区间时间校验
  + cA 标志、pathLenConstraint 约束
  + 若有 EKU 须允许 TLS 目标用途；处理关键扩展
  + 吊销状态核验（根据已证实吊销阻断；未确定按既定策略决策）
       |  (验证不合规 -> 中止连接)
       v
[步骤二：服务身份匹配 (RFC 6125)]
  + 提取期望连接的完全限定域名 (FQDN)
  + 匹配 subjectAltName 中的 dNSName (DNS-ID)
  + (若无受支持标识类型，按历史规则受限回退 CN)
       |  (主机名不匹配 -> 中止连接)
       v
[信任达成：确认对端公钥合法有效且属于目标主机]

只有当密码学证书链验证与目标服务主机名身份双重校验全部通过，客户端才能确认对端预期服务所对应的公钥；在此基础上，握手过程还必须通过后续消息（如 TLS 1.3 的 CertificateVerify）证明对端确实持有该公钥对应的私钥，才能安全地建立完整信任关系。

参考资料与固定版本来源

  • RFC 5280 §3.2: Certification Paths and Trust
    D. Cooper, S. Santesson, S. Farrell, et al. Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile, May 2008. 阐明了证书路径与信任模型，明确信任锚在验证中的决定性起点地位。
  • RFC 5280 §4.1.2.5: Validity
    定义了证书有效期的判定规则，明确时间区间包含 notBefore 与 notAfter 两端。
  • RFC 5280 §4.2.1.6: Subject Alternative Name
    定义了使用者备用名称（SAN）扩展及其承载 dNSName 等标识符的规范格式。
  • RFC 5280 §4.2.1.9: Basic Constraints
    阐明了 cA 标志与 pathLenConstraint（不计叶子证书）在防止非 CA 证书越权签发中间链时的约束机制。
  • RFC 5280 §4.2.1.10: Name Constraints
    规定了上级 CA 施加的名称约束与处理关键扩展的要求。
  • RFC 5280 §4.2.1.12: Extended Key Usage
    规定了证书用途扩展若存在时的限制机制，明确 KU 与 EKU 须同时满足。
  • RFC 5280 §6.1: Basic Path Validation
    详细给出了 X.509 证书路径验证的形式化算法与递归校验状态机。
  • RFC 5280 §6.1.1: Inputs
    规定了路径验证的初始输入，包括候选路径与带外提供的信任锚信息。
  • RFC 6125 §1.4: Applicability
    P. Saint-Andre, J. Hodges. Representation and Verification of Domain-Based Application Service Identity within PKIX, March 2011. 界定了服务身份校验为通用指导、不取代既有特定应用协议规则的适用边界。
  • RFC 6125 §6: Verification of Identity
    规定了服务身份比对的通用原则。
  • RFC 6125 §6.4: Matching the Certification Path to the Service Identity
    详细规定了参考标识符与出示标识符的匹配规则（§6.4.3 通配符建议、§6.4.4 受支持标识类型存在时不应回退 CN 的规范要求）。
  • RFC 4158 §1: Introduction
    M. Cooper, Y. Dzambasow, P. Hesse, et al. Certification Path Building, September 2005. 说明了复杂 PKI 拓扑下的证书路径搜寻与多种候选构建机制。
  • RFC 6818 §1: Introduction
    P. Yee. Updates to RFC 5280, January 2013. 更新了自签名根证书与信任锚处理的规范要求。
