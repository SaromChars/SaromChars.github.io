邮箱迁移与网关切换

2022年1月19日
|

历史邮件复制完成之后，旧入口仍可能收到外来信件，用户也会在旧客户端上继续标记已读或移动目录。在自建或自研邮件系统的架构演进中，将存量邮箱搬迁至新存储并切换公网邮件交换记录，必须处理存储数据收敛与网络路由所有权转移的交错。

如果在状态转移窗口内未能界定写入权，或是网关转发流转中缺少对过滤链路的隔离，容易引发信箱状态分叉、邮件丢失、客户端缓存错乱以及重注入死循环。本文面向自建与自研邮件系统的工程师，梳理存储同步机制、状态标识边界、网关割接与控制面补偿设计。

存量邮箱增量追平与 UID 语义边界

邮箱数据迁移并非简单的底层文件复制。对于支持互联网邮件访问协议（Internet Message Access Protocol，IMAP）的系统，协议层状态与存储层标识紧密耦合。

根据 RFC 3501 第 2.3.1.1 节与第 6.3.1 节规定，IMAP 消息的唯一标识符（unique identifier，UID）并不是全局独立的，它被严格限定在特定的邮箱名与 32 位无符号整数——唯一标识符有效性（unique identifier validity，UIDVALIDITY）的作用域内。客户端在本地持久化缓存消息的 UID 映射时，前提是该邮箱的 UIDVALIDITY 保持不变。

一旦服务端的 UIDVALIDITY 发生变更，协议规定客户端必须废弃本地该邮箱的 UID 映射并重新同步。这并不意味着客户端必然无条件全量重新下载所有邮件体（具体行为取决于客户端自身的缓存与条件同步策略），但会引发大规模的元数据对齐与状态重核。在自研或自建目标系统时：

  • 正确处理代际变更：如果目标存储无法完全保持与源端一致的 UIDVALIDITY 和单调递增 UID 空间，应按协议规范分配新的 UIDVALIDITY 并让客户端重新对齐，而不应强行捏造一个表面相同但内部映射完全混乱的旧有效性标识。
  • 内部 GUID 与局部 UID 的分层：在 Dovecot 等系统内部，底层消息会拥有全局唯一标识符（global unique identifier，GUID）。IMAP UID 是特定文件夹视图下的单调递增序号，而工具（如 dsync）通过消息的 GUID 来识别不同存储端之间存在的 UID 冲突。
  • 避免用 Message-ID 作为全局去重键：RFC 5322 格式规范中的 Message-ID 头字段由发信客户端生成。在同一邮件被分发到多个文件夹、定时重试投递、或在不同文件夹间复制时，合法邮件拥有完全相同的 Message-ID 是常见现象。直接以 Message-ID 去重会导致合法邮件丢失。

在开源实现中，Dovecot 2.3.16 的 dsync 工具集（参见官方包手册 doveadm-sync(1) 与源码实现 doveadm-dsync.c）明确划分了同步语义：

  • 单向覆盖备份（doveadm backup）：执行单向同步。目标端独有的修改会被清除，使目标端严格拟合源端。在正式切写入前可用于全量基线铺底。
  • 双向合并同步（doveadm sync）：双向合并两端更改。
  • 增量单向合并（doveadm sync -1）：在源码 cmd_mailbox_dsync_parse_arg 中，-1 参数将 oneway 与 backup 均设为真，并在运行时通过 DSYNC_BRAIN_FLAG_NO_BACKUP_OVERWRITE 限制覆盖行为。手册明确指出其合并在实现上存在局限，仅作为“多次 backup 铺底、切断源端写流量后、在短暂窗口内把最后一批新信扫入目标端”的特定过渡手段，不可作为无限制的任意并发合并方案。手册举例说明：若源与目的两端各自生成了内容不同的 UID 6 邮件，系统可能为两封邮件重新分配更高的 UID 7 和 UID 8，以避免客户端对原有 UID 6 产生混淆；这说明即使两封信件都被保留，原有的局部 UID 身份也无法保证不变。

在增量同步算法上：

  1. 全量扫描（-f）：遍历所有文件夹与消息，计算完备但耗费 I/O；
  2. 快速同步（默认 fast 模式）：通过比较元数据中的 NEXTUID 与最高修改序号（highest modification sequence，HIGHESTMODSEQ）。若两端恰好发生等量异动，元数据可能显示相同数值而漏过具体变化；
  3. 状态化同步（-s）：传入前一次运行保存的状态标记。该状态代表内部状态机快照，并非单纯的单调递增 UID 水位。状态损坏或无法核对时，本方案停止推进，核实后再选择重新扫描或重建基线。在源码 cmd_dsync_run 中，若同步运行中实际检查到非预期的底层变动，系统会输出告警并设定退出码 2。

网关切换与流量残留控制

RFC 5321 第 5 节规定通过域名系统（Domain Name System，DNS）查询处理邮件交换记录（Mail Exchange record，MX 记录）的路由。切换设计还须考虑尚未到期的 DNS 缓存、已有简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）连接以及旧队列的重试目标；降低生存时间（Time to Live，TTL）不能撤回已经缓存的旧记录。同时，部分外部邮件传输代理（Mail Transfer Agent，MTA）可能持有尚未结束的 SMTP 长连接，或处于本地重试队列的投递周期中。因此，在 DNS 变更后的一段时间内，旧网关入口仍可能收到残留投递。

为了避免新旧存储同时承接写入造成状态分叉，系统必须在切换窗口内明确划分写入权：

  1. 清点所有写入口：不能仅寄希望于前端认证代理切为只读。必须全面拦截或冻结交互式 IMAP 标记与移动、客户端 SMTP 提交附带的已发送副本写入、入站投递以及后台定时任务。
  2. 切流排队与尾部同步：在执行最终增量对齐期间，新旧两套存储均应禁止业务写入。入口可持久接收后在本机队列暂存，也可在接受责任前返回 SMTP 4xx 由发送方保留重试；后者不是已进入本机队列。避免在已确认 250 OK（以 DATA 命令结束确认责任）后又假装未接收。最终同步完成前，不得将转发流量写入新存储。
  3. 放行新写入：验收确认后，将新存储设为权威读写端，恢复客户端交互认证，并逐步排空和转发旧网关暂存队列，严禁在最终底层同步仍在运行的过程中向新存储并发写入业务数据。

网关内容过滤与防循环架构

邮件网关通常集成了反垃圾邮件、反病毒与安全审计组件。新旧网关并行或多跳流转时，必须在拓扑上明确过滤职责，避免重复计算与投递死循环。

过滤路径明确化

在教学与工程设计中，通常选择让整封邮件只经历一次完整的内容安全检查。若旧网关已完成全套检测，仅在具备内网隔离、双向认证且具备可信审计证据的前提下，新网关才可考虑跳过扫描；若缺乏完备的受信审计凭据，不得仅凭信件头部声称的标记直接免检，通常更清晰的做法是将旧网关配置为纯中继，将过滤策略统一收拢到新网关执行。

队列后内容过滤防循环：以 Postfix 为例

以 Postfix 3.6.2 为例（参见包内文档 FILTER_README 中关于高级队列后过滤器的说明），邮件在初次入队后交给内容过滤进程，过滤完成的合规邮件需要通过本地回注监听端口重新提交给邮件系统。

在此类重注入链路中，必须显式重写配置以打断循环：

# 示例截取自 Postfix 3.6.2 FILTER_README 队列后过滤高级配置说明
# 仅供本机隔离链路参考，非完整生产部署模板
localhost:10026 inet  n       -       n       -       10      smtpd
    -o content_filter=
    -o receive_override_options=no_unknown_recipient_checks,no_header_body_checks,no_milters

参数原理解析：

  • 清空过滤配置（-o content_filter=）：主配置全局开启了内容过滤，若在回注端未显式清空该项，重新注入的邮件会被再次标记为待过滤，从而在队列与过滤器之间陷入死循环。
  • 覆盖选项设置（receive_override_options）：通过指定 no_milters、no_header_body_checks 与 no_unknown_recipient_checks，防止已完成检查的邮件被 Milter 应用程序或内置头部规则重复扫描。在该示例中不配置 no_address_mappings，以便在内容过滤完成后正常执行虚拟别名与地址映射展开。
  • FILTER 动作的优先级：文档特别强调，在访问表（access maps）或检查规则中触发的 FILTER 动作，其优先级高于静态配置的 content_filter。如果回注端的消息命中了带有 FILTER action 的访问映射，仍会再次强行指定过滤路由，引发死循环；此外，关闭 Milter 并不等同于关闭 content_filter。
  • 网络访问控制安全：回注端口通常放宽了常规客户端限制。如果未施加严格的本机监听绑定或网络访问控制列表，非授权客户端一旦向该端口发送邮件，将可能绕过安全检测规则，因此必须确保非授权来源无法连接该接口。

配置、数据模式与存储协议兼容

在版本跨度较大的迁移中，软件版本与元数据结构的演进需要平滑过渡。以下方案为工程教学设计，而非特定组件的原生强制机制：

  1. 配置指令与路由查询兼容：新旧版本之间常存在已废弃或新增的指令语法，直接复制配置文件易导致进程启动失败。用户目录服务在交替期应同时支持新旧字段查询，并能根据用户迁移状态正确返回其归属的主机路由。
  2. 数据库模式的扩展与收缩（Expand-Contract）：
    • 增加新特性字段时，新列应设计为可空或带有安全默认值，保持旧版本程序依然能够正常读取与写入；
    • 必须在旧队列责任全部交接、备份恢复经验证、旧程序退出且兼容与回退需求已关闭后，才安排独立窗口删除废弃旧字段与存储，在此之前须完成完整备份与回滚演练。
  3. 存储与索引元数据保全：存储格式迁移不仅要复制邮件体，更须完整保全 UID 映射、已读与标记（flags）状态、自定义关键字以及用户自定义元数据。部分私有状态直接持久化在专用索引或头文件中，一旦丢失将导致用户状态重置。

控制面迁移任务状态机与检查点设计

针对批量邮箱迁移，自研控制面应维护具备检查点（checkpoint）的任务状态机。

[Init: 初始化任务]
       |
       v
[Sync_Base: 冷数据全量基线铺底]
       |
       v
[Lock_Source: 冻结写权限与队列暂存]
       |
       v
[Sync_Tail: 最终增量对齐与校验]
       |
       v
[Cutover_Route: 激活新路由与放行读写]
       |
       v
[Observe_Completed: 监控长尾并收缩资源]

任务跟踪与幂等推进

控制面任务记录应包含唯一任务标识、账号标识、迁移方向、配置版本、尝试序号以及最后一次成功持久化的检查点位点。系统不能仅凭消息 GUID 假定多次重试完全等价；如果增量校验或执行发生失败，状态机不能自动退回 Sync_Base，否则可能导致单向覆盖备份误将业务数据冲掉。正确的做法是暂停在当前检查点，人工或补偿程序核对两端独有数据与同步方向后，再行有条件重试。只有当底层同步成功返回且元数据清单对齐无误后，控制面才向前提交检查点。

回退路由与数据恢复的边界界定

当割接遇到严重异常时，必须区分路由回退与数据恢复：

  • SMTP 责任转移原则：根据 RFC 5321 第 4.5.3.2.6 节与第 6.1 节，在 SMTP 会话中一旦服务端对 DATA 结束标记响应了 250 OK，投递责任便正式确立。新系统在接管期间收到的新邮件、用户产生的标记修改与删除操作，都已成为有效业务事实。
  • 避免破坏性直接覆盖：若新系统已承接流量并产生独立业务写入，直接使用割接前的旧快照覆盖新系统会导致切流期接收的数据全部丢失。如果必须回退，正确的做法是先冻结新系统写入，保全新系统产生的新邮件、标记异动与未结队列；在确认旧程序与数据模式能够安全解析的前提下，通过经过校验的逆向增量同步将数据合入旧端，或选择向前修复。若无法安全合并，应保持队列暂存，进入离线恢复流程。

阶段检查与判定边界

分阶段检查要点

  • 基线铺底阶段：验证源端与目标端各文件夹的 UIDVALIDITY 规划；核对用户目录服务对新旧路由的返回；检查存储写入权限与文件锁机制。
  • 切写前夕阶段：核对回注端口的 -o content_filter= 与安全访问控制；排查是否存在带有 FILTER action 的规则干扰回注；检查各服务组件配置文件语法。
  • 割接实施阶段：阻断源端交互式写操作；将旧网关配置为排队暂存或受控转发模式，但在最终同步完成前不得将转发流量写入新存储，只能转往受控暂存入口；执行尾部增量对齐，核对文件夹列表、UIDVALIDITY、UID 与消息内容的对应关系及单调分配（允许空洞）、抽样附件、关键字、访问权限、标记与删除状态及配额限制；切换认证与路由，放行新存储写入并结清暂存队列。
  • 观察收缩阶段：监控新网关队列健康度，确认无异常堆积；监控旧网关残留连接与长尾转发情况；在旧队列责任全部交接、备份恢复经验证、旧程序退出且兼容与回退需求已关闭后，才按计划收缩旧系统资源与废弃字段。

继续、暂停与终止边界

  • 终止切换：在执行尾部增量同步时，若发现源端仍有未隔离的写流量，或同步返回非零退出码且存在未解决的元数据冲突，必须终止切换，维持旧系统对外服务。只有在目标端未接管任何独有业务写入且保留排查证据的前提下，方可重置目标端测试数据。
  • 暂停推进：网关切换后，若发现队列出现非预期堆积或重复转发迹象，应立即暂停公网继续流入，将邮件保持在前端排队缓冲，排查过滤配置与回注链路。
  • 回退决策：若新系统承接流量后发生不可恢复的故障，须先封锁新端写入，保全已落盘邮件与队列，确认数据具备合并或归档条件后，再执行受控路由回退。

模拟验证场景设计

以下案例为工程架构验证设计，用于在测试演练环境中核对边界条件，非生产实际执行实录。

场景一：验证队列后内容过滤防死循环配置

  • 测试环境：单机部署 Postfix 3.6.2，配置高级队列后过滤，过滤完成后由 127.0.0.1:10026 回注。
  • 人为注入故障：在 localhost:10026 服务定义中故意省略 -o content_filter=。
  • 预期现象与检查方法：向系统注入一封测试邮件。由于回注时 SMTP 实例仍继承全局过滤参数，邮件将被反复投递给过滤器。检查时应注意：SMTP 重注入通常会生成新的队列标识（Queue-ID），因此不能仅靠单一队列 ID 判重，而应通过关联前后队列日志、自定义测试标记或特定信封属性观察重复入队事件。在配置修复并重新加载后，仅针对隔离的测试邮件路径进行复验，确认邮件经单次扫描后正常送达。

场景二：验证并发变更下的 UID 编排现象

  • 测试环境：部署源与目的两套 Dovecot 2.3.16 实例，源端包含 UID 1..5。
  • 构造冲突操作：执行 doveadm backup 铺底后，模拟在源端写入新邮件（分配 UID 6），同时在目的端直接写入一封不同内容的消息（同样分配 UID 6），随后运行 doveadm sync -1。
  • 预期现象与检查方法：检查目标端邮箱状态。根据手册说明，两封邮件预期均会被保全，但系统可能为冲突邮件分配更高的 UID（如 UID 7 和 UID 8），原有 UID 6 映射不再保持原样。使用 IMAP 测试客户端重新连接并同步，检查客户端能否依照协议标准正确处理新的 UID 映射，验证两端在缺乏互斥锁定时的状态收敛行为。

场景三：数据模式不兼容时的回退阻断

  • 测试环境：自研存储服务升级，新版本引入了扩展字段与新的状态编码。
  • 构造异常：新程序接管后写入了包含新字段的数据，此时因上游故障需紧急回退至旧版本程序，但旧程序遇到无法识别的数据模式直接崩溃或抛出解析异常。
  • 预期判据：遇到数据模式不兼容时应立即阻止盲目回退旧版本程序；数据修补必须具备离线验证与备份支持，不能直接运行未经演练的修复脚本盲目修改数据。
