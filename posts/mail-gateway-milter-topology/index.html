反垃圾邮件网关的拓扑与 Milter 接入设计

2021年12月8日
|

邮件传输代理（mail transfer agent，MTA）在简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）会话中，收到 DATA 传输结束标记并给出最终 250 OK 应答时，正式接管对该邮件的可靠交付责任。依 RFC 5321 第 4.2.5 节与第 6.1 节规定，接收端一旦给出该应答，就不能再在传输层对原会话直接拒收，后续故障只能由本方承担转递、隔离或退信责任#。

网关规划需要区分物理机器布局与接受责任时机两个正交维度。

公网前置网关与同机扫描是机器物理拓扑的部署选择；队列前（before-queue）与队列后（after-queue）则是 SMTP 接受责任确认的时机选择。在部署工程取舍上，公网前置网关独立承接公网连接与扫描负载，但需要维护受控的下游安全投递链路；同机扫描则可通过本地套接字直接交互减少网络传输开销，但扫描进程与 MTA 共享 CPU、内存和故障边界，两者都不能凭机器物理布局直接决定 SMTP 接受时机。

队列前判定发生在向外部返回最终 250 OK 之前，临时失败或拒绝仍由外部客户端负责调度；队列后判定则在邮件存入本方主队列之后异步进行，由本方全权负责后续流转。

队列前过滤与 Milter 的机制差异

邮件过滤协议（mail filter protocol，Milter）与透明 SMTP 代理过滤器（如 Postfix 的 smtpd_proxy）或队列后内容过滤器经常被混淆，但三者责任时机与交互方式截然不同###。

smtpd_proxy 在外部客户端与后端接收进程之间透传 SMTP 会话，在客户端发送正文结束标记后等待后端同样返回 250 再透传给客户端。这种方式同属队列前判定，但在外部连接较多时，长时间阻塞的检查会占用前端工作进程。队列后 content_filter 彻底解耦入站会话与内容检查，入站进程先将邮件落盘至队列并返回 250 OK，再异步交给扫描器处理。其代价是后续一旦决定拦截，外部会话早已结束，发送退信容易引发反散射（backscatter）垃圾邮件，静默丢弃则使发信方无法获知状态。

Milter 机制由 MTA 在驱动会话状态机时，通过结构化协议与独立过滤进程同步通信#。队列前 Milter 允许在会话进行中细粒度介入，并借助底层队列清理服务修改内容与邮件头，所有判定均在向客户端返回最终 250 OK 之前完成。需要说明的是，Postfix 在队列前阶段也可以预先将邮件写入暂存队列文件，队列前过滤并不等同于系统在处理期间完全不触碰磁盘。

队列后拓扑的防护与重注入

当因深度沙箱或反病毒分析而必须采用队列后过滤时，重注入链路必须严格受控，防止邮件循环过滤或服务沦为开放中继（open relay）。

在典型队列后拓扑中，邮件流经入站 smtpd、入队、派发至扫描进程，再由专用端口重注入 MTA。为避免已扫描邮件被重复处理，工程上不能仅依赖邮件中添加的自定义头信息来判断跳过，因为外部发件人可伪造相同头部。通常在服务配置中为重注入设立独立端口，并限制接入源：

# 内部重注入监听端点示意（仅供隔离参考）
127.0.0.1:10025 inet n n n - - smtpd
    -o content_filter=
    -o smtpd_milters=
    -o mynetworks=127.0.0.0/8
    -o smtpd_client_restrictions=permit_mynetworks,reject
    -o receive_override_options=no_unknown_recipient_checks,no_header_body_checks

该端点通过清空 content_filter 与 Milter 配置避免二次过滤，同时限定来源网络为本机回环地址。需要注意，receive_override_options 仅跳过其明确指定的检查项，其他规则仍需核对；同机回环监听也不等同于基于进程维度的身份认证，本机非受信程序仍须通过系统权限与网络命名空间进行隔离。

跨跳流转时，必须保留原始连接的远程客户端 IP 地址。如果内部扫描进程直接以本机地址重注入，发送方策略框架（Sender Policy Framework，SPF）评估将因客户端 IP 变为回环地址而得出错误结论；虽然域密钥识别邮件（DomainKeys Identified Mail，DKIM）依赖邮件头与正文签名而不受网络跳数影响，但丢失原始 IP 会破坏日志审计与限速。跨跳传递真实 IP 可使用受控的 XFORWARD 命令（仅对受信任的扫描端开放）或受信元数据通道，外来 Received 头不能直接证明来源。同样，依据 RFC 8601 第 5 节与第 7 节关于信任边界的规定，跨跳传递认证结论时，不能因邮件头存在 Authentication-Results 或特定标识就盲目信任，必须由 MTA 显式校验并剥离不可信边界外的注入字段#。

Postfix Milter 的生命周期与源码实现

在 Postfix 3.6.2 源码树中，MTA 端对 Sendmail 8 Milter 协议的驱动位于 src/milter/milter8.c，内容修改支持位于 src/cleanup/cleanup_milter.c##。

MTA 在 milter8_connect() 函数中与过滤器建立连接，并通过 SMFIC_OPTNEG 命令包协商协议版本、允许请求的修改动作掩码（rq_mask，如 SMFIF_ADDHDRS、SMFIF_CHGBODY）以及事件掩码（ev_mask）。在会话推进中，smtpd 收到 MAIL 或 RCPT 后经 milter_mail_event 与 milter_rcpt_event 分派到 milter8_mail_event 与 milter8_rcpt_event，再调用 milter8_event 打包事件并处理响应。随后由 milter8_header 与 milter8_eoh 分别发送头字段和头结束事件：

/* 源码文件路径：src/milter/milter8.c */
static const char *milter8_event(MILTER8 *milter, int event,
                                 int skip_event_flag, int skip_reply,
                                 ARGV *macros, ...)

进入正文阶段后，milter8_message() 通过多用途互联网邮件扩展（Multipurpose Internet Mail Extensions，MIME）回调处理数据。正文内容由 milter8_body() 接收并推送到 SMFIC_BODY。受单次最大 65535 字节的缓冲区限制，正文以分块形式流式传递，过滤器接收到的是连续数据块而非装配完毕的 MIME 对象。正文结束时的真实回调符号为 milter8_eob（源码中不存在 milter8_eom 函数符号）：

/* 源码文件路径：src/milter/milter8.c */
if (LEN(milter->body) > 0) {
    skip_reply = ((milter->ev_mask & SMFIP_NR_BODY) != 0);
    msg_ctx->resp =
        milter8_event(milter, SMFIC_BODY, SMFIP_NOBODY,
                      skip_reply, msg_ctx->eod_macros,
                      MILTER8_DATA_BUFFER, milter->body,
                      MILTER8_DATA_END);
    if (MILTER8_MESSAGE_DONE(milter, msg_ctx))
        return;
}
msg_ctx->resp =
    milter8_event(msg_ctx->milter, SMFIC_BODYEOB, 0,
                  DONT_SKIP_REPLY, msg_ctx->eod_macros,
                  MILTER8_DATA_END);

该函数先将残存的正文数据块刷新发送，再发送代表正文结束的 SMFIC_BODYEOB，并等待过滤器返回最终决定。

过滤器返回的指令具有严格的阶段范围与语义边界：

  1. SMFIR_ACCEPT：在 milter8_event 内部，该指令将当前 Milter 实例状态置为 MILTER8_STAT_ACCEPT_MSG（连接阶段为 ACCEPT_CON），仅表示该过滤器不再接收本消息的后续事件，并不代表系统立即放行，后续其他 Milter 仍按序执行。
  2. SMFIR_CONTINUE：放行当前事件，继续等待下一阶段。
  3. SMFIR_REJECT 与 SMFIR_TEMPFAIL：在 RCPT 阶段返回时仅代表对当前单个收件人执行拒绝或临时失败，未被拒绝的收件人会话仍可继续推进；在连接阶段返回可影响后续连接命令，在正文结束阶段返回则作用于当前邮件。
  4. SMFIR_QUARANTINE：Milter 返回隔离请求时附带原因说明，Postfix 将其内部置为 "H"，在入队时将队列记录置于暂挂（hold）状态等待运维介入，这只是队列标记，不等于提供完整的隔离区检索与释放功能。
  5. SMFIR_DISCARD：若在此前无其他拒绝动作，MTA 在消息结束（end of message，EOM）阶段接收该指令后会向客户端正常回复 250 OK，并在内部静默丢弃该邮件。系统日志中仍会记录队列 ID 及丢弃事件（如 milter-discard），并非完全无痕，但在排查时发件方通常无法获知丢弃状态。

在正文结束阶段若需要修改头部或正文（SMFIR_CHGHEADER、SMFIR_REPLBODY 等），milter8.c 通过父级接口调用 src/cleanup/cleanup_milter.c 中的函数就地修改队列记录结构。

对于非 SMTP 途径提交的邮件（如本地 sendmail 命令或 qmqpd），Postfix 提供了 non_smtpd_milters 支持。这些邮件由 cleanup 服务模拟 CONNECT、HELO、MAIL 等事件。需要注意的是，在模拟收件人事件中，Milter 若返回 SMFIR_REJECT 或 SMFIR_TEMPFAIL，Postfix 3.6.2 会将其视为服务配置错误并记录警告保留在队列中，而不能像 SMTP 交互那样直接退信拒收。

过滤服务接口与异常处理

在开发自研过滤分析微服务时，直接解析底层 Milter 帧较为繁琐。这是自研服务内部接口示意，不是 Milter 原生帧或现成 API：

// 过滤服务输入上下文示意
struct InspectionRequest {
    string connection_id;      // 会话跟踪标识
    string transaction_id;     // 事务跟踪标识
    string client_ip;          // 连接事件解析的对端地址
    string envelope_sender;    // 信封发件人
    list<string> envelope_rcpt;// 信封收件人列表
    bytes body_chunk;          // 流式正文数据块
    bool is_body_eof;          // 正文结束标志
    int processing_budget_ms;  // 本级处理超时预算
    string policy_version;     // 当前生效策略版本号
}

// 过滤服务输出决策示意
struct InspectionDecision {
    enum Action { CONTINUE, ACCEPT, REJECT, TEMPFAIL, DISCARD, QUARANTINE } action;
    string smtp_reply_code;    // 自定义 SMTP 应答码
    list<HeaderEdit> edits;    // 邮件头修改操作
    list<string> reason_codes; // 规则命中编号
}

在异常处理设计中，外部连接断开或发信方重置时，过滤引擎不一定能收到明确的 SMFIC_ABORT（MTA 在特定状态下会跳过发送或直接以 QUIT 断开）。服务必须在检测到套接字关闭或收到重置时主动清理当前事务分配的内存与暂存文件，避免状态污染下一事务。同时，协议宏（如 {auth_authen}）仅在 MTA 显式提供且完成对应验证时才存在，过滤器不应依赖未配置的宏，更不能从易被伪造的邮件头中反推连接属性。

故障矩阵与超时管理

故障场景责任归属与表现
队列前超时原发送端重试
队列前 accept网关接收
队列前 quarantine网关 hold
队列后扫描暂时失败网关原队列重试
队列后重注入应答丢失重注入侧状态不确定

表中的 accept 与 quarantine 只表示该过滤器的处理；网关还须完成其余检查和持久化，才能最终确认接收。

队列前超时默认返回 4xx 临时失败由原发送端调度重试，配置为 accept 则由网关承担漏检风险，quarantine 则由网关接收后存入暂挂队列。在队列后场景中，扫描暂时失败要求扫描器尚未向原投递代理确认接管，邮件才得以保留在本地主队列中持续重试；若重注入已提交但确认应答丢失，发送端在状态不确定时重投可能产生重复邮件，系统无法保证严格的恰好一次递送。

Postfix 3.6.2 官方文档中给出的默认超时参数如下#：

milter_connect_timeout = 30s
milter_command_timeout = 30s
milter_content_timeout = 300s

内容检查超时 milter_content_timeout 并非整封信件的总耗时预算，而是单次内容交互等待的最长时限。工程设计中应结合整体容量与对端客户端的等待时限分配有界的子预算，并在超时后主动放弃计算，确保迟到的判定结果不会修改已经完成的事务状态。在网关向客户端发出最终 250 OK 之后，依照 RFC 5321 第 4.2.5 节的要求，不能再回溯修改该连接的应答#。

教学验收方案：模拟扫描器无响应（未执行）

为了验证网关在服务故障时的容灾逻辑，设计如下未在生产环境中实际执行的推演方案：

在队列前验证中，搭建一个能够正常完成协议协商与信封事件处理、但在收到 SMFIC_BODYEOB 后故意不返回任何应答的测试桩服务。使用客户端发起投递，观察前置 MTA 在超出 milter_content_timeout 后是否向客户端返回 451 4.7.1 Service unavailable - try again later。检查确认该事务未获得最终 250 OK 且未被正常调度投递（暂存工作文件可能存在，但不应生成正规投递任务）。

在队列后验证中，配置 Postfix 将邮件派发至停止应答的后端扫描端口。由于扫描器在确认接管前未向原队列投递进程确认，MTA 将邮件保留在原队列中，并在日志中持续记录投递代理连接超时的报警，验证邮件在故障期间未丢失且维持原队列重试。若扫描器设计为提前确认接管，则由扫描器自身承担持久化存储与恢复责任。

在恢复与状态防重验证中，恢复扫描服务并使其将邮件重注入到专用端口。观察重注入端口接收该邮件后顺利流转至下游投递阶段，且日志显示其未再次触发外部内容检查。恢复后原队列与新队列的事务可通过受控的元数据与日志进行映射关联。
