DMARC 的身份对齐与报告机制

2021年9月15日
|

在电子邮件体系中，发件人策略框架（Sender Policy Framework，SPF，RFC 7208）与互联网域名密钥识别邮件（DomainKeys Identified Mail，DKIM，RFC 6376）分别提供了基于域名的验证能力。然而，在实际运行中，这两种协议与终端用户在邮件客户端中所感知的身份之间存在显著脱节。

SPF 验证的是简单邮件传输协议（Simple Mail Transfer Protocol，SMTP，RFC 5321）信封阶段声明的反向路径（Reverse-path，即 MAIL FROM）或 HELO / EHLO 主机名；DKIM 验证的则是对邮件头部与正文生成数字签名的签名域（即 DKIM-Signature 头部字段中的 d= 标签）。这两种机制校验的域名通常位于信封或隐藏的信件头部中，普通邮件用户代理（Message User Agent，MUA）展示给收件人的却是邮件内容头部中的 From: 地址，其域名部分即符合 RFC 5322 规范的邮件作者域（Author Domain）。

攻击者完全可以使用自己控制的合法域名完成 SPF 授权或 DKIM 签名，而在可见的 From: 头部伪造受信任品牌的域名。

此外，在缺乏反馈渠道的情况下，域所有者（Domain Owner）难以获知外部网络对其域名的冒用情况，也无法向接收方传达统一的失败处置偏好。

为了防范可见发件人伪造并建立发信策略与反馈闭环，2015 年 3 月发布的 RFC 7489《Domain-based Message Authentication, Reporting, and Conformance (DMARC)》（基于域的消息认证、报告与一致性，DMARC）定义了身份对齐（Identifier Alignment）、策略发布与报告反馈框架。需要说明的是，RFC 7489 属于信息性备忘录（Informational Memo），并非 IETF 正式标准（Standards Track）。

可见 From 与身份对齐

DMARC 机制的核心立足点，是将 MUA 展示给终端用户的 RFC 5322 From: 域作为首要评估标识（Primary Identifier，RFC 7489 第 1 与 3.1 节）。这是因为在符合规范的邮件中，From: 头部是必须存在且通常由客户端显著渲染给用户的来源依据。

1. DMARC 通过条件

DMARC 本身并不发明新的底层密码学签名或网络传输协议，而是直接建立在 SPF 与 DKIM 的验证输出之上。RFC 7489 第 4.2 节规定：

一封邮件若要在 DMARC 检查中获得通过（pass），SPF 或 DKIM 中至少一种机制须同时满足以下两个条件：

  1. 该机制产出 pass 验证结果；
  2. 产出该结果的底层验证标识与 RFC 5322 From: 域处于身份对齐（in alignment）状态。

简而言之，只要 (SPF pass 且 SPF 标识对齐) 或者 (DKIM pass 且 DKIM 标识对齐) 中有一项成立，邮件即通过 DMARC 检查；若两项均未达成有效对齐通过，则视为 DMARC 机制检查失败。若单封邮件带有多个 DKIM 签名，只要其中任意一个签名通过验证且与 From: 对齐，即可使 DKIM 分支获得通过（第 3.1.1 节）。

2. 组织域（Organizational Domain）概念

在评估对齐之前，首先必须确定域名的层次边界。根据 RFC 7489 第 3.2 节，组织域（Organizational Domain）指的是在顶级域名注册层次下确定的基准实体域（如 example.com 或 example.co.uk）。其计算算法依赖于维护一份公共后缀列表（Public Suffix List，PSL）：

  1. 将待判定的完全限定域名（Fully-Qualified Domain Name，FQDN）从右向左按点号拆分成标签（例如 a.b.news.example.com 中 com 为第 1 标签，example 为第 2 标签）；
  2. 在公共后缀列表中匹配出最长后缀（假设匹配到长度为 x 的 com 标签）；
  3. 取该匹配后缀及其左侧紧邻的第 x+1 个标签，拼接构成组织域（即 example.com）。
Note

RFC 7489 第 3.2 节特别指出，公共后缀列表在当前体系中属于启发式（Heuristic）方案，没有任何单独列表能保证绝对实时或准确。

3. 严格对齐与宽松对齐

DMARC 允许域所有者为 SPF 和 DKIM 分别配置对齐模式：宽松模式（Relaxed Mode，r，默认值）与严格模式（Strict Mode，s）。域名比较遵循域名系统（Domain Name System，DNS）规则，不区分大小写（第 3.1 节）。

认证类型对齐模式对齐要求（与 RFC 5322 From 比较）典型场景示例（From 为 user@news.example.com）结果
SPF宽松（aspf=r）认证域与 From 具有相同的组织域MAIL FROM 为 bounces@news.example.com 或 bounces@example.com对齐（pass）

在 SPF 评估中，DMARC 使用的是 SMTP MAIL FROM 声明的身份；如果遇到系统退信导致 MAIL FROM:<> 为空反向路径，则依照 RFC 7208 规则退回使用 HELO / EHLO 域名作为 SPF 评估对象（RFC 7489 第 3.1.2 节）。

DMARC 记录格式与策略发现流程

域所有者通过在 DNS 中发布特定前缀的 TXT 资源记录（Resource Record，RR）来声明自身策略。

1. 策略记录标签语法

DMARC 记录使用类似 DKIM 的 tag=value 分号分隔键值语法，统一发布在 _dmarc.<domain> 节点上。

_dmarc.example.com. IN TXT "v=DMARC1; p=quarantine; sp=reject; pct=100; rua=mailto:dmarc-reports@example.com!10m; aspf=r; adkim=s"

RFC 7489 第 6.3 节定义的核心标签规范如下：

  • v=DMARC1（必须，REQUIRED）：版本声明。其值必须严格等于 DMARC1，且必须作为记录的首个标签出现。若版本不符或缺失，整条记录必须被直接忽略。
  • p=（策略记录中必须，REQUIRED）：域所有者向邮件接收端（Mail Receiver）请求的处置策略。可选值包括：
    • none：仅监控与收集反馈，不请求接收端对信件采取特殊处置；
    • quarantine：请求接收端将未通过 DMARC 的信件视为可疑（如投递至垃圾箱、强化安全审查或添加风险标记）；
    • reject：请求接收端在 SMTP 会话期间拒绝该信件（SHOULD）。
  • sp=（可选，OPTIONAL）：专门针对该域之下所有子域（Subdomains）的策略。若未显式指定，子域默认继承 p= 所声明的策略。
  • pct=（可选，OPTIONAL，默认 100）：策略应用的流量百分比（取值 0 到 100 的整数），用于灰度渐进式部署。接收端不得（MUST NOT）将请求的策略实施在超过指定百分比的受影响邮件上（第 6.6.4 节）。对于因采样未命中 quarantine 的邮件，接收端应当应用本地常规分类；若处于 reject 策略下未被采样的部分，则应当（SHOULD）降级为 quarantine 处理，而非直接放行。无论百分比为何值，所有相关流量均必须计入实际生成的反馈报告。
  • rua=（可选，OPTIONAL）：聚合报告（Aggregate Report）接收地址列表，以逗号分隔的 URI（如 mailto:）。rua 为指定报告目的地的标签。
  • ruf=（可选，OPTIONAL）：失败报告（Failure Report）接收地址列表。失败报告由 fo 标签控制触发选项，接收端仅在愿意支持时生成，且因可能包含单封邮件头及正文片段而涉及隐私，通常作为调试参考。
  • adkim= 与 aspf=（可选，OPTIONAL，默认 r）：分别定义 DKIM 与 SPF 的对齐模式，可选 r（宽松）或 s（严格）。
  • ri=（可选，OPTIONAL，默认 86400）：请求的聚合报告发送间隔秒数。接收端必须能够支持每日报告（MUST），并尽量支持每小时报告（SHOULD）。

2. 策略发现算法（Policy Discovery）

当接收端邮件传输代理（Message Transfer Agent，MTA）解析出一封邮件的 RFC 5322 From: 域为 sub.mail.example.com 时，必须按 RFC 7489 第 6.6.3 节定义的层级顺序检索 DNS：

                提取 RFC 5322 From 域名
                         |
                         v
             查询 _dmarc.sub.mail.example.com
                         |
                         v
                过滤非 v=DMARC1 记录
                         |
             +-----------+-----------+
             |                       |
       过滤后集合非空?         过滤后集合为空 (0 条)
             |                       |
             |                       v
             |            计算组织域: example.com
             |            (若与 From 相同则不回退)
             |                       |
             |                       v
             |            查询 _dmarc.example.com
             |                       |
             |                       v
             |              过滤非 v=DMARC1 记录
             |                       |
             +-----------+-----------+
                         |
                         v
                检查剩余记录集合数量
                         |
        +----------------+----------------+
        |                |                |
     正好 1 条        多于 1 条         0 条
        |                |                |
        v                v                v
   解析策略标签      终止发现(不执行)  终止发现(不执行)
        |
   +----+--------------------------+
   |                               |
p/sp 有效                   p/sp 语法无效
   |                               |
   v                               v
正常应用策略             rua 存在有效 URI?
                        +----------+----------+
                        |                     |
                      是 (SHOULD 视作)        否
                        v                     v
                   v=DMARC1; p=none       终止发现(不执行)
  1. 发起初次精确查询：接收端首先发起 DNS TXT 查询 _dmarc.<from-domain>；
  2. 记录有效性过滤：丢弃不以 v=DMARC1 开头的记录；
  3. 空集合组织域回退：若过滤后的记录集合为空，且该域不同于其组织域，接收端必须（MUST）查询其组织域对应的 _dmarc.<organizational-domain>（例如 _dmarc.example.com），并同样丢弃不以 v=DMARC1 开头的记录；
  4. 数量判定与终止：若剩余集合中包含多条记录或零条记录，策略发现终止，不对该邮件执行 DMARC 策略；
  5. 策略有效性与 rua 容错处理：若恰好保留一条记录，接收端检查其 p（或适用于子域的 sp）标签。若标签有效则正常应用；若记录缺失有效 p 标签或包含无效 sp 标签：
    • 当该记录包含至少一个语法有效的 rua URI 时，接收端应当（SHOULD）将该记录视同包含有效版本声明与 p=none 并继续处理；
    • 否则终止策略发现，不对该邮件执行 DMARC 处理（第 6.6.3 节第 6 步）。
  6. DNS 临时错误处理：若在查询中遇到超时或服务器暂时失效等 DNS 临时错误，由接收端本地策略决定放行（fail open）或返回 SMTP 451/4xx 临时错误推迟重试（fail closed），并不等同于记录不存在。

报告机制与跨域授权验证

DMARC 提供了反馈机制，用于汇总接收端观察到的认证结果与处置情况。其中，聚合报告汇总周期内的批量统计。

1. 外部报告目标与滥用防护

域所有者常常委托第三方专业 SaaS 服务商收集并分析 DMARC 报告。例如，域名 blue.example.com 在其 DMARC 记录中声明：

rua=mailto:reports@red.example.net

如果接收端不加校验地直接向 reports@red.example.net 发送聚合报告，恶意域所有者可通过将 rua 指向受害者邮箱并发起大量失败邮件，利用接收端的报告投递形成反射泛洪。

2. 外部目标授权验证步骤

为了防止此类报告泛洪，RFC 7489 第 7.1 节规定，通常应通过 DNS 流程验证外部授权（除非接收端已有可信的本地外部报告授权清单等独立安排）。当实际检索到策略记录的域（如 blue.example.com）其组织域与接收报告目标 URI 主机的组织域不一致时，接收端执行以下检验流程：

  1. 提取目标 URI 中的主机部分作为目标主机（例如 red.example.net）；
  2. 构造特定验证域名：<policy-domain>._report._dmarc.<destination-host>。例如： 
    blue.example.com._report._dmarc.red.example.net
  3. 查询该域名的 DNS TXT 记录，并过滤出以 v=DMARC1 开头的记录；
  4. 授权判定：
    • 若返回有效记录，表明报告接收方（red.example.net）显式确认愿意接收该策略域的报告，授权成立。若确认记录中包含 rua / ruf，可在保持目标主机相同的前提下覆盖报告目的地；
    • 若未通过校验或无有效记录，外部授权未确认，接收端必须（MUST）丢弃该 URI，不得向其投递报告。
  5. 通配符支持：专门提供 DMARC 报告代收的服务商可在 DNS 中发布通配符记录以接收任意外部域名的报告（RFC 7489 第 7.1 节）： 
    *._report._dmarc.red.example.net. IN TXT "v=DMARC1"

3. 聚合报告的内容结构

聚合报告通常以 XML 格式生成并经 GZIP 压缩后通过电子邮件（mailto:）发送。RFC 7489 附录 C 定义了报告的 XML Schema，其包含的关键数据节点如下：

  • 元数据（report_metadata）：报告生成者组织名称、报告编号（report_id）、涵盖的时间区间（起始与结束 Unix 时间戳）；
  • 策略声明（policy_published）：记录实际检索到策略记录的域（domain）及公布的策略参数（p、sp、pct、adkim、aspf 等）；
  • 记录明细（record）：
    • 行统计与策略评估（row）：发信源 IP 地址、匹配该结果的消息数量（count），以及 policy_evaluated 节点。policy_evaluated 中包含依据 DMARC 实施的处置动作（disposition：none / quarantine / reject）、对齐后的认证结果（dkim 与 spf 的 pass / fail 状态），以及可选的策略覆盖原因（policy_evaluated/reason，内含覆盖类型 type 与可选说明 comment）；
    • 评估标识（identifiers）：邮件头部中的 header_from（RFC 5322 From）；
    • 原始认证结果（auth_results）：记录底层机制未经对齐约束的原始输出，包括 DKIM 验签域、选择符及原始结果（pass / fail 等）；SPF 评估域及原始结果。

边界限制、例外与工程实践

DMARC 主要用于约束直接冒用 RFC 5322 From 域名的邮件伪造，但在实际互联网邮件流转中存在固有的协议限制与处置例外。

1. 邮件列表与转发

在邮件中继与列表分发场景中，DMARC 面临天然的互操作性限制（RFC 7489 第 10.5 节）：

  • 转发对 SPF 的影响：当邮件经由第三方服务转发时，中间服务器的 IP 通常不在原 MAIL FROM 域的 SPF 授权列表中，导致接收端对原域的 SPF 评估失败；即使转发服务器使用自身域名改写信封并获得 SPF 通过，该域名通常与原作者域不同，无法达成 SPF 身份对齐；
  • 邮件列表对 DKIM 的影响：邮件列表若改变了签名实际覆盖且规范化后仍有差异的头字段或正文内容，可能使原 DKIM 验签失败；仍有其他对齐有效签名时，DKIM 分支仍可通过。

若原发件域发布了 p=reject 策略且两项机制均无法对齐通过，严格实施 DMARC 的接收端可能会拦截此类合法信件。从机制上推导，列表若将可见 From: 改为自己的域，并用自身对齐身份认证，可能绕开原作者域对齐失败；这会改变可见作者身份，属于有条件的工程折中，并非 RFC 7489 已证明的通行部署。

2. 接收端策略覆盖（Policy Override）与本地偏好

在协议规范中，接收端对 DMARC 策略的执行具有明确的弹性空间：

  • RFC 7489 第 6 节明确规定：邮件接收端应当尽力（SHOULD make a best-effort attempt）遵循域所有者发布的策略；但在复杂的邮件流场景下，接收端可以偏离（MAY deviate）发布的策略，并应当（SHOULD）在聚合报告中通过 policy_evaluated/reason 向发件域反馈偏离事实与原因（如发件人已在本地可信列表、启发式识别转发等）；
  • 最终处置权归属于接收端本地安全策略（第 6.7 节）。DMARC 通过并不能证明信件绝对安全，接收端可以（MAY）因本地反垃圾防病毒引擎判定而隔离或拦截通过 DMARC 的邮件；反之，即便 DMARC 失败且标记为 reject，接收端在特定场景下仍可能根据本地信任策略接受邮件。

3. SMTP 同步拒绝与回散射防护

对于未通过 DMARC 且策略为 reject 的邮件，RFC 7489 第 6.3 与 10.3 节强调：拒绝操作应当（SHOULD）在 SMTP 事务期间同步完成（例如直接返回 550 5.7.1 永久拒绝错误码）。

若接收端先在会话中接受信件，随后在投递阶段再异步生成投递状态通知（Delivery Status Notification，DSN），一旦信封中的反向路径地址被攻击者伪造，退信将投向无辜第三方，形成垃圾退信反弹（即回散射，Backscatter）。若接收端采用静默丢弃（Silent Discard，返回 250 伪造成功后丢弃），虽然阻断了回散射，但会给发件方的合法调试排查带来困难。
