隔离邮件的释放与申诉

2022年1月9日
|

在反垃圾邮件网关与自研邮箱系统的开发中，控制台显示“释放成功”并不意味着邮件已经落入收件人邮箱。当下游邮件传输代理（Mail Transfer Agent，MTA）队列积压、网络超时、目标账号停用或网关重启时，若把请求受理当作最终投递，系统容易发生重复外发、邮件丢失或状态失真。

本文以教学自研邮件网关为背景，推导隔离邮件从暂存、申诉、审批、入队到下游投递的状态流转与一致性边界。文中所述方案属于接口与状态机层面的工程教学推导，并非开源过滤引擎 Rspamd 等工具的原生完整隔离产品能力，也不涉及特定开源软件未核实的内部源码细节。

隔离暂存责任与数据模型

当邮件网关在简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）的 DATA 阶段结束并向对端返回 250 OK 响应时，依据 RFC 5321 第 6.1 节的规定，接收方 MTA 即承担了递送或转发该邮件的持久责任（第 6.2 节对判定为恶意的邮件保留了特殊处理边界）。本设计要求网关在发出 250 OK 前，必须将原始邮件内容写入持久对象存储生成不可变二进制大对象（Binary Large Object，BLOB）引用及校验摘要，并连同信封元数据和可恢复的处理意图一并写入数据库。

邮件进入网关后的处置策略有多种工程选项。在协议会话期间，网关可根据策略返回 5xx 永久拒收，或因临时依赖不可用返回 4xx 临时错误；对边缘可疑邮件，网关可选择投递至用户邮箱的垃圾箱文件夹；而对命中合规拦截或高危特征的邮件，系统可将其移入集中隔离库。

在数据建模上，不能以邮件标头中的 Message-ID 字段作为数据库主键或唯一约束，因为该标头可被发件人伪造、复用或省略。一份原始邮件 BLOB 可能对应多个信封收件人，存储引用必须与收件人维度的处理生命周期解耦。整个模型拆分为三类核心实体：

  1. 隔离收件项实体（QuarantineItem）：主键为 (tenant_id, item_id)，记录所属租户、单一信封收件人、目标邮箱标识与路由版本（mailbox_id、route_version）、不可变 blob_ref、内容摘要、策略版本、保留期限（retention_expires_at）、状态（quarantined、releasing、released）、独立的 expired（布尔标记）及乐观锁版本号（version）。到期采用独立的 expired=true 标记，不能直接把 QuarantineItem 的事实状态改写为 expired，避免覆盖已有的 released 事实。逐收件人独立建项可防止某一收件人释放邮件时连带影响其他收件人。
  2. 申诉实体（Appeal）：按 (tenant_id, appeal_id) 组织，关联具体 item_id，状态包括待处理（pending）、已批准（approved）、已驳回（denied）和已撤回（withdrawn）。
  3. 释放任务实体（ReleaseJob）：按 (tenant_id, release_id) 组织，跟踪移交下游的异步动作，状态包括待派发（pending）、派发中（dispatching）、下游接手（accepted）、不确定（uncertain）、失败（failed）和已取消（cancelled）。任务附带独立的 cancel_requested 布尔标记表示取消意图，而不覆盖当前真实执行状态。

必须区分的是，ReleaseJob 的 accepted 状态统称下游系统已确认接手，在受控队列场景下指取得唯一持久入队凭证，在普通 SMTP 场景下指收到最终明确的 250 OK，两者都不等于邮件已送达最终物理邮箱。跨租户引用在每一跳均需校验租户归属，item、blob 以及 job 的交叉引用均在服务端严格校验 tenant_id；blob_ref 仅为底层内部引用，不作为公开下载凭据；当收件人发生别名路由变更或账号停用时，释放任务必须重新核验当前授权。

接口设计与访问控制边界

系统接口严格区分身份认证（authentication，确认主体身份）与授权（authorization，判定主体操作权限）。服务端的认证上下文决定当前操作的租户标识 tenant_id，不允许调用方跨租户指定。普通用户仅能查询和申诉归属自身的收件项；管理员权限细分为概览预览、原始数据下载、申诉审批与强制释放，且高风险邮件禁止终端用户自助释放。

在交互协议上，资源修改遵循 RFC 7232 第 3.1 节，使用强比较的 If-Match 标头进行状态版本匹配；异步受理请求依据 RFC 7231 第 6.3.3 节返回 202 Accepted，并在响应中提供任务监视链接。这里的路径和 X-Idempotency-Key 标头均为系统自定义设计，不冒充行业既有规范。

除创建释放任务使用专用的 POST 接口外，本设计定义以下接口：查询收件项详情使用 GET /api/v1/quarantine/items/{item_id}，返回包含当前 version 的 ETag；用户提交申诉使用 POST /api/v1/quarantine/items/{item_id}/appeals；管理员审批使用 POST /api/v1/quarantine/appeals/{appeal_id}/review 并携带 If-Match 校验申诉版本，审批通过仅更新申诉状态，不自动触发下游投递；查询释放进度使用 GET /api/v1/quarantine/releases/{release_id}；取消释放使用 POST /api/v1/quarantine/releases/{release_id}/cancel。

发起释放的教学接口示例如下：

POST /api/v1/quarantine/items/item_8901/releases HTTP/1.1
Host: mail-gw.example.test
Authorization: Bearer <admin_token>
X-Idempotency-Key: rel-key-7788
If-Match: "v3"
Content-Type: application/json

{
  "target_recipient": "user@example.test",
  "override_reason": "业务核实放行"
}

HTTP/1.1 202 Accepted
Location: /api/v1/quarantine/releases/rel_3344
Content-Type: application/json

{
  "release_id": "rel_3344",
  "item_id": "item_8901",
  "status": "pending",
  "cancel_requested": false,
  "monitor_url": "/api/v1/quarantine/releases/rel_3344"
}

请求体中的 target_recipient 仅作为调用方的意图校验声明，服务端核对时必须与隔离项固化的收件人目标严格匹配，禁止请求任意更改收件人地址。在安全设计上，HTML 邮件预览必须在受限沙箱中运行，剥离脚本节点并屏蔽外部资源的自动加载，避免触发探测回连。原始邮件下载需提供独立的下载权限检查，禁止通过穷举或猜测 blob_ref 直接读取存储底层。申诉审批通过（approved）仅表明业务审核完成，若要重新裁决须以版本条件控制，且审批结论不自动将发件人列入全局免检白名单或直接转入分类器训练集。

并发控制与幂等性保障

在并发请求与网络重试场景下，幂等性（idempotency，即同一操作在相同上下文下多次发起产生的副作用一致）是防止重复放行的基础机制。系统采用自定义的 X-Idempotency-Key 标头记录客户端提交的唯一标识，在数据库层建立多租户唯一索引 UNIQUE (tenant_id, operation, idempotency_key)。

处理释放请求时，先核验当前主体的租户与动作授权，再在事务中查询幂等记录。命中且完整 payload_hash（覆盖完整有效载荷包括 target_recipient、override_reason、操作类型与期望版本）相同则返回已有任务，命中但载荷不同返回 409，不因原始 If-Match 已过期拒绝同一请求的重试。

只有未命中才在行锁保护下再次查同键，再以 status = 'quarantined' 且 version = 请求版本 的条件更新或等价的比较并交换（compare-and-swap，CAS）操作检查状态和强 If-Match，不匹配返回 412；更新与幂等记录、释放任务、事务发件箱（transactional outbox）事件和审计日志（audit log）同事务提交。并发唯一键冲突回滚后重新读取胜出记录比对哈希。

系统在租户与收件项维度设置活动任务排他约束：同一 tenant_id 与 item_id 下，在同一时刻只能存在一个处于活动状态（包含 pending、dispatching 和 uncertain）的 ReleaseJob。只要前序任务处于不确定（uncertain）或在途状态，系统即阻止任何新键创建新的释放任务；只有当任务进入 failed 或未派发前被取消（cancelled），且收件项未标记 expired=true、当前授权仍然有效时，收件项才允许回退为 quarantined 供后续重新发起；而一旦任务进入终态 accepted，收件项被标记为 released，此后禁止对该项再开启任何释放任务。

后台派发、受控入队与重投防环

后台工作协程（worker）异步从 outbox 读取事件执行外发。为防止网络分区或长时间垃圾回收停顿导致旧 worker 与新 worker 并行外发，系统引入租约机制与隔离令牌（fencing token）。必须指出的是，租约本身无法物理阻止停顿后的旧进程发送网络数据包，且普通 SMTP 服务器无法识别 fencing token；只有在专门支持租约与令牌校验的受控下游接收端，才能在服务端识别并拒绝过期 worker 的写请求。

在执行派发动作前，worker 必须重新核验多项前置条件：原操作主体与审批记录的授权版本未被撤销、当前租户归属有效、原始 BLOB 存储文件存在且摘要校验匹配，以及目标邮箱标识与路由版本（mailbox_id、route_version）保持一致。若收件人账号已被禁用或别名路由发生变更，系统暂停派发并要求重新复核，避免将邮件投递至相同地址但不同归属的新邮箱。

worker 领取任务必须与客户端取消竞争同一状态条件更新：worker 仅能原子地将任务状态从 pending 推进为 dispatching。若此时取消请求已胜出并将状态置为 cancelled，worker 更新行数为零并放弃处理，防止从旧 outbox 事件中将已取消任务复活。

向受控下游队列投递时，worker 携带全局稳定的 release_id 作为持久去重依据。受控队列在接收邮件时以此标识做原子幂等登记与收据持久化，并提供收据查询接口。若 worker 外发后由于网络闪断未能直接收到响应，暂未查到收据不能证明对端未接收；只有在当前授权与到期策略均允许的前提下，才使用相同的 release_id 重新提交，由受控接收端持久去重。若反查确认已接收，任务顺利收敛为 accepted。

为防止放行的邮件再次被网关入站扫描捕获陷入死循环，重投邮件必须通过受保护的网关内部通道传输，并在邮件元数据中关联原始的 release_id。系统不采信外部可伪造的邮件标头来豁免安全检查。在重投阶段，网关仅对触发此前隔离决定的特定启发式规则实施受限豁免，依然保留基础的病毒特征码查杀与恶意附件扫描。

事务边界跨越、SMTP 交互与故障收敛

数据库事务无法使本地数据库提交与远端 SMTP 接收构成原子提交。当 worker 与普通下游 SMTP 服务器交互时，若在发送完数据块结尾的 <CRLF>.<CRLF> 并等待 250 OK 回执期间网络中断，系统无法确认对端是否已持久化接收。依据 RFC 5321 第 4.5.3.2.6 节，数据结束阶段发生超时容易导致重复邮件。普通 SMTP 不承诺端到端的“恰好一次”（exactly-once）投递保证。

由于普通 SMTP 服务不提供基于 release_id 的持久去重与反查机制，系统不能盲目自动重试，而是必须将 ReleaseJob 推进至不确定状态（uncertain）。在普通 SMTP 场景下，对端日志缺失不能作为绝对未收到的否定证据，不能将 uncertain 随意标记为 failed。若人工经评估后必须选择重新投递，必须明确记录接受重复接收风险的人工决策，系统不承诺恰好一次。若经人工核查依然无法证实对端状态，任务需保持 uncertain 并持续保留原始 BLOB 存储，直到不确定性通过明确的策略消除。若收到明确的 4xx 临时错误码或建连前失败，任务保持在 dispatching 并调度重试；若收到明确的 5xx 永久拒收码，任务标记为 failed，保留原始 BLOB 供管理员查验。

当下游为普通 SMTP 服务并明确返回了最终 250 OK 时，任务同样更新为终态 accepted（在此处代表下游确认接手，保留响应文本作为凭据），收件项对应更新为 released。

任务撤销与审计生命周期

释放任务支持明确的撤销语义。若任务仍处于待派发（pending）状态，取消请求通过原子条件更新（UPDATE ... WHERE release_id = ? AND status = 'pending'）胜出后，任务状态更新为 cancelled，收件项在未到期且授权有效的前提下恢复为 quarantined。

若任务已处于 dispatching 或 uncertain 状态，由于底层可能已经在建立网络连接或发送数据，系统仅将任务的 cancel_requested 标记置为 true；只有在尚未实际外发并能明确证实停下时，任务才允许收敛为 cancelled，绝不能在数据发出后虚假报告取消成功；一旦下游系统已返回 accepted 确认接手，该流转在物理上无法召回，系统不承诺取消。

系统在单事务中记录审计日志，保障本地业务与审计同提交，但并不赋予审计记录天生的物理不可篡改性。审计字段记录 request_id、时间戳、操作人标识 actor_id、租户 tenant_id、前置与后置状态、策略版本、授权版本以及业务原因，严禁记录邮件正文、附件内容或认证令牌。审计数据遵循独立的数据保留策略，在到期后清理或精简为最小化墓碑记录，不永久保留包含个人信息的字段。读取和拒绝访问事件也记录审计；拒绝事件独立持久化，与成功的业务变更记录分开保存。

对于数据生命周期管理，当收件项到达保留期限（retention_expires_at）后，系统将其标记为 expired=true，此后禁止针对该项创建任何新的释放请求或重新提交未派发任务，但到期动作不自动取消已在运行中的释放任务，对已发生并确认接手的记录照事实记录。垃圾回收机制必须等待所有关联的 ReleaseJob 均退出在途与 uncertain 状态并完成明确处置，且确认无其他收件项引用该内容哈希后，方可清除物理 BLOB 数据，杜绝删除仍被活动任务引用的文件。

贯穿场景：受控队列接收超时与故障收敛

考虑如下贯穿场景：

一封发往 user@example.test 的邮件被隔离，生成主键为 (tenant_A, item_8901)、版本为 v3 的收件项。管理员 Alice 发起释放请求，携带 X-Idempotency-Key: key_A 与 If-Match: "v3"。几乎在同一瞬间，管理员 Bob 使用 key_B 和 If-Match: "v3" 并发发起释放。数据库本地事务内，Alice 的请求抢先获得行级排他更新，成功将版本自增为 v4 并创建 ReleaseJob 实体 rel_3344；而 Bob 的请求在事务内执行条件更新时，检测到当前版本已非 v3，立即失败并收到 412 Precondition Failed；即便 Bob 随后以最新版本重试，也会触发活动任务排他约束被直接拦截。

后台 worker 拾取 rel_3344，将其状态置为 dispatching，并向下游受控持久队列投递。受控队列将邮件安全落盘后，在返回响应数据包的瞬间网络链路闪断，worker 遭遇读取超时，未收到回执。

此时调度节点发生重启。新启动的 worker 扫描到超时的租约并恢复处理。与此同时，Alice 因界面超时以相同参数和 key_A 再次调用释放接口。服务端在单事务中识别到重复的 key_A 且 payload_hash 完全一致，直接返回已存在的任务 rel_3344，未创建新任务。

在任务恢复处理期间，上游目录服务触发了目标收件人 user@example.test 的账号注销事件（这不同于操作人 Alice 自身的授权撤销），且收件项达到了保留期限被标记 expired=true。新 worker 按照受控队列恢复流程，凭唯一的 rel_3344 标识向下游受控队列发起收据查询。由于受控队列此前已成功持久化该任务，查询接口返回了明确的持久收据（receipt）。worker 依据返回的收据，将 rel_3344 的状态顺利收敛为 accepted，并将收件项标记为 released。已由下游持久接手的事实成立，系统不会因为后续的目标账号注销或到期而将已接手的任务强行篡改为 failed。下游持久接手之后，后续在物理邮箱投递层面的成功与失败，由下游逐收件人投递队列负责跟踪，系统不丢弃对端的接收责任。

若将下游替换为不提供收据查询的普通 SMTP 服务，遭遇上述 DATA 结束断线后，worker 无法查证对端落盘结果，任务将停留在 uncertain 状态。即便收件项到期，系统也不在过期后无条件强行重投，而是保持 uncertain 直到人工根据对端日志做出明确处置。

验证计划与工程设计边界

针对上述状态机与边界控制逻辑，设计如下未实际运行的集成测试验证计划，使用合成 EML 样本与虚构租户执行预期断言：

  1. 并发冲突与条件更新断言：在多租户环境下，针对同一 item_id，模拟两个并发客户端使用相同的 If-Match 标头及不同幂等键发起释放。预期断言：仅有一个请求能够成功创建 ReleaseJob 并返回 202 Accepted，另一请求必须收到 412 Precondition Failed 或单活动任务冲突响应。
  2. 幂等键防篡改与同键并发断言：使用相同的 X-Idempotency-Key，先后发送针对同一收件项但修改了目标收件地址或原因的释放请求，预期断言服务端返回 409 Conflict；若同时发起两个相同 key 的并发写请求，数据库事务唯一约束保证仅生成唯一一条 ReleaseJob 记录。
  3. 授权撤销与路由变更重试断言：在释放任务创建后，分别模拟两种分支：（a）若撤销操作主体调用权限，使用原幂等键重试时，在首道当前授权检查阶段即被拒绝；（b）若仅发生目标收件人 route_version 变更，重试 API 可安全返回既有任务监视信息，但 worker 在实际外发的前置检查中必须识别出路由版本失配并暂停外发。
  4. BLOB 完整性与双租户越权隔离断言：模拟底层存储对象丢失或摘要不匹配，worker 必须中断派发；模拟双租户环境（tenant_alpha 与 tenant_beta），使用前者凭据请求后者 item_id、blob_ref 或下载接口，网关必须拒绝且底层存储不执行任何对象读取。
  5. 受控队列 fencing 与普通 SMTP 故障断言：模拟旧 worker 发生长停顿导致租约过期后苏醒。预期断言：若目标为受控队列，接收端校验 fencing token 拒绝旧 worker 的写入；若目标为普通 SMTP 且在 DATA 结尾中断，任务被置为 uncertain 并保持活动槽位，阻断自动重投。
  6. 到期清理排他断言：设置收件项到期触发 expired=true 标记，同时保持关联的释放任务处于 uncertain。预期断言：垃圾回收程序在任务退出 uncertain 并完成明确处置前，严禁删除底层的物理 BLOB 文件。
  7. 节点崩溃与事务完整性断言：模拟在数据库事务提交前应用进程崩溃，预期断言数据库无任何半写入残留；模拟事务提交后、outbox 消息发出前节点崩溃，重启后 worker 从 outbox 恢复派发且使用相同的 release_id；模拟 HTML 预览时输入恶意载荷，预期断言脚本节点彻底剥离且不发出任何外部网络请求。

在不可靠的网络与复杂的系统交互中，将边界显式暴露为 uncertain 状态会增加人工核查的成本，但能避免在缺乏依据时伪造成功的系统状态，这是保障邮件处理严谨性所必需的技术取舍。
