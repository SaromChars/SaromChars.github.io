域名和 IP 信誉与投递反馈

2021年9月22日
|

在互联网邮件系统的运行中，邮件传输代理（Message Transfer Agent，MTA）仅凭简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）连接初期的网络层与信封信息，很难直接断定对端主机将要投递的是业务通知还是海量垃圾邮件。为此，接收端发展出了结合网络层与应用层行为的多层评估体系：一方面借助基于域名系统（Domain Name System，DNS）分发的名单判定来源信誉，另一方面借助灰名单（Greylisting）等状态机机制对未知来源进行延时验证。

在发信端，外发邮件的送达效果与投递呈现（例如进入收件箱还是垃圾箱）高度依赖发信 IP 地址与域名的信誉积累。当发信端面对共享出口、突发速率控制、用户垃圾举报与退订诉求时，如何设计闭环反馈并遵循协议规范，成为保障系统稳定性的关键课题。

基于 DNS 的信誉名单（DNSBL）实践与边界

为了低开销地在全网分发针对对端 IP 或域名的信誉评估结果，业界广泛采用基于 DNS 的名单机制（DNS-Based List，DNSBL）。互联网研究任务组（Internet Research Task Force，IRTF）的反垃圾研究组在 RFC 6471（信息性备忘录，Informational）中系统总结了公共 DNSBL 的运维与使用规范。

1. 名单分类与使用职责

DNSBL 是利用 DNS 查询分发各类信誉信息的统称，常见类型包括：

  • IP 黑名单：收录有恶意滥用、开放中继（Open Relay）或僵尸网络特征的对端 IP 地址；
  • 基于 DNS 的白名单（DNS Whitelist，DNSWL）：收录已知行为良好、低风险的发信 IP 或域名；
  • 域名名单（Right Hand Side Blacklist，RHSBL）：针对邮件发件人域或反向 DNS 指针（PTR）中的域名进行信誉匹配；
  • 统一资源标志符黑名单（Uniform Resource Identifier Blacklist，URIBL）：收录邮件正文中出现的可疑网页链接域名或主机名。

RFC 6471 第 1.2 节强调，DNSBL 仅仅是运营方公开表达的一种观点（expressing an opinion），名单本身并不具备在网络上强制拦截通信的能力。是否采用某个名单、是将其作为一票否决依据还是纳入多因子加权评分（Scoring），完全取决于收件端邮件管理员的本地策略。因此，DNSBL 的使用者必须自行承担采用该名单指导过滤所带来的一切后果（The DNSBL user MUST assume responsibility for dealing with the consequences）。

2. 测试标识与异常识别

为了让邮件接收端能够以自动化方式探测 DNSBL 服务是否正常运作，RFC 6471 第 3.3 节与第 3.5 节给出了标准测试约定：

  • 服务存活探测：绝大多数针对 IP 的 DNSBL 约定查询 127.0.0.2（即向 <2.0.0.127.dnsbl.example.com> 发起 A 记录查询），若正常运行应返回表示命中的 A 记录（通常为 127.0.0.2 本身）；若返回域名不存在（NXDOMAIN）或返回 127.0.0.0/8 之外的地址，说明该名单当前处于非正常工作状态。
  • 全局拦截误报识别：根据 RFC 6471 第 3.5 节，正常运行的 DNSBL 绝不能收录 127.0.0.1（A functioning DNSBL MUST NOT list 127.0.0.1）。如果收件端探测发现对 127.0.0.1 返回了正向命中结果，通常意味着该名单已被恶意篡改，或者运营方在清退阶段对全网所有 IP 进行了通配拦截（listing the world），此时本地系统应立即停用该名单以避免严重的邮件误杀。

3. 名单维护与移除申请准则

针对公共名单的维护周期与争议处理，RFC 6471 规定了以下操作边界：

  • 临时性与自动老化：RFC 6471 第 2.2.1 节指出，名单条目通常应当是临时性的（SHOULD be temporary），并在问题解决或达到合理时限后自动失效，除非引发收录的原因仍然持续存在；
  • 申诉响应时限：RFC 6471 第 2.2.3 节要求，名单运营方对移除请求或收录咨询的响应应当迅速，应该在 2 天内响应，最迟必须在 7 天内响应（SHOULD respond within 2 days and MUST respond within 7 days）；唯一的例外是运营方认定进一步沟通无法达成移除条件，并已将此决定正式通知了申请人；
  • 利益冲突禁止：RFC 6471 第 2.2.5 节明确要求，负面信誉名单绝不能收取移除费用或索要捐款（negative-connotation DNSBLs MUST not charge fees or require donations for delisting），亦不得以“加急处理”为名收费；
  • 有序下线规范：历史上部分商业或志愿名单终止维护时，曾通过将全网所有 IP 解析为黑名单来强制迫使管理员卸载配置。RFC 6471 第 3.4 节严令禁止这种破坏性行为，要求停运时绝不能收录整个互联网（Shutdowns MUST NOT list the entire Internet），应提前发布公告（推荐提前一个月或更长时间），并可通过将 DNS 服务器地址重定向至 192.0.2.1 等保留测试网段（TEST-NET，RFC 5735）制造查询超时，温和提示管理员清理配置。

灰名单（Greylisting）机制与状态机

除外部名单外，利用发信端行为模式进行低成本前置拦截的经典手段是灰名单（Greylisting）。IETF 在 RFC 6647《Email Greylisting: An Applicability Statement for SMTP》（标准跟踪，Standards Track）中对该技术的实现与工程权衡进行了正式规范。

1. 核心原理与元组设计

大量简易垃圾邮件发送程序（Spamware）为了追求吞吐量，仅实现了精简版 SMTP 协议，在遇到临时性失败（4xx 状态码）时不会保留队列并按照退避算法重试，而是直接丢弃并转向下一个目标。灰名单正是利用了这一非对称特性：对未曾见过的陌生连接来源返回 SMTP 临时失败响应，推迟其投递，直到对端按标准协议发起合法重试才予以放行并记录在案。

RFC 6647 第 5 节推荐的最佳实践基于三元组（Tuple）进行评估：该三元组由对端 IP 地址、RFC5321.MailFrom 反向路径以及首个 RFC5321.RcptTo 收件人地址组成。

阶段分类记录的评估标识阻断动作时机工程优缺点
连接级别（第 2.1 节）对端 IP 地址 / 主机名TCP 握手后返回 421 断开连接，或后续命令均返回 4yz开销最低；但对动态出口或新 IP 会一刀切拦截，影响范围最大
HELO/EHLO 级别（第 2.2 节）对端 IP + HELO 参数问候阶段或后续命令返回 4yz参数易被伪造，单一区分度有限
MAIL 级别（第 2.3 节）对端 IP + MAIL FROM 反向路径MAIL 命令后返回 4yz无法区分发往不同收件人的会话
RCPT 级别（第 2.4 与第 5 节推荐）对端 IP + MAIL FROM + 首个 RCPT TORCPT 阶段或后续命令返回 4yz推荐实践：粒度精确，合法 MTA 重试通常不重排收件人顺序
DATA 级别（第 2.5 节）完整信封；可选结合邮件头（From/To/Subject）或正文哈希摘要收到 DATA 命令时，或在正文传输结束（.）后返回 4yz收到命令时阻断开销可控；若选择在正文结束后基于内容哈希摘要做判断，则须完整接收正文并计算摘要，开销极大且非典型实践

在放行逻辑上，RFC 6647 第 5 节建议，当某个三元组首次成功完成合规重试后，系统可以放行该 IP 后续的所有 SMTP 流量，而无需对每个信封组合反复施加延迟。

2. 时间窗口与数据库淘汰

根据 RFC 6647 第 5 节，灰名单引擎推荐包含两个关键的可配置时间参数：

  1. 重试接纳窗口（Retry Window）：由最小重试间隔与最大超时组成。RFC 6647 推荐的默认范围应当介于 1 分钟至 24 小时之间（default range SHOULD be from one minute to 24 hours）。在具体实现中，这是一个可配置的时间区间：若对端在低于窗口下限（如 1 分钟内）过早重试，系统仍应保持临时失败而不放行，且不重置首次记录时间；只有在窗口范围内的重试才满足要求并予以放行；若重试发生在上限定时（如 24 小时）之后，系统应当（SHOULD）将其作为全新投递重新计算首次观察时间。
  2. 记录老化淘汰（Aging Timeout）：数据库中长期无流量活跃的已放行 IP 记录，推荐的默认保存时间应当至少为 1 周（SHOULD be at least one week）后再予清除，以便在对端 IP 发生网络重划或易手时重新对其生效。

3. 副作用与多主机协作例外

灰名单技术以牺牲部分邮件的即时性为代价换取防垃圾收益：

  • 投递延迟：合规邮件可能被推迟数十分钟至数小时，对时效敏感的业务通知存在延迟影响；
  • 集群与多 MX 裂脑：收件域若配置了多台 MX 主机（例如 mail1.example.com 与 mail2.example.com），根据 RFC 6647 第 4.1 与第 5 节，同一个管理域内的所有入口 MTA 应该共享同一个灰名单数据库（SHOULD share a common greylisting database）。否则，客户端在 mail1 收到 450 后轮询重试 mail2，又会遭遇全新延迟，导致延迟成倍放大；
  • 外发集群 IP 漂移：发信方由多台外发节点共享队列时，重试可能切换至集群内的另一台 IP。RFC 6647 第 5 节指出，灰名单系统可以按 /24 等网段（CIDR 块）或统一的服务器域名进行归纳统计，以容忍合理的出口漂移；
  • 本地认证豁免：RFC 6647 第 5 节明确强调，对于已通过身份认证（authentication）的本域外发会话（如 SMTP 提交服务），不应该施加灰名单延迟（Greylisting SHOULD NOT be applied against any authenticated ADMD session）。

发信信誉、共享出口与速率控制

在发信端架构中，外发服务器的信誉是接收端判定策略的重要输入。

1. 独享出口与共享出口的信誉隔离

邮件发信架构通常分为独享 IP（Dedicated IP）与共享 IP 池（Shared IP Pool）：

  • 独享 IP：能够有效减少其他租户行为对自身信誉的干扰。若发送量平稳、列表质量高，有助于独立积累良好的投递声誉；但若发信量极低，在接收端可能因样本不足而被视作未知来源，可能触发灰名单延迟或基础限速；
  • 共享 IP 池：多租户共用一组外发出口。虽然能平摊网络成本并维持稳定的活跃流量，但存在潜在连带风险：池内某租户若突发垃圾邮件，可能导致对应出口 IP 被特定名单收录，连带影响共用该出口的其他业务。由于不同 DNSBL 的收录粒度覆盖单 IP、子网段或域名（RHSBL），受损范围取决于具体名单机制。

因此，在系统设计上，根据业务时效与租户风险进行分流是有价值的工程实践：将事务类邮件（Transactional Mail，如重置密码、账单）与营销类邮件（Marketing Mail）配置在不同的外发通道与出口 IP 上，可以降低营销邮件投诉对高优先级事务通知的连带影响。

2. 速率控制与连接收敛

接收端通常会对来源 IP 与域名实施动态的速率控制（Rate Limiting）。当发信速率超出接收方的处理能力或本地信誉配额时，接收端常返回 421（连接超限）或 450/451 临时错误；需要注意，4xx 临时失败同样可能由前述灰名单机制或接收端临时资源短缺引起。

发信系统面对此类反馈时，应当根据具体响应码与诊断文本区分原因，并在本地队列调度中进行收敛与退避：

  • 识别持续的临时失败状态，有针对性地调低对该目标域的并发连接数（Concurrency Limits）与发信速率；
  • 采用可配置的退避算法重试，避免短时间内高频冲击接收端导致资源持续过载；
  • 对于新启用的外发 IP，工程上常采用逐步提升发信量的预热（Warm-up）调度，以便在接收端逐步建立历史行为样本。

投诉处置与单键退订机制（RFC 8058）

在邮件交互中，用户不仅可以通过邮件客户端的“垃圾举报”表达负面反馈，还可以通过“退订”通道脱离列表。RFC 8058 第 1 节指出，发信方通常高度关注邮件的送达率与呈现位置；当收件人频繁将邮件标记为垃圾时，发信方的投递表现往往会变差。如果退订流程过于繁琐，用户往往会转向直接举报。提供便利的退订通道有助于降低收件人的举报动机。

1. 自动预取对传统退订的破坏

按照 RFC 2369 的传统做法，邮件列表通过在头部添加 List-Unsubscribe 声明 HTTP(S) 或 mailto 退订链接：

List-Unsubscribe: <https://example.com/unsubscribe?id=12345>

然而在实际运行中，现代邮件安全网关与反垃圾防病毒软件在收到邮件时，通常会自动并发抓取并解析邮件头及正文中的所有网页链接，以检测是否存在恶意软件或钓鱼挂马。如果 List-Unsubscribe 中的链接设计为访问 GET 请求即刻完成退订，这些自动化爬取机制就会在收件人完全不知情的情况下触发误退订（Accidental Unsubscriptions）。

为了防御自动误退订，发信方过去往往会在用户点击链接后弹出一个确认网页（Landing Page），要求用户再次点击“确认”按钮。但这导致退订需要人工在浏览器中进行多步交互。当邮件系统希望在用户点击客户端垃圾举报时自动联动退订，或者客户端希望提供原生的退订按钮时，无法依靠程序去解析复杂的网页确认表单。

2. 单键退订与 DKIM 签名

为了解决自动误退订与客户端直接交互之间的矛盾，IETF 于 2017 年 1 月发布了标准跟踪规范 RFC 8058《Signaling One-Click Functionality for List Email Headers》，定义了基于 HTTPS POST 动作的单键退订（One-Click Unsubscribe）。

发信方头部语法与 DKIM 约束

发信方若声明支持单键退订，必须在邮件头部同时包含以下两个字段（RFC 8058 第 3.1 节）：

  1. List-Unsubscribe：必须包含且仅包含一个 HTTPS URI（MUST contain one HTTPS URI），可以同时包含其他非 HTTP/S 方案（如 mailto:）；
  2. List-Unsubscribe-Post：必须严格包含单组键值对 List-Unsubscribe=One-Click。
List-Unsubscribe: <https://example.com/unsubscribe/opaque-token-987>
List-Unsubscribe-Post: List-Unsubscribe=One-Click

更为关键的是完整性与防篡改约束。为了防止传输路径上的中间节点篡改退订参数，RFC 8058 第 3.1 与第 4 节做出了明确规定：

  • 邮件必须具备至少一个有效的域名密钥识别邮件（DomainKeys Identified Mail，DKIM）签名（MUST have a valid DKIM signature）；
  • 该 DKIM 签名的 h= 标签必须完整覆盖 List-Unsubscribe 与 List-Unsubscribe-Post 两个头部字段（MUST be covered by the signature）；
  • 若邮件未包含满足上述要求的 DKIM 签名，接收端不应该为该邮件展示单键退订入口（SHOULD NOT offer a one-click unsubscribe）。

必须厘清的是，DKIM 签名的作用是保护邮件头部字段在传输过程中的完整性与来源域归属，它并不验证发起后台 POST 请求的调用者身份。根据 RFC 8058 第 6 节的安全考量，任何能够接触到该邮件内容的实体，理论上都可以利用其中的链接为该收件人执行退订。

此外，RFC 8058 第 3.1 节规定，List-Unsubscribe 中的 URI 必须包含足够的信息来识别收件人以及待退订的列表，以便退订处理能由系统自动完成。因为单键退订协议没有提供额外的 POST 参数传递空间，也不支持在退订过程中向用户询问邮件地址或列表名称。

接收端交互与 HTTP 规范

当邮件用户代理（Message User Agent，MUA）展示退订功能，且用户明确同意执行退订时（RFC 8058 第 3.2 节要求：MUST NOT perform a POST on the HTTPS URI without user consent）：

  1. MUA 或接收系统在后台向 List-Unsubscribe 中的 HTTPS URI 发起 POST 请求；
  2. POST 的请求体内容为 List-Unsubscribe=One-Click，内容类型（Content-Type）应该（SHOULD）为 multipart/form-data，或可以（MAY）为 application/x-www-form-urlencoded；
  3. 无状态隔离要求：RFC 8058 第 3.1 节明确规定，该 POST 请求绝不能附带 Cookie、HTTP 身份凭证或其他上下文状态（MUST NOT include cookies, HTTP authorization, or any other context information），防止发信端将该动作与收件人之前的网页浏览历史不当关联；
  4. 禁止重定向：发信端的退订处理服务器绝不能返回 HTTPS 重定向（如 301/302）（The mail sender MUST NOT return an HTTPS redirect），因为历史上许多客户端对 POST 重定向的处理并不规范，极易降级为 GET 请求从而引发逻辑混乱。
POST /unsubscribe/opaque-token-987 HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 26

List-Unsubscribe=One-Click

不透明标识符防攻击建议

由于发信端服务无法从 POST 请求头中辨别调用者真实身份，RFC 8058 第 3.1 节建议：退订 URI 中应该包含不透明标识符（Opaque Identifier）或难以伪造的令牌，并由发信端服务器校验其合法性。这有助于防范攻击者直接针对退订服务器暴力遍历收件人邮箱发起 POST 批量取消订阅，或者伪造含有受害者退订链接的垃圾邮件诱发连锁退订。

投递反馈闭环与工程推导

邮件的信誉治理并非单向拦截，发信端通过接收端的状态码与相关反馈机制，逐步调整外发策略。

      |                                                |

      |                                                |
      |--- 3. 队列重试 ------------------------------->|
      |    (接收端接受邮件后，依本地安全策略决定存放位置)
      |                                                |
      |    [用户交互阶段]                              |
      |    +-- 分支 A: 用户触发退订 (RFC 8058) --------|
      |<------ 后台无状态 HTTPS POST (One-Click) -------|
      |        [移除订阅名单，降低后续举报风险]        |
      |                                                |
      |    +-- 分支 B: 用户点击垃圾举报 ---------------|
      |<------ 若服务商提供且已接入反馈循环 (FBL) -----|
               [排查涉事外发业务与账号]

结合协议机制与运维实践，发信端在设计投递反馈处理时通常遵循以下工程推导：

  1. 退订分流与降低投诉：提供遵循 RFC 8058 的原生单键退订通道，能够让无意继续接收邮件的用户便捷退订，减少因退订困难而直接点击“垃圾邮件举报”的情况；
  2. 退订接口的幂等与异步解耦：发信端退订接口通常设计为幂等处理（重复提交不产生副作用），并可将退订事件写入本地任务队列异步处理，按服务承诺的时限更新订阅数据库；
  3. 闭环排查与信誉保护：若特定大型服务商提供了反馈循环（Feedback Loop，FBL）机制且发信域已完成接入申请，发信方可据此收集投诉样本，定位被盗账号或违规外发租户；而在未接入 FBL 或服务商不提供此类通道的场景下，发信端则主要依赖退信响应码与投递成功率等综合指标监控外发健康度。
