Postfix SMTP 出站连接与并发控制

2021年11月10日
|

邮件外发系统向远端投递邮件时，网络连接与远端主机的运行状态存在较多不确定性。远端服务器可能因网络异常无响应、因策略限制临时拒绝，或针对同一会话中的不同收件人给出差异化的状态码。如果投递调度器无法准确识别这些失败的阶段与影响范围，盲目重试或粗暴截断并发，很容易引发本地队列积压或被远端限流。

理解出站投递的核心在于厘清其内部生命周期与边界：一次投递请求如何在各阶段流转？域名系统（Domain Name System，DNS）路由异常、逐收件人响应与并发退避之间又是如何联动？本文结合固定分析版本 Postfix 3.6.2 的源码实现#与 RFC 5321 规范#，梳理出站连接控制的核心机制，并推导外发引擎的接口契约与失败处理设计。

出站投递流程与状态传递

在 Postfix 架构中，队列管理器（queue manager，qmgr）负责消息调度，而实际的网络出站协议交互由 smtp 投递代理进程（delivery agent）执行，二者通过 UNIX 域套接字通信。

qmgr (队列管理器)
   │ DELIVER_REQUEST
   ▼
smtp_service() ──> deliver_message()
                         │
                         ▼
                   smtp_connect() ──> smtp_connect_inet()
                                            │
                                            ▼
                                     smtp_xfer() (协议交互)

当 qmgr 分配投递任务时，smtp 进程在 smtp_service() 中通过 deliver_request_read() 读取投递请求结构体 DELIVER_REQUEST#。DELIVER_REQUEST 封装了消息标识（queue_id）、发件人、下一跳目的地（nexthop）以及收件人列表（rcpt_list）。

随后调用的 deliver_message() 会分配单次投递的上下文结构体 SMTP_STATE#。SMTP_STATE 聚合了当前投递请求（state->request）、打开的邮件文件流（state->src）以及递送状态缓存。该函数调用 smtp_connect(state) 建立物理或复用会话，处理完毕后调用 smtp_state_free(state) 释放资源，最后经由 deliver_request_done() 将执行结果回传给 qmgr。

在 smtp_connect() 中，请求根据传输模式进入网络连接分支 smtp_connect_inet()#。此时系统围绕待处理收件人（SMTP_RCPT_LEFT(state)）展开循环：

  1. 会话上下文挂载：建立网络连接后生成 SMTP_SESSION 结构体，内部持有网络流（vstream）、服务端特性掩码、传输层安全协议（Transport Layer Security，TLS）状态及错误掩码。
  2. 协议传输执行：调用 smtp_xfer(state) 发送简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）信封与邮件数据。
  3. 收件人状态更新与清理：在一次会话结束后，调用 smtp_rcpt_cleanup(state)。收件人在投递过程中会被标记为 KEEP（保留并在后续备用服务器重试）或 DROP（本次投递请求已完成处理并移出待处理列表，可能已成功、已记退信或已记延期，不代表收件人最终送达）#。若当前会话终止且仍有未完成的收件人，未标记的收件人将进入备用主机重试；若所有候选节点耗尽，由 smtp_sess_fail(state) 统一记录状态。

DNS 路由解析与主机排序

在发起网络传输前，投递代理必须确定下一跳目的地的具体 IP 地址。在 smtp_connect.c 中，当 SMTP 启用了 DNS 解析且目的地未以方括号 [ 开头时，系统调用 smtp_domain_addr() 查询 MX 记录；若指定了方括号形式的目的地（如配置 [relay.example.com]:25 显式绕过 MX 查询），或关闭了 DNS 查询，则直接调用 smtp_host_addr() 执行主机地址直查#。当进入 smtp_domain_addr() 时#，解析逻辑对 DNS 查询结果有严格的分支判定：

  • 正常 MX 查询（DNS_OK）：获取邮件交换记录（mail exchanger record，MX record）后，首先按优先级数值（preference）升序排序（数值越小优先级越高）。解析出的 IP 地址列表在配置项 smtp_randomize_addresses（源码对应变量 var_smtp_rand_addr）开启时会执行地址乱序洗牌（dns_rr_shuffle），随后再按地址族偏好重新归类。这种机制主要用于同优先级服务器与多地址之间的分摊，并不会颠倒高低优先级的尝试顺序。
  • MX 记录缺失（DNS_NOTFOUND）：依据 RFC 5321 第 5.1 节规定，若域名未配置 MX 记录，系统自动回退至隐式主机地址查询（implicit address lookup），直接查询该域名的 A 或 AAAA 记录。
  • Null MX 记录（DNS_NULLMX）：依据 RFC 7505#，若 MX 记录主机名为单个点号且优先级为 0，代表该域明确声明不接收任何邮件。Postfix 识别后直接置状态为 5.1.0 永久拒绝，不再尝试隐式 A 记录查询。
  • DNS 致命失败（DNS_FAIL）：当解析服务返回不恢复的硬错误时，Postfix 记录 5.4.3 状态；若管理员开启了 ignore_mx_lookup_error 配置例外，系统仍会尝试将该域名作为主机名查询 A 记录。
  • 临时查询错误与超时（默认分支）：对于网络超时或临时服务器异常，默认置软错误状态 4.4.3；若开启 ignore_mx_lookup_error，同样会尝试隐式 A 记录回退。开发时不能将所有查询错误一律视为“不存在 MX”。
  • 环路检测与截断：若在解析结果中发现了本机自身的 IP 地址（smtp_find_self()），Postfix 会截断优先级低于或等于自身的主机，避免邮件在本地与远端之间产生投递回环。

连接缓存与并发调节机制

建立网络连接与执行握手的开销显著，连接缓存因此成为降低延迟的重要手段。但在工程实现上必须注意：连接缓存用于复用空闲连接，本身并不负责限制并发连接数。

连接缓存 scache

Postfix 在 smtp_reuse.c 中通过 scache 实现了两级会话缓存#。缓存键的生成由 smtp_key.c 与 smtp.h 严格控制#：

  • 逻辑目的地缓存（next-hop destination）：将下一跳逻辑域名与成功的物理端点建立映射。其核心作用在于，当主 MX 服务器持续不可达时，后续投递请求可以直接复用已验证可用的备份主机，跳过不可用的首选节点。
  • 物理端点缓存（endpoint address）：键由 SMTP_KEY_MASK_SCACHE_ENDP_LABEL 掩码控制，包含服务名（service）、远端 IP 地址与端口、请求的 TLS 级别（requested TLS level），以及依配置条件启用的发件人地址、当前下一跳和远端主机名。Postfix 借助这些离散属性作为上下文代理，区分不同交付请求。
  • 连接探活：缓存的连接从池中取出后，不能直接发送邮件数据。在 smtp_reuse_common() 中，投递代理必须先向远端发送 RSET 命令进行探活。若远端无应答或返回错误，说明网络通道已失效，系统会调用 smtp_session_free() 关闭并销毁该连接，重新发起 TCP 握手。

队列并发退避与恢复

出站连接的并发控制由队列管理器 qmgr 统一管理。在 qmgr_deliver.c 中，投递代理向 qmgr 上报每个批次的执行状态与投递状态通知（delivery status notification，DSN）#：

  • 当请求返回状态为 DELIVER_STAT_DEFER 时，若附带的 DSN 诊断表明该目的地发生整体通信障碍，qmgr 会调用 qmgr_queue_throttle(queue, dsn) 抑制该目的地队列#。
  • 若投递顺利完成且无故障诊断，则调用 qmgr_queue_unthrottle(queue) 尝试增加并发。

并发窗口调节包含以下关键工程机制：

  1. 滞回周期与平滑调节：目的地队列维护着当前的并发窗口大小 queue->window。单个收件人的临时软错误并不会导致全域并发骤降。系统通过正向与负向反馈参数（pos_feedback 与 neg_feedback）进行滞回（Hysteresis）控制。成功投递累加正向反馈，达到阈值后才增加窗口，且成功调节时会清零失败伪批次计数（queue->fail_cohorts = 0）；当因目的地整体通信失败触发负反馈时，系统先按配置逐步调小窗口（保持至少为 1）；同时每次失败累加失败伪批次（queue->fail_cohorts += 1.0 / queue->window），仅当该累计值达到阈值 fail_cohort_limit 后，队列才会被置为挂起状态 QMGR_QUEUE_STAT_THROTTLED#。
  2. 定时器恢复：被挂起的队列会注册事件定时器（按最小退避时间 var_min_backoff_time 等待）。定时器超时后，队列重回就绪状态。若此时仍有未完成的活跃请求（busy_refcount > 0），窗口恢复为当前活跃数；若无活跃请求，则重置为初始并发值 init_dest_concurrency。
  3. 目的地作用域划分：并发控制的键值取决于传输映射配置（transport）与下一跳（nexthop）。当配置了 smtp_destination_recipient_limit = 1 时，每个投递请求仅包含一个收件人，目的地并发粒度退化为单收件人级别。需要注意的是，独立的目的地队列虽然隔离了各自的窗口状态，但底层仍共享宿主机的并发进程池与出站网络带宽。

协议阶段错误划分与接收责任

在 SMTP 协议交互过程中（smtp_proto.c），错误发生的不同阶段决定了发信系统该如何归咎与重试#。本地邮件传输协议（Local Mail Transfer Protocol，LMTP）与标准 SMTP 在此存在显著差异。

逐收件人响应与 DATA 终态

在信封协商阶段，每个 RCPT TO 命令都有单独响应（支持命令流水线以批量接收）：

  • 返回 2xx：远端接受该收件人，进入待发送正文阶段。
  • 返回 4xx：远端对该收件人返回临时软错误（如灰名单机制或单用户配额满）。在 Postfix 中，该收件人被标记为暂不处理，若当前主机还有备用 MX 且未耗尽，可继续保留（SMTP_RCPT_KEEP）尝试下一主机；若候选主机全部耗尽，交由队列落盘延期。
  • 返回 5xx：在通常未开启 soft_bounce 的配置下，代表用户不存在或策略永久拒绝，直接调用 bounce_append() 记录退信并剔除（标记为 DROP）#。

当进入 DATA 阶段并传输末尾句点（.）后：

  • 在标准 SMTP 中，终态响应（250 OK、4xx 或 5xx）是对前面所有已被 2xx 接受的收件人的共同结果。
  • 这与 LMTP（RFC 2033#）存在本质区别：LMTP 在数据段末尾针对每个被接受的收件人单独返回独立的一行状态响应，而标准 SMTP 只有一个整体应答。

接收责任转移与边界状态

根据 RFC 5321 第 4.2.5 节，发送方必须收到数据段末尾的 2xx 响应，才能确认邮件投递责任已成功转移给远端接收方。

在实际网络环境中存在不可忽视的边界状态：若远端已经成功将邮件写入持久化存储并返回了 250 OK，但这串数据在网络传输中途因连接断开或超时而丢失，发信方只会捕获到网络异常。此时发信方无法确认远端是否已经入库，只能将这批收件人置为未知状态（remote_accepted = null）并放回重试队列。随后的重试可能导致远端收到重复邮件。标准 SMTP 协议本身既不保证“恰好一次投递”（exactly-once），也不保证无条件的“至少一次”（at-least-once），因为在重试生命周期耗尽或遇到不可恢复错误时，邮件最终会被退信终止。

生产自建基础与网络前提

在设计外发服务时，底层基础设施的协同配置是建立稳定投递的前提：

  1. 出站 TCP 25 端口连通性：公网直接投递要求主机的出站 25 端口可达。实际部署时需要向网络或服务提供商核实该端口的外发策略与网络连通性。
  2. DNS 正反向解析与标识协同：
    • 运营实践中，发送节点的公网 IP 通常需要配置反向 DNS 指针记录（pointer record，PTR record），且 PTR 指向的主机名应能正向解析回该 IP（FCrDNS 验证），以降低被远端判为可疑节点的概率。
    • PTR 记录仅用于接收方校验发信节点身份，绝不用于发信方查找目标域名的 MX 路由。
    • 客户端 HELO/EHLO 宣告的主机名建议与反向解析域名保持协同，但不同接收方的策略各有差异，这属于运营协同实践，而非 SMTP 规范本身的连通性硬要求。
  3. 安全传输策略：出站通常采用机会性加密。对于配置了严格策略的域名，投递客户端可依据本地规则验证证书链与域名匹配；未强制加密的节点则保留回退明文的机制。
  4. 直投与中继代理（relayhost）：直投是由本地节点根据目标域 MX 记录直接分发；若受限于网络出口或策略，且本地到中继的路径可达并获得中继授权，系统可通过配置 relayhost 将邮件转发给中继网关。中继能够规避本地出口的网络限制，但并不免除远端邮件系统的信誉审查与垃圾过滤规则。

外发引擎接口契约与失败处理设计

基于上述机制推导，外发网关可将出站尝试（Attempt）与队列调度解耦。以下为工程推导的数据契约与边界设计（并非 Postfix 现有 C 结构体或 HTTP API）：

投递尝试数据契约

尝试输入（调度器下发给 Worker）：

queue_idString队列消息唯一标识
attempt_idString每次投递尝试的唯一标识（租约凭证）
routeObject下一跳域名与投递模式（直投或中继）
config_versionString配置版本标识
timeoutsObject各阶段超时控制（连接、命令交互、正文等待）
recipientsArray待投递收件人列表（包含 recipient_id 与地址）

尝试输出（Worker 回传给调度器）：

包含顶层 queue_id、attempt_id、remote_endpoint（实际连接的远端 IP 与端口，如 192.0.2.25:25），以及逐收件人结果列表 results。results 中的每一项结构如下：

字段类型说明

调度器权威与原子租约

为了避免网络超时或执行节点假死带来的并发重复投递，系统应遵守以下设计原则：

  1. 调度器为唯一重试权威：执行 Worker 仅负责单次协议交互与结果收集，不得擅自启动内部异步重试。会话中切换备用 MX 属于单次尝试内部的故障转移；真正的跨时间重试必须由调度器在持久化队列中重新派发。
  2. 原子租约与失租保护：调度器派发任务时为消息附加租约时间（lease_until）与尝试凭据（attempt_id）。数据库更新必须采用带有版本条件的原子操作，确保在任意时刻只有一个有效所有者。执行 Worker 若因长时间 GC 或网络阻塞导致租约过期，调度器可将任务重新派发给其他 Worker；失租 Worker 无法通过条件更新写入结果，且检测到自身租约过期时应立即停止后续动作。但必须注意，在网络分区下，旧 Worker 依然可能在失租判定前执行了外部网络动作。
  3. 不可撤销的副作用边界：租约机制只能规范内部数据库状态的更新归属，并不能撤销远端已经发生的动作。若原 Worker 在断网前已成功将邮件写入远端但未能收到 ACK，调度器将任务派发给新节点后，远端依然可能收到两封邮件。

复杂异常处理案例

假设向目标域发送一封邮件，包含三个收件人：收件人 A、收件人 B、收件人 C：

  1. 连接阶段：解析到主主机 mx1（优先级 10）与备用主机 mx2（优先级 20）。连接 mx1 发生超时无响应，Worker 在本次尝试内平滑顺延，成功连上 mx2（远端端点为 192.0.2.25:25）。
  2. 信封交互阶段：
    • 发送 RCPT TO:<A>，远端响应 250 OK。
    • 发送 RCPT TO:<B>，远端响应 450 4.2.1 Greylisted。Worker 将收件人 B 判定为 TRANSIENT_FAILURE，remote_accepted = false。
    • 发送 RCPT TO:<C>，远端响应 550 5.1.1 User unknown。Worker 将收件人 C 判定为 PERMANENT_FAILURE，remote_accepted = false。
  3. 正文传输阶段：
    • 系统仅为收件人 A 发送 DATA 内容并传输结束符 .。
    • 分支一（正常确认）：远端响应 250 2.0.0 OK。收件人 A 确认为终态成功（remote_accepted = true）；收件人 B 留由调度器按退避策略重试；收件人 C 触发退信通知。
    • 分支二（确认丢失的不确定边界）：远端已将邮件落盘并发出 250 OK，但本地在等待应答时发生 TCP 连接重置（RST）。此时收件人 A 的阶段停留在 DATA_DOT，remote_accepted 被置为 null（接收状态未知）。调度器将收件人 A（未知状态）与收件人 B（明确的临时拒绝）分别按各自状态入库，两者均触发重试，但原因与接收状态严格区分。收件人 A 的后续重试可能会使远端收到重复邮件。

验证与测试设计

为了在离线环境中验证上述边界逻辑，可采用隔离测试桩进行仿真验证（以下为测试方案设计，并非当前环境已运行的操作）：

  1. DNS 异常仿真（测试 DNS 服务）：
    • 搭建轻量 DNS 测试服务，分别注入特定响应：配置单条 Null MX、配置查询超时的域名、配置无 MX 仅有 A 记录的域名，以及配置相同 Preference 的多条 MX 记录。
    • 预期表现：验证投递客户端对 Null MX 立即判定永久失败；对无 MX 域名平滑回退 A 记录查询；对相同 Preference 的候选节点呈现打散分布。
  2. SMTP 桩服务交互仿真（测试 SMTP 服务）：
    • 编写轻量 SMTP 桩服务，支持动态注入响应规则。
    • 场景 A：首选端口建立连接后挂起，验证客户端能否根据超时配置自动切换至备用 MX 节点。
    • 场景 B：针对不同收件人依次返回 250、450、550，验证客户端在 DATA 阶段是否仅发送有效收件人，并正确区分软硬错误状态。
    • 场景 C：在收到 DATA 结束符 . 后故意切断 TCP 连接，验证客户端是否正确将收件人归类为未知状态（null），并在重试机制下保持状态派发的安全性。
